# Раскладка docpipe на целевой машине

Инструмент и его настройка живут в **разных местах**, и разделение здесь
смысловое, а не для порядка.

| | Где | Почему там |
|---|---|---|
| **Инструмент** | на машине (`uv tool install`), вне репозитория продукта | обновляется отдельно от продукта, не попадает в его diff и не связан версией с его историей |
| **Настройка** | внутри репозитория продукта, в каталоге на ваш выбор | правила классификации, владение, реестры, шаблоны — это решения о продукте, им место рядом с продуктом |

Раньше в репозиторий продукта клался и код: пакет, `pyproject.toml`, лок,
`.venv` с нативными колёсами. Отсюда росло всё остальное — `docs_scan_exclude`,
чтобы обход документов не заходил в `.venv`, `.gitignore` на полдюжины строк,
`--no-install-project` с `PYTHONPATH` на случай, когда пакет нечем собрать.
Ничего этого больше нет.

```
<репозиторий продукта>/<каталог настройки>/
├── docpipe.yaml          что документируем, куда не заходим, куда пишем
├── rules.yaml            правила классификации (секции dotnet: и web:)
├── ownership.yaml        кому принадлежит документ
├── pages.yaml            ручной состав страниц фронта
├── registries.yaml       описание реестров платформы
├── arch-registry.yaml    нормализованный реестр (точки входа, швы, данные)
├── templates/            скелеты документов шага 2 и бизнес-слоя
├── business/             бизнес-документы (коммитятся)
├── artifacts/            манифест и индекс графа (в .gitignore)
└── .gitignore
```

Кэши разбора лежат **вне репозитория** — гигабайту машинного мусора в дереве
продукта делать нечего, а строка в `.gitignore` защищает от случайного коммита
хуже, чем отсутствие файлов.

## Установка

```bash
export UV_TOOL_DIR=$WORK/.uv  UV_TOOL_BIN_DIR=$WORK/.uv/bin
export PATH="$UV_TOOL_BIN_DIR:$PATH"

cd $WORK/docpipe/documentation_pipeline
./deploy/install.sh --repo $WORK/cfml/sbt.cms.cashflow \
                    --config-dir docs/ml/docpipe \
                    --engine $WORK/.local/bin/codebase-memory-mcp
```

`UV_TOOL_DIR` и `UV_TOOL_BIN_DIR` заданы до вызова намеренно: без них uv возьмёт
свои умолчания внутри `$HOME`, а на целевой системе работа идёт вне `$HOME`.
Установщик их не выставляет сам — молча решать за пользователя, куда ставить
инструмент, он не должен, но в сообщении об ошибке называет.

Флаги:

| Флаг | Когда |
|---|---|
| `--repo ПУТЬ` | обязателен: корень документируемого репозитория |
| `--config-dir ПУТЬ` | обязателен: каталог настройки внутри него. Относительный — значение уходит в `docpipe.yaml`, который читают и на других машинах |
| `--cache-dir ПУТЬ` | абсолютный, вне репозитория. По умолчанию `$WORK/.docpipe/cache`, без `$WORK` — `~/.cache/docpipe` |
| `--engine ПУТЬ` | путь к `codebase-memory-mcp` 0.6.0. Без него откажутся работать только команды `graph *` |
| `--index URL` | адрес внутреннего зеркала пакетов; записывается в `uv.toml` клона, а `uv tool install` получает этот файл явно (см. ниже) |
| `--python 3.12.13` | доступна одна конкретная сборка Python. Скачивать интерпретатор запрещено (`python-downloads = "never"`), поэтому его надо назвать |
| `--no-tool` | только разложить настройку, инструмент не ставить |

**Версии берутся из `uv.lock` клона, а не решаются заново.** Установщик снимает
их через `uv export --frozen` и передаёт `uv tool install` ограничениями. Без
этого установка подобрала бы свежие релизы, и окружение разошлось бы с тем,
на котором гонялись тесты, — молча и в удобный момент.

Хэши при этом не переносятся (`--no-hashes`): на внутреннем зеркале файл может
быть пересобран, и сумма не сойдётся при той же версии. Пин версии остаётся.

**Кэш uv — в клоне, а не в `~/.cache/uv`.** Установщик дописывает в начало
`uv.toml` клона строку `cache-dir = "<клон>/.uv-cache"` (если её там ещё нет)
и сам ставит инструмент с тем же кэшем. Поэтому и установка, и `uv run` или
`uv sync` из корня клона держат скачанные пакеты в одном месте рядом с кодом.
Перенести кэш — поправить эту строку; заданную руками установщик не трогает.

**`uv tool …` не читает `uv.toml` проекта** — только пользовательский
(`~/.config/uv/uv.toml`) и системный. Поэтому установщик передаёт файл клона
флагом `--config-file`, когда в нём описан источник пакетов (`[[index]]`,
`find-links` или `offline`): иначе зеркало и сертификаты из клона на саму
установку не действовали бы, и запрос ушёл бы на pypi.org. Когда в файле
только `cache-dir`, флаг не передаётся: `--config-file` **замещает**
пользовательский конфиг, а не дополняет его, и отнял бы зеркало, настроенное
на машине. Звать `uv tool` руками — по тем же правилам.

### `invalid peer certificate`

TLS-прокси компании подписывает соединения сертификатом внутреннего
удостоверяющего центра, которого нет в наборе, вшитом в uv. В `uv.toml.example`
для этого стоит `native-tls = true` — использовать системное хранилище. Если
корневого сертификата нет и там, укажите его явно:

```bash
SSL_CERT_FILE=/путь/до/corp-root-ca.pem ./deploy/install.sh --repo … --index …
```

Свежий uv на строку `native-tls` ругается: «deprecated, use `system-certs`».
Настройка при этом работает. Переименовывать её можно, только зная версию uv
на машине: неизвестный ключ uv.toml не игнорирует, а падает с ошибкой разбора.

### Если зеркало отдаёт не всё

Тогда состав зависимостей подбирается один раз руками внутри контура, а результат
фиксируется в клоне. Пошагово: [`OFFLINE.md`](OFFLINE.md).

## Обновление

```bash
cd $WORK/docpipe/documentation_pipeline && git pull
./deploy/install.sh --repo … --config-dir … --engine …
```

Что установщик **не** трогает: настроенные `docpipe.yaml`, `rules.yaml`,
`ownership.yaml`, `pages.yaml`, `registries.yaml`, `arch-registry.yaml`
и правленые шаблоны — новые версии кладутся рядом как `*.new`. Правка правил
классификации это недели работы, и молча заменить её обновлением недопустимо.

## Запуск

```bash
cd $WORK/cfml/sbt.cms.cashflow      # цели записи отсчитываются от текущего каталога
CFG=docs/ml/docpipe/docpipe.yaml

docpipe config check --config $CFG --root .        # что и откуда прочитается
docpipe scan --root . --config $CFG --stats        # состояние решений
docpipe scan --root . --config $CFG --jobs 4       # построить манифест
docpipe web scan --root . --config $CFG            # фронт
docpipe graph build --root . --config $CFG         # индекс связей
```

**`config check` первым — не для порядка.** Пути в конфигурации разрешаются
от трёх разных баз, и по имени ключа базу не угадать: входы ищутся от текущего
каталога, затем от каталога `docpipe.yaml`; цели записи — только от текущего;
`docs_root`, кэш и корни обхода — от `--root`. Проверить это за секунду
дешевле, чем узнать на двадцатой минуте разбора.

Код возврата 1 — настройка сломана: остался плейсхолдер установщика
(`@CONFIG_DIR@` и т. п. — проверяли файл поставки, а не установленный), вход
не найден, каталога из `roots` или `web.roots` нет, у адаптера нет файла
на входе, названного движка нет.
Строки «каталога пока нет» у целей записи на свежей установке — норма, а не
проблема: каталоги создаст первый прогон, и код они не меняют. Код 2 —
конфигурация не читается. `--format json` даёт тот же отчёт структурой;
его читает ассистент настройки. Полностью — в
[`docs/configuration.md`](../docs/configuration.md), «Чем это проверить».

**`--config` обязателен всегда.** Умолчания ведут в другие места, и прогон
без флага не откажется, а молча возьмёт не тот набор правил.

## Агент: скилл и MCP-сервер (gigacode)

Агент на контуре — gigacode, форк qwen code со своими каталогами: он читает
`.gigacode/`, а `.qwen/` — нет. Ему нужны две вещи, и обе лежат в **клоне**,
а не в `~/.gigacode`:

| Что | Где | Откуда |
|---|---|---|
| скилл разведки `recon` | `.gigacode/skills/recon/SKILL.md` | в git |
| MCP-сервер графа `docpipe graph serve` | `.gigacode/settings.json`, ключ `mcpServers.docpipe` | пишет `install.sh`, вне git |

До 07.10.2026 установщик писал запись в `.qwen/settings.json`. Если такой
файл в клоне остался, установщик об этом скажет и файл не тронет: в нём
могут быть чужие серверы, а агент его всё равно не читает.

Поэтому gigacode запускают **из корня клона**. Сервер при этом работает
с репозиторием продукта: в записи стоят полный путь к запускалке, `--config`
и `--root` продукта и `cwd` — корень продукта (оттуда отсчитывается
`graph.out`, как у `graph build`).

Если в gigacode включено доверие папкам (`security.folderTrust.enabled`),
клон нужно один раз отметить доверенным: до этого проектные настройки,
скиллы и MCP-серверы не подключаются.

Сервер индекс не собирает: пока не прошёл `docpipe graph build`, формы
вопроса по графу отвечают внятной ошибкой с командой сборки, а `overview`
работает и так.

Повторная установка уже лежащий `.gigacode/settings.json` не затирает: если
он отличается (переставили на другой репозиторий или дописали своё),
новая версия ляжет рядом как `settings.json.new`. С `--no-tool` файл
не пишется — запускалки нет; как прописать сервер руками в этом режиме,
сказано в [`OFFLINE.md`](OFFLINE.md).

## Разведка

Разведка (R01) едет вместе с инструментом — это подкоманда, а не внешний файл:

```bash
cd $WORK/cfml/sbt.cms.cashflow
docpipe recon --root . --json recon.json --text recon.txt
```

Ей нужны только `python3` и `git`; сети она не касается и репозиторий только
читает. Она же отвечает на `docpipe_overview` через MCP — то есть работает
и на репозитории, где индекс графа ещё не собран.

**Модуль не импортирует ни одной сторонней библиотеки, и это не случайность.**
Первое, что делают с незнакомым репозиторием, — смотрят на него, и делают это
там, где ещё ничего не установлено. Поэтому `docpipe/recon.py` продолжает
работать скопированным одним файлом:

```bash
python3 путь/до/recon.py --root <репозиторий> --json recon.json
```

Свойство держится тестом (`test_imports_only_stdlib`, `test_runs_as_a_single_copied_file`):
внутри пакета `yaml` и `pydantic` установлены, и строка `import yaml` заработала
бы молча, отняв единственную среду, ради которой разведка написана.

Скилл `recon` и `tools/recon-frontend.sh` остаются **в клоне**: первый — часть
рабочего процесса агента, второй кодом не вызывается и нужен разово. Скилл
лежит в `.gigacode/skills/recon/SKILL.md` — там его находит gigacode,
запущенный из корня клона, без записи чего-либо в `~/.gigacode`.

Всё остальное — в `<каталог настройки>/README.md`.

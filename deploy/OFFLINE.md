# Сборка окружения внутри закрытого контура

Когда это нужно: обычная установка не проходит, потому что часть пакетов зеркало
не отдаёт вовсе. Тогда состав зависимостей подбирается **один раз руками** внутри
контура, результат фиксируется в клоне (`pyproject.toml`, `uv.lock`, `uv.toml`),
и дальше установка на любую машину периметра идёт уже без подбора.

Если `install.sh --index` отработал — этот документ не нужен, см.
[`README.md`](README.md).

**Что подбирать, скорее всего, не придётся.** У всех пяти нативных пакетов
(`pydantic-core`, `pyyaml` и три `tree-sitter`) есть готовые колёса под
`cp312 manylinux x86_64`, и при их наличии компилятор на контуре не нужен.
Проверяется это одной командой, и делать это стоит **до** всего остального:

```bash
pip download --only-binary=:all: --no-deps --dest /tmp/whl \
    "pydantic-core==2.46.4" "pyyaml==6.0.3" "tree-sitter==0.26.0" \
    "tree-sitter-c-sharp==0.23.5" "tree-sitter-typescript==0.23.2"
```

`--only-binary=:all:` здесь существенен: без него `pip` молча возьмёт `sdist`
и соберёт его, и вы не узнаете, что колеса не было.

## Что понадобится

- `uv` в `PATH` (`uv --version`);
- интерпретатор Python 3.12 — в целевой системе это `cpython-3.12.13`;
- адрес внутреннего зеркала пакетов;
- корневой сертификат компании, если системное хранилище его не содержит.

Всё, что дальше, происходит **в клоне инструмента**, а не в репозитории продукта.
Клон — единственное место, где живут `pyproject.toml` и `uv.lock`; в репозиторий
продукта уезжает только настройка, и зависимостей у неё нет.

```bash
CLONE=$WORK/docpipe/documentation_pipeline
CF=$WORK/cfml/sbt.cms.cashflow
```

Инструмент ставится в `UV_TOOL_DIR`. На системе, где работа идёт вне `$HOME`,
задайте его и каталог запускалок до всего остального — иначе uv возьмёт свои
умолчания внутри `$HOME`:

```bash
export UV_TOOL_DIR=$WORK/.uv  UV_TOOL_BIN_DIR=$WORK/.uv/bin
export PATH="$UV_TOOL_BIN_DIR:$PATH"
```

---

## Шаг 1. Склонировать репозиторий

```bash
mkdir -p $WORK/docpipe && cd $WORK/docpipe
git clone <адрес репозитория> documentation_pipeline
```

## Шаг 2. Настроить uv

```bash
cd $CLONE
cp deploy/uv.toml.example uv.toml
```

Вписать адрес зеркала в `[[index]].url`. Остальное в шаблоне уже готово:
`native-tls = true` (системное хранилище сертификатов) и
`python-downloads = "never"` (не ходить за интерпретатором на github.com).

Файл лежит в корне клона намеренно: uv читает настройки из каталога, из которого
его зовут, а зовут его отсюда — и `uv lock`, и `uv tool install`. В `.gitignore`
клона он уже перечислен: адрес внутреннего зеркала за периметр не уезжает.

Если корневого сертификата нет и в системном хранилище — он задаётся переменной
окружения, в `uv.toml` для этого места нет:

```bash
export SSL_CERT_FILE=/путь/до/corp-root-ca.pem
```

Проверка, что зеркало отвечает и сертификат принимается, — **до** всякого подбора.
Отдельный пустой проект, чтобы не трогать клон:

```bash
mkdir -p /tmp/probe && cd /tmp/probe
printf '[project]\nname="probe"\nversion="0"\nrequires-python=">=3.12"\ndependencies=["pyyaml"]\n[tool.uv]\npackage=false\n' > pyproject.toml
cp $CLONE/uv.toml .
uv lock --python 3.12.13
```

`Resolved 2 packages` — зеркало отвечает. `invalid peer certificate` — дело
в сертификате, а не в составе пакетов; чинить `SSL_CERT_FILE`, а не `pyproject.toml`.

## Шаг 3. Подобрать состав зависимостей

```bash
cd $CLONE
uv lock --python 3.12.13
```

Лок в клоне собран против pypi.org и ссылается на файлы поимённо. `uv lock`
пересоберёт его против зеркала, предпочтя уже записанные версии, если зеркало
их отдаёт: тогда окружение совпадёт с тем, на котором гонялись тесты. Если
не отдаёт — цикл: читать ошибку → править `pyproject.toml` → повторять.

**Свобода по каждому пакету разная, и это важно.** Не все ограничения
в `pyproject.toml` — вкусовщина:

| Пакет | Зачем | Что можно менять |
|---|---|---|
| `tree-sitter>=0.25,<0.27` | разбор C# и TypeScript | **ниже 0.25 нельзя.** В 0.25 сменился API запросов (`Query(LANG, src)` + `QueryCursor(q).captures()`), на старом код не работает вовсе — это не стилистика |
| `tree-sitter-c-sharp>=0.23,<0.24` | грамматика C# | другая версия допустима, но её номер попадает в манифест и в ключ кэша: вывод может измениться, кэш обнулится. Золотые файлы в репозитории собраны на этой |
| `tree-sitter-typescript>=0.23,<0.24` | грамматика TypeScript | то же самое: номер идёт в ключ кэша шага `web`, и апгрейд грамматики обязан кэш сбросить |
| `pydantic>=2.7,<3` | модели данных | любая 2.x посвежее; на 1.x код не работает |
| `typer>=0.12,<1` | командная строка | тянет `click`, `rich`, `shellingham`. Версия почти безразлична |
| `pyyaml>=6,<7` | конфигурация и правила | 6.x; 5.x, скорее всего, заработает, но не проверялось |

Что делать с типовыми отказами:

| Ошибка | Что это значит | Как чинить |
|---|---|---|
| `no versions available` для пакета | зеркало его не проксирует вовсе | шаг 4 |
| диапазон не удовлетворяется | зеркало отдаёт только старые версии | ослабить границы по таблице выше; `tree-sitter` — не ниже 0.25 |
| качается `.tar.gz` вместо `.whl`, сборка падает | зеркало отдаёт только исходники, а пять пакетов — расширения на C и Rust | нужен компилятор и заголовки Python (`gcc`, `python3.12-devel`), для `pydantic-core` ещё и Rust. Если их нет — шаг 4 |
| нет `hatchling` | сборочный бэкенд самого `docpipe` | шаг 5, вариант «без сборки пакета» |

## Шаг 4. Если пакета нет вовсе: принести колёса

Путь последней надежды, и на многих контурах он закрыт: принести файл извне
бывает нельзя. Проверьте это раньше, чем начнёте.

На машине, у которой доступ есть, выгрузить весь набор:

```bash
uv export --no-dev --no-emit-project --format requirements-txt > requirements.txt
pip download -d wheels -r requirements.txt \
    --only-binary=:all: --python-version 3.12 --platform manylinux2014_x86_64
```

Каталог `wheels` перенести внутрь контура и указать его в `uv.toml` клона:

```toml
find-links = ["/абсолютный/путь/до/wheels"]
offline = true
```

`offline = true` запрещает любой сетевой доступ: uv соберёт окружение только из
принесённых файлов. Это же и проверка — если чего-то не хватает, вы узнаете об
этом сразу и по имени пакета, а не по таймауту.

## Шаг 5. Поставить инструмент

```bash
cd $CLONE
./deploy/install.sh --repo $CF --config-dir docs/ml/docpipe --python 3.12.13
```

Установщик снимает версии из `uv.lock` клона и ставит по ним, а не решает
зависимости заново: иначе окружение разошлось бы с тем, на котором гонялись
тесты, — молча и в удобный момент.

**Без сборки пакета.** Если зеркало не отдаёт `hatchling`, `uv tool install`
собрать `docpipe` не сможет. Тогда — окружение в клоне и запуск через него:

```bash
cd $CLONE
uv sync --frozen --no-dev --no-install-project --python 3.12.13
PYTHONPATH=$CLONE uv run --no-sync python -m docpipe version
```

Настройку при этом раскладывает тот же установщик с `--no-tool`, а вместо
команды `docpipe` заводится алиас:

```bash
alias docpipe="PYTHONPATH=$CLONE uv run --no-sync --project $CLONE python -m docpipe"
```

`--no-sync` обязателен: без него `uv run` при каждом вызове сверяется с индексом
и на машине без доступа к нему падает — на команде, которая с зависимостями
ничего не делает.

## Шаг 6. Проверить

По возрастанию требовательности; важна последняя — она поднимает разбор,
грамматику, модели и YAML разом:

```bash
docpipe version
docpipe schema --out /tmp/schema.json                                  # pydantic жив
cd $CF
docpipe config check --config docs/ml/docpipe/docpipe.yaml --root .    # пути настройки
docpipe scan --root . --config docs/ml/docpipe/docpipe.yaml --stats    # весь конвейер
```

`config check` стоит перед прогоном не для порядка: пути в конфигурации
разрешаются от трёх разных баз, и по имени ключа базу не угадать. Проверить их
за секунду дешевле, чем узнать на двадцатой минуте разбора.

## Шаг 7. Зафиксировать результат

Подобранные `pyproject.toml` и `uv.lock` уже лежат в клоне — они и есть
результат. Осталось решить, что с ними делать дальше:

- **внутри контура** коммит полезен: следующий человек не повторяет подбор;
- **на внешний remote** пересобранный `uv.lock` пушить не стоит — он содержит
  адрес внутреннего зеркала. `uv.toml` за периметр не уедет в любом случае:
  он в `.gitignore`.

После этого установка на другую машину периметра — одна команда без флага
`--index`: адрес зеркала берётся из `uv.toml`, версии — из `uv.lock`.

```bash
cd $CLONE
./deploy/install.sh --repo <другой репозиторий> --config-dir docs/ml/docpipe
```

## Что будет при следующем обновлении инструмента

`git pull` в клоне и повторный `install.sh`:

- **не тронет** настройку в репозитории продукта — новые версии `docpipe.yaml`,
  `rules.yaml`, `ownership.yaml`, `pages.yaml`, `registries.yaml`,
  `arch-registry.yaml` и правленых шаблонов лягут рядом как `*.new`;
- **не тронет** `uv.toml` клона, то есть адрес зеркала;
- **переставит** сам инструмент по версиям из `uv.lock`.

Если `git pull` принёс изменившийся `pyproject.toml`, лок придётся пересобрать
(`uv lock`) — тогда и только тогда снова понадобится связь с зеркалом.

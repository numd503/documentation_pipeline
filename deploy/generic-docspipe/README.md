# Настройка docpipe

Этот каталог положил `deploy/install.sh` из клона docpipe. Инструмент стоит
на машине, здесь — только его настройка: что документируем, по каким правилам,
куда пишем. Набор нейтральный: в нём нет ни одного решения о вашем
репозитории, только пути, которые подставил установщик.

| Файл | Что в нём |
|---|---|
| `docpipe.yaml` | область, правила, цели записи; каждый ключ записан значением или комментарием-умолчанием |
| `rules.yaml` | правила классификации: секции `dotnet:` и `web:`, эталонный набор |
| `ownership.yaml`, `pages.yaml`, `arch-registry.yaml` | заготовки: пустые и рабочие |
| `registries.yaml` | заготовка; ключ `registries` в `docpipe.yaml` закомментирован, пока в ней нет реестра |
| `templates/` | скелеты документов |
| `artifacts/` | манифесты, индекс графа, очередь — в `.gitignore` |

Повторная установка ваши правки не затирает: новая версия файла ложится рядом
как `*.new`.

## Первое — проверка

Команды зовут из корня репозитория: от текущего каталога отсчитываются цели
записи.

```bash
docpipe config check --config <этот каталог>/docpipe.yaml --root .
```

Пути разрешаются от трёх разных баз, и по имени ключа базу не угадать;
проверить это за секунду дешевле, чем узнать на двадцатой минуте разбора.

## Настройку ведёт скилл `setup`

Агент (gigacode), запущенный из корня клона docpipe, видит скилл `setup`
и два MCP-сервера, которые прописал установщик: `docpipe` (граф) и
`docpipe-setup` (настройка). Скилл спрашивает о том, что из кода не выводится,
пишет правила прямо в файлы этого каталога и перезапускает проверки; ревью —
`git diff`, решение — ваш коммит.

## Ручной путь

Тот же порядок без агента — в клоне docpipe: `README.md`, раздел «Настройка
под конкретный проект». Что делает каждый ключ, от чего отсчитывается путь
и что ломается молча — `docs/setup-map.md`; ключи `docpipe.yaml` —
`docs/configuration.md`; раскладка и обновление — `deploy/README.md`.

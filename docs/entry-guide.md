# Как заполнять `entry`: от своего класса до рабочей ссылки

Пошаговое руководство. Формат целиком — в [`business-layer.md`](business-layer.md),
обоснования — в [`business-implementation-plan.md`](business-implementation-plan.md).

## Что такое `entry` в одном абзаце

`entry` — список **«чем этот процесс запускается»**, лежит во front matter
бизнес-документа. Каждый элемент — **якорь**: строка, по которой платформа сама
находит код. Не имя класса. Класс можно переименовать, и триггер не изменится —
сработает он всё равно по строке из реестра. Поэтому якорь — эта строка,
а связь «якорь → класс → технический документ» инструмент находит сам.

## Порядок работы

### 1. Найти якорь по своему классу

Если вы знаете свой тип — идите от него:

```bash
docpipe anchors which artifacts/doc-tree.json UserTasksAddedTriggerEventReceiver \
    --registries registries.yaml --root .
```

Ищет по FQN, по `doc_path` и по простому имени типа. Печатает **готовый кусок
`entry`** — его и вставляйте, собирать строку в поля глазами не нужно:

```
list_event  UserTasks/ItemAdded
  реестр:  structure
  файл:    Structure.xml
  совпало: impl_fqn = Sbt.Cashflow.ML.EventReceivers.UserTasksAddedTriggerEventReceiver
  на том же якоре ещё: Sbt.Cashflow.Reports.EventReceivers.AuditEventReceiver  (сборка …)
  якорь общий на всех: он адресует контракт, а не класс

  entry:
  - kind: list_event
    ref: ItemAdded
    scope: UserTasks
```

Если класса под рукой нет — смотрите перечень целиком: `docpipe anchors list`.
«Якорей не найдено» — код 0 и нормальное состояние: точка входа есть не
у всякого типа.

### 2. Завести документ и вставить якорь

```bash
docpipe business new bp.tasks.scoring --title "Оценка задачи" --config docpipe.yaml
```

Создаётся скелет с `entry: []`. Замените его на выданный сниппет:

```yaml
docpipe:
  schema: business/1
  id: bp.tasks.scoring
  kind: process
  title: Оценка задачи
  status: draft
  entry:
  - kind: list_event
    ref: ItemAdded
    scope: UserTasks
```

### 3. Собрать и проверить

```bash
docpipe business build  artifacts/doc-tree.json --config docpipe.yaml --root .
docpipe business lint   artifacts/doc-tree.json --config docpipe.yaml --root .
```

Якорь разобран верно, если он появился в таблице «Точки входа» с непустой
колонкой «Где объявлено». `не найдено` означает, что `kind`, `ref` или `scope`
не совпали с реестром.

## Что писать по видам

| `kind` | `ref` | `scope` | `version` |
|---|---|---|---|
| `grid_service` | `@name` из `services.config` (**не** класс) | — | — |
| `job` | `JOBTITLE` | — | — |
| `workflow` | `Id` определения | — | обязателен, если версий несколько |
| `workflow_step` | `Id` шага | `Id` workflow | — |
| `list_event` | `EventType` | `InnerName` списка | — |
| `table` | `InnerName` списка | — | — |
| `kafka` | имя топика | — | — |
| `http` | маршрут | — | — |
| `type` | FQN | — | — |

`table` — единственный вид, где слово в `anchors` и слово в документе не
совпадают: реестр объявляет `list`, аналитик пишет `table`. Расхождение
намеренное — словари предметной области и платформы разные.

## Своя часть общей точки входа: `only`

На одной паре «список + `EventType`» бывает несколько подписчиков — платформа
вызывает всех. Якорь их не различает: он адресует **контракт**, а не класс.

Без сужения это означает три вещи: в вашей «Реализации» стоит чужой обработчик,
а чужая подписка меняет `business_hash` и гонит документ в `drifted`.

Сузить можно селектором `only` — он не участвует в поиске, а **отбирает
из уже найденного**:

```yaml
  entry:
  - kind: list_event
    ref: ItemAdded
    scope: UserTasks
    only:
      assembly: Sbt.Cashflow.ML.EventReceivers
```

```yaml
    only:
      team: ml            # по ownership.yaml, через реализацию
```

| | `assembly` | `team` |
|---|---|---|
| Переживает переименование класса | да | да |
| Переживает переезд между сборками | нет | да |
| Требует настройки | нет | да, [`ownership.yaml`](ownership.md) |

**Рекомендация: `assembly`, пока `ownership.yaml` не заполнен; `team` — после.**
`team` устойчивее и выражает намерение прямо («наша часть»), но без правил
владения не сужает ничего.

Что делает сужение:

- **«Реализация»** содержит только вашу часть;
- **`business_hash`** считается по вашей части — чужая правка перестаёт давать
  вам `drifted`;
- **в «Точках входа»** появляется строка «Сужено до своей части: … — сборка …»,
  чтобы читатель не решил, что перечислено всё;
- **на покрытие не влияет:** пара остаётся покрытой целиком. Иначе отчёт
  требовал бы документ на чужой обработчик — линт, красный с первого дня.

Правила: ровно один ключ из `assembly`/`team`; `only` на якоре с
`verify: false` запрещён (там нечего сужать). Оба нарушения — ошибка каталога
при загрузке, документ в каталог не попадает.

### Когда `only` не нужен

Если на якоре только ваша запись — не пишите его. Лишний селектор добавляет
строку, которая может промахнуться, и ничего не даёт. `anchors which` прямо
говорит, общий якорь или нет: строка «на том же якоре ещё» появляется только
когда подписчиков несколько.

## Куда что класть: `entry`, `upstream`, `produces`

| Список | Раздел в документе | Смысл | В `business_hash` |
|---|---|---|---|
| `entry` | «Точки входа» | чем процесс запускается | да |
| `upstream` | «Вне зоны ответственности» | чужой триггер выше по течению | **нет** |
| `produces` | своего раздела нет | что процесс порождает | да |

`verify: false` — про **проверку**, а не про раздел. Якорь с ним не разрешается
вовсе, находкой линта не становится и в хэш не входит. Чтобы запись попала
в «Вне зоны ответственности», её надо положить в `upstream`.

## Пять ошибок, на которых спотыкаются

1. **Имя класса вместо якоря.** `ref: UserTasksAddedTriggerEventReceiver`
   не разрешится никогда: реестр объявляет пару «список + `EventType`», класс
   в нём — значение атрибута, а не ключ.
2. **Забытый `scope`.** У `list_event` и `workflow_step` ключ разрешения —
   тройка `(вид, scope, ref)`. Без `scope` ищется по пустому.
3. **Двоеточие в `JOBTITLE` без кавычек.** `ref: PM: Load limits` — YAML
   разберёт как вложенный словарь. Нужно `ref: 'PM: Load limits'`.
4. **`version` числом.** `version: 2` — ошибка валидации; нужно `version: '2'`.
5. **Реестры и манифест из разных корней.** `--root` один и тот же для `scan`
   и для `business build`: литеральная ступень (`kafka`, `http`, `type`) ищет
   по путям из манифеста относительно `--root`.

## Известное ограничение: шаг workflow с несколькими версиями

Если у workflow больше одной версии, якорь `workflow_step` использовать нельзя:
без `version` линт даёт `ambiguous-version`, а с `version` якорь не
разрешается — поля `version` у записи шага не существует.

`anchors which` предупреждает об этом прямо в выводе. Обход: сослаться на
workflow целиком с `version` и описать свой шаг прозой.

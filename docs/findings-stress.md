# Стресс-тест на четырёх репозиториях

Прогон всего написанного (T04–T13) на четырёх реальных .NET-проектах. Два новых —
[opentelemetry-dotnet](https://github.com/open-telemetry/opentelemetry-dotnet) и
[semantic-kernel](https://github.com/microsoft/semantic-kernel); последний интересен
тем, что полиязычный (2960 файлов C#, 1244 Python, TypeScript, каталог Java) — по составу
это самый близкий аналог АС CF из доступных.

Предыдущие отчёты: [eShopOnWeb](findings-eshoponweb.md), [ABP](findings-abp.md).

## Что подтвердилось

**`.slnx` — уже не экзотика.** Три репозитория из четырёх содержат этот формат,
причём semantic-kernel держит **оба сразу** (2 `.sln` и 2 `.slnx`), а OpenTelemetry,
как и ABP, перешёл на него целиком. Правка, сделанная после ABP, окупилась дважды.
Все 154 проекта из решений semantic-kernel и 69 из OpenTelemetry разрешились в файлы,
которые существуют на диске.

**Полиязычный репозиторий не мешает.** semantic-kernel — 165 МБ, из них большая часть
Python и TypeScript. Обход занял 0,09 с; посторонние языки просто не попадают в выборку.

**Кэш даёт стабильные 8–18×** и на всех репозиториях возвращает результат, побитово
равный полному разбору.

## Что было сломано и исправлено

### 1. Безымянные члены (настоящий баг)

Три члена на двух репозиториях получили пустое имя. Причина: при восстановлении после
ошибки грамматика отдаёт `field_declaration` без имени — обломок выражения из-под `#if`.

```csharp
#else
        => value.Replace("\\", "\\\\");   // ← стало «полем» без имени
#endif
```

Один случай оказался интереснее: `extension(char) { … }` — **члены-расширения C# 14**
(.NET 10). Грамматика `tree-sitter-c-sharp` 0.23 их не знает и разбирает как поле
без имени.

Безымянный член в манифесте превратился бы в безымянный раздел документации.
Исправлено фильтрацией в `parser._member_names`; после правки безымянных членов
на всех четырёх репозиториях **ноль**.

### 2. `ProjectReference` через подстановки MSBuild

В OpenTelemetry разрешались **2 ссылки из 109**. Все остальные записаны так:

```xml
<ProjectReference Include="$(RepoRoot)\src\OpenTelemetry.Api\OpenTelemetry.Api.csproj" />
```

Хуже того, старый код склеивал такое значение с каталогом проекта и получал
правдоподобный, но выдуманный путь `test/X/$(RepoRoot)/src/OpenTelemetry.Api/…` —
он никогда ни с чем не совпадёт, но выглядит как настоящий.

Значение `$(RepoRoot)` вычисляется **функцией** MSBuild
(`$([System.IO.Directory]::GetParent($(MSBuildThisFileDirectory)).Parent.FullName)`),
и воспроизводить это здесь нечем. Но **имя файла проекта записано буквально**, и его
достаточно.

Исправление: значения с `$(` больше не склеиваются с путём, а новый проход
`csproj.resolve_references` дорезолвит их по имени файла — **только при единственном
совпадении**, потому что имена проектов уникальны не везде (в ABP 39 повторов).

| | до | после |
|---|---|---|
| OpenTelemetry | 2 / 109 | **108 / 109** |
| semantic-kernel | 532 / 532 | 532 / 532 |
| ABP | 2383 / 2383 | 2383 / 2383 |
| eShopOnWeb | 18 / 18 | 18 / 18 |

Оставшаяся одна — `@(TrimmerRootAssembly->'%(Path)')`, преобразование item-группы
MSBuild, а не путь к проекту. Правильно осталась неразрешённой.

## Что найдено, но осознанно не исправлено

### 3. `TargetFramework` через цепочку props-файлов: 70 модулей из 70 без TFM

Все проекты OpenTelemetry объявляют платформы так:

```xml
<TargetFrameworks>$(TargetFrameworksForLibraries)</TargetFrameworks>
```

Переменная определена в `build/Common.props`, который **не импортируется** ни из
`Directory.Build.props`, ни из самого `.csproj` — цепочка идёт через
`Common.prod.props`/`Common.nonprod.props`. Её значение, в свою очередь, содержит ещё
одну подстановку. Достать это можно только полноценным вычислением свойств MSBuild
с раскрытием `Import`, условий и функций — то есть переписыванием MSBuild.

План с самого начала объявляет это границей подхода, и граница подтвердилась.
Практический вывод: `target_frameworks` — **метаданные, а не опора**. Ни одно правило
классификации на них не завязано, и пустой список ничего не ломает. Но `validate` (T20)
обязан сообщать о модулях без TFM, чтобы пустое поле не приняли за свойство кода.

### 4. Связанные исходники: 5 % типов вне модулей

OpenTelemetry и semantic-kernel подключают общий код не отдельным проектом, а ссылкой
на файл:

```xml
<Compile Include="$(RepoRoot)\src\Shared\Guard.cs" Link="Includes\Guard.cs" />
```

Такой файл физически лежит вне каталога любого проекта, и правило «ближайший `.csproj`
вверх по дереву» не находит для него модуля:

| | файлов вне модулей | типов в них |
|---|---|---|
| OpenTelemetry | 39 (`src/Shared/**`) | 50 из 999 (5,0 %) |
| semantic-kernel | 131 (`dotnet/src/InternalUtilities/**`) | 205 из 4274 (4,8 %) |
| ABP, eShopOnWeb | 0 | 0 |

Эти типы не попадают в индекс вовсе: ни документа, ни участия в графе наследования.

Исправление требует читать `<Compile Include>` из каждого `.csproj` — и там те же
подстановки MSBuild, — а главное, ломает нынешнее предположение «файл принадлежит
**одному** модулю: связанный файл компилируется в несколько сборок сразу. Это меняет
сигнатуру `build_symbol_index` и порождает вопрос, в каком модуле показывать документ.

Вынесено в план отдельной задачей **T05b** вместо тихой переделки уже сданных задач.
Приоритет невысокий: приём характерен для библиотек, избегающих лишней зависимости
между пакетами, и реже встречается в приложениях. Для АС CF нужно проверить
`grep -c "Compile Include" **/*.csproj` до того, как принимать решение.

### 5. Препроцессор внутри выражений — та же ловушка, новые места

Все 170 файлов с ошибками разбора на четырёх репозиториях — это одна и та же причина,
[найденная на ABP](findings-abp.md): директива препроцессора внутри выражения. Стресс-тест
добавил к списку мест три новых:

```csharp
// модификатор под #if
[Experimental(...)]
public
#else
internal
#endif
    abstract class LoggerProvider

// базовый список
internal sealed class TagsComparer :
#if NET9_0_OR_GREATER
    IAlternateEqualityComparer<...>,
#endif
    IEqualityComparer<Tags>

// шаблон в pattern matching
if (value is DateTime or decimal or IList
#if NET
    or DateOnly
#endif
)
```

Доля пострадавших файлов зависит от того, насколько репозиторий мультиплатформенный:
0 % в eShopOnWeb (один TFM), 0,5 % в ABP, 2,2 % в semantic-kernel и **8,7 %**
в OpenTelemetry, который таргетит от `netstandard2.0` до `net10.0`.

Проверено, что причина именно в директивах: если удалить из файла все строки, начинающиеся
с `#`, он разбирается без единой ошибки, и все объявления находятся.

Обойти это в рамках tree-sitter нельзя — грамматика не выполняет препроцессор.
Требование к T20 остаётся прежним и становится важнее: `parse_errors > 0` при пустом
списке объявлений обязано давать ненулевой код возврата. На этих репозиториях так
теряются 7 и 9 типов соответственно.

## Наблюдения

**Скорость разбора зависит от размера файлов, а не от их числа.** 1374 файла/с
на eShopOnWeb против 481 на OpenTelemetry: в последнем файлы крупнее и плотнее
(7844 члена на 999 типов против 958 на 257).

**`ambiguous` остаётся редчайшим событием**: одна неоднозначность на 14 221 символ
по всем четырём репозиториям, и та настоящая.

**Slug-коллизии внутри модуля** — 2, 195, 13 и 165. Подтверждает, что суффикс
в `doc_path` (T15) нужен не для экзотики, а для обычного случая.

**Эндпоинтов мало в библиотеках** (11 и 13), много в прикладных проектах (26 и 356).
Ожидаемо: OpenTelemetry и semantic-kernel — SDK, а не веб-приложения.

## Как воспроизвести

`examples/` в репозиторий не входит. Скрипт прогона одноразовый; всё, что из него
следует, перенесено в тесты `tests/test_project_graph.py` и `tests/test_parser_members.py`.

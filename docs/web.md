# Шаг `web`: что на выходе и как им пользоваться

Справочник по выходу шага `web`. Обоснования решений — в
[`frontend-analysis.md`](frontend-analysis.md) и
[`frontend-implementation-plan.md`](frontend-implementation-plan.md), факты
о боевом репозитории — в [`findings-cashflow-frontend.md`](findings-cashflow-frontend.md).
Здесь — что лежит в файлах и какими командами это получается.

## Три файла

```
artifacts/doc-tree.web.json       манифест фронта — та же схема, что у шага 1
artifacts/doc-tree.web.run.json   сидкар: время, хост, версии, счётчики
artifacts/web-link.json           отчёт связи фронт↔бэк
```

Манифест **отдельный**, схема **общая**. `materialize`, `docs status`
и бизнес-слой работают от `Manifest` и про язык не знают, поэтому шаг `web`
не меняет ни байта в `doc-tree.json` и не удваивает время `scan`.

Различает манифесты поле `modules[].lang`: `"cs"` либо `"ts"`.

## Команды

```bash
# разбор фронта
uv run docpipe web scan --root . --out artifacts/doc-tree.web.json

# настройка набора правил: счётчики и срезы, ничего не пишет
uv run docpipe web scan --root . --stats
uv run docpipe web scan --root . --stats --format json   # то же структурой

# с ручным составом страниц; в CI — с отказом на протухшее правило
uv run docpipe web scan --root . --pages pages.yaml --fail-on-stale-overrides

# связь двух манифестов
uv run docpipe web link artifacts/doc-tree.json artifacts/doc-tree.web.json \
    --out artifacts/web-link.json

# документы фронта — той же машиной, что и .NET
uv run docpipe materialize artifacts/doc-tree.web.json --root .
uv run docpipe docs status artifacts/doc-tree.web.json --root .
```

Полный прогон на тестовой фикстуре:

```bash
uv run docpipe web scan --root tests/fixtures/WebWorkspace --out /tmp/web.json
uv run docpipe scan --root tests/fixtures/WildSolution --out /tmp/net.json
uv run docpipe web link /tmp/net.json /tmp/web.json --out /tmp/link.json
uv run docpipe materialize /tmp/web.json --root /tmp/webdocs
uv run docpipe docs status /tmp/web.json --root /tmp/webdocs
```

## Настройка на новом репозитории

Настраивается шаг двумя секциями с одинаковым именем в двух разных файлах —
их легко перепутать, поэтому по порядку.

**1. Секция `web` в `docpipe.yaml`: где искать и куда писать.**

```yaml
web:
  roots: ["src/Front"]                       # по умолчанию "." — весь репозиторий
  rules: "rules/rules.yaml"                  # файл правил; читается его секция `web`
  out: "artifacts/doc-tree.web.json"
  link_out: "artifacts/web-link.json"
  pages: ""                                  # ручной состав страниц; флаг --pages важнее
  modules_dir: ""                            # ветка документов фронта внутри docs_root
  url_rewrite: []
  registry_calls: []
```

`out` и `link_out` — относительно **текущего каталога**, как `out` шага 1,
а не относительно `--root`. Команды зовут из корня продукта, поэтому
умолчания напишут артефакты туда же; на поставке их подставляет установщик —
в каталог настройки.

**`enrolled` и `domains` на шаг `web` не действуют.** Каждый модуль фронта
документируется (`enrolled: true`) и остаётся без домена (`web/modules.py`).
Область фронта задают три вещи: `web.roots` — какие каталоги обходить,
`exclude` верхнего уровня — куда не заходить вовсе (встроенный список уже
отсекает `node_modules`, `dist`, `.angular`, `coverage`), и отсев секции
`web` файла правил — что внутри области не документировать, с причиной.

**Адреса переписываются при `web scan`, а не при `web link`.** `url_rewrite`
применяется к вызовам во время разбора, и в манифест фронта ключ вызова
попадает уже переписанным; `web link` берёт из секции только `link_out`
и имена модулей `url_rewrite`, чтобы назвать ненастроенные. Правка префикса
без повторного `web scan` меняет лишь список «модуль не настроен».

`pages` и `modules_dir` относятся к странице как единице документации:
что пишется в `pages.yaml` и почему пустой `modules_dir` значит «та же
ветка, что у бэкенда», — в [`pages.md`](pages.md).

**2. Секция `web` в `rules.yaml`: что считать страницей, компонентом, сервисом.**

Файл правил один на проект, секции две — `dotnet` и `web`. Секцию называет
команда, умолчания у неё нет: плоский файл, прочитанный шагом `web`, дал бы
правила .NET на TypeScript. Подробно — в [`configuration.md`](configuration.md).

**`require_public` в секции `web` обязан быть `false`.** У TypeScript
модификатора `public` на уровне объявления нет вовсе: видимость задаётся
словом `export`. Значение, скопированное из секции `dotnet`, даёт пустое
дерево без единого сообщения об ошибке.

**3. Довести «решение не принято» до нуля** тем же циклом, что и на шаге 1:

```bash
docpipe web scan --root . --stats          # посмотреть срезы
# дописать одно правило в секцию `web`
docpipe web scan --root . --stats          # повторить
docpipe web scan --root . --fail-on-undecided   # закрепить в CI
```

Срезов шесть, как у `scan --stats`. Для фронта главный из них — «последнее
слово»: словарь «окончаний имён» зашит под .NET, и `Component`, `Guard`,
`State`, `Interceptor` уходят у него в «(прочее)», а последнее слово
CamelCase имени берётся из самого имени (`authInterceptor` → `Interceptor`).

`--format json` печатает тот же отчёт структурой той же схемы, что
у `scan --stats` (`schema_version` `1.0`), с `lang: "ts"`. На
`tests/fixtures/WebWorkspace` блок `decisions` — 25 документируем,
4 не документируем, 0 без решения и 5 `page_covered`. Два поля
фронта отличаются от .NET: `stale_overrides` — правила `pages.yaml`,
не легшие ни на что (`kind`, `key`, `reason`; в stderr они печатаются
по-прежнему), а `scope` всегда `null`, потому что скоуп-прогона у шага
`web` нет. `--top` усекает `items` каждого среза, `total` среза — число
строк до усечения. `--format json` без `--stats` — отказ с кодом 2.

Сами символы за этими числами показывает `symbols --lang ts`: секция
`web` правил, тот же обход и тот же `pages.yaml`, что у `web scan`,
поэтому `page_covered` у них сходится. Фильтр `--path` работает и здесь
(пути фронта — те же репо-относительные пути):

```bash
docpipe symbols --root . --lang ts --state any --path src/app/routes/models --format json
```

В JSON у каждой строки три поля решения: `winner_rule` — правило, давшее
вид, `exclusion` — `{id, reason}` отсева, `page` — `{id, title}` страницы,
внутри документа которой описан символ (только у `page_covered`; `id` —
узел страницы в `doc-tree.web.json`; по заголовку его не найти, заголовок
не уникален). **Сама страница здесь — `kind:
component` и `winner_rule: web.component`**: `symbols` отвечает по правилам,
а страницей компонент делает повышение по таблице роутов. Почему класс
страница — вопрос к `web pages` (ниже).

**4. Заполнить `url_rewrite` — по записи на модуль.** Отсутствие записи это
не «преобразования нет», а ненастроенный модуль, и `web link` называет его
вслух. Пустые поля при указанном `module` означают «проверено, не преобразуется».

**5. Прогнать `web link` и посмотреть пять категорий отчёта.** Кодом возврата
управляет `--fail-on`; по умолчанию отчёт печатается, но прогон не роняет —
непокрытые вызовы это состояние работы, а не дефект.

**6. Решить о концах без пары — секция `link` в `docpipe.yaml`.** Эндпоинт,
который зовут извне, вызов во внешний адрес и вызов, который статически
не восстановить, правилом разбора не закрываются: дефекта разбора там нет.
Для них — запись с причиной (раздел «Концы без пары» ниже); `web scan`
после правки не нужен, секцию читает `web link`.

Артефакты после настройки — три файла из первого раздела плюс документы
фронта в дереве шага 2.

## Что такое модуль фронта

Модуль объявляется одним из четырёх способов, и правила применяются **по месту**,
а не глобально: `angular.json` в корне не отменяет nx-проекта в соседнем каталоге.

| Форма | Что даёт модуль | Граница |
|---|---|---|
| `angular.json` | каждый элемент `projects` | `sourceRoot`, при его отсутствии `root` |
| `nx.json` + `apps/*/project.json` | каждый `project.json` | каталог самого `project.json` |
| `package.json` вне корня | сам каталог | каталог `package.json` |
| ничего из перечисленного | репозиторий целиком | корень |

**Ключ модуля — каталог-граница, а не файл объявления.** Один многопроектный
`angular.json` объявляет несколько модулей, и ключ по файлу склеил бы их в один
вместе с символами: ключ модуля входит в ключ символа.

Файл принадлежит модулю с самой длинной подходящей границей.

## Узел манифеста

Всё как на шаге 1, плюс четыре поля: `routes`, `web_calls`, `uses`,
`absorbed_by`. У узлов .NET они пусты всегда. На уровне манифеста —
список `unresolved_calls` (см. «Невосстановленные вызовы» ниже): у вызова
без адреса связи нет, и узлу он не приписывается.

```jsonc
// страница: маршрут и то, что она зовёт
{
  "id": "type:src#src/app/routes/models/quiz/quiz.component.QuizComponent`0",
  "kind": "page",
  "module": "tr-p",
  "routes": [
    { "path": "models/loader/quiz", "component": "…QuizComponent", "route_unresolved": false,
      "source": "src/app/routesPath/models.ts", "table": "modelsPath" }
  ],
  "uses": [
    { "target": "src/app/shared/services/items.service.ItemsService",
      "member": "dictionaries", "via": "load", "action": "" }
  ],
  "web_calls": [],
  "absorbed_by": ""
}
// сервис: здесь вызов и записан
{
  "id": "type:src#src/app/shared/services/items.service.ItemsService`0",
  "kind": "api-service",
  "web_calls": [
    { "file": "src/app/shared/services/items.service.ts", "line": 31, "member": "dictionaries",
      "key": { "http_method": "GET", "route": "api/items", "discriminator": "dictionaries" },
      "confidence": "high", "via_action": null, "host": "" }
  ],
  "absorbed_by": "type:src#src/app/routes/models/quiz/quiz.component.QuizComponent`0"
}
```

- **`fqn` строится от пути файла**, а не от каталога: в TypeScript единица
  изоляции — файл, и два файла одного каталога законно объявляют одноимённый
  `Helper`;
- **`namespace` — каталог файла.** Пространств имён в языке нет; по этому полю
  матчатся правила `namespace_regex`;
- **вызовы лежат на узле того файла, где записаны**, — на том, в чей диапазон
  строк вызов попал (из накрывающих — самый узкий). Связь строит сервис,
  а не страница. До S16 вызов доставался **каждому** узлу файла, и DTO рядом
  с сервисом получал все его вызовы — отчёт связи считал их дважды. Вызов
  вне диапазона любого узла (фабрика уровня модуля, не ставшая узлом)
  по-прежнему раздаётся всем узлам файла и считается в `calls_unattributed`
  сидкара. `member` — член, в теле которого записан вызов (пустая
  строка — вне члена); `via_action` заполнен, только когда вызов записан
  прямо в обработчике `@Action`; `host` — хост абсолютного адреса в нижнем
  регистре, без порта (пусто у относительного): в ключ он не входит, его
  читает правило внешнего адресата;
- **шаблон `.html` входит в `sources` и в `impl_hash`**, стили `.scss` — нет;
- **`uses` — граф вызовов**: «член этого узла зовёт вот этот член другого».
  Не то же, что `dependencies`: внедрить сервис и звать его метод — разные
  утверждения, и разница между ними на боевом модуле была вчетверо.
  `via` — член источника; у обращения из разметки это `<шаблон>`.
  `action` — тип экшена NGXS, если до цели дошли цепочкой
  `dispatch(new X())` → `@Action(X)`: тип живёт на ребре, а не на вызове,
  потому что тот же метод сервиса зовут и обработчик, и компонент напрямую;
- **`absorbed_by`** — идентификатор страницы, внутри документа которой узел
  описывается. Пустая строка: у узла свой документ;
- **`source` и `table` называют, откуда взялся маршрут** — файл с таблицей
  и имя массива. Дерево собирается межфайлово, и без этой пары по узлу нельзя
  сказать, какой из восьми массивов `Routes` привёл сюда.

## Виды

Одиннадцать видов заводятся секцией `web` файла правил, два — фактами,
один — объявлением человека:

| Вид | Чем определяется |
|---|---|
| `component`, `state`, `ng-module`, `pipe`, `directive` | декоратор |
| `interceptor`, `guard` | базовый тип либо суффикс имени |
| `service` | `@Injectable` либо суффикс `Service` |
| `action`, `routes`, `dto` | путь и вид объявления |
| **`page`** | компонент, до которого можно дойти по таблице роутов |
| **`api-service`** | сервис, который делает HTTP-вызовы |
| **`feature`** | раздел без маршрута, объявленный в `pages.yaml` (`features:`) |

`page` и `api-service` — повышения: их выдаёт не правило, а факт. Таблица
роутов собирается межфайлово, вызовы разбираются отдельно, и в символе нет
ни того, ни другого. `matched_rules` при повышении не меняется — там записано,
что сработало. `feature` — синтетический узел без символа: границей служит
каталог, а узлы внутри описываются в его документе; подробно — в
[`pages.md`](pages.md).

## Список страниц и обоснование

> Страница как **единица документации** — состав, ручное управление, агрегатный
> документ — описана отдельно: [`pages.md`](pages.md). Здесь только выход шага.

```bash
docpipe web pages artifacts/doc-tree.web.json [--depth 3] [--not-pages]
                  [--route ПОДСТРОКА] [--module ПОДСТРОКА] [--format text|json|csv]
```

Отвечает на вопрос, на который не отвечают ни `scan --stats`, ни `symbols`:
**почему этот класс — страница.** Оба показывают срабатывания правил, а правило
здесь сказало `component`; страницей класс делает повышение.

```
/models/loader/quiz   QuizComponent   [tr-p]
  почему страница  web.component -> component, затем повышение по таблице роутов (1)
  маршруты         /models/loader/quiz   <- src/app/routesPath/models.ts : modelsPath
  документ         docs/modules/pages/tr-p/quiz-component.md
  состав           членов 4, внешний шаблон нет
  зовёт            AuditService (api-service, шаг 1): log
                   ItemsService (api-service, шаг 1): dictionaries
  эндпоинтов       2 зовёт, 2 достижимо по внедрению (вторая величина — инвентарь, а не состав страницы)
                   GET /api/items   <- через ItemsService.dictionaries, шаг 1
                   POST /integration/log/auditj   <- через AuditService.log, шаг 1
```

- **вызовы вычисляются обходом графа вызовов** (`uses`), а не читаются полем:
  они лежат на узле сервиса, где и записаны. Отсюда `--depth` (умолчание 3)
  и посредник у каждой строки; до цели, достигнутой диспатчем, дописывается
  тип экшена;
- **`--not-pages`** печатает обратную сторону — компоненты, страницами
  не ставшие, с причиной. Вопрос «почему этого экрана нет в списке» задаётся
  так же часто, как прямой;
- **`--format csv`** даёт таблицу, которой удобно размечать страницы руками;
- **счётчики считаются по всему дереву**, а не по суженному списку.

Заметки отчёта — подсказки, а не смена вида: `kind` в манифесте они не меняют.

| Заметка | Что значит |
|---|---|
| маршрут пустой | обычно layout с `<router-outlet>`, а не экран |
| признаков функционала не найдено | ни членов, ни внешнего шаблона, ни вызовов |
| страница не ходит за данными сама | члены есть, а ни прямого вызова сервиса, ни диспатча нет: обычно данные приходят через `@Input` от родителя либо из платформенного грида |
| цепочка вызовов обрывается на символах без решения | ребро ведёт в символ, про который решение не принято, и список эндпоинтов короче правды; чинится настройкой правил, а не глубиной |
| маршрут не восстановлен ни у одной записи | вид `page` есть, а якорь поставить нельзя: в покрытие страниц такая не попадёт |

**Ноль страниц при непустом манифесте — почти всегда неопознанная таблица.**
Таблица опознаётся по аннотации типа (`const x: Routes = [...]`); массив,
записанный прямо в `RouterModule.forRoot([...])` или без аннотации, таблицей
не считается и не даёт ни одной ошибки разбора.

## Отчёт связи

```
Вызовов фронта: 18 (не восстановлено и в связь не идёт ещё 1), эндпоинтов бэкенда: 10.

      6  связь найдена точно
      3  почти совпало: ключи различаются только числом {}
      9  вызов без эндпоинта
      3  эндпоинт без вызывающего
      1  ОДИН КЛЮЧ У ДВУХ УЗЛОВ БЭКЕНДА

Решено секцией `link`:
      0  вызов во внешний адрес (`link.external_targets`)
      0  эндпоинт зовут извне (`link.external_callers`)
      0  невосстановимый вызов (`link.unresolvable`)
```

| Категория | Дефект? |
|---|---|
| связь найдена точно | — |
| почти совпало | нет, инвентарь: одна сторона знает про параметр, вторая нет |
| эндпоинт без вызывающего | нет: его может звать другая система или мобильный клиент |
| вызов без эндпоинта | нет: часть бэка на конвенциональной маршрутизации |
| один ключ у двух узлов бэкенда | **да**: приложение с такой парой не выберет действие |
| решено секцией `link` (три строки) | нет: решение человека с причиной; уходит из «без эндпоинта», «без вызывающего» и `calls_unresolved` (см. «Концы без пары» ниже) |

**Находка не меняет кода возврата**, пока не названа в `--fail-on`, — включая
коллизию. Линт, красный с первого дня, выключат на второй.

Отдельно отчёт печатает:

- **контроллеры с конвенциональной маршрутизацией** — их URL задан
  в `MapControllerRoute`, а не атрибутами, и вызовы к ним честно попадают
  в «вызов без эндпоинта». Сюда идёт только настоящий: класс не абстрактный,
  у него есть публичный метод, своего `[Route]` нет, и ни у одного эндпоинта
  маршрут не собрался — ни свой, ни унаследованный от базы. Голый `[HttpGet]`
  шаблона не задаёт, и действие под ним остаётся конвенциональным. До S17
  сюда попадали абстрактные базы и контроллеры с `[Route]` без глагола:
  на squidex и abp — 10 записей, настоящих из них 2;
- **эндпоинты с невосстановленным маршрутом** (`unresolved_endpoints`,
  `counts.endpoints_unresolved`) — аргумент маршрута записан выражением,
  которое не разрешилось в константу (см. [`manifest.md`](manifest.md#маршрут-эндпоинта)).
  В ключи связи они не идут, и без этого списка пропали бы из отчёта молча:
  константа в проекте вне `roots` — обычный путь к такому исходу;
- **модули фронта без записи в `web.url_rewrite`** — пустое правило и отсутствие
  правила разные вещи: первое значит «проверено, преобразования нет». Модуль
  с вызовами — с восстановленными **или** невосстановленными
  (`Manifest.unresolved_calls`): до S18 считались только первые, и модуль,
  у которого не восстановлен ни один вызов, молчал (на abp — `core`).

`counts.calls_unresolved` — невосстановленные вызовы манифеста фронта, **о которых
решения нет**. В связь они не идут вовсе (маршрута нет) и в `calls_total`
не входят; без числа рядом «вызовов фронта 4» читалось бы как «всего четыре».
Объявленные невосстановимыми (`link.unresolvable`) считает
`counts.declared_unresolvable`, а первая строка текста печатает сумму обоих —
вместе с `calls_total` это все вызовы в коде.

Вызов без эндпоинта несёт `host` — хост абсолютного адреса (у относительного
пусто), и текст печатает его рядом: без него вызов во внешнюю систему
неотличим от вызова своего бэка с тем же путём.

**Эндпоинт с методом `*`** — действие с `[Route]` без глагола — принимает
любой метод и связывается с вызовом любого метода: точно (`GET api/x`
с `* api/x`) и «почти» (`GET api/x` с `* api/x/{}`). Вызов, совпавший
и с `GET api/x`, и с `* api/x`, связывается с обоими; дублем такая пара
не считается — ASP.NET выберет действие с методом.

Формат `web-link.json` — `schema_version: "1.3"`: в 1.1 добавлены
`unresolved_endpoints` и `counts.endpoints_unresolved` (S17), в 1.2 —
`counts.calls_unresolved`, и `unconfigured_modules` видит модули только
с невосстановленными вызовами (S18), в 1.3 — решения секции `link`
(`external_targets`, `external_callers`, `declared_unresolvable` и их счётчики),
`host` у вызова без эндпоинта, а `counts.calls_unresolved` — только
невосстановленные без решения (S20).

```bash
uv run docpipe web link A.json B.json --fail-on duplicate_endpoints
```

Известные категории: `linked`, `almost`, `calls_without_endpoint`,
`endpoints_without_caller`, `duplicate_endpoints`. Опечатка отвергается кодом 2:
незнакомое имя означало бы молча выключенную проверку. Категорий секции `link`
среди них нет: решение человека — не находка, и ронять прогон за него нечего.

### Концы без пары: секция `link`

Три вида конца шва остаются без пары не из-за разбора, и правилом разбора
их не закрыть — только решением человека «документируем или нет, и почему».
Решение записывается в `docpipe.yaml`, секция верхнего уровня:

```yaml
link:
  external_targets:                 # вызов во внешний адрес
    - host: "raw.githubusercontent.com"
      reason: "справка с GitHub, не наш бэк"
    - route: "auth/**"              # свой адрес, но обслуживает его шлюз
      reason: "OAuth на шлюзе"
      document: true                # по умолчанию false
  external_callers:                 # эндпоинт, который зовут извне
    - route: "content/{app}/**"
      reason: "публичный API для SDK"
    - route: "api/hooks/**"
      http_method: POST             # пусто — любой метод
      reason: "вебхуки платёжной системы"
      document: false               # по умолчанию true
  unresolvable:                     # вызов, адрес которого статически не восстановить
    - path: "**/links.service.ts"
      reason: "гипермедиа: адрес и метод приходят в ответе"
```

| Запись | Что накрывает | Категория вместо |
|---|---|---|
| `external_targets[]` | вызов **без эндпоинта**: `host` — маска хоста абсолютного адреса (без схемы, порта и пути), `route` — маска маршрута ключа; ровно одно из двух | `calls_without_endpoint` → `external_targets` |
| `external_callers[]` | эндпоинт **без вызывающего**: `route` — маска маршрута эндпоинта, `http_method` — глагол или пусто | `endpoints_without_caller` → `external_callers` |
| `unresolvable[]` | невосстановленный вызов (`Manifest.unresolved_calls`) в файле под глобом `path` | `calls_unresolved` → `declared_unresolvable` |

- **Решение действует только на конец без пары.** Вызов, которому эндпоинт
  нашёлся — точно или «почти», — остаётся связью, как бы ни совпало правило;
  эндпоинт, который зовёт фронт, — тоже. Поэтому широкое `api/**` в
  `external_targets` не трогает связанных вызовов, а забирает только
  несвязанные — и это стоит проверить по списку.
- **Маска маршрута — в форме ключа.** Подстановки пишутся как в атрибуте
  (`{app}`, `{id:guid}`, `:id` — всё становится `{}`), регистр и крайние `/`
  не важны; `*` пересекает `/`, как у глобов путей. Сравнение — с ключом
  **после** `web.url_rewrite` и с маршрутом эндпоинта вместе с префиксом базы
  (S17): маска, записанная до преобразования, не совпадёт никогда.
- **Эндпоинт с методом `*`** совпадает с правилом любого метода.
- **`unresolvable` накрывает файл целиком**, и будущие вызовы тоже: новый
  вызов, который можно восстановить обёрткой или построителем, уйдёт
  в `declared_unresolvable` молча. Глоб уже файла — каталога, а не репозитория.
- **Сработала первая совпавшая запись** в порядке файла; одно условие,
  записанное дважды, — отказ загрузки (вторая не применялась бы никогда).
- `reason` обязателен и непуст; строка вместо записи, пустая или отсутствующая
  причина, оба или ни одного из `host`/`route`, хост со схемой или портом,
  неизвестный `http_method` — отказ загрузки.

У каждой записи этих категорий — `decision`: `index` (номер записи в своём
списке, с нуля), `rule` (условие как написано — по нему запись находят
в файле) и `reason`; у `external_targets` и `external_callers` — ещё
`document`. В документы `document` пока не проецируется — пункт бэклога
«Фронт↔бэк в документах». Какие записи секции касаются данного кода, —
`docpipe setup explain ПУТЬ` (ключи `link.*` в `decisions`).

## Адрес вызова: что восстанавливается

Первый аргумент `this.http.get(…)` даёт либо адрес, либо отказ с причиной.
Третьего — правдоподобного ключа, который не совпадёт ни с чем, — быть
не должно: до S16 пять форм давали именно его, и число «восстановлено»
росло за счёт ошибок.

| Форма | Результат |
|---|---|
| `'api/x'`, `` `api/x` `` | литерал, `high` |
| `` `api/x/${id}` `` | `api/x/{}`, `high`: целый сегмент — параметр |
| `` `${this.baseUrl}/x` `` | база восстановлена — литерал; нет — отказ «база в начале шаблона не восстановлена» |
| `` `api/x/search${buildQuery(q)}` `` | подстановка, прилипшая к концу сегмента и последняя в шаблоне, отбрасывается: `api/x/search`, `medium`. После `?` или `#` не трогается: query и так срежет нормализация, и уверенность не падает |
| `'api/x/' + id` | `api/x/{}`, `medium`. Первая часть не восстановлена (`this.base + '/api/x'`) — отказ «база в начале конкатенации не восстановлена»; оператор не `+` (`url \|\| 'api/x'`) — «выражение не восстановлено» |
| `url` | `const` ближайшего охватывающего блока, объявленный выше вызова, → внешних блоков → уровня файла. `const` **другой** функции не виден никогда; `let`/`var` — константа, пока им не присваивают; параметр затеняет одноимённую константу файла |
| `this.baseUrl` | поле своего класса с литералом, которому **не присваивают** вне инициализатора (`readonly` — тоже: в конструкторе его присвоить можно) |
| `https://host/x` | хост — в `WebCall.host`, ключ — без хоста |

Причины отказа различают вид, и по ним группируется невосстановленное:

| Причина | Что в коде |
|---|---|
| значение переменной — вызов `` `apiUrl.buildUrl(…)` `` | `const url` инициализирован вызовом — построитель адреса |
| значение переменной — параметр функции | адрес пришёл аргументом — обычно тело обёртки |
| поле присваивается вне инициализатора | `public fileSource = ''` и `this.fileSource = src` в методе |
| переменная присваивается после объявления | `let url = 'a'; … url = 'b'` |
| база в начале шаблона / конкатенации не восстановлена | `` `${base}/x` ``, `base + '/x'` с неизвестной `base` |
| значение переменной не восстановлено | имя не найдено, деструктуризация, `link.href`, `const` с шаблоном (`` const url = `${a}/x` ``) |
| выражение не восстановлено | вызов прямо в аргументе, `a \|\| b`, прочее |
| в объявленном аргументе обёртки нет адреса | вызов объявленной обёртки, у которого аргумента `url.arg` нет или в нём нет поля `url.field` |
| метод HTTP из аргумента обёртки не восстановлен | `http_method: {arg: …}`, а там не литерал (`link.method`) |
| в имени обёртки нет глагола HTTP | `http_method: {from_name: true}` у `upload`, `requestVersioned` |
| в объявленном аргументе построителя нет пути | объявленный построитель позван без аргумента `path.arg` |

## Невосстановленные вызовы

Каждый вызов `HttpClient` без адреса лежит в манифесте фронта — список
`unresolved_calls` уровня манифеста (формат 2.3; `via` — с 2.4), отсортированный
по файлу и строке. Раньше он был только числом `calls_unresolved` в сидкаре, и ни одно
из 78 мест squidex нельзя было открыть, не перечитав исходники.

```jsonc
"unresolved_calls": [
  { "file": "frontend/src/app/services/apps.service.ts", "line": 28, "http_method": "GET",
    "reason": "значение переменной — вызов `apiUrl.buildUrl(…)`",
    "expression": "url", "module": "seam-web", "member": "list" },
  { "file": "frontend/src/app/framework/http-extensions.ts", "line": 16, "http_method": "GET",
    "reason": "значение переменной — параметр функции",
    "expression": "url", "module": "seam-web", "member": "" }
]
```

`reason` — та же формулировка, что в таблице выше: построитель адреса
(«вызов `X.m(…)`»), тело обёртки («параметр функции»), гипермедиа
(«не восстановлено») не сливаются. `module` — имя модуля фронта (по нему
отчёт связи находит модуль без `url_rewrite`); `member` — член класса,
в котором записан вызов, пустая строка — вне членов (функция модуля:
тела `export module HTTP { export function getVersioned(…) }`).
Только файлы модулей; `len(unresolved_calls)` равно `calls_unresolved`
сидкара. `via` — объявленная обёртка или построитель, через которые вызов
прошёл и всё же не восстановлен (гипермедиа `buildUrl(link.href)`), — см. ниже.

## Обёртки и построители

Вызов, у которого нет глагола `HttpClient`, — `HTTP.getVersioned(this.http, url)`,
`this.rest.request({ method, url })` — без настройки прогон не видит вовсе:
ни в `web_calls`, ни в `unresolved_calls`. Адрес от построителя
(`const url = this.apiUrl.buildUrl('/api/apps'); this.http.get(url)`) виден,
но невосстановлен. Обёртку по имени не распознать (у squidex
`get<T>(path, default)` — чтение состояния), поэтому в разбор она входит
**записью** в секции `web` `docpipe.yaml`, а находит её `docpipe setup
candidates http-wrappers` и `url-builders` ([`setup.md`](setup.md)):

```yaml
web:
  http_wrappers:
    - receiver: HTTP
      method_regex: "^(get|post|put|delete)Versioned$"
      url: {arg: 1}                      # адрес — второй аргумент: первым идёт сам HttpClient
      http_method: {from_name: true}     # getVersioned → GET
      reason: "обёртка над HttpClient с версией (framework/angular/http)"
    - receiver: HTTP
      method: requestVersioned
      url: {arg: 2}
      http_method: {arg: 1}              # метод — литерал во втором аргументе
    - receiver: rest
      method: request
      url: {arg: 0, field: url}          # поле объекта-запроса
      http_method: {arg: 0, field: method}
  url_builders:
    - receiver: apiUrl
      method: buildUrl
      path: {arg: 0}
```

| Ключ | Что |
|---|---|
| `receiver` | получатель как в коде; сравнивается **последний сегмент без регистра**: `this.rest`, `rest`, `Rest` — одно |
| `method` / `method_regex` | ровно одно из двух: имя точно (с регистром) или регулярка **целиком** (`re.fullmatch`, как `name_regex` в правилах) |
| `url`, `path` | `arg` — номер аргумента с нуля, без комментариев (та же позиция, что у кандидата: `1`, `0.url`); `field` — поле объектного литерала в нём |
| `http_method` | ровно один способ: `arg` (и `field`) — литерал из аргумента; `fixed: GET`; `from_name: true` — ведущий глагол имени (`getVersioned` → `GET`, `getter` — не глагол) |
| `reason` | необязательна; показывает `setup explain` |

Что делает прогон (`web/calls.py`, `build_calls`):

1. **Вызов обёртки** — вызов-кандидат S18, совпавший с записью, становится
   вызовом: адрес — значение аргумента `url` (литерал, шаблон, `const` по
   правилам «Адрес вызова» выше), метод — по `http_method`. Дальше —
   обычный путь: `url_rewrite` модуля, `registry_calls`, нормализация.
   У вызова в манифесте `via: "HTTP.getVersioned"`.
2. **Построитель** — адрес вызова (прямого или через обёртку), который
   есть значение вызова объявленного построителя (`const url =
   this.apiUrl.buildUrl(…)` или вызов прямо в аргументе), берётся из его
   аргумента `path`; `via: "apiUrl.buildUrl"`, у обоих сразу —
   `"HTTP.getVersioned, apiUrl.buildUrl"`. Путь из данных
   (`buildUrl(link.href)`) остаётся невосстановленным, но с причиной
   и выражением **пути** (`link.href`): после объявления вопрос уже не
   в построителе.
3. **Тело обёртки** — вызов `HttpClient` в функции с именем обёртки, адрес
   которого — ровно тот её параметр, что запись называет адресом
   (`http.get(url)` в `getVersioned(http, url)` при `url: {arg: 1}`;
   `config.url` и `{ url }` при `url: {arg: 0, field: url}`), — в
   `unresolved_calls` не идёт: вызов продукта восстановлен там, где обёртку
   зовут. Счётчик — `calls_inside_wrappers` сидкара, и `web scan` печатает
   строку «Вызовов в телах объявленных обёрток». Получатель записи здесь
   не сверяется (у функции `export module HTTP` его нет), поэтому
   одноимённая функция в другом классе с адресом в том же параметре тоже
   уйдёт в счётчик.
4. Невосстановленный адрес или метод вызова через обёртку — запись
   `unresolved_calls` с `via`; адрес важнее метода: у гипермедиа
   (`link.method`, `link.href`) названа причина адреса — та же, что у прямого
   вызова.

Отказы: две записи с одним получателем и `method` (и два построителя одного
вызова) — отказ загрузки; вызов, совпавший с двумя записями (`method_regex`
пересекаются), — отказ прогона с кодом 2 и обеими записями: выбор «первой
в файле» менял бы ключи от перестановки строк. Запись, не совпавшая ни с чем,
молчит — это видно по `configured: false` у кандидата.

**Факт пишет извлечение, запись применяет интерпретация.** Извлечение от
записей не зависит (`extract_call_facts(root, path)` — без настройки), поэтому
вызов, который не стал фактом, запись не увидит. Факт о вызове члена
пишется, если аргумент похож на адрес, если его значение — результат вызова
или если аргументом передан сам `HttpClient` (`this.http`, `http`): без
последнего обёртка с адресом-параметром функции, с `link.href` напрямую
или с шаблоном, внутри которого построитель, осталась бы невидимой и после
объявления. Шаблон с построителем внутри
(`` `${this.apiUrl.buildUrl(x)}${q}` ``) запись построителя не разбирает:
вызов виден невосстановленным. Различитель реестра в **теле** у вызова через
обёртку не берётся (только из query адреса).

Правка записи без повторного `web scan` не меняет ни одной связи: ключи
вызовов строятся в `web scan`, а `web link` сводит готовые манифесты.

## Ключ связи

Пара `(HTTP-метод, маршрут)`, нормализованная общей функцией `docpipe/route.py`.
Шесть шагов в фиксированном порядке:

1. отбросить схему и хост;
2. отбросить query и фрагмент — **разделитель ищется вне подстановки**, иначе
   шаблон `{id?}` обрезается по своему же вопросительному знаку;
3. применить преобразование префикса модуля (`web.url_rewrite`);
4. заменить подстановки на `{}`: `${id}`, `{id:guid}`, `{id?}`, `{*rest}`, `:id`;
5. схлопнуть `//`, снять ведущий и замыкающий `/`;
6. привести к нижнему регистру.

**Различитель в сопоставление не входит.** `api/items/query` — один эндпоинт
платформы для всех имён списков; `listInnerName` отвечает на вопрос «зачем
звали», а не «куда». Два обращения с разными именами дают две связи с одним
эндпоинтом.

## Что шаг не делает

| Не делает | Почему |
|---|---|
| не разбирает `.html` грамматикой | грамматики шаблонов нет; выражения из `{{ … }}` и биндингов (`(click)=`, `[value]=`, `*ngIf=`) достаются регулярными выражениями и сверяются с объявленными членами (`web/templates.py`): обращение к члену зависимости становится ребром `uses` с `via: "<шаблон>"`, к своему члену — только счётчиком, неопознанное имя не становится ничем |
| не выводит логику интерцепторов | это интерпретатор TypeScript; преобразование задаётся `web.url_rewrite` |
| не поддерживает `this.http.request(method, url)` без записи | первый аргумент там не URL, и обработка «через раз» дала бы маршрут `get`. С адресом, похожим на адрес или построенным построителем, такой вызов виден находкой `http.request` у `setup candidates http-wrappers` (на squidex — 16, все гипермедиа через `buildUrl(link.href)`) и объявляется обёрткой: `receiver: http, method: request, url: {arg: 1}, http_method: {arg: 0}`. Вызов с методом и адресом из данных (`request(link.method, link.href)`) фактом не становится и не виден и после записи |
| не параллелит разбор | 1301 файл разбирается за 1,4 с; пул процессов стоил бы дороже |

В самом манифесте недетерминированных полей нет: проверка воспроизводимости —
побайтовое сравнение файла. `host` у вызова в манифесте — хост адреса из кода,
а не машины; хост машины живёт только здесь.

`calls_unattributed` — вызовы вне диапазона любого узла, розданные всем узлам
своего файла. Больше нуля — `web scan` печатает строку «Вызовов вне диапазона
узлов»: в отчёте связи такой вызов посчитан столько раз, сколько узлов в файле.

`calls_inside_wrappers` — тела объявленных обёрток (раздел «Обёртки
и построители»): ни в восстановленные, ни в невосстановленные они не идут,
и `calls_resolved + calls_unresolved + calls_inside_wrappers` равно числу
вызовов `HttpClient` плюс вызовов через объявленные обёртки.

# Python в пайплайне: аналитика перед планом

Документ отвечает на два вопроса: как устроены два уже работающих парсера
(.NET и Angular) и что из этого переносится на Python, а что нет.

Кода в этом заходе не написано ни строки — намеренно. Половина решений здесь
зависит от фактов о боевом репозитории, которых у нас пока нет; чем их собрать,
описано в §8, а собирает их `tools/recon-python.sh`.

## Что известно от владельца

Факты, вокруг которых собран документ. Первые два заданы в постановке,
остальные уточнены во втором заходе и переписали §2 и §4.1.

| Факт | Что из него следует |
|---|---|
| Python живёт во многих сервисах, зовёт их .NET | стрелка вызова развёрнута относительно фронта — §2 |
| В том числе через tornado | маршрут — регулярное выражение, а не шаблон — §3 |
| **Python 2 нет.** Сейчас в основном 3.9, скоро поднимут до 3.14 | версия не блокер, но диапазон широкий, и апгрейд грамматики придётся планировать — §5.5 |
| **Есть `tornado_service.py`, где регистрируются все питон-модули** | это **реестр**, а не просто точка входа; он и есть главная цель разбора — §2.4 |
| Дальше модули **как-то** зовутся через Grid-сервисы — как именно, надо выяснить | ключ связи может оказаться не HTTP-маршрутом, а именем модуля — §2.5 |
| Часть модулей лежит отдельно: `inner_debts` — на одном уровне с `grid` | у сервисов нет общего родителя, и правило «модуль ⇔ каталог под X» не годится — §4.1 |
| Где именно .NET зовёт питон — соберут в следующий заход | §8 вопрос №8 остаётся открытым, но перестаёт быть единственным блокером |

Ловушки грамматики в §5 проверены на `tree-sitter-python` 0.25.0 против
`tree-sitter` 0.26.0 — той же версии рантайма, что стои́т в проекте. Каждая
из них однажды прошла бы приёмку и дала бы неверный результат молча.

## 0. Как устроены два существующих парсера

### 0.1 Общая ось

Оба шага — `scan` (.NET) и `web scan` (Angular) — это одна и та же цепочка
из шести звеньев. Различаются они только тем, чем заполнено каждое звено.

| Звено | .NET | Angular |
|---|---|---|
| обход ФС | `discovery.discover` — общий, один проход, поля `cs_files`/`csproj_files`/`sln_files` | тот же вызов, поля `ts_files`/`html_files`/`web_project_files` |
| единица сборки | `dotnet/csproj.py` — модуль ⇔ файл `.csproj` | `web/modules.py` — модуль ⇔ **каталог-граница**, потому что один `angular.json` объявляет несколько проектов |
| разбор файла | `dotnet/parser.py` → `FileParseResult` | `web/parser.py` → `FileParseResult` |
| резолв имён | `dotnet/resolve.py` — по **namespace** и `using` | `web/resolve.py` — по **файлам**: импорты + алиасы `tsconfig` + бочки `index.ts` |
| классификация | `classify.py` + секция `dotnet:` файла правил | тот же `classify.py` + секция `web:` |
| сборка узлов | `tree.build_nodes` | `web/tree.build_nodes` — свой, потому что ключ модуля другой |

Всё, что после манифеста, языка не знает вовсе: `materialize`, `docs status`,
`worklist`, бизнес-слой работают от `Manifest` и добавления языка не заметят —
кроме шести мест, перечисленных в §4.1.

### 0.2 Что уже общее, и это главный капитал

Эти модули писались один раз и обслуживают обе стороны. Питон обязан въехать
в них, а не завести рядом второй экземпляр:

| Модуль | Что делает | Почему общий |
|---|---|---|
| `docpipe/route.py` | нормализация HTTP-маршрута, `RouteKey`, `almost_equal` | две копии нормализации разойдутся молча: маршруты просто перестанут находить друг друга |
| `docpipe/symbols.py` | `symbol_key(модуль, FQN, арность)`, `strip_generics` | схема ключа обязана совпадать с id узла, иначе символы не сопоставятся с узлами |
| `docpipe/classify.py` + `ruleset.py` | движок правил: десять предикатов, `priority`, `unless`, отсев с `reason` | правила — данные; новый язык = новая секция YAML, а не новый Python-код |
| `docpipe/tree.doc_path_for` | раскладка документов | одна раскладка на всё дерево |
| `docpipe/hashing.py`, `cache.py`, `diff.py`, `emit.write_*` | хэши, кэш разбора (ключ включает версии грамматик), запись артефактов | — |
| `docpipe/model.py` | `Attribute`, `Member`, `RawDeclaration`, `FileParseResult`, `Symbol`, `Module`, `DocNode`, `Manifest` | одна схема на все языки, версия `2.0` |

Правило изоляции, записанное в `symbols.py`: **`docpipe/web/**` не имеет права
импортировать `docpipe/dotnet/**` и наоборот.** Общее живёт в корне пакета.
Для Python оно действует ровно так же.

### 0.3 Три вещи, которые в этих парсерах устроены неочевидно

Это не детали реализации, а решения, которые Python обязан унаследовать.

**Вид объявления — синтаксический, а не классификационный.** `TypeKind` — это
`class`/`interface`/`enum`/`function`/`const`. `controller`, `component`,
`page` — это `DocNode.kind`, результат работы правил. Парсер правил не читает.
Ровно поэтому добавление Python не требует ни одного нового вида в парсере,
кроме тех форм, которых у C# и TypeScript нет.

**Про каждый символ принимается решение, и «не документируем» — тоже решение.**
Три исхода: `<kind>`, `not_documented` (с обязательной причиной), `undecided`.
Последнее — единственное число, которое обязано идти к нулю, и `scan --stats`
показывает именно его. Питон получит свою колонку в этом же отчёте.

**Факты о вызовах отделены от их интерпретации.** `web/calls.py` разделён
на `extract_calls` (факты из синтаксиса, кэшируемы, от конфигурации
не зависят) и `build_calls` (применение `url_rewrite` и `registry_calls`).
Смена настройки меняет ключи, не заставляя перечитывать исходники. Для Python
это разделение важнее, чем для фронта: маршрут tornado — регулярное выражение,
и его перевод в шаблон — как раз интерпретация (см. §3).

## 1. Что требуется от шага `py`, в проверяемых формулировках

| Требование | Проверяемая формулировка |
|---|---|
| Питон-сервисы попадают в дерево документации | `docpipe py scan` даёт манифест схемы 2.x, где каждый сервис — `Module` с `lang: py`, а документируемые классы и функции — узлы |
| Видно, какой .NET-код зовёт какой питон-эндпоинт | отчёт связи, где строка — пара «член C# → обработчик tornado», сведённая по `(HTTP-метод, маршрут)`, а не по имени класса |
| Непокрытое названо, а не пропущено | у каждого эндпоинта tornado есть либо вызывающий, либо строка в категории «эндпоинт без вызывающего»; сумма категорий равна общему числу |
| Настройка заканчивается проверяемо | `undecided` по питон-символам доводится до нуля, `--fail-on-undecided` держит это в CI |
| Детерминизм не хуже, чем у двух существующих шагов | два прогона подряд дают побайтово одинаковый манифест |

Требование, которого здесь **нет** намеренно: «понять, что сервис делает».
Это шаг 3 и агент. Граница пайплайна та же, что была.

## 2. Главное отличие: стрелка вызова развёрнута

### 2.1 Фронт зовёт .NET; .NET зовёт Python

На шаге `web` роли распределены так:

```
Angular  ──HTTP──▶  .NET
клиент             сервер
web/calls.py       dotnet/endpoints.py
(WebCall)          (Endpoint)
        └── web/link.py сводит по RouteKey ──┘
```

На шаге `py` они меняются местами:

```
.NET  ──HTTP──▶  Python (tornado)
клиент           сервер
   ???           py/endpoints.py
                 (Endpoint)
```

Знака вопроса не должно быть, но он там есть. **Извлечения исходящих
HTTP-вызовов на стороне .NET в инструменте нет вообще** — проверено
поиском: `HttpClient` упоминается только в комментариях `web/`. Шаг 1 умеет
разбирать `[HttpGet]` (сервер) и `services.AddScoped` (DI), но не умеет
`httpClient.PostAsync(...)`.

Это не мелкая доработка, а второй экстрактор фактов сопоставимого с
`web/calls.py` размера (431 строка), и жить он обязан в `docpipe/dotnet/`.
Планировать его надо отдельной задачей и, возможно, отдельной веткой:
он полезен сам по себе (интеграции .NET↔.NET) и не блокируется разбором Python.

### 2.2 Что из этого следует для `link.py`

Хорошая новость: `web/link.py` уже устроен как «манифест-потребитель ×
манифест-поставщик». Направление там — **данные, а не код**:

```python
def build_report(backend: Manifest, web: Manifest, ...) -> LinkReport
#                 └ у кого endpoints    └ у кого вызовы
```

Заменив «backend» на «манифест питона» и «web» на «манифест .NET», получаем
ровно нужный отчёт с теми же пятью категориями. Переписывать нечего —
надо обобщить имена и вынести модуль из `web/` в корень, как уже вынесены
`route.py` и `symbols.py`.

Плохая новость — имя поля. Вызовы лежат в `DocNode.web_calls`, и на .NET-узле
поле с таким именем будет враньём в каждом отчёте. Читают его пять мест:
`web/link.py`, `web/pages.py`, `materialize/build.py`. Решение — в §7.2.

### 2.3 Ключ связи по HTTP, и что в нём надо проверить

Пара `(HTTP-метод, маршрут)`, а не ссылка на узел: идентификатор узла содержит
путь проекта и FQN, и переименование класса рвало бы связь при неизменном
HTTP-контракте. Для .NET↔Python довод даже сильнее: это два разных репозитория
кода в одном дереве, и переименовать питон-класс можно, не открывая C#.

Но у ключа есть предпосылка, которая на фронте выполнялась, а здесь **не
проверена**: обе стороны должны знать один и тот же путь. На фронте базу
дописывал прокси, и её преобразование записано в `web.url_rewrite`. Чем
и как .NET узнаёт адрес питон-сервиса — неизвестно (`appsettings.json`?
Consul? переменная окружения? `BaseAddress` именованного `HttpClient`?).
Если база лежит в конфигурации, а в коде остаётся только путь — ключ сходится.
Если в коде лежит полный URL с хостом — `normalize_route` хост отбрасывает,
тоже сходится. Если путь целиком собирается из настроек — не сходится ничего,
и нужен аналог `url_rewrite` для .NET. Это вопрос №8.2 разведки, и он блокирующий.

### 2.4 `tornado_service.py` — это реестр, а не точка входа

Уточнение владельца («есть `tornado_service.py`, где регистрируются все питон-модули»)
меняет ожидаемую форму разбора сильнее, чем кажется на первый взгляд.

Ожидание по умолчанию было такое: у каждого сервиса свой `Application([...])`
с маршрутами своих обработчиков — то есть N мелких таблиц, разбросанных
по N сервисам, как `Routes` в Angular. Реальность, судя по описанию, другая:
**один файл перечисляет все модули**, и это в точности та конструкция, которую
инструмент уже умеет называть по имени — реестр.

Разница в том, что́ является ключом. У таблицы роутов ключ — путь; у реестра
ключ — **имя записи**, а путь может отсутствовать вовсе. В АС CF на стороне .NET
всё уже устроено так: джобы, workflow и обработчики событий объявлены в XML,
диспетчеризуются по данным, и «литерала конкретного workflow в C# структурно
не существует». Механика якорей бизнес-слоя (`docpipe/registry/**`,
`business/resolve.py`, `REGISTRY_KIND`) написана ровно под этот случай.

Отсюда три следствия для плана:

1. **`tornado_service.py` разбирается отдельной задачей**, и она важнее задачи
   про `Application([...])`: имя зарегистрированного модуля — кандидат в главный
   якорь питон-стороны, а маршрут — только если модули действительно отдают HTTP.
2. **Реестр здесь в коде, а не в XML.** Существующий `registry/reader.py`
   декларативно читает xml и json; питон-реестр читается парсером Python.
   Это не повод плодить второй механизм якорей — повод отдать в общий механизм
   готовые записи.
3. **Форма регистрации неизвестна и определяет объём задачи.** Словарь
   `{"inner_debts": InnerDebtsModule}`, список кортежей, цепочка `register(...)`,
   декоратор `@register("inner_debts")` — четыре разные задачи. Первое, что надо
   увидеть глазами, — сам файл целиком; §2 разведки печатает его без обрезки.

### 2.5 Через Grid, а не по HTTP: третий возможный путь

«Модули каким-то образом вызываются через Grid-сервисы» — это ровно тот случай,
когда ошибка стои́т не задачи, а всего подхода. Возможны два сценария, и они
дают **разные ключи связи**:

| Сценарий | Что зовёт .NET | Ключ связи | Что делать |
|---|---|---|---|
| .NET → HTTP → tornado | `HttpClient` с путём | `(метод, маршрут)`, как на фронте | §2.1–§2.3 в силе; нужен `dotnet/calls.py` |
| .NET → Grid-сервис → питон-модуль | метод grid-сервиса по имени | **имя модуля из реестра** | нужен разбор `tornado_service.py` и цепочка через grid |

Второй сценарий не гипотетический: в CLAUDE.md уже записано, что имена методов
grid-сервиса — «единственное исключение» в `business_hash`, потому что «их
вызывают по имени через прокси, поэтому они и есть контракт». То есть механизм
grid-вызова в проекте уже осмыслен, просто с другой стороны.

**Практический вывод: не закладывать в план `dotnet/calls.py` как единственный
мост.** Порядок работ должен быть таким, чтобы разбор питон-стороны
(`tornado_service.py` + обработчики) не зависел от того, каким окажется ответ:
он полезен в обоих сценариях. А задача про мост ставится после разведки —
и в одном из вариантов это вообще не HTTP-экстрактор, а прослеживание цепочки
«grid-сервис → имя модуля».

Промежуточный вариант тоже возможен и вероятен: .NET зовёт grid-сервис,
а тот внутри себя ходит в tornado по HTTP. Тогда нужны оба звена, и связь
получается двухступенчатой — а это уже вопрос к тому, как её показывать
в документе, а не только как считать.

## 3. Маршрут tornado — регулярное выражение, а не шаблон

Это самая дорогая находка аналитики, и она проверена на боевом коде
нормализации, а не предположена.

Tornado объявляет маршрут регулярным выражением:

```python
tornado.web.Application([
    (r"/api/ml/models/([^/]+)/predict", PredictHandler),
    (r"/api/ml/health/?$",              HealthHandler, dict(cfg=cfg)),
    tornado.web.url(r"/api/ml/items/(?P<item_id>\d+)", ItemHandler, name="item"),
] + EXTRA_ROUTES, **settings)
```

`docpipe.route.normalize_route`, которому такое отдали бы напрямую, ломается
**тремя разными способами**, и каждый результат выглядит правдоподобно
(прогон на текущем коде):

| Вход | Результат `normalize_route` | Что произошло |
|---|---|---|
| `/api/ml/models/([^/]+)/predict` | `api/ml/models/([^/]+)/predict` | группа не распознана как подстановка; с `.NET`-ключом `api/ml/models/{}/predict` не совпадёт никогда |
| `/api/ml/items/(?P<item_id>\d+)` | `api/ml/items/(` | шаг «отбросить query» обрезал строку по `?` **внутри** `(?P<…>)` |
| `/api/ml/(?:v1\|v2)/run` | `api/ml/(` | то же самое, на некаптурящей группе |
| `^/api/ml/score/(\d+)/?$` | `^/api/ml/score/(\d+)` | якорь `^` остался в маршруте, `$` срезался вместе с `/?` |
| `/api/ml/health/?$` | `api/ml/health` | случайно правильно — по совпадению |

Последняя строка опаснее остальных: на простых маршрутах всё работает,
и дефект вылезет только там, где есть параметр — то есть ровно на тех
эндпоинтах, ради которых связь и строится.

**Решение.** Перевод регулярного выражения в шаблон — обязанность питон-стороны,
и делается он **до** `normalize_route`, отдельной функцией
(`py/routes.regex_to_template`). Она снимает якоря `^`/`$`, хвост `/?`,
и заменяет сбалансированные группы `(…)`, `(?:…)`, `(?P<name>…)` на `{}`.
Только после этого строка идёт в общую нормализацию.

Трогать `normalize_route` нельзя: там зафиксированный порядок шести шагов,
на котором стоят обе существующие стороны, а «понимать регулярки» — свойство
одного диалекта, а не общего ключа.

Открытый вопрос: что делать с маршрутом, у которого регулярка сложнее
подстановки — `(?i)`, альтернатива на уровне сегмента, `.*` в середине.
Рекомендация: такой маршрут получает `route_unresolved`, как ленивая ветка
роутов на фронте. Пропустить его нельзя — он занизит знаменатель покрытия.

## 4. Как Python ложится на существующие модели

### 4.1 Модуль

`Module.lang` объявлен как `Literal["cs", "ts"]` и обязателен. Добавление
`"py"` — правка одной строки, но она задевает **шесть мест**, где сегодня
язык проверяется двузначно, то есть «не ts» означает «.NET»:

| Место | Что делает сейчас | Чем грозит третий язык |
|---|---|---|
| `materialize/build.py:122` | `web_modules = … if module.lang == "ts"` | питон-узлы не получат своих разделов — приемлемо, но должно быть решением, а не следствием |
| `materialize/build.py:448` `_web_sections` | печатает «Маршрут страницы» и «Вызовы к бэкенду» | у питона будут «Эндпоинты» (уже есть) и, возможно, «Кто зовёт» |
| `materialize/plan.py:614` `is_web` | `any(module.lang == "ts")` | выбирает ветку дерева документов; питон получит ветку бэкенда молча |
| `materialize/plan.py:621` `expected_root` | префикс `doc_path` | то же самое: третья ветка или общая с .NET — решение §7.4 |
| `cli.py:429–470` `symbols --lang` | принимает только `cs`/`ts` | нужен `py` и выбор секции правил |
| `web/tree.parser_versions` | `grammar_typescript` | нужно поле `grammar_python`, иначе кэш не сбросится при апгрейде грамматики |

Ни одно из них не упадёт при появлении `lang: py`. Все шесть **промолчат** —
поэтому они перечислены здесь, а не оставлены на «найдётся при реализации».

**Чем объявлен модуль на Python.** У .NET это `.csproj` (один к одному),
у Angular — каталог-граница из `angular.json`/`project.json`. У Python
однозначного файла нет вовсе: сервис объявляют `pyproject.toml`, `setup.py`,
`setup.cfg`, `requirements.txt`, `Dockerfile`, `docker-compose.yml` — или
не объявляют ничем, и сервис есть просто каталог с `main.py`. Порядок правил
придётся строить как у фронта (первое сработавшее выигрывает **по месту**,
а не глобально), и последним правилом обязан быть каталог верхнего уровня.
Что реально лежит в АС CF — вопрос №1 разведки.

**Общего родителя у сервисов нет.** Уточнение владельца: часть модулей имеет
модульную структуру и лежит отдельно — `inner_debts` находится **на одном уровне
с `grid`**, а не под ним. Значит правило вида «модуль ⇔ каталог первого уровня
под `grid/`» даст ровно то, чего боимся: часть сервисов найдётся, часть нет,
а в отчёте это будет выглядеть как «в них ничего нет».

Отсюда два требования к правилу границы:

- **граница ищется снизу вверх от файла**, а не сверху вниз от корня — как
  `_nearest_upwards` у фронта и `map_files_to_modules` у .NET. Оба существующих
  парсера уже так и делают, и это ровно тот случай, ради которого;
- **каждый `.py` обязан получить модуль или явно остаться ничьим.** Файл вне
  всех границ на .NET просто не попадает в манифест (документировать код вне
  проектов некуда), и это законно там, где проекты объявлены файлами. Здесь
  границы угадываются, поэтому «ничьих» файлов должно быть посчитанное число
  в сидкаре, а не тишина.

Второй разрез той же проблемы: **зарегистрированный модуль может лежать где
угодно**. `tornado_service.py` называет модули по имени, а где они физически —
отдельный вопрос. Проверка «каждое имя из реестра нашлось в дереве» и обратная
«каждый найденный модуль зарегистрирован» — это две готовые строки отчёта линта,
и обе стоят копейки, если реестр разобран (§2.4).

**Граница модуля важнее, чем кажется**, и по причине, которой нет у двух других
языков: у каждого питон-сервиса **свой `sys.path`**. Модуль `utils.py` в двух
сервисах — два разных модуля с одинаковым импортируемым именем `utils`.
Ключ символа (`модуль # FQN ` арность`) это разводит, а вот резолв импорта —
только если знает корень импорта своего сервиса. Отсюда: граница модуля
и корень `sys.path` — одно и то же значение, и брать его надо оттуда, откуда
сервис запускается (`Dockerfile`, `CMD`, `docker-compose`), а не угадывать.

### 4.2 Символ

FQN на Python строится честнее, чем на TypeScript: там namespace — это каталог
(в TS пространств имён нет), здесь есть настоящий импортируемый путь модуля.

```
services/ml/scoring/handlers.py  →  namespace = "scoring.handlers"   (от корня sys.path модуля)
class PredictHandler             →  fqn = "scoring.handlers.PredictHandler"
```

Ключ — та же тройка `symbol_key(модуль, FQN, арность)`. Арность у Python
почти всегда 0 (PEP 695 `class Box[T]` встречается редко), но поле есть и врать
не будет.

Аналога `partial class` нет, а вот **переобъявление есть**: класс, объявленный
в обеих ветках `try/except ImportError`, или функция, переопределённая ниже
по файлу. Правило то же, что для `#if` на .NET: препроцессор не выполняется,
документируются оба варианта, дедупликации нет.

**Модуль как единица документации — открытый вопрос.** Модель `DocNode`
типоцентрична: узел — это класс (или функция/константа, добавленные ради TS).
Если питон-сервисы написаны классами (tornado к этому располагает: обработчик —
класс), модель ложится без натяжки. Если существенная часть кода — модульные
функции без классов, то единицей документации естественно становится **файл**,
а такого вида узла в модели нет. Это вопрос №11 разведки, и от ответа зависит,
нужна ли задача «узел-модуль». Рекомендация: не закладывать его заранее, но
померить долю до планирования.

### 4.3 Член

| Форма Python | Куда ложится | Замечание |
|---|---|---|
| `def m(self)` / `async def m(self)` | `Member(kind="method")` | `async` — модификатор |
| `@property def x` | `kind="property"` | как аксессор в TS: снаружи это поле |
| `NAME = "x"` в теле класса | `kind="field"` | `assignment` внутри `block` |
| `limit: int = 5` | `kind="field"` | у `assignment` есть поле `type` |
| `self.client = HttpClient(url)` в `__init__` | `kind="field"` | нужен для графа вызовов — см. §4.6 |
| `__init__` | `kind="constructor"` | по имени, как в TS |
| декоратор члена | `Member.attributes` | но лежит он **не там**, где ждёт код TS — §5.1 |

Сигнатура режется по полю `body`: у `function_definition` есть именованные поля
`name`, `parameters`, `return_type`, `body` — то есть проще, чем у C#, где
терминаторы приходится перечислять множеством.

### 4.4 Резолв

Резолв Python ближе к TypeScript (по файлам), чем к .NET (по namespace),
но отличается от обоих:

| Задача | TypeScript | Python |
|---|---|---|
| корень разрешения | `baseUrl` + `paths` из `tsconfig` (JSONC!) | `sys.path`: корень сервиса, плюс `src/`-раскладка, плюс `sys.path.append` в коде |
| относительный импорт | `./x`, `../x` — обычный путь | `from ..pkg import X` — уровень задан **числом точек** в `import_prefix` |
| «бочка» | `index.ts` с `export *` | `__init__.py` с `from .impl import X` — то же самое, и встречается чаще |
| звёздочный импорт | `import * as ns` (пространство) | `from mod import *` (имена вываливаются в текущий модуль) — резолву помочь не может, но и молчать о нём нельзя |
| алиас | `import { A as B }` | `import a.b as ab`, `from x import Y as Z` — обе формы дают `aliased_import` |
| внешние пакеты | `node_modules` вырезан обходом | `site-packages`/`.venv` вырезаны обходом; `tornado`, `numpy` остаются сырыми именами — и правила классификации матчатся именно по ним |

Отдельная ловушка, которой нет у двух других языков: **`sys.path.append(...)`
в коде**. Сервис, который дописывает путь руками перед импортом, резолвится
по таблице, которой в конфигурации нет. Разведка обязана посчитать такие
места (вопрос №12); если их единицы — это ключ конфигурации вида
`py.extra_roots`, если десятки — отдельное решение.

### 4.5 Видимость: мина, на которой уже подрывались

В секции `dotnet:` файла правил стои́т `require_public: true`. В CLAUDE.md
записано, чем это кончилось для TypeScript: модификатора `public` у TS нет
вовсе, и значение, перенесённое из чужой секции, даёт **пустое дерево без
единого сообщения об ошибке**.

У Python ситуация ровно та же, и даже хуже: `public` там нет, а есть две
конвенции — ведущее подчёркивание (`_helper`) и список `__all__`. Ни одна
из них не является модификатором и через `symbol.modifiers` не выражается.

Отсюда два следствия для плана:

1. секция `python:` в файле правил обязательна, и `require_public` в ней —
   `false` (или отсутствует);
2. отсев «внутренней кухни» пишется правилом отсева с `name_regex: ["_.*"]`
   и причиной, а не переключателем. Это ровно тот случай, ради которого
   `reason` сделан обязательным.

Вопрос к разведке (№11): используется ли `__all__` и насколько дисциплинированно
ведущее подчёркивание. Если `__all__` есть и покрывает модули, стоит завести
одиннадцатый предикат — но только если данные это оправдают.

### 4.6 Зависимости и граф вызовов

На фронте зависимость узла — параметр конструктора с типом
(`constructor(private http: HttpClient)`), и типы там есть всегда: TypeScript
без них не компилируется. На Python аннотации **необязательны**, и от их
покрытия зависит, будет ли граф зависимостей вообще.

Три источника, по убыванию надёжности:

1. `def __init__(self, service: FooService)` — аннотированный параметр,
   тот же разбор, что на фронте (`typed_parameter` → поле `type`);
2. `self.client = HttpClient(url)` в `__init__` — тип берётся из вызываемого,
   это `assignment` с `attribute`-целью и `call`-значением;
3. модульный синглтон (`client = HttpClient()` на уровне файла, импортируемый
   другими) — уверенность `low`.

Замер покрытия аннотаций — вопрос №10 разведки. Ниже примерно половины
источник (1) один не вытянет, и задача «граф вызовов» должна опираться
на (2), а `Dependency.confidence` честно показывать разницу.

Правило, вынесенное со страниц фронта, действует и здесь: **«внедрил сервис»
и «зову метод» — разные утверждения**, и считать состав надо по рёбрам
`Usage`, а не по списку зависимостей.

## 5. Ловушки, проверенные на грамматике

Все семь проверены прогоном на `tree-sitter-python` 0.25.0. Каждая даёт
неверный результат **молча** — при нулевом числе ошибок разбора.

### 5.1 Декоратор — РОДИТЕЛЬ объявления. Третья форма из трёх возможных

```
C#:          declaration > attribute_list        — атрибут ПОТОМОК
TypeScript:  export_statement > decorator, class — декоратор СОСЕД
Python:      decorated_definition > decorator, class_definition
                                    ^^^^^^^^^^^ декоратор в РОДИТЕЛЕ
```

Проверено:

```python
@web.stream_request_body
class ModelHandler(tornado.web.RequestHandler): ...
```
```
decorated_definition
  decorator            @web.stream_request_body
  class_definition     class ModelHandler(...)
```

То есть `class_definition.parent.type == "decorated_definition"`, а сами
декораторы — **предшествующие соседи внутри этого родителя**.

Хуже всего то, что реализация, перенесённая с TypeScript буквально, здесь
почти сработает: `_anchor()` фронта поднимается к родителю `export_statement`
и собирает его детей — та же форма. Но для **члена класса** фронт обходит
`prev_sibling`, а в Python декорированный метод обёрнут в собственный
`decorated_definition` внутри `block`, и обход соседей не найдёт ничего.
Результат: у классов декораторы есть, у методов нет — и это выглядит
как особенность кода, а не как дефект разбора.

Цена ошибки максимальная: во Flask, FastAPI и aiohttp маршрут объявлен
**декоратором метода** (`@app.route("/x")`), и без него эндпоинтов не будет
вовсе.

### 5.2 Docstring — первый оператор ВНУТРИ тела, а не сосед снаружи

```
C#:          /// <summary>   — предшествующий СОСЕД объявления
TypeScript:  /** … */        — предшествующий СОСЕД export_statement
Python:      """…"""         — ПЕРВЫЙ ОПЕРАТОР ВНУТРИ body
```

Проверено: `class_definition > block > expression_statement > string >
string_content`.

Обход предыдущих соседей, скопированный с любого из двух языков, вернёт `None`
для **всех** символов при нулевом числе ошибок разбора. `Symbol.xml_doc`
окажется пустым везде, и объяснить это будет нечем — выглядит как «в коде
нет комментариев».

Второе следствие: комментарий `#` перед `def` — **не** документация,
и подхватывать его нельзя, иначе в поле описания поедут `# TODO` и
`# -*- coding: utf-8 -*-`.

### 5.3 Базовые типы лежат в `argument_list`, и там же `metaclass=`

```python
class A(Base, metaclass=M): ...
```
```
class_definition
  field superclasses: argument_list  (Base, metaclass=M)
```

Поле называется `superclasses`, но узел — обычный `argument_list`, и в нём
вперемешку базовые типы и именованные аргументы. Реализация, берущая все
именованные дочерние узлы, положит в `base_types` строку `metaclass=M`.

Это дословный повтор ловушки C#, где в базовый список попадает `argument_list`
primary constructor'а (`class MyTests(ITestOutputHelper output) : BaseTest(output)`).
Фильтр нужен тот же по духу: отбрасывать `keyword_argument`.

Мусор отсюда расползается дальше — в замыкание наследования и в
`signature_hash`, — то есть создаёт работу агенту шага 3 на ровном месте.

### 5.4 Поля `type_parameters` у Python нет

У C# параметры-дженерики лежат в `type_parameter_list`, у TypeScript берутся
через `child_by_field_name("type_parameters")`. У Python (PEP 695,
`class Box[T]`) узел называется `type_parameter`, и **поля с таким именем
нет**: проверено, `child_by_field_name("type_parameters")` вернул `None`
при существующем в дереве `type_parameter`.

Арность при этом уедет в ключ символа нулём. На сегодняшнем коде это ничего
не сломает — PEP 695 требует Python 3.12+, а репозиторий пока на 3.9, — но
**срок известен**: владелец говорит про переезд на 3.14. То есть это не
«обнаружится когда-нибудь», а «сработает после апгрейда», и выглядеть будет
как «два класса склеились в один узел».

### 5.5 Диапазон версий 3.9 → 3.14: где грамматика ломается

Python 2 в репозитории нет (подтверждено владельцем), поэтому вопрос стоит
иначе: язык сейчас в основном 3.9, и его скоро поднимут до 3.14. Грамматика
обязана переварить обе границы диапазона, потому что переезд будет постепенным
и какое-то время в дереве будет лежать и то, и другое.

Прогон по версиям на `tree-sitter-python` 0.25.0:

| Конструкция | Версия | Ошибок |
|---|---|---|
| walrus, positional-only `/`, `dict \| dict` | 3.8–3.9 | 0 |
| `match`/`case`, и `match` **как имя переменной** | 3.10 | 0 |
| `int \| None` в аннотации, `except*` | 3.10–3.11 | 0 |
| `type Point = …`, `class Box[T]`, `def first[T]` | 3.12 | 0 |
| вложенные f-строки, кавычки внутри `f"{d["k"]}"` | 3.12 | 0 |
| `t"…"` (t-строки, PEP 750) | 3.14 | 0 — разбирается как обычная строка |
| **`def f[T = int]` (умолчания TypeVar, PEP 696)** | **3.13** | **1 ошибка** |

Две находки из этой таблицы стоят того, чтобы попасть в план.

**Первая: PEP 696 грамматика 0.25.0 не знает.** Ошибка локальная — объявление
выживает, имя функции читается, — но счётчик `parse_errors` при переезде
на 3.13+ начнёт расти без всякой поломки кода. Проверять поддержку надо
при апгрейде языка, и это ровно то, ради чего версия грамматики лежит
в манифесте: `ParserVersions` входит в ключ кэша, поэтому апгрейд грамматики
кэш сбрасывает, а дифф манифеста показывает, что именно изменилось от версии,
а не от кода.

**Вторая тоньше и касается разведки.** `except ValueError, TypeError:` —
это Python 3.14 (PEP 758), и разбирается он в **тот же узел**, что
питон-2-шный `except ValueError, e:`; обе формы дают 0 ошибок. То есть
grep-маркер «питон-2», которым разведка сейчас проверяет отсутствие второй
версии языка, после переезда на 3.14 начнёт давать ложные срабатывания —
и выглядеть это будет как внезапно найденный Python 2. Маркер оставлен
в скрипте (это дешёвая страховка), но помечен: смотреть на него можно только
вместе с датой и версией языка.

Остаётся и общий факт, который никуда не делся: **грамматика Python
снисходительна**, и правило, вынесенное с .NET — «`parse_errors > 0` при пустом
списке объявлений выдаёт файл, уничтоженный препроцессором», — здесь ловит
сильно меньше. Это не повод его не заводить, но и полагаться на него как
на единственный сигнал нельзя.

### 5.6 Члены под `if`/`try` — не прямые дети тела

```python
class Cond:
    if sys.version_info >= (3, 12):
        def new(self): ...
    try:
        from x import y
    except ImportError:
        y = None
```

`function_definition` лежит внутри `if_statement > block`, то есть на два
уровня глубже. Это дословный аналог ловушки `#if` из ABP: реализация,
перебирающая прямых детей тела, потеряет такие члены молча.

Лечится тем же приёмом, что уже применён в обоих парсерах: запрос находит
члены по всему дереву, а владелец ищется **обходом вверх** до ближайшего
`class_definition`. Проверено — работает.

Условный импорт в `try/except ImportError` — та же конструкция и очень частая
идиома. Резолв обязан видеть оба варианта.

### 5.7 `self.a, self.b = 1, 2` — это `pattern_list`

Одно присваивание объявляет два поля. У C# ровно та же ловушка с
`private int _a = 1, _b = 2;` (там `variable_declarator`), и решена она
возвратом **списка** имён из одного узла. На Python форма другая
(`assignment > pattern_list > attribute`), а лечение то же.

Пропущенное поле исчезает из документации молча.

### 5.8 Таблица маршрутов собирается конкатенацией списков

```python
Application([ (r"/a", A), … ] + EXTRA_ROUTES, **settings)
```

Дерево: `argument_list > binary_operator > (list, identifier)`. То есть часть
маршрутов приходит из **другого файла**, и разбор одного `app.py` даст
неполную таблицу — при том, что выглядеть она будет полной.

Это дословный повтор находки Angular: «дерево роутов собирается спредом
импортированного массива, а не `loadChildren`; разбор одного `app.routes.ts`
даёт два пути из двадцати шести, и молча». Механизм сборки таблицы
из `web/routes.py` переносится сюда почти целиком — и это единственное место,
где переиспользование фронтового кода даёт больше, чем стоит.

Формы, которые обязаны разбираться все четыре (иначе счётчик врёт):
кортеж из двух элементов, кортеж из трёх (третий — словарь настроек),
`tornado.web.url(...)` с `name=`, и `application.add_handlers(host, [...])`.

| | Модуль | Действие |
|---|---|---|
| **Переиспользуется как есть** | `discovery.py` | добавить `py_files` и имена файлов-объявлений сервиса |
| | `classify.py`, `ruleset.py` | новая секция `python:` в том же файле правил |
| | `symbols.py`, `hashing.py`, `cache.py`, `diff.py` | ничего |
| | `tree.doc_path_for` | ничего |
| | `materialize/**`, `business/**` | ничего, кроме §4.1 |
| **Обобщается** | `route.py` | ничего внутри; питон приводит регулярку к шаблону ДО вызова (§3) |
| | `web/link.py` → `link.py` | вынести из `web/`, обобщить имена; направление — уже данные |

| **Пишется заново** | `py/parser.py` | разбор `.py` → `FileParseResult` (§5) |

| | **`py/registry.py`** | **разбор `tornado_service.py`: какие модули зарегистрированы под какими именами (§2.4)** |

| | **`dotnet/calls.py`** | **исходящие HTTP-вызовы .NET — но только если ответ на вопрос №4 разведки «напрямую по HTTP»; см. §2.5** |

Оценка объёма, по аналогии с шагом `web` (≈3 900 строк на 19 задач):
питон-сторона легче фронта на роуты (проще) и тяжелее на резолв (сложнее),
плюс отдельно `dotnet/calls.py`. Точные числа — после разведки.

## 7. Решения, которые стоит зафиксировать до плана

### 7.1 Отдельный манифест, а не общий

`doc-tree.py.json`, ключ `py.out`, команда `docpipe py scan` — по образцу
шага `web`. Довод тот же, что был у фронта: общий манифест заставил бы
`scan` разбирать оба языка на каждом прогоне и удвоил бы время там, где
изменился один файл. Схема при этом общая, и `materialize` разницы не видит.

### 7.2 `web_calls` → общее имя, со сменой версии схемы

Рекомендация: **переименовать в `http_calls` и поднять `SCHEMA_VERSION`
до `3.0`**, а не заводить второе поле.

Довод от обратного: два поля с одним смыслом — это ровно та ошибка, которую
проект уже разбирал дважды (`_prepare` в шаге 2 существовал в трёх копиях;
зеркало `business_hash` во front matter выкинуто как «второй источник обязан
отстать»). Отчёт связи читал бы то одно, то другое, и разошлись бы они на
первом же прогоне.

Цена переименования мала: манифест — генерируемый артефакт, принятые хэши
живут в документах и от имени поля не зависят. Правок — пять мест.

### 7.3 Исходящие вызовы .NET — отдельная задача, и, возможно, отдельная ветка

Она не блокируется разбором Python и полезна сама по себе. Разумный порядок:
сначала `dotnet/calls.py` (проверяется на существующем манифесте .NET,
даёт отчёт «кто куда ходит» уже сегодня), потом питон-сторона, потом связь.

### 7.4 Ветка дерева документов

У фронта своя ветка (`web.modules_dir`, задача P13) — потому что единица
документации там страница, а не класс. У Python единица та же, что у .NET
(класс/функция), поэтому третья ветка не нужна **если** сервисы документируются
как обычные модули. Рекомендация: `py.modules_dir` завести пустым (значит
«та же ветка, что у бэкенда»), как это сделано у фронта — тогда решение
откладывается, ничего не ломая.

### 7.5 Умолчания обхода

В `emit.DEFAULT_EXCLUDE` сегодня восемь шаблонов, четыре из них — про фронт.
Питону нужны свои, и они не менее обязательны, чем `node_modules`:

```
**/.venv/**  **/venv/**  **/site-packages/**  **/__pycache__/**
**/*.egg-info/**  **/.tox/**  **/.mypy_cache/**  **/.pytest_cache/**
```

Отдельно — `*_pb2.py` / `*_pb2_grpc.py` (генерат protobuf) и `migrations/`:
это уже не обход, а отсев правилом с причиной, потому что решение
«не документируем» обязано быть названным.

Ловушка, которую стоит записать в план сразу: `.venv` внутри репозитория
содержит **тысячи** `.py`-файлов, и без исключения прогон не столько
замедлится, сколько наполнит дерево чужими символами, выглядящими своими.

## 8. Разведка боевого репозитория: что нужно выяснить

Ниже — то, ради чего написан `tools/recon-python.sh`. Скрипт **только
читает**: `git grep`, `git ls-files`, `sed`, `awk`; в сеть не ходит,
рабочее дерево не трогает.

```bash
# из корня репозитория АС CF
bash tools/recon-python.sh > recon-python.txt 2>&1

# с сужением: область питона и область .cs, которая его зовёт
bash tools/recon-python.sh sbt.cms.cashflow.subrepo/ml-services \
                          sbt.cms.cashflow.subrepo/Sbt.CMS.Cashflow.NetCore \
                          > recon-python.txt 2>&1
```

Сужение важно по причине, которая уже стоила одного захода на фронте: срезы
«примеры» ограничены по объёму и показывают первые файлы **по алфавиту**.
Если сервисов много, интересующий вас может не попасть ни в один срез —
и в выводе это неотличимо от «такого в нём нет».

Вопросы, на которые отчёт обязан ответить, в порядке важности:

| № | Вопрос | Почему блокирует | Раздел скрипта |
|---|---|---|---|
| 1 | **Что в `tornado_service.py`**: какой формой регистрируются модули и сколько их | форма регистрации — это и есть объём задачи разбора реестра; имя модуля — кандидат в главный якорь (§2.4) | §2 |
| 2 | **Раскладка модулей**: где `grid`, где соседи вроде `inner_debts`, у кого `__init__.py` | общего родителя нет, правило границы ищется снизу вверх (§4.1) | §1 |
| 3 | Чем объявлен сервис: `pyproject.toml`, `setup.py`, `requirements.txt`, `Dockerfile` — или ничем | без этого нет понятия «модуль», а значит нет ни ключа символа, ни `doc_path` | §1 |
| 4 | **Как .NET доходит до питона**: напрямую по HTTP или через grid-сервис | от ответа зависит, какой ключ у связи и нужен ли `dotnet/calls.py` вообще (§2.5) | §8, §9 |
| 5 | Как объявлены маршруты tornado: литералы в одном `Application([…])` или собираются из кусков | определяет, хватит ли разбора одного файла (§5.8) | §5 |
| 6 | Сколько маршрутов содержат регулярные группы | верхняя оценка того, сколько ключей нужно переводить в шаблон (§3) | §5 |
| 7 | Точки входа НЕ по HTTP: celery, kafka, cron, CLI, gRPC | если их много, «эндпоинт» — не единственная точка контракта, и якорей нужно больше | §7 |
| 8 | Какой веб-фреймворк и сколько его: tornado, flask, fastapi, aiohttp | маршрут объявляется по-разному в каждом; ставка на tornado должна подтвердиться числами | §6 |
| 9 | Сколько на стороне .NET вызовов с литеральным путём | верхняя оценка покрытия связи, ровно как «литералы ко всем вызовам» на фронте | §8 |
| 10 | Покрытие аннотациями типов | от него зависит, будет ли граф зависимостей (§4.6) | §10 |
| 11 | Классы против модульных функций; `__all__`; ведущее подчёркивание | типоцентричность модели (§4.2) и настройка отсева (§4.5) | §11 |
| 12 | `sys.path.append` в коде | резолв по таблице, которой нет в конфигурации (§4.4) | §12 |
| 13 | Разброс версий языка в дереве: 3.9 сегодня, 3.14 завтра | PEP 696 грамматика 0.25.0 не знает; апгрейд языка = плановый апгрейд грамматики (§5.5) | §3 |
| 14 | Кодировки, docstring, генерат, `.venv` в дереве | умолчания обхода и законность пустого `xml_doc` (§7.5) | §4, §13, §14 |

Блокирующие — №1, №2 и №4. Пока на них нет ответа, план писать рано: от каждого
зависит состав задач, а не их формулировки. Вопрос про Python 2 из этого списка

## 9. Открытые вопросы к владельцу

1. **Питон-сервисы лежат в том же репозитории, что .NET?** Вся конструкция
   связи предполагает одно дерево (как фронт и бэк сегодня). Если сервисы
   в отдельном репозитории, отчёт связи собирается из двух манифестов,
   собранных в разных прогонах, — это работает, но требует решения, где
   лежит второй манифест и кто его обновляет.
2. **Документируется ли питон целиком или выборочно?** У фронта первой
   документируется одна команда (`Sbt.CMS.Cashflow.ML`), а модель обязана
   пережить остальные шесть. Здесь тот же вопрос, и от него зависит,
   насколько агрессивно настраивается `enrolled`.
3. **Нужен ли отчёт «кто зовёт этот сервис» как отдельная команда** (аналог
   `docpipe web pages`), или достаточно раздела в документе узла?
4. **Что считается точкой контракта питон-сервиса** для бизнес-якоря:
   HTTP-маршрут, имя очереди, имя задачи celery? На .NET якоря — это
   `JOBTITLE`, `Id@Version` workflow, HTTP-маршрут; здесь список надо
   пополнить, и сделать это может только владелец.
5. **Что считать «модулем» в терминах `tornado_service.py`?** Регистрируется
   ли там ровно то, что мы хотим называть модулем документации, или регистрация
   мельче (по обработчику) либо крупнее (по группе)? От этого зависит, совпадает
   ли имя из реестра с `Module.name`, — а если не совпадает, нужна таблица
   соответствия, и её кто-то должен вести.
6. **Есть ли у питон-сервисов свой договор о версиях API** (`/api/v1/…`)?
   Если да, версия — часть маршрута и в ключ входит; расхождение версий
   между .NET и питоном станет находкой линта, а не дефектом инструмента.

## 10. Предлагаемая разбивка на задачи

Черновик, который уточнится после разведки. Префикс `PY`, потому что
`T`, `M`, `B`, `F` и `P` заняты.

| Задача | О чём | Зависит от |
|---|---|---|
| PY01 | обход `.py`, файлы-объявления сервиса, умолчания исключений, фикстура `PyServices` | — |
| PY02 | `py/parser.py`: объявления, члены, декораторы, docstring — все семь ловушек §5 | PY01 |
| PY03 | `py/modules.py`: чем объявлен сервис, граница снизу вверх, корень `sys.path`, счётчик ничьих файлов | PY01, разведка №2,3 |
| PY04 | **`py/registry.py`: разбор `tornado_service.py`, имена зарегистрированных модулей** | PY02, разведка №1 |
| PY05 | `py/resolve.py`: импорты, относительные уровни, `__init__.py`, замыкание | PY02, PY03 |
| PY06 | `py/routes.py`: таблица tornado, четыре формы записи, `regex_to_template` | PY02, разведка №5,6 |
| PY07 | `py/endpoints.py`: обработчик + маршрут → `Endpoint` | PY06 |
| PY08 | модели: `lang: py`, `grammar_python`, шесть мест из §4.1 | — |
| PY09 | `docpipe py scan` и секция `python:` файла правил | PY02–PY08 |
| PY10 | сверка реестра и дерева: зарегистрированные модули без кода и код без регистрации | PY04, PY09 |
| PY11 | **мост .NET↔питон** — форма зависит от ответа на вопрос №4: `dotnet/calls.py` либо цепочка через grid-сервис | разведка №4 |
| PY12 | `link.py`: вынести из `web/`, обобщить, `docpipe py link` | PY09, PY11 |
| PY13 | граф вызовов внутри питона (`Usage`), зависимости | PY05, разведка №10 |
| PY14 | шаг 2 для питона: шаблоны, разделы документа | PY09 |
| PY15 | бизнес-слой: якорь на питон-модуль и/или эндпоинт | PY12, вопрос владельцу №4 |
| PY16 | детерминизм и боевой объём | всё выше |
| PY17 | документация: `docs/python.md`, правка `CLAUDE.md`, `CASHFLOW.md` | всё выше |

Порядок выбран так, чтобы **не зависеть от неизвестного ответа**. PY01–PY10
дают полезный результат при любом сценарии вызова: дерево питон-сервисов,
разобранный реестр и сверка «зарегистрировано против найдено» — это уже
работающая документация, даже если мост окажется совсем не HTTP-овским.
PY11 ставится последней из содержательных именно поэтому.

Задача PY04 (реестр) вынесена вперёд относительно первоначального черновика
и стои́т раньше маршрутов: если модули зовутся через grid, маршруты могут
оказаться второстепенными, а реестр — главным, и обратный порядок означал бы
неделю работы над тем, что окажется не нужно.

## 11. Что намеренно не входит

- **Выполнение кода.** Ни импорта модулей, ни `inspect`, ни запуска
  приложения. Разбор остаётся синтаксическим — по той же причине, по которой
  на .NET не поднимается Roslyn: инструмент обязан работать на репозитории,
  который не собирается.
- **Вывод типов.** Аннотация есть — берём; нет — уверенность `low`.
  Ни `mypy`, ни собственного инференса.
- **Динамическая регистрация обработчиков** (`importlib`, имя класса строкой).
  Синтаксически не видна; если такое в репозитории есть, это ручной состав
  по образцу `pages.yaml`, а не разбор.
- **Jupyter-ноутбуки.** Отдельный формат и отдельный разговор.

# `ownership.yaml`: кто владеет кодом

Справочник по правилам владения: что в файле, как он считается и на что влияет.
Заготовка для копирования — [`ownership.example.yaml`](../ownership.example.yaml).

## Зачем файл нужен

Владение отвечает на один вопрос: **какой команде принадлежит узел документации**.
Из ответа следуют четыре вещи:

| Кто пользуется | Что даёт |
|---|---|
| `docpipe docs status --team T` | отбор документов своей команды |
| раздел «Участники» бизнес-документа | граница ответственности внутри чужого процесса **вычисляется**, а не ведётся руками |
| проверка линта `team-mismatch` | расхождение `@team` реестра с правилами владения |
| селектор `only: {team: …}` в якоре | сужение общей точки входа до своей части |

Файл **необязателен**. Без него всё работает, но у всех документов `team: null`,
`--team` не отбирает ничего, а «Участники» печатают `(не задан)`.

## Где считается и почему не в манифесте

Владение считается на **шаге 2**, а не попадает в `doc-tree.json`. Состав команд
меняется чаще кода; попав в манифест, владение сделало бы его зависящим от
орг-структуры и сломало бы свойство «манифест — чистая функция кода и правил
классификации».

**Владелец определяется по узлу, а не по модулю.** Соблазн «команда = проект»
разбивается о шэренный `.csproj` — ровно ту ситуацию, ради которой владение
и заводится.

## Устройство файла

```yaml
version: "1"
ownership_version: "2026-08-04.1"

teams:
  - id: ml
    title: Машинное обучение
  - id: reports
    title: Отчётность

rules:
  - id: ml.modules
    team: ml
    priority: 10
    when:
      module_glob: ["**/Sbt.Cashflow.ML.*/**"]
```

`teams` — плоский список; правило со ссылкой на необъявленную команду
**отвергается при загрузке**, а не молча не срабатывает.

## Восемь предикатов

Намеренно мало — та же причина, что в правилах классификации: большой набор
означает, что настройщик каждый раз выбирает из десяти способов написать одно
и то же.

| Предикат | По чему | Когда |
|---|---|---|
| `path_glob` | пути источников типа, **любой** из них | главный инструмент: режет шэренный проект по каталогам |
| `module` | имя модуля, точное совпадение | короткая запись |
| `module_glob` | путь `.csproj` | имена проектов не уникальны — сравнивать по пути |
| `domain` | домен из `docpipe.yaml` | когда домены уже размечены |
| `kind` | вид сущности (`controller`, `service`, …) | редко и только в паре с другими |
| `namespace_prefix` | начало namespace | зона внутри чужого проекта |
| `namespace_regex` | namespace целиком, `re.fullmatch` | когда префикса не хватает |
| `fqn_prefix` | начало FQN | точечно, один тип |

Условия комбинируются `all:` и `any:`:

```yaml
    when:
      all:
        - path_glob: ["src/Cf.Shared/**"]
        - namespace_prefix: ["Cf.Shared.Pricing.Serialization"]
```

**Отрицаний нет намеренно.** Правила только положительные: более специфичное
выражается более высоким приоритетом, а не исключением из общего. Отрицания
превращают набор в систему уравнений, которую нельзя прочитать построчно.

**`path_glob` истинен, если совпал хотя бы один источник.** У `partial`-класса
файлы бывают в каталогах разных команд. Правило «все источники» оставило бы
такой тип ничьим, и это выглядело бы дефектом инструмента; такие типы уходят
в предупреждения `docs owners --lint`.

## Приоритеты: слои, а не порядок в файле

Побеждает правило с **наибольшим** `priority`; при равенстве — лексикографически
меньший `id`. Порядок строк в YAML решением не является: иначе перестановка
двух правил меняла бы вывод.

Рабочая раскладка — слоями с промежутками, чтобы вставка нового уровня
не требовала перенумерации:

| `priority` | Слой | Предикат |
|---|---|---|
| 10 | проект целиком | `module_glob` |
| 50 | каталог внутри шэренного проекта | `path_glob` |
| 80 | namespace внутри чужого каталога | `namespace_prefix` |
| 100 | точечно, один тип | `fqn_prefix` |

**Слой 100 держите коротким.** `fqn_prefix` — единственный предикат, который
ломается от переименования типа. Длинный список точечных правил означает, что
границы команд не выражены структурой кода, и сопровождать его придётся руками.

## Как размечать: снизу вверх, а не сверху вниз

Порядок, который работает:

1. **Начните с проектов.** Если сборка принадлежит команде целиком — одно
   правило на неё, `priority: 10`. Обычно это закрывает большую часть.
2. **Посмотрите, что осталось ничьим.** `docs owners --lint` печатает срезы
   по модулям и по каталогам внутри модуля — это и есть список того, что
   дописывать.
3. **Режьте шэренные проекты каталогами** (`path_glob`, `priority: 50`).
4. **Точечные правила — в последнюю очередь** и только там, где тип реально
   живёт не у своей команды.

Пример для команды, которой принадлежит сборка обработчиков событий целиком:

```yaml
  - id: ml.event-receivers
    team: ml
    priority: 10
    when:
      module_glob: ["**/Sbt.Cashflow.ML.EventReceivers/**"]
```

Одно правило покрывает **все** обработчики команды — включая те, которых ещё
нет. Это принципиальная разница с перечислением FQN: список ломается на первом
переименовании и требует правки при каждом новом классе.

## Диагностика

```bash
docpipe docs owners artifacts/doc-tree.json --ownership ownership.yaml
docpipe docs owners artifacts/doc-tree.json --ownership ownership.yaml --lint
docpipe docs owners artifacts/doc-tree.json --ownership ownership.yaml \
    --explain docs/modules/services/Sample.Pricing.Api/pricing-service.md
```

`--lint` отвечает на три вопроса:

| Находка | Что означает |
|---|---|
| «Правила, не совпавшие ни с одним узлом» | **самый частый дефект сопровождения**: каталог переименовали, правило осталось |
| «Узлов без владельца: N из M» плюс срезы | что дописывать; один счётчик бесполезен, отвечают именно срезы |
| «Команды, которым не досталось ни одного узла» | команда объявлена, правил под неё нет |

`--explain` показывает **все** совпавшие правила, а не только победившее: без
этого настройка границ превращается в гадание. Отдельно отмечается `tie` —
максимальный приоритет делят несколько правил. Формально решение
детерминированно, но почти всегда это забытый `priority`.

## Отказы, а не молчание

Проверяется при загрузке, а не при первом применении:

- правило со ссылкой на необъявленную команду;
- опечатка в имени предиката;
- битая регулярка в `namespace_regex`;
- повтор `id` правила.

Причина одна: каждое из этих условий даёт правило, которое **просто никогда
не сработает**, и узлы молча окажутся ничьими. Обнаружилось бы это в лучшем
случае через месяц.

## Связь с бизнес-слоем

Селектор `only: {team: …}` у якоря сужает общую точку входа до записей, чья
реализация принадлежит названной команде — по этим же правилам. Подробно:
[`entry-guide.md`](entry-guide.md).

**Без `ownership.yaml` селектор `only.team` не сужает ничего** и говорит об этом
находкой `selector-empty`, а не пустым результатом: молча пустой набор
неотличим от «наших записей на якоре нет».

**Идентификатор команды регистрозависим.** `only: {team: ml}` при объявленной
`ML` не отберёт ни одной записи. Приводить регистр инструмент не станет: это
завело бы два написания одного имени, и первое же правило, написанное в другом
регистре, начало бы работать «иногда». Несовпадение называется проверкой
`unknown-team` с перечнем объявленных идентификаторов — ровно так же, как
`load_ownership` отвергает правило с неизвестной командой.

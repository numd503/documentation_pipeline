# Фронтенд в пайплайне: аналитика перед планом

Что нужно, чтобы Angular-часть АС CF попала в документацию тем же способом, что и .NET.
Здесь — разбор задачи и принятые решения с обоснованием. Исполнительный план (задачи
с критериями приёмки) пишется по этому документу отдельно.

Проверочные прогоны грамматики, на которые ссылается текст, сделаны на
`tree-sitter-typescript` 0.23.2 с `tree-sitter` 0.26.0 — той же версией, что стоит
в проекте.

---

## 1. Четыре требования и их проверяемые формулировки

Задача поставлена четырьмя пунктами. Каждый переведён в свойство, которое можно
проверить командой, — иначе «связь есть» останется мнением.

| Требование | Проверяемая формулировка |
|---|---|
| Документация по выбранным частям фронтенда создаётся автоматически | `web scan` даёт манифест, `materialize` — скелеты; про каждый экспортируемый символ принято решение, счётчик «решение не принято» доводится до нуля так же, как на .NET |
| Явная связь фронтенда и бэкенда | для каждого HTTP-вызова из кода фронта известен нормализованный ключ `(метод, маршрут)`; для каждого ключа известно, какой узел `.NET` его объявляет и какие узлы фронта его зовут; **число невосстановленных вызовов названо вслух** |
| Бизнес-документацию можно мапить на страницы | у бизнес-документа есть якорь `kind: page` с маршрутом; линт печатает страницы без бизнес-документа тем же отчётом, что и непокрытые точки входа |
| Управление через те же файлы | `docpipe.yaml`, `rules/*.yaml`, `registries.yaml`, `ownership.yaml` — те же ключи и тот же движок правил; новых языков конфигурации не появляется |

Второе требование — главное, и на него уходит бо́льшая часть этого документа: три
остальных решаются переиспользованием того, что уже построено, а связь фронт↔бэк
приходится проектировать заново.

---

## 2. Главное решение: связь — это якорь, а не ссылка

### 2.1 Что известно про цепочку вызова

Со слов владельца системы, общий шаблон такой:

```
Angular Component → NGXS Action → Angular Service (HttpClient) → FixUrlInterceptor → .NET Controller
```

и при этом в реальном коде (`structuring.service.ts`, покрывающий одну из основных
страниц продукта) маршруты записаны литералами прямо в сервисе:

```ts
'api/ml/structure/getforupdate'
`api/ml/structure/innerDebtsSnapshot/${modelVersionId}`
```

Это лучший из возможных раскладов, и вот почему. Литеральный маршрут в коде —
единственная форма, при которой связь **выводится**, а не декларируется вручную.
Сгенерированный из OpenAPI клиент дал бы связь тоже, но через посредника, а слой
с константами (`this.urls.save`) потребовал бы разрешения значений констант, то есть
куска интерпретатора. Здесь ничего этого не нужно.

### 2.2 Почему ключом не может быть идентификатор узла

Соблазн очевиден: у бэкенд-узла есть `id`, положить его в узел фронта — и связь готова.
Это ровно та схема, которая уже была признана неподдерживаемой в бизнес-слое, и по тем же
причинам:

- манифесты лежат в **разных файлах** и строятся разными прогонами; ссылка на `id` из
  другого файла обязана протухнуть, и первым же признаком этого будет висящая ссылка,
  которую никто не чинит;
- `id` бэкенд-узла содержит путь `.csproj` и FQN. Переименование контроллера или переезд
  проекта рвёт связь, хотя HTTP-контракт не менялся — то есть работа создаётся там, где
  смысл не менялся. Это прямо запрещено принципом, на котором стоит бизнес-слой.

**Ключ связи — нормализованная пара `(HTTP-метод, маршрут)`.** Это буквально то, что
обязан знать вызывающий: фронт не знает про класс `StructureController`, он знает строку
`api/ml/structure/getforupdate`. Ровно тот критерий якоря, который сформулирован
в `docs/business-layer.md`: «якорь — то, что обязан знать вызывающий».

Отсюда следствие, которое стоит проговорить: связь **симметрична и косвенна**. Ни один
из двух манифестов не ссылается на другой. Оба независимо объявляют свою сторону
контракта, а сводит их третий артефакт.

```
doc-tree.json      узлы .NET  → endpoints[] (метод, маршрут)  ──┐
                                                                ├──▶ doc-tree.link.json
doc-tree.web.json  узлы Angular → calls[]  (метод, маршрут)  ───┘
```

### 2.3 Нормализация маршрута — здесь всё и ломается

Обе стороны пишут маршрут по-своему. Сводить их обязана одна функция, и она обязана
быть **одна на весь проект**: две копии разойдутся на первом же частном случае, и
разойдутся молча. Тот же довод, по которому `matches_any_type` в `classify.py` сделана
публичной ради `ownership.py`.

Правила нормализации и почему каждое нужно:

| Правило | Почему |
|---|---|
| привести к нижнему регистру | Маршрутизация ASP.NET Core нечувствительна к регистру, и обе стороны этим пользуются. Разведка (§6.9) посчитала: токенов `[controller]` — 0, `[action]` — 0 на 433 `[Route]`, то есть маршруты записаны литералами и совпадают посимвольно. Правило остаётся **страховкой**, а не несущей конструкцией: регистр литералов расходится и без токенов, а цена правила — ноль |
| снять префикс приложения по таблице модуля | Тот же эндпоинт фронты зовут по-разному: ML — `api/…`, `PM.Front` — `/pm/api/…`, `Sbt.CMS.Cashflow.Front` — `/cf/api/…`. Префикс срезает прокси (`pathRewrite`), в маршрут контроллера он не входит. Таблица — в [`findings-cashflow-frontend.md`](findings-cashflow-frontend.md); у ML она пустая, поэтому на нём одном ошибку не увидеть |
| срезать ведущий и завершающий `/`, схлопнуть `//` | `'/api/x'` и `'api/x'` — один маршрут |
| отбросить query string и фрагмент | `?id=5` не участвует в сопоставлении маршрута |
| параметры → `{}` | бэкенд: `{id:guid}`, `{id?}`, `{*rest}`; фронт: `${modelVersionId}`. Обе формы адресуют одну позицию, и различать их нечем |
| ведущая подстановка шаблона — это база, а не сегмент | `` `${environment.apiUrl}/api/ml/structure/save` `` → `api/ml/structure/save`. Подстановка **в начале** строки не может быть значением параметра пути |
| префикс интерцептора — из конфигурации, не из догадки | см. ниже |

**`FixUrlInterceptor` был назван здесь самой опасной неизвестной. Прочитан 09.08.2026,
и ответ хороший: он трогает базу, а не путь.** Интерцептор делегирует конвейеру
`cf-api/url-decorator`, тот сверяет URL со списком `EXCLUDE_URLS` и прогоняет через
список декораторов; единственный зарегистрированный по умолчанию — `SetApiUrl`,
подставляющий базу `CF_API_URL` к относительному URL. Ветка вообще не выполняется,
если `environment.apiUrl` пуст. Значит **литерал в сервисе и есть маршрут контроллера**,
а нормализации остаётся регистр, параметры и префикс приложения. Полный разбор —
в [`findings-cashflow-frontend.md`](findings-cashflow-frontend.md).

Архитектурное решение от этого не меняется, а подтверждается: **преобразование задаётся
в конфигурации, а не выводится из кода интерцептора**. У конвейера конфигурация уже
есть — списки `URL_DECORATORS` и `EXCLUDE_URLS` в DI, и они расширяемы. Выводить это
статически значило бы исполнять `reduce` по списку, который собирается при старте
приложения; результат был бы неверным ровно в тех случаях, ради которых он писался.

```yaml
web:
  # Как маршрут из кода превращается в маршрут, который видит бэкенд.
  # Читается сверху вниз, первое совпадение выигрывает.
  url_rewrite:
    - from: "^api/ml/(.*)$"
      to: "api/ml/\\1"        # интерцептор не трогает — записано явно
```

Пустой `url_rewrite` — законное состояние: значит, интерцептор ничего значимого
не делает. Но записать это должен человек, прочитавший интерцептор, а не инструмент,
не нашедший, что переписать.

### 2.4 Про каждый вызов принимается решение

Это перенос главного принципа классификации (`CLAUDE.md`, «Классификация: решение,
а не покрытие») на новую сущность. У HTTP-вызова три исхода, и два из них — не ошибка:

| Исход | `confidence` | Когда |
|---|---|---|
| маршрут восстановлен точно | `high` | первый аргумент — строковый литерал |
| маршрут восстановлен с параметрами | `medium` | шаблонная строка: литеральные фрагменты плюс подстановки |
| маршрут восстановлен частично | `low` | конкатенация (`'api/ml/structure/' + id`), значение из константы того же файла |
| маршрут не восстановлен | — | URL пришёл переменной, собран в другом месте, вызов через обёртку |

Последняя строка — **именованное число, а не тишина**. Ровно тот же довод, по которому
отсев без `reason` запрещён: «связь построена для 340 вызовов» без второго числа
не значит ничего, потому что неизвестно, 340 из 350 это или из 1200. Отчёт обязан
печатать обе цифры, а невосстановленные вызовы — перечислять с файлом и строкой,
чтобы их можно было либо починить, либо назвать исключением с причиной.

Замер на пробном файле (см. §5): из пяти форм записи URL, встречающихся в реальном
Angular-коде, четыре восстанавливаются структурно, пятая (`this.urls.save`) требует
разрешения константы и честно попадает в невосстановленные.

**Замер на боевом модуле (ML, 09.08.2026): 79 вызовов, 26 литералов, 27 шаблонных
строк, 21 «переменная».** Две трети восстанавливаются как есть — но третья корзина
обманчива: почти вся она это две формы, разрешаемые тривиально.

```ts
export const auditUrl = '/integration/log/AuditJ';            // 10 вызовов в одном сервисе
private readonly baseUrl: string = '/api/ml/debtsconsgroup';  // `${this.baseUrl}/saveAlternative` и ещё пять
```

Константа уровня модуля и `readonly`-поле с литеральным значением. Разрешение этих двух
форм обязано стоять в задаче извлечения вызовов, а не «когда-нибудь потом»: без него
отчёт назовёт невосстановленными 27 % вызовов там, где настоящая дыра — единицы, и
доверие к числу пропадёт раньше, чем его успеют починить.

**Число параметров может не совпасть, и это самая полезная находка.** Владелец приводит
вызов `'api/ml/structure/getforupdate'` без параметра, а контроллер объявляет
`getforupdate/{modelVersionId}` — с параметром. Объяснений три: это разные эндпоинты,
идентификатор уходит query-строкой, либо вызов действительно устарел. Инструмент
различить их не может и не должен, но обязан **не молчать**: ключи, совпадающие по всем
сегментам, кроме числа `{}`, попадают в отдельную категорию «почти совпало». Строгое
сравнение отправило бы такую пару в две разные корзины — «эндпоинт без вызывающего»
и «вызов без эндпоинта», — и связь, которая почти нашлась, выглядела бы как две
независимые дырки.

### 2.5 Что делать с расхождениями

Две ситуации, и они принципиально разные:

| Находка | Это дефект? | Почему |
|---|---|---|
| эндпоинт бэкенда никто не зовёт | **нет**, инвентарь | его может звать другая система, мобильный клиент, интеграция или человек курлом |
| вызов фронта не находит эндпоинта | **нет по умолчанию**, инвентарь | `endpoints.py` разбирает только атрибутную маршрутизацию. Конвенциональная (`MapControllerRoute`) и minimal API не разбираются вовсе — при их наличии сотни вызовов «не найдут» эндпоинт, и это будет свойством инструмента, а не кода |

Обе печатаются всегда, кода возврата не меняют, пока не названы в `--fail-on`. Это
прямое следствие правила бизнес-слоя: «находка роняет прогон, только если её может
починить автор документа». Линт, красный с первого дня, выключат на второй.

Отдельно стоит третья, которая **является** дефектом и её стоит завести сразу: один
и тот же нормализованный ключ объявлен двумя разными узлами бэкенда. Это коллизия
маршрутов, и она ломает не документацию, а само приложение.

### 2.6 Один маршрут на много смыслов: обращения к реестру

Найдено разведкой в ML и меняет модель ключа, а не детали:

```ts
this.http.post('api/items/query', { listInnerName: 'users', fields, filters });
this.http.post('api/items/query', { listInnerName: 'OkkChain', fields: ['OkkChainTitle'] });
this.http.post('api/items/query', { listInnerName: 'MODELVERSIONPRODUCTTYPES', … });
```

Четырнадцать вызовов идут в **один** эндпоинт платформы и различаются значением
`listInnerName`. Ключ `(метод, маршрут)` склеит их в одну точку: вместо пяти связей
получится одна, и потеряется ровно то, ради чего связь строится, — какой именно
справочник читает экран.

**Для таких вызовов якорь — пара «маршрут + имя списка», и это уже существующий
якорь бизнес-слоя** (вид `list`, реестр `Cashflow.Structure.xml`, мост
`resolve.REGISTRY_KIND`). Фронт цепляется к реестру напрямую, минуя C#: связь
фронт↔бизнес здесь короче, чем фронт↔бэк.

Из этого следует требование к извлечению вызовов: для маршрутов, объявленных
в конфигурации «обращение к реестру», разбирается **и тело запроса** — литеральное
значение поля, названного в той же конфигурации. Перечислять маршруты в коде нельзя
по тому же доводу, что и всегда: `api/items/query` — имя платформенное, но не вечное.

Того же порядка `api/ml/draft/get?itemId=…&itemInnerName=…`: различающий смысл параметр
уехал в query-строку, которую нормализация маршрута отбрасывает. Отбрасывать её всё
равно надо — но список маршрутов, где query значима, обязан быть данными, а не
исключением в коде.

## 3. Как фронтенд ложится на существующие модели

### 3.1 Модуль

На .NET единица — `.csproj`. На фронте кандидатов три, и какой из них верен, знает
только боевой репозиторий (см. разведку, §6):

| Кандидат | Признак | Что даёт |
|---|---|---|
| проект Angular workspace | `angular.json`, ключ `projects.<имя>.root` | ровный аналог `.csproj`: имя, корень, тип (application/library) |
| проект nx | `project.json` рядом с кодом | то же плюс объявленные зависимости |
| пакет монорепозитория | `package.json` не в корне | грубее, но работает всегда |

Порядок выбора детерминированный: `angular.json` → `project.json` → `package.json` →
корень фронта одним модулем. Последний вариант — не заглушка: если фронт представляет
собой одно приложение без библиотек, один модуль и есть правда.

**Поле `Module.csproj` придётся обобщить.** Мы выбрали одну схему на два файла, значит
модель одна. Предлагается `project_file` с алиасом `csproj` для чтения старых
манифестов; запись идёт новым именем. Цена честная и её надо назвать: это разовый
сдвиг байтов в `doc-tree.json`, `schema_version` 1.1 → 2.0 и правка мест, где имя поля
зашито (`tree.py`, `ownership.py::_module_glob`, `merge.py`, `csproj.py`, тесты).
Альтернатива «положить путь к `angular.json` в поле с именем `csproj`» дешевле ровно
на один коммит и дороже на всё остальное время жизни: следующий человек прочитает
имя поля и поверит ему.

### 3.2 Символ

`Symbol` переиспользуется целиком, и это главная экономия во всей задаче — за него
цепляются `classify.py`, `ownership.py`, `stats.py`, `symbols`, весь шаг 2.

| Поле `Symbol` | Чем становится в TypeScript |
|---|---|
| `name` | имя экспортируемого класса |
| `fqn` | `путь/к/файлу.ts#Имя` — namespace в Angular-коде не используется, другой идентичности нет |
| `type_kind` | `class`, `interface`, `enum` плюс новые `type_alias`, `function`, `const` |
| `namespace` | пусто. Предикаты `namespace_*` на web-узлах не работают — это надо сказать вслух в `ownership.md`, иначе правило будет молча не срабатывать |
| `modifiers` | `export`, `default`, `abstract`, `readonly` |
| `attributes` | **декораторы**: `@Component({selector: 'cf-x'})` → `Attribute(name="Component", named_args={"selector": "cf-x"})` |
| `base_types` | `extends` и `implements` — в C# они тоже в одном списке |
| `members` | методы, свойства, поля; `@Input()`/`@Output()` попадают в `attributes` члена |
| `xml_doc` | JSDoc `/** … */` — тоже предшествующий сосед, как и в C# |

**Декоратор и атрибут — одно и то же, и это не метафора.** Правило
`attribute: ["Component"]` работает в `rules/web.yaml` и в `ownership.yaml` без единой
строки нового кода. Это самая крупная удача в задаче: движок правил, диагностика
опечаток, приоритеты, `matched_rules`, отчёт `--stats` — всё переиспользуется как есть.

Цена этого решения, которую надо назвать честно: **идентичность узла фронта содержит
путь к файлу**. Перенос файла в другой каталог на .NET узел не меняет, а на фронте даёт
`removed` + `added` в диффе. Обойти нечем: другой идентичности у TS-класса не существует,
а имя без пути даст `ListComponent` в двенадцати экземплярах.

### 3.3 Страница

Страница — не класс, и в этом её особенность. Компонент становится страницей оттого,
что на него ссылается таблица роутов, а таблица — это массив объектов в отдельном файле:

```ts
export const routes: Routes = [
  { path: '', component: StructuringPageComponent, canActivate: [AuthGuard] },
  { path: 'detail/:id', component: StructureDetailComponent },
  { path: 'reports', loadChildren: () => import('./reports/reports.routes').then(m => m.REPORT_ROUTES) },
];
```

Отсюда два вывода.

**Первый: нужен отдельный проход по таблице роутов** — он собирает дерево маршрутов
и приписывает компоненту его полный путь. Проход межфайловый: `loadChildren` ведёт
в другой файл через динамический `import()`, и путь ленивой ветки собирается только
после перехода туда. Разбор `import('./reports/reports.routes').then(m => m.REPORT_ROUTES)`
структурно возможен (проверено), но требует разрешения модульных путей — того же, что
и для `extends` (§3.4).

**Межфайловость оказалась обязательной, а форма — другой.** В ML `loadChildren` — ноль,
`RouterModule.forRoot`/`forChild` — ноль, зато дерево собирается спредом
импортированного идентификатора:

```ts
export const appRoutes: Routes = [{
  path: '', component: RoutesComponent,
  children: [
    { path: 'models',   children: [...modelsPath] },    // ← ./routesPath/models
    { path: 'forecast', children: [...forecastPath] },  // ← ./routesPath/forecast
  ],
}];
```

Разбор одного `app.routes.ts` даст два пути из двадцати шести, причём молча: ошибок
разбора нет, узлы просто не появятся. Значит проход обязан уметь **обе** формы —
динамический `import()` и spread импортированного массива, — и вторая встретилась
первой на реальном коде.

**Второй: якорь страницы — маршрут, а не имя компонента.** `/structuring/detail/{}`
знает пользователь, на него ведёт закладка, его пишут в инструкции. `StructureDetailComponent`
не знает никто снаружи. Это опять критерий якоря уровня 1 из `business-layer.md`.

Компонент, до которого нельзя дойти по таблице роутов, страницей не является — он
переиспользуемый и документируется как компонент. Компонент, до которого дойти можно,
но маршрут собрать не удалось (роуты построены кодом, а не литералом), — это
**невосстановленный маршрут**, ещё одно именованное число, а не тихо пропущенная страница.

### 3.4 Резолв: чего в TypeScript нет из коробки

Аналог резолва `using` → FQN, без которого не работает `inherits`:

- **относительные импорты** `'./base-api.service'` → путь в репозитории. Плюс правила
  разрешения: `.ts`, `/index.ts`;
- **алиасы `tsconfig.json`** (`"@cf/shared/*": ["libs/shared/src/*"]`). Читать
  обязательно: без них любой базовый класс из библиотеки останется нерезолвнутым, и
  правило `inherits: ["BaseApiService"]` не сработает нигде. Ловушка усугубляется тем,
  что `extends` тогда сохранится сырой строкой и правило по `base_type` **сработает** —
  то есть часть набора будет работать, а часть нет, без видимой причины;
- **бочки** (`index.ts` с `export * from './x'`) — переэкспорт, из-за которого имя
  импортируется не оттуда, где объявлено;
- **`extends` наследуется цепочкой**, как и в C#: замыкание считается тем же способом.

## 5. Ловушки, проверенные на грамматике

Каждая проверена запуском на файле, воспроизводящем описанный владельцем шаблон кода
(NGXS-стор, сервис с `HttpClient`, таблица роутов, компонент). Каждая прошла бы
поверхностное ревью и дала бы молча неверный результат.

### 5.1 Декоратор — сосед объявления, а не потомок. И наоборот

Самая злая находка, полная инверсия правила C#. Проверено:

```
export_statement                         ← @Injectable() export class A {}
  decorator          '@Injectable(...)'  ← СОСЕД
  class_declaration  'class A'

class_declaration                        ← @Injectable() class B {}   (без export)
  decorator          '@Injectable()'     ← ПОТОМОК
  class_body
```

В C# записано ровно наоборот: «модификаторы и атрибуты — потомки узла объявления,
а XML-doc — предшествующий сосед». Реализация, перенесённая с .NET буквально, найдёт
декораторы **только у неэкспортируемых классов**. В Angular экспортируется всё, что
имеет декоратор, — то есть не будет классифицировано ни одного компонента, сервиса
и стора, и отчёт покажет ровный ноль документируемых узлов при полном отсутствии ошибок
разбора. Искать причину в этом состоянии крайне тяжело.

Правило для реализации: декораторы собираются с **обоих** уровней — с самого
`class_declaration` и с охватывающего `export_statement`.

### 5.2 Списки захватов tree-sitter не выровнены между собой

`QueryCursor.captures()` возвращает `dict[str, list[Node]]`, и списки под разными
ключами идут в **разном порядке**. Проверено на одном и том же запросе:

```
@method: ['innerDebtsSnapshot', 'get', 'post', 'get', 'delete', 'dispatch', ...]
@call:   ['this.http.get(...)', 'this.httpClient.get(...)', 'this.http.delete(...)', ...]
```

`zip(caps["method"], caps["recv"])` даёт пары, которых в коде нет: `post` склеивается
с `this.httpClient`, `dispatch` — с чужой шаблонной строкой. Проверка «а верно ли»
проходит на первом же примере из одного вызова и разваливается на файле с пятью.

Правило: захватывается **узел вызова целиком**, а его части достаются
`child_by_field_name` от него. Индексная склейка запрещена.

Это общая ловушка API, а не свойство грамматики TypeScript. Существующий разбор C#
её не содержит — проверено: `parser.py` и `di.py` забирают из `captures()` **один**
ключ (`declaration`, `member`, `using`, `call`) и спускаются к частям от него. Правило
уже соблюдается на .NET, и записать его надо потому, что соблюдается оно там неявно:
новый парсер естественно начинается с запроса на несколько захватов сразу.

### 5.3 Шаблонная строка разбирается на части, и это спасает нормализацию

```
`api/ml/structure/innerDebtsSnapshot/${modelVersionId}`
  → [string_fragment 'api/ml/structure/innerDebtsSnapshot/', template_substitution '${modelVersionId}']

`${environment.apiUrl}/api/ml/structure/save`
  → [template_substitution '${environment.apiUrl}', string_fragment '/api/ml/structure/save']
```

Различие между «подстановка — это параметр пути» и «подстановка — это база URL»
выражается позицией: в начале строки параметра пути быть не может. Правило §2.3
опирается именно на это и потому проверяемо, а не эвристично.

### 5.4 Пять форм записи URL, и все встречаются

Проверено на пробном файле; первый аргумент HTTP-вызова бывает:

| Узел грамматики | Пример | Исход |
|---|---|---|
| `string` | `'api/ml/structure/getforupdate'` | `high` |
| `template_string` | `` `api/.../${id}` `` | `medium` |
| `binary_expression` | `'api/ml/structure/' + id` | `low` |
| `identifier` / `member_expression` | `this.urls.save` | не восстановлен |
| дженерик в вызове | `.get<StructureDto>('…')` | на разбор аргументов не влияет |

Последняя строка стоит отдельного слова: параметр типа стоит между именем метода
и скобкой, и наивный поиск «идентификатор, потом сразу скобка» его не переживает.
Через `child_by_field_name("arguments")` проблемы нет.

### 5.5 Прочее, проверенное там же

- **JSDoc — предшествующий сосед**, как и XML-doc в C#. Здесь асимметрии нет;
- **битый файл** даёт `has_error=True` и обрубок дерева — тот же признак, что
  используется на .NET для `parse_error_files`. Механизм переносится;
- `export default class` — отдельная форма, у неё нет имени в привычном месте;
- разбор `.tsx` требует **другой** грамматики (`language_tsx()`), не той, что для `.ts`.
  Если в репозитории есть `.tsx`, файл, разобранный не той грамматикой, даст ошибки
  разбора там, где кода нет.

## 6. Разведка боевого репозитория: что надо выяснить до плана

Часть решений не может быть принята из этого репозитория — данных нет. Ниже то, что
нужно посмотреть, с командами. Порядок — по влиянию на конструкцию.

**Разведка проведена 09.08.2026, отчёт — в

§6.2, §6.4, §6.5, §6.7 и §6.9 получены и уже внесены выше по тексту; подразделы ниже
оставлены как описание того, что и зачем спрашивалось, — их придётся повторить для
каждого следующего фронта.

**Всё это собирает один скрипт:** [`tools/recon-frontend.sh`](../tools/recon-frontend.sh).
Запускается из корня репозитория АС CF, только читает, выводит около двухсот строк:

```bash
bash tools/recon-frontend.sh МОДУЛЬ_ФРОНТА [МОДУЛЬ_БЭКА] > recon-frontend.txt 2>&1
```

**Область — не удобство, а условие осмысленности отчёта.** Фронтов в АС CF семь,
а срезы «примеры» и «содержимое» ограничены по объёму и режут список по алфавиту.
Первый прогон без области не ответил ни на один из четырёх своих главных вопросов:
`Sbt.CMS.Cashflow.ML` идёт седьмым и выпал целиком вместе с `fix-url.interceptor.ts`.
В выводе это неотличимо от «в модуле такого нет».

Разделы скрипта пронумерованы так же, как подразделы ниже. Знание TypeScript для
запуска не требуется — требуется только прочитать глазами четыре места, они перечислены
в конце вывода.

Все поиски — через `git grep`: в репозитории АС CF лежит `artifacts/bin`, и обычный
`grep -r` даёт сотни ложных вхождений (уже зафиксировано в `findings-cashflow-registries.md`).

Две ловушки pathspec, на которых скрипт попался сам, — обе стоят того, чтобы их знал
всякий, кто будет писать здесь свой поиск:

- `:(exclude)**/node_modules/**` **не исключает** `node_modules/` в корне. В pathspec
  без магии `:(glob)` звёздочка перекрывает `/`, поэтому ведущее `**/` требует хотя бы
  одного каталога перед именем. Это та же ловушка `**`, что записана в `CLAUDE.md`
  про `fnmatch`, — она повторяется в каждом инструменте со своим матчером путей;
- сужение **нельзя** задать префиксом в самом pathspec. На git 2.55 положительный
  шаблон с литеральным каталогом в паре с любым `:(exclude)` обнуляет выборку целиком,
  даже если исключению нечему совпадать:

  ```
  git ls-files -- 'МОДУЛЬ/*.ts'                            → 6
  git ls-files -- 'МОДУЛЬ/*.ts' ':(exclude)ничего-такого'  → 0
  git ls-files -- '*.ts'        ':(exclude)node_modules/**' → работает
  ```

  Отчёт при этом не пустой, а с нулями в счётчиках, то есть выглядит как «во фронте
  ничего нет». Область задаётся через `git -C`, шаблоны остаются прежними.

### 6.9 Сторона .NET: чем записан маршрут

Пункт добавлен после уточнения владельца: контроллер объявляет
`[HttpGet("getforupdate/{modelVersionId}")]` — литералом, а не токеном. Если так
написан весь набор, маршруты сравниваются посимвольно и связь будет точной; если
часть контроллеров использует `[controller]`/`[action]`, там подставится PascalCase
имени класса и метода, и нормализация регистра станет обязательной.

```bash
git grep -cE '\[Route\("' -- '*.cs' | awk -F: '{s+=$2} END{print "Route всего:", s+0}'
git grep -cE '\[Route\("[^"]*\[(controller|action)\]' -- '*.cs' | awk -F: '{s+=$2} END{print "с токенами:", s+0}'
git grep -cE 'MapControllerRoute|app\.Map(Get|Post|Put|Delete)' -- '*.cs' | awk -F: '{s+=$2} END{print "вне атрибутов:", s+0}'
```

Третья строка важна отдельно: `endpoints.py` разбирает **только** атрибутную
маршрутизацию. Каждый эндпоинт, объявленный конвенционально или minimal API, даст
«вызов фронта без эндпоинта» — и это будет свойством инструмента, а не кода. Пока
число не измерено, порог `--fail-on` для этой находки ставить нельзя.

## 7. Три вопроса, где решение стоит зафиксировать заранее

### 7.1 `.html`-шаблоны в манифест не разбираются, но участвуют в `impl_hash`

В шаблоне живёт то, чего нет в `.ts`: использование дочерних компонентов, `routerLink`,
разметка. Разбирать его грамматикой Angular-шаблонов — отдельный язык и отдельная
грамматика, в объём не входит.

Но **описание страницы зависит от шаблона напрямую**. Если `impl_hash` считать только
по `.ts`, переписанный экран не пометит документ устаревшим, и документация будет
уверенно описывать вчерашний интерфейс. Поэтому: путь шаблона попадает в узел (агент
шага 3 его прочитает), а **хэш содержимого шаблона входит в `impl_hash` компонента**.
Стили (`.scss`) — не входят: их правка смысла документа не меняет.

### 7.2 `node_modules` исключается на уровне обхода, а не правил

`discovery.py` умеет отсекать каталоги целиком (`_directory_globs`), и это как раз тот
случай, ради которого механизм писался: `node_modules` — это десятки тысяч файлов.
В умолчания добавляются `**/node_modules/**`, `**/dist/**`, `**/.angular/**`,
`**/*.spec.ts`. Складываются со встроенными, а не замещают их, — как и на .NET.

`*.spec.ts` отсекается **правилом отсева с причиной**, а не обходом: тестовые
вспомогательные классы иначе пропадут из индекса, и наследование через них порвётся.
Это ровно та же ловушка, что уже описана для .NET-тестов в README.

### 7.3 Ленивая ветка роутов без литерала — не «нет страницы»

Если маршрут собирается кодом, страница существует, а её якорь неизвестен. Такое
состояние обязано называться (`route_unresolved`), а не выражаться отсутствием узла:
отсутствие неотличимо от «страницы нет», и покрытие бизнес-документами посчитается
по заниженному знаменателю — то есть отчёт покажет успех там, где его нет.

## 8. Как это выглядит в работе

Команды предлагаются группой `docpipe web` — по образцу уже существующих групп
`docs`, `anchors`, `business`.

```bash
# шаг 1 для фронта: свой манифест, та же схема
docpipe web scan --root . --config docpipe.yaml --out artifacts/doc-tree.web.json
docpipe web scan --root . --stats            # состояние решений, ничего не пишет

# связь: два манифеста -> третий артефакт, детерминированный и коммитабельный
docpipe web link artifacts/doc-tree.json artifacts/doc-tree.web.json \
    --out artifacts/doc-tree.link.json

# шаг 2 — та же команда, что и на .NET
docpipe materialize artifacts/doc-tree.web.json --root . --link artifacts/doc-tree.link.json
docpipe docs status artifacts/doc-tree.web.json --root .

# бизнес-слой видит страницы
docpipe business lint artifacts/doc-tree.json --web artifacts/doc-tree.web.json
```

Отчёт `web link` — то, ради чего всё делается:

```
Связь фронт ↔ бэк

  вызовов HTTP найдено            412
    маршрут восстановлен точно    287   high
    восстановлен с параметрами     94   medium
    восстановлен частично          19   low
    НЕ ВОССТАНОВЛЕН                12   <- это работа

  эндпоинтов бэкенда              515
    есть вызывающий фронт         301
    вызывающего нет               214   инвентарь, не дефект

  вызовов без эндпоинта             8   инвентарь: атрибутная маршрутизация разбирается,
                                        конвенциональная и minimal API — нет
```

Последняя строка каждого блока — единственная, которая обязана идти к нулю. Ровно та же
конструкция отчёта, что у `scan --stats`, и по той же причине: у настройки должен быть
признак завершения.

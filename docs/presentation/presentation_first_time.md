# Презентация
## Решаемая проблема
Техническая документация не пишется или не обновляется.

## Предлагаемые решения

### Как обновлять техническую часть документации?
Предлагается следующий пайплайн:
- Парсинг кодовой базы
- Определение документируемых частей
- Матеарилизация дерева документации
- Наполнение документа


#### Определение документируемых частей
Мы не хотим документировать все детали реализации, однако хотим чтобы были покрыты все важные узлы.
Я выделил 4 основных элемента, которые будут документироваться:
- Grid Сервисы - Основные элементы выполнения логики
- Контроллеры - Связь между Фронтэндом и Бэкэндом
- Data-Провайдеры - Связь Бэкэнда с Базой Данных
- Event-Receiver - Обработчики событий БД, которые вызывают бэкэнд
- Workflow - Структурированные процессы
- Job (TBD) - Выполняемые по расписанию джобы
- Front Page (TBD) - Страница на фронтэнде
- Front API (TBD) - API вызовы фронтэнда - связь с контроллерами бэкэнда


#### Парсинг кодовой базы
Используем библиотеки tree-sitter для парсинга кодовой базы. Не применяем комплексные инструменты типа Roslyn чтобы инструмент не требовал сборки решения.

#### Материализация дерева документации
Дерево документации обретают физическую форму - создается (обновляется) структура документации, обновляются метаданные документов и ссылки на кодовую базу.
На уровне материализации решается требует ли документ ревью или создания.
- Если код появился новый код, который удовлетворяет правилам докуметирования (Шаг 1) - создается новый документ
- Если изменлась сигнатура или реализация - документ требует ревью

#### Наполнение документа
Это основной этап, где применяются LLM. Если бы наполнение происходило вручную, то решение бы не имело смысла.
Для каждого документа, который нужно создать или провести ревью мы вызываем агента, которому передаем необходимый документ. Документ уже содержит в себе ссылки на кодовую базу и всю необходимую метаинформацию.
Задачи агента:
- Прочитать документ
- Прочитать источники документа
- Сформировать описание по шаблону

##### Шаблон элемента документации
Чтобы разделить ответственность между детерминированной сборкой и недетерминированным наполнением документа, агенту на вход передается не только элемент документации, но и шаблон как его нужно описать. 
Это решает несколько задач:
- Разная структура у разных объектов - http методы актуальны для контроллеров, но в сервисах их документация не требуется.
- Простота валидации итогового документа - мы можем убедиться что агент не стер нужную информацию и дописывал только в специально отведенные блоки


### Как связать техническую документацию с бизнес документацией?
Основным недостатком решения является отсутствие бизнес контекста. Можно сделать reverse-engeneering кода и создать документацию, но из кода тяжелее (а иногда невозможно) достать бизнес-процессы и бизнес-правила.
Бизнес документация у нас уже существует и основной задачей является маппинг между технической и бизнес частью.
Для этого часть бизнес-документов будут оформлены как "точки входа" в бизнес-процессы. Такие точки входа будут связаны с технической частью прямым маппингом через frontmatter.
Примеры бизнес процессов и точек входа:
- Кредитоемкость - маппится на Job AutoML и контроллеры тестовых страниц
- Стандартный процесс - маппится на контроллеры и страницы фронтэнда
- ЭлектроКИ - маппится на workflow
- Актуализация при пробитии ИПМ/МБП - маппится на event-receiver

При этом документируется именно точка, где начинается работа нашей команды. Например, в ЭлектроКИ мы начинаем работу когда оркестратор CFI нас вызовет -> Этот шаг и будет точкой входа. Что произошло до этого момента можно отметить, но это не является обязательным.


## Как это работает

Мы можем вызывать команды из корня репозитория.
```bash
# Вызываем сканирование
docpipe scan --root . --config docs/ml/docspipe/cashflow-docspipe/docpipe.yaml --rules docs/ml/docspipe/cashflow-docspipe/rules.yaml --jobs 4
# Создает дерево модулей и нод и артифакт прогона
ls docs/ml/docspipe/cashflow-docspipe/artifacts
# Материализуем дерево по нашей команде
# Можно использовать с флагом --dry-run чтобы просто посмотреть, что будет сделано, без создания директорий
docpipe materialize docs/ml/docspipe/cashflow-docspipe/artifacts/doc-tree.json --root . --config docs/ml/docspipe/cashflow-docspipe/docpipe.yaml --rules docs/ml/docspipe/cashflow-docspipe/rules.yaml --team ML
# Создание списка документов на обновление
docpipe worklist docs/ml/docspipe/cashflow-docspipe/artifacts/doc-tree.json --root . --config docs/ml/docspipe/cashflow-docspipe/docpipe.yaml
# Запуск агента - проход по списку и вызов скилла с описанием
npm exec -- ai-conductor run docs/ml/flows/agent-docs-update.mjs --input docs/ml/docspipe/cashflow-docspipe/artifacts/doc-worklist.json --skill create-documentation --web
# После этого можно перейти на UI и увидеть отдельные процессы с выполнением задач.

```

## Затраты на на прогон и поддержание
### Отдельный прогон
- Без AI агента - до 30 секунд
- С AI агентом зависит от количества документов требующих ревью и создания. Запускается пачками примерно по 4 процесса и отрабатывает примерно на за минуту
### Поддержание
Инструмент требует настройки всех настроечных файлов и поддержания их в актуальном состоянии. Основная работа уже сделана, но потенциально потребуются минорные правки при появлении новых элементов документирования.


## Сценарии использования

### Обновление документации по расписанию
Раз в релиз проходим полный пайплайн по обновлению. Заходит отдельным PR в team при отрезании с dev.
### Создание схемы при подтягивании dev/team
За счёт того что время на обновление/создание документации не очень большое (30 секунд), то в теории техническую часть документации можно всегда держать актуальной. 
 - При подтягивании к себе любой незадокументированной части можно прогонять детерминированную часть пайплайна
 - При создании нового функционала в конце можно также прогонять и команды из детерминированной части пайплайна, для создания скелета.

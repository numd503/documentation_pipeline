Постановка зачем это вообще 02

Три способа документировать большой проект, и почему нужен четвёртый

Писать руками

Документ устаревает в момент мержа PR, который его не открывал. На 491 проекте никто не удержит соответствие, и через год документации не доверяют — а значит, её не читают.

Сгенерировать целиком

DocFX и подобные пересказывают сигнатуры. Получается зеркало кода: формально полное, практически бесполезное — на вопрос «зачем этот сервис» оно не отвечает.

Отдать всё LLM

Недетерминированно и невоспроизводимо: два прогона дают разное, ревьюить нечего, а на каждом прогоне агент обходит всё дерево заново — это тысячи документов и соответствующий счёт.

Требования постановки

  • документация генерируется из кода, а не пишется отдельно от него;
  • имеет понятную структуру, одинаковую для всех сущностей одного вида;
  • описывает, а не пересказывает код;
  • содержит ссылки до конкретной реализации — файл и строки.
Решение «этот класс — контроллер» принимает правило из YAML. Решение «что этот контроллер делает» принимает агент.

Отсюда всё остальное. Структура, пути, состав документов и признак «устарел ли документ» считаются детерминированно и проверяются побайтовым сравнением. Агенту остаётся ровно то, что нельзя вычислить, — смысл.

Шаг 1 — без сайд-эффектов

Не создаёт каталогов, не пишет .md, не вызывает LLM, не читает существующую документацию. Один вход — один манифест, побайтово воспроизводимый.

Шаг 2 — никогда не удаляет

Затирает только то, что принадлежит инструменту. Авторский текст, чужие ключи front matter и всё остальное в теле переживают любой прогон. Ни один сценарий не удаляет файл.

Шаг 3 — единственный недетерминированный

Работает по очереди, которую выдаёт шаг 2, а не по всему дереву. Что именно устарело — уже посчитано, агенту не нужно это выяснять.

Отдельно от трёх шагов стоит бизнес-слой: процессы и сущности, которые из кода не выводятся и пишутся аналитиками. Он связан с технической документацией по якорю, а не по имени класса — слайд 10.

Воркфлоу как это будет работать в CI 04

Цикл обновления: от мержа кода до принятого документа

Что происходит после изменения кода

  1. Разработчик мержит PR. Документацию он не трогал.
  2. docpipe scan — новый манифест. Он детерминирован, поэтому коммитится и читается в диффе как обычный файл.
  3. docpipe diff old new — что изменилось: added, removed, reclassified, moved, signature_changed. На узел — одно, самое существенное.
  4. docpipe materialize — новые скелеты, автоперенос переехавших документов, пересборка генерируемых блоков. Авторский текст не тронут.
  5. docs status --format json — очередь для агента: по каждому документу решение write / review / skip и причина.
  6. Агент шага 3 наполняет только секции. Front matter не трогает.
  7. docs accept — зафиксировать соответствие коду: хэши берутся из манифеста, а не из документа.
  8. PR с документацией → ревью человеком → мерж. Агент не мержит сам.

Ворота в CI

docpipe docs status manifest.json \
    --fail-on broken \
    --fail-on stale

Код возврата 1 — сборка красная. Значение вне перечня статусов — ошибка, а не пустой фильтр: опечатка --fail-on statle иначе дала бы вечно зелёную проверку.

Почему это дёшево

signature_hash не включает номера строк и пути. Переформатирование файла не создаёт работы. На большом проекте это разница между «агент обходит 4000 документов» и «агент обходит 30».

Прогон шага 1 — десятки секунд: ABP целиком (671 проект, 3,9 ГБ) — 9,7 с, с тёплым кэшем 2,8 с. Ожидание по АС CF — около 11 с при --jobs 4.

Чего в цикле нет намеренно

Автомержа документации, генерации индексов «для людей» и правки кода агентом. Документация лежит в репозитории набором .md; навигацию даёт файловое дерево и поиск.

Семантика для структуры почти не нужна: классификация идёт по атрибутам, базовым типам и конвенциям имён — это синтаксис. Цепочки наследования внутри решения достраиваются по индексу символов.

Два режима, и оба честны

Инкрементальный (по умолчанию): хэшируются все файлы, перепарсиваются изменённые. Результат по построению совпадает с полным сканом.

Скоуп (--scope): ABP — 2,1 с вместо 10,2 с. Изменение вне скоупа он не увидит, поэтому манифест помечен partial, а источником истины в CI остаётся полный прогон.

Шаг 1 манифест 06

Узел — это один тип и один будущий документ

{

  "impl_hash":      "sha256:74ba5471…",         // тело
  "symbol": { "fqn": …, "sources": [ … ], "members": [ … ] },
  "endpoints":    [ {"http_method": "GET", "route": "api/v1/Pricing/{id:guid}",
                     "member": "GetAsync", "line": 18} ],
  "dependencies": [ {"target": "…IPricingService", "via": "constructor",
                     "confidence": "high"} ]

doc-tree.json — манифест

Ни времени, ни хоста, ни абсолютных путей. Два прогона дают побайтово одинаковый файл, поэтому тест на детерминизм — обычный diff, без логики «сравнить, игнорируя поля».

doc-tree.run.json — сидкар

Всё недетерминированное: время, хост, длительность, счётчики и parse_error_files — единственный признак того, что тип исчез при разборе.

Идентичность

Узел — не файл и не проект. partial-класс из трёх файлов даёт один узел; файл с пятью классами — до пяти.

id = модуль + FQN + арность дженерика. Одного FQN мало: на ABP — 255 коллизий на 9075 объявлений. Имена проектов тоже не уникальны (39 повторов), поэтому идентификатор модуля строится от пути, а не от имени.

Два хэша — два уровня приоритета

хэшчто ловитрешение
signature_hashсменился публичный контрактwrite
impl_hashпереписано тело при том же контрактеreview

Ни один из них не включает номера строк и пути. Иначе переформатирование файла заставило бы агента перегенерировать документ впустую — и вся экономия пропала бы.

Ссылки до реализации

symbol.sources[] — список: путь плюс строки, у каждого члена свой line, у эндпоинта тоже. Это и закрывает требование постановки о ссылках на конкретное место в коде.

Две вещи, которые ломаются молча

Подсказки в шаблонах — только HTML-комментарии. «Секция пуста» = «после удаления комментариев ничего не осталось». Обычный текст сделал бы каждый новый документ уже написанным, и агент обошёл бы всё дерево впустую.

Сравнение «писать или нет» — по нормализованному тексту. Иначе на репозитории с core.autocrlf=true каждый документ оказался бы изменённым при каждом прогоне.

Шаг 2 статусы, приёмка, переносы 08

Плюс два статуса не про содержимое: broken — структуру прочитать не удалось, файл не тронут; orphan — узла с таким node_id в манифесте нет. Порядок фиксирован, первое сработавшее выигрывает.

Ссылки на переехавший документ из других документов чинятся сами: генерируемые блоки пересобираются в том же прогоне.

Два правила приёмки, которые неочевидны

accept берёт хэши из манифеста, а не из front matter: тот — зеркало и мог отстать. Приняв его значение, документ навсегда остался бы current, будучи stale.

Приёмка идёт через тот же план и ту же запись, что и обычный прогон. Отдельный путь записи — это вторая реализация слияния зон, и она разойдётся с первой на первом же документе с чужими ключами.

Шаг 3 агент · не начат 09

Что уже готово к приходу агента

Вход агента — это JSON, а не дерево каталогов

{ "action": "write",
  "doc_path": "docs/modules/Sample.Common/controllers/base-api-controller.md",
  "kind": "controller",
  "node_id": "type:src/Sample.Common/Sample.Common.csproj#…BaseApiController`0",
  "reason": "документ не наполнен: purpose, api, behaviour, collaboration, notes",
  "empty_sections": ["purpose", "api", "behaviour", "collaboration", "notes"],

  "example_ref": "templates/examples/controller.md",
  "changes": { "members_added": [], "members_removed": [], "kind_changed": null },

Реальный вывод docs status --format json на тестовом решении. Агенту не нужно выяснять, что устарело, — это уже посчитано. Он получает и причину, и перечень изменившихся членов, и образец нужной глубины.

Шаблоны

Семь скелетов — controller, service, provider, workflow, repository, ignite-service, ignite-compute — и четыре заполненных образца, показывающих глубину и стиль.

Имена скелетов сверяются с набором правил тестом: добавить вид сущности — значит дописать правило и завести скелет, иначе прогон упадёт с явной ошибкой вместо молчаливой потери документов.

Правила работы агента

  • пишет только внутри секций, front matter не трогает;
  • идёт по очереди write → review, а не по всему дереву;
  • результат фиксируется docs accept — иначе документ остаётся undeclared и попадёт в очередь снова.

Что нужно измерить до начала

Покрытие XML-doc. Разброс между проектами огромный: ABP 3,8 %, eShopOnWeb 6,5 %, semantic-kernel 52,5 % (и 93,4 % по типам, попавшим в дерево). Если в АС CF как в semantic-kernel — агенту есть с чего начинать; если как в ABP — описания придётся выводить из структуры кода.

Плюс средний размер типа: от него зависит, сколько контекста агент читает на один документ.

Бизнес-слой B01–B04 из B11 10

Точки входа АС CF объявлены не в коде

Разведка боевого репозитория, 29.07.2026. Джобы, workflow и обработчики событий диспетчеризуются по данным: универсальный раннер получает имя типа или идентификатор из строки XML. WorkflowRequestRunner.StartWorkflow(request.WorkflowId, …) — литерала конкретного workflow в C# не существует структурно.

Граф триггеров не восстанавливается статическим анализом — ни tree-sitter, ни Roslyn. Этой информации в коде нет. Реализация, считающая пустой литеральный поиск ошибкой, даст вечно красный линт по всем 45 workflow.

Стрелка одна: техника ссылается на бизнес. Бизнес-документ не знает ни node_id, ни doc_path, ни FQN — и потому рефакторинг физически не может его сломать.

business_hash не содержит имён C#-типов

Переименование класса шага хэш не меняет; добавление шага — меняет. Единственное исключение — имена методов grid-сервиса: их вызывают по имени через прокси, поэтому они и есть контракт.

Предпосылки что заложено в шаги 11

Восемь посылок, из которых выведено всё остальное

1 · Детерминизм — проверяемое свойство, а не пожелание
Каждый список сортируется явным sorted() с явным ключом; порядок обхода ФС никогда не источник порядка; коллизии разводятся хэшем ключа, а не порядком вставки. В манифесте нет ни времени, ни хоста, ни абсолютных путей — они в сидкаре. Тест на воспроизводимость — побайтовый diff.
2 · Классификация — данные, а не код
Новый вид сущности = правило в YAML + шаблон. Код не трогается. Опечатка в предикате роняет загрузку сразу, а не молча не срабатывает. При равном приоритете побеждает лексикографически меньший id — перестановка строк в файле не меняет манифест.
3 · Документ принадлежит двум авторам
Инструмент затирает только то, что сам породил. Всё остальное — секции, чужие ключи front matter, произвольный текст в теле — переживает любой прогон. Проверяется инвариантом обратимости разбора.
4 · Идентичность кода нестабильна, контракт — стабилен
doc_path меняется даже при неизменном коде: достаточно поправить rules.yaml, и тип переклассифицируется. Поэтому бизнес-слой якорится на строку, которую знает вызывающий, а не на имя класса.
5 · Полнота недостижима, честность обязательна
Динамические DI-регистрации синтаксически не видны; внешние типы не резолвятся; скоуп-режим слеп к изменениям вне скоупа. Каждое ограничение выражено в данных: confidence у зависимостей, partial у манифеста, parse_error_files в сидкаре.
6 · Всё, что мешает надёжно прочитать состояние, — отказ, а не самолечение
Единственный экземпляр принятых хэшей живёт в самом документе. Испорченный документ не переписывается даже тогда, когда узел на его пути выглядит «без файла».
7 · Инструмент видит репозиторий, а не боевую БД
Флаги IsActive, Override, JOBDISABLED не читаются намеренно: это политика поставки и состояние БД, а не бизнес-смысл. Прочитанный флаг рано или поздно кто-нибудь примет за факт.
8 · Реализовывать будет агент послабее
Поэтому каждая найденная ловушка попадает в план с объяснением, а не обходится молча. План и журнал — часть продукта, а не сопровождающая записка.
Проверено ловушки на реальном коде 12

Каждая однажды прошла бы все критерии приёмки и сломалась бы в проде

Разбор проектов

.csproj сохранены с BOM. В ABP — с BOM и 72 % файлов .cs. read_text(encoding="utf-8") роняет ET.fromstring: читать байтами.

TargetFramework обычно не объявлен. В eShopOnWeb — 0 из 10: значение приходит из Directory.Build.props выше по дереву.

Имена проектов не уникальны — в ABP 39 повторов. Идентификаторы строятся от путей.

Include собран из подстановок MSBuild. Склейка с каталогом проекта даёт выдуманный путь, который выглядит настоящим.

Разбор C#

#if внутри выражения рвёт разбор — и вместе с атрибутом ломается объявление: остаток файла переразбирается как top-level statements, и тип исчезает из вывода целиком. Доля растёт с числом целевых платформ: 0 % → 0,5 % (ABP) → 2,2 % → 8,7 % (OpenTelemetry). Единственный признак — parse_errors > 0 при пустом списке объявлений.

#if — контейнер, #region — плоский маркер. Реализация, перебирающая прямых детей тела, потеряет члены молча.

Модификаторы и атрибуты — потомки узла, XML-doc — предшествующий сосед.

Program.cs — top-level statements, без класса и метода: искать DI-регистрации нужно по всему дереву файла.

Классификация и объём

fnmatch не понимает ** как «ноль или больше сегментов»: **/obj/** не ловит obj/x.cs в корне.

Правило «тесты по имени типа» отсекает ноль узлов. Шум идёт из вспомогательных типов внутри тестовых проектов — AuditTestController, …PermissionDefinitionProvider. На ABP это 104 узла из 828, и убирает их только path_glob.

Регистрация маркерным интерфейсом не видна как регистрация. В ABP через ITransientDependency проходит 997 типов, а вызовов services.Add* там всего 182.

Одноимённые типы — норма. На ABP суффиксом-хэшем разведены 315 узлов из 828.

Проверочная база: eShopOnWeb, ABP, OpenTelemetry, semantic-kernel — 11 850 файлов, 941 проект, ноль падений. Каждая ловушка воспроизведена в tests/fixtures/WildSolution/, чтобы её нельзя было потерять при рефакторинге.

Общее для всех четырёх

Это данные, а не код. Добавить вид сущности, команду или реестр — значит дописать YAML. Один и тот же движок условий обслуживает rules.yaml и ownership.yaml, поэтому диагностика опечаток одна на всех.

Правила только положительные

Отрицаний нет намеренно: более специфичное выражается более высоким приоритетом, а не исключением из общего. Набор с отрицаниями превращается в систему уравнений, которую нельзя прочитать построчно.

Конфигурация не подхватывается сама

Путь всегда задаётся флагом --config. Конфигурация, молча не применившаяся, — худший вид ошибки: тот, который выглядит как успех. Поэтому в поставке есть run.sh, подставляющий все пути.

Две ловушки конфигурации

Шаблон обязан заканчиваться на /**. "docs" совпадёт с самим каталогом, но не с файлами под ним, — и будет выглядеть работающим.

Заданные шаблоны складываются со встроенными (**/obj/**, **/bin/**, **/*.g.cs), а не замещают их: иначе одна строка вернула бы obj/ в документацию.

Правило классификации

- id: ignite.service
  kind: ignite_service        # попадёт в doc_path
  template: ignite-service    # скелет документа
  priority: 95
  when:
    all:
      - type_kind: ["class", "record"]
      - inherits: ["Apache.Ignite.Core.Services.IService"]

Десять предикатов: attribute, base_type, inherits, name_suffix, name_regex, namespace_regex, path_glob, type_kind, modifier, has_member_with_attribute — комбинируются через any/all любой вложенности.

Что важно знать, когда пишешь правила

  • inherits сильнее base_type: он смотрит на всё замыкание наследования и срабатывает через ваш промежуточный базовый класс из другого проекта;
  • приоритеты решают, matched_rules объясняет — в узел пишутся все совпавшие правила;
  • начинать с самого частого: одно правило на ITransientDependency покрыло бы 997 типов ABP — больше, чем весь набор по умолчанию;
  • набор по умолчанию покрывает 1–9 % типов. Это исходное состояние, а не дефект: словарь «контроллер / сервис / провайдер» описывает прикладной код, и его нужно заменить словарём проекта.

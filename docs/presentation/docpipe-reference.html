Архитектураобщая схема02 / 13

Три шага, один манифест и отдельный бизнес-слой

Граница проходит по одной линии: классификация — правила, описание — агент. Решение «этот класс — контроллер» принимает YAML. Решение «что этот контроллер делает» принимает агент.

  • *.sln, *.slnx, *.csproj, *.cs
  • docpipe.yaml — где искать
  • rules/dotnet.yaml — что считать чем
  • templates/ — из чего состоит документ
  • ownership.yaml — чей документ
  • registries.yaml — где точки входа
▸
docpipe scan
Разбор C# через tree-sitter, классификация правилами, дерево документов. Один вход — побайтово один выход.
docpipe materialize · docs status · docs accept
Скелеты документов, генерируемые блоки, статусы и приёмка. Авторский текст не затрагивается никогда.
агент наполнения
Пишет текст в пустые секции по docs status --action write. Отдельного плана пока нет.
▸
  • doc-tree.json — манифест, коммитится
  • doc-tree.run.json — сидкар прогона
  • docs/**/*.md — документы со скелетами
  • business/**/*.md — каталог процессов
  • коды возврата для CI

Процессы и сущности из кода не выводятся: их пишут аналитики. Связь с техникой держится на якоре — строке, которую обязан знать вызывающий: имя grid-сервиса, JOBTITLE джоба, Id@Version workflow, пара «список + EventType», HTTP-маршрут.

реестры платформы ──▶ якоря ──┐
                                  ├──▶ бизнес-документы ◀──▶ технические
каталог аналитика ──▶ процессы ──┘        связь по якорю, не по коду

Стрелка одна: техника ссылается на бизнес. Бизнес-документ не знает ни node_id, ни doc_path, ни FQN — поэтому рефакторинг физически не может его сломать.

готовоШаг 1, T00–T26 — scan
готовоШаг 2, M01–M12 — materialize, docs
готовоБизнес-слой, B01–B11 — anchors, business
нетШаг 3 — наполнение агентом

Скоуп текущей версии — только .NET (C#). .NET SDK не требуется: разбор идёт через tree-sitter, без сборки решения.

Шаг 1docpipe scan03 / 13

Из исходников — в манифест, без сборки решения

Чистая функция от кода и правил. В выходе нет ни времени, ни имени машины, ни абсолютных путей: всё недетерминированное вынесено в сидкар, поэтому манифест можно коммитить и читать в диффе.

  • Дерево исходников — --root
  • docpipe.yaml — enrolled, exclude, domains
  • rules/dotnet.yaml — отсев и правила видов
  • .docpipe/cache — разобранные файлы

Решения и файлы решения читаются, но TargetFramework часто приходит из Directory.Build.props выше по дереву; .csproj читаются байтами — BOM встречается часто.

▸
  1. discovery — обход, решения, .csproj, исключения
  2. parser — tree-sitter, символы, базы, атрибуты, XML-doc
  3. index — ключ символа: модуль + FQN + арность дженерика
  4. classify — отсев с причиной, затем правила по priority
  5. tree — doc_path, домены, разрешение коллизий по хэшу
  6. emit — сортировка всего явным key, запись
▸
doc-tree.json  детерминированный
  schema_version, ruleset_version
  parser: {tree_sitter, grammar}
  modules[] id, domain, enrolled,
          target_frameworks,
          project_references
  nodes[]   id, kind, doc_path,
          matched_rules[], endpoints[],
          dependencies[], symbol{…}
          signature_hash — контракт
          impl_hash      — тело

doc-tree.run.json  сидкар
  generated_at, host, duration
  stats{symbols, documented,
        not_documented, undecided}
  parse_error_files[]

Хэшей два, и это два уровня приоритета. signature_hash — контракт, без номеров строк и путей: переформатирование файла не создаёт работы. impl_hash — тело: «переписано при том же контракте».

Три исхода на каждый символ: <kind> — правило сработало, not_documented — отсев с обязательной причиной, undecided — решения нет. К нулю обязано идти только последнее.

parse_error_files в сидкаре — файлы, где разбор дал ошибки и ни одного типа. Обычно это #if внутри выражения: тип исчезает из вывода целиком, и больше этот случай ничем не виден. Ловит его validate.

Шаг 2docpipe materialize · docs04 / 13

Документ принадлежит двум авторам сразу

Инструмент пересобирает свои зоны и не трогает чужие. Инвариант, на котором это стоит: assemble(parse_document(t)) == t байт в байт.

  • doc-tree.json — манифест шага 1
  • templates/ — 7 скелетов + default.md
  • ownership.yaml — команда документа
  • существующее дерево docs/

Без ownership.yaml у всех документов team: null — это видимый факт, а не отсутствие строки.

▸
  1. План — что создать, что обновить, что перенести
  2. Проверка — блокирующие ошибки собираются целиком
  3. Запись — сравнение по нормализованному тексту; без изменений файл не открывается на запись вовсе

При блокирующей ошибке не записывается ничего: половина обновлённого дерева хуже необновлённого, потому что о ней никто не узнает. Инструмент не удаляет никогда.

Переезд — это когда изменился код и пересчитался doc_path, а файл с текстом остался на старом месте. Совпал node_id или impl_hash при единственной паре — перенос; кандидатов несколько — решает человек командой docs adopt.

broken и orphan — не про содержимое: первый значит «структуру не прочитать, файл не тронут», второй — «узла с таким node_id в манифесте нет».

docs accept — единственный писатель принятого состояния, и хэши он берёт из манифеста, а не из front matter документа. Тот — зеркало и мог отстать; приняв его значение, документ навсегда остался бы current, будучи stale.

Бизнес-слойdocpipe anchors · business05 / 13

Точки входа объявлены не в коде, а в реестрах платформы

Джобы, workflow и обработчики событий диспетчеризуются по данным: раннер получает имя типа из строки XML. Литерала конкретного workflow в C# не существует структурно — граф триггеров статическим анализом не восстанавливается, поэтому источник истины о точках входа — реестры.

  • registries.yaml — описание реестров: путь, item_xpath, поля
  • сами реестры — XML платформы
  • doc-tree.json — чтобы найти реализацию
  • business/**/*.md — каталог аналитика:
    bp. процесс · be. сущность · cap. возможность
▸
  1. Инвентаризация — из реестров читаются якоря: grid_service, job, workflow, workflow_step, list_event, http…
  2. Разрешение — якорь → запись реестра → тип → узел документации. Словари видов сводит мост resolve.REGISTRY_KIND: аналитик пишет table, реестр объявляет list.
  3. business_hash — по разрешённым фактам, без имён C#-типов. Переименование класса шага хэш не меняет, добавление шага — меняет.
  4. Сборка — генерируемый блок и обратные ссылки в технических документах
▸
  • Инвентарь точек входа — anchors list
  • Генерируемые блоки бизнес-документов: точки входа, реализация, участники, данные
  • Статусы и docpipe_state с принятым хэшем
  • Отчёт линта: что сломано и сколько ещё писать

Статусов missing и orphan здесь нет: документ — и есть файл. О ненаписанном сообщает отчёт о непокрытых точках входа, он считается по реестрам.

УсловиеСтатусРешение
документ не разбираетсяbrokenreview

якорь не разрешается, verify ≠ falsebrokenreview
приёмки не было, а текст естьundeclaredreview

иначеcurrentskip

Находка роняет прогон, только если её может починить автор документа. Непокрытые точки входа и записи реестров без узла — состояние работы, а не дефект: они печатаются всегда, но кода возврата не меняют, пока не названы в --fail-on.

Требование покрытия 100 % не ставится и не должно: у большей части кода бизнес-смысла нет, а линт, красный с первого дня, выключат на второй — и вместе с ним пропадут шесть работающих проверок.

Настройкапять файлов06 / 13

Что где настраивается и почему это разные файлы

Файлы разделены не по удобству, а по скорости изменения и владельцу. Словарь сущностей переносится между проектами, пути — нет, орг-структура меняется чаще кода.

ФайлОтвечает на вопросКто ведётПереносится
в другой проект		Как задаётся
docpipe.yaml Где искать код, куда писать результат Владелец пайплайна Нет — свой у каждого репозитория --config
rules/dotnet.yaml Что считать сущностью какого вида и что не документировать Архитектор Да — это словарь платформы --rules · ключ rules
templates/ Из чего состоит документ каждого вида Архитектор, техписатель Да --templates · ключ templates
ownership.yaml Чей это документ Тимлиды Нет — орг-структура --ownership · ключ ownership
registries.yaml Где объявлены точки входа платформы Команда платформы Нет — пути и XPath платформы --registries · ключ registries

Флаг важнее ключа в конфигурации — но только тогда, когда флаг действительно задан. Значения по умолчанию: rules/dotnet.yaml, templates, docs, business, artifacts/doc-tree.json, .docpipe/cache.

rules/dotnet.yaml		 Что не документируем, но читаем. Каждое решение с reason Отсев без причины запрещён на уровне загрузки: иначе «не документируем 4820» — снова безымянное число

docpipe.yaml		 Куда не заходим вовсе. Файл не читается и символов не даёт Наследование через такой файл рвётся. Нужно ровно для чужого кода внутри репозитория

  • Шаблон в exclude обязан заканчиваться на /**. "docs" совпадёт только с самим каталогом, но не с файлами под ним — и будет выглядеть работающим.

exclude в docpipe.yaml складывается со встроенными **/obj/**, **/bin/**, **/*.g.cs. docs_scan_exclude — со встроенными **/.venv/**, **/node_modules/**, **/.git/**. Ничто из этого не замещает список по умолчанию.

Примерdocpipe.yaml — где искать код07 / 13

Один файл на репозиторий, двенадцать ключей

Копируется из docpipe.example.yaml и правится под проект. Ниже — полный набор с тем, что стоит поменять первым.

# ── шаг 1: где искать код ────────────────────────────
enrolled:                  # что документируем
  - "src/**"
  # - "modules/*/src/**"

exclude:                   # куда не заходим вовсе
  - "docs/**"                # обязательно с /**
  - "third_party/**"

domains:                   # смысловая группировка модулей
  "src/Cf.Pricing.*/**": "pricing"
  "src/Cf.Risk.*/**":    "risk"
  "src/Cf.Common.*/**":  "platform"

rules:      "rules/dotnet.yaml"
out:        "artifacts/doc-tree.json"   # путь от cwd
cache_dir:  ".docpipe/cache"            # путь от --root

# ── шаг 2: документы ─────────────────────────────────
templates:  "templates"
ownership:  "ownership.yaml"
docs_root:  "docs"
docs_scan_exclude: []

# ── бизнес-слой ──────────────────────────────────────
registries:    "registries.yaml"
business_root: "business"
  1. enrolled — без него в документацию попадёт всё, включая тесты и вспомогательные проекты. Начинать с одного модуля: "src/Cf.Pricing.*/**"
  2. exclude — если инструмент лежит внутри сканируемого дерева или в репозитории есть вендоренные зависимости
  3. domains — когда модулей больше нескольких десятков. Без совпадения доменом становится имя модуля
  4. ownership — когда документов больше, чем одна команда может прочитать

Проверяется первый совпавший глоб в лексикографическом порядке ключей, а не в порядке записи в файле: перестановка строк не должна менять манифест.

uv run docpipe scan --root . \
  --config docpipe.yaml --stats

# --stats ничего не пишет: показывает
# счётчики решений и подсказки по правилам
Примерправила · владение · реестры08 / 13

Один синтаксис условий на три файла

У правил классификации и правил владения общий движок: одни предикаты, одна диагностика опечаток. Правила только положительные — более специфичное выражается более высоким priority, а не исключением из общего.

exclude:
  require_public: true   # не поле-правило:
                       # отрицаний в движке нет
  rules:
    - id: data.contracts
      reason: "Контракт передачи данных:
        смысл в вызывающем коде"
      priority: 50
      when:
        name_regex:
          - "^.*Dto$"
          - "^.*Request$"

rules:
  - id: ignite.service
    kind:     ignite_service
    template: ignite-service   # файл
    priority: 95
    when:
      all:
        - type_kind: ["class", "record"]
        - inherits:  ["IService"]

template обязан совпадать с именем скелета в templates/ — иначе прогон падает с явной ошибкой вместо молчаливой потери документов.

teams:
  - id: pricing
    title: Ценообразование

rules:
  # 10 — проект целиком
  - id: pricing.modules
    team: pricing
    priority: 10
    when:
      module_glob: ["src/Cf.Pricing.*/**"]

  # 50 — шэренный проект по каталогам
  - id: risk.shared-folders
    team: risk
    priority: 50
    when:
      path_glob: ["src/Cf.Shared/Risk/**"]

  # 80 — namespace внутри чужого каталога
  # 100 — точечная передача одного типа

Владелец определяется по узлу, а не по модулю: «команда = проект» разбивается о шэренный .csproj — ровно ту ситуацию, ради которой владение и заводится. Слои с шагом 10/50/80/100 — чтобы вставка уровня не требовала перенумерации.

registries:
  - id: grid-services
    kind: grid_service
    path: …/services.config
    format: xml
    item_xpath: "./dotNetServices/add"
    fields:
      ref:       "@name"      # якорь
      impl_fqn:  "@class"
      assembly:  "@assembly"
      team:      "@team"

  - id: jobs
    kind: job
    paths: ["…/Items*.xml"]
    item_xpath: "./Lists/List[@InnerName=
      'JOBS']/Items/Item[@KeyField='JOBTITLE']"
    fields:
      ref:           "@KeyValue"   # якорь
      contract_fqn:  "@JOBCLASS"
      schedule_raw:  "@JOBSCHEDULE"

Якорь — @name, а не @class: имя сервиса не выводится из класса и переименованием класса не меняется. item_xpath берёт только прямых детей: обход по .//add подобрал бы интерцепторы как сервисы.

Флаги состояния — Override, IsActive, JOBDISABLED — описывают политику поставки и состояние боевой БД, а не бизнес-смысл. Инструмент видит репозиторий и состояния БД не знает никогда, поэтому «джоб выключен» или «версия активна» он сказать не может, а прочитанный флаг рано или поздно кто-нибудь прочтёт как факт. Читается то, что описывает контракт: идентификатор, класс, сборка, команда, расписание, заголовок, версия.

Онбордингнастройка под свой репозиторий13 / 13

Шесть шагов до нуля нерешённых символов

Порядок важен: сначала посмотреть на цифры, потом записать решения, и только потом включать проверку в CI. Каждый шаг проверяется одной командой.

ШагЧто делатьЧем проверить
0 Прогнать как есть и посмотреть на состояние решений — сколько символов, сколько нерешённых scan --stats
1 Посмотреть, за что зацепиться: какие базовые типы, атрибуты и суффиксы повторяются в нерешённых symbols --state undecided
2 Записать решения «не документируем» в exclude набора правил — каждое с reason symbols --state not_documented
3 Enrollment: что вообще входит в документацию. Список только положительный, тестовые проекты перечислять не нужно stats
4 Правила: словарь сущностей проекта. Новое правило — это kind, template и скелет в templates/ symbols --rule ID
5 Домены и владение: как сгруппировать модули и кому принадлежат документы docs owners --lint
6 Довести undecided до нуля и закрепить в CI --fail-on-undecided 
# манифест: решение принято про каждый символ
docpipe scan --root . --config docpipe.yaml \
        --out artifacts/doc-tree.json --fail-on-undecided

# инварианты, которые схема не покрывает
docpipe validate artifacts/doc-tree.json

# документы: битые и отставшие от контракта
docpipe docs status artifacts/doc-tree.json \
        --fail-on broken --fail-on stale

# бизнес-каталог: дефекты, которые чинит автор
docpipe business lint artifacts/doc-tree.json \
        --config docpipe.yaml

Манифест детерминирован — его стоит коммитить: тогда docpipe diff в PR показывает, что изменилось в структуре документации, ещё до того, как кто-то откроет документы.

  • Общий код по ссылке на файл, а не отдельным проектом: такие файлы не принадлежат ни одному модулю и в документацию не попадают. На OpenTelemetry и semantic-kernel это 5 % типов.
  • Подстановки MSBuild в путях. Ссылки между проектами дорезолвливаются по имени файла, а TargetFramework через цепочку props достать нечем.
  • Плотность условной компиляции. Чем больше целевых платформ, тем чаще #if стоит внутри выражения и молча уносит тип целиком.
  • «Тест» как бизнес-понятие. В финансовом моделировании StressTest и BackTest — настоящие сущности, а правило отсева тестов их выкинет.

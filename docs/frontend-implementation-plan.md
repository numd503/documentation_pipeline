# План реализации: фронтенд Angular в пайплайне — шаг `web`

Исполнительный план для агента-реализатора. Обоснования решений — в
[`frontend-analysis.md`](frontend-analysis.md), факты о боевом репозитории —
в [`findings-cashflow-frontend.md`](findings-cashflow-frontend.md). Здесь только
исполнение: что создать, что изменить, чем проверить.

Шаги 1 и 2 и бизнес-слой закончены и здесь не переделываются. Единственные правки
существующего кода — задачи F02, F09 и F10, и каждая названа отдельно.

---

## Как работать с этим планом

1. Задачи выполняются по графу зависимостей. Задача закрыта, только когда **её команда
   проверки проходит зелёной**.
2. Перед каждым коммитом:
   `uv run ruff check . && uv run ruff format --check . && uv run mypy docpipe && uv run pytest -q`.
3. **Ничего не додумывай.** Нет в спецификации — реализуй минимально необходимое для
   критериев приёмки. Никаких возможностей «на будущее».
4. Сообщения об ошибках, docstring и комментарии — по-русски; имена в коде — по-английски.
   Комментарий объясняет **почему**, а не что.
5. При расхождении плана с реальностью — **править план**, а не молча обходить. Каждая
   найденная ловушка дописывается сюда с объяснением: следующий реализатор наступит
   на неё снова.
6. Всё, что печатается в отчётах, обязано быть **именованным числом**. «Связь построена
   для 340 вызовов» без второго числа не значит ничего.

## Что делает шаг `web`

```
исходники .ts ──▶ docpipe web scan  ──▶ doc-tree.web.json   (та же схема, что у .NET)
                                    ──▶ doc-tree.web.run.json (сидкар: время, хост, версии)

doc-tree.json + doc-tree.web.json
              ──▶ docpipe web link ──▶ artifacts/web-link.json + отчёт
                                       «кто зовёт какой эндпоинт и чего не хватает»

doc-tree.web.json ──▶ docpipe materialize ──▶ docs/**/*.md   (шаг 2 без изменений)
```

**Чего шаг не делает:** не разбирает `.html` как язык (только хэширует, §F14), не
исполняет TypeScript, не выводит логику интерцепторов (она задаётся конфигурацией),
не строит связь по именам классов.

## Ключевые решения

| Решение | Почему так |
|---|---|
| **Ключ связи — нормализованная пара `(HTTP-метод, маршрут)`**, а не ссылка на узел | Идентификатор узла содержит путь проекта и FQN: переименование контроллера рвало бы связь при неизменном HTTP-контракте. Тот же довод, по которому бизнес-слой не знает `node_id` |
| **Два манифеста, одна схема** | `materialize`, `docs status`, `business` работают от `Manifest` и про язык не знают. Отдельный файл не меняет ни одного байта .NET-манифеста и не удваивает время `scan`. Свести их в один можно позже — модели это позволяют |
| **Преобразование URL задаётся конфигурацией** (`web.url_rewrite`), а не выводится из кода интерцептора | Выводить — значит исполнять `reduce` по списку декораторов, собираемому при старте приложения. В АС CF конвейер вообще выключен (поля `apiUrl` нет ни в одном окружении), и это факт, который обязан быть записан, а не угадан |
| **Префикс приложения снимается по таблице модуля** | `pathRewrite` из `proxy.conf` срезает `/pm`, `/cf`, `/tm`, `/realty`, а у админки `^/api/` наоборот дописывается. У ML таблица пустая — на нём одном ошибку не увидеть |
| **Обращение к реестру — якорь-пара, а не маршрут** | `api/items/query` с `listInnerName` в теле и `api/items?listInnerName=…` в query — один маршрут на много смыслов. Ключ «метод + маршрут» склеил бы обращения к пользователям, моделям и справочникам в одну точку |
| **Якорь страницы — маршрут, а не имя компонента** | `/models/loader/quiz` знает пользователь, на него ведёт закладка. `LoaderQuizComponent` не знает никто снаружи |
| **Невосстановленный маршрут — состояние, а не отсутствие** | Отсутствие узла неотличимо от «страницы нет», и покрытие посчитается по заниженному знаменателю: отчёт покажет успех там, где его нет |
| **Хэш шаблона `.html` входит в `impl_hash` компонента**, стили — нет | Переписанный экран обязан помечать документ устаревшим. Правка `.scss` смысла документа не меняет |
| **`node_modules` исключается обходом, `*.spec.ts` — правилом с причиной** | Первое — десятки тысяч файлов, второе — часть графа наследования: тестовые базовые классы нужны резолву, но документами не становятся |
| **Ключ кэша включает версию грамматики TypeScript** | Иначе апгрейд грамматики не сбросит кэш и прогон отдаст старый разбор — молча |

## Конфигурация: секция `web`

Добавляется в `docpipe.yaml`. Все пути репо-относительные, проверяются теми же
валидаторами, что и существующие ключи (`config.py`, `_repo_relative`).

```yaml
web:
  # Каталоги-модули фронта. Пусто — искать автоматически (F06).
  roots: ["sbt.cms.cashflow.subrepo/Sbt.CMS.Cashflow.ML"]

  rules: rules/web.yaml
  out: artifacts/doc-tree.web.json
  link_out: artifacts/web-link.json

  # Преобразование URL по дороге к бэкенду. Пустой список — законное значение:
  # значит, проверено и ничего не преобразуется. Читается сверху вниз,
  # первое совпадение выигрывает.
  url_rewrite:
    - module: "Sbt.CMS.Cashflow.ML"
      strip_prefix: ""          # proxy.conf: context '/**', pathRewrite нет
    - module: "PM.Front"
      strip_prefix: "/pm"       # pathRewrite: {'^/pm': ''}
    - module: "Sbt.CMS.Front"
      add_prefix: "/admin"      # pathRewrite: {'^/api/': '/admin/api/'}

  # Маршруты платформы, где смысл вызова различается не маршрутом.
  # Без этого все обращения к спискам склеятся в один ключ.
  registry_calls:
    - route: "api/items/query"
      discriminator: { in: body,  name: listInnerName }
      kind: list
    - route: "api/items"
      discriminator: { in: query, name: listInnerName }
      kind: list
```

> **Ловушка.** `strip_prefix: ""` и отсутствие записи — **разные** вещи. Первое значит
> «проверено, префикса нет», второе — «модуль не настроен». Второе обязано печататься
> в отчёте как непокрытый модуль, иначе забытая настройка выглядит как исправная связь.

## F02 — обход `.ts`/`.html` и фикстура `WebWorkspace`

**Цель:** `discovery` находит исходники фронта, а тесты получают дерево, на котором
воспроизводятся все известные ловушки.

**Изменить:** `docpipe/discovery.py`, `docpipe/emit.py`, `tests/conftest.py`,
`tests/test_discovery.py`, `.gitignore`
**Создать:** `tests/fixtures/WebWorkspace/**`, `tests/test_fixture_web.py`

**Зачем.** Все последующие задачи проверяются на этой фикстуре. Если она не содержит
конструкцию — задача пройдёт приёмку и сломается на боевом коде.

**Спецификация**

1. `_EXTENSIONS` дополняется: `ts_files: (".ts",)`, `html_files: (".html",)`.
   Файлы, объявляющие модуль фронта, отбираются по **полному имени**, а не по
   расширению, поэтому в `_EXTENSIONS` не влезают: заводится отдельное множество
   `_WEB_PROJECT_FILE_NAMES = {"angular.json", "nx.json", "project.json",
   "package.json"}` и отдельное поле `Discovered.web_project_files`.
2. В умолчания исключений (`emit.DEFAULT_EXCLUDE`) добавляются `**/node_modules/**`,
   `**/dist/**`, `**/.angular/**`, `**/coverage/**`. Складываются со встроенными,
   а не замещают.
3. `*.spec.ts` и `*.d.ts` **не исключаются обходом** — они нужны резолву; отсев идёт
   правилом с причиной в F12.
4. Обход остаётся **один** на оба языка: два прохода по дереву пришлось бы держать
   согласованными по `exclude`, `scope` и `roots`, и разошлись бы они молча.

**Состав фикстуры** (каждый пункт — воспроизведение факта из отчёта разведки;
27 файлов `.ts` вне `node_modules`, 29 всего):

> **Ловушка. `paths` дочернего `tsconfig` замещает родительский целиком, а не
> дополняет его.** Поэтому в фикстуре алиасы объявлены **только** в
> `tsconfig.base.json`, а `tsconfig.json` их не переобъявляет: иначе цепочка
> `extends` была бы декорацией, и резолв, её игнорирующий, всё равно проходил бы
> тесты. Реализация F05 обязана воспроизводить именно замещение, а не слияние.

> **Ловушка. Комментарий внутри фикстуры ломает проверку по подстроке.** Тест
> «`@State(` без дженерика в фикстуре не встречается» падал на комментарии,
> объясняющем эту самую ловушку, а тест «в `proxy.conf` нет `pathRewrite`» —
> на комментарии «`pathRewrite` нет». Пояснение в фикстуре не должно содержать
> формы, отсутствие которой утверждается.

> **Ловушка. Не добавлять `node_modules/` в `.gitignore`.** В фикстуре есть файл под
> `node_modules/`, на котором проверяется исключение. Стандартный `.gitignore` Angular
> его выкинет, и тест продолжит проходить, ничего не проверяя. Это ровно та же ошибка,
> что описана для `obj/` в `SampleSolution` (`CLAUDE.md`, «Инварианты фикстур»).

> **Ловушка. Тест фикстуры проверяет наличие конструкций, а не файлов.**
> `tests/test_fixture_web.py` обязан утверждать: в фикстуре есть неэкспортируемый класс
> с декоратором, есть спред роутов, есть вызов с базой в поле, есть `?listInnerName=`.
> Иначе «упрощение» фикстуры оставит тесты зелёными и бессмысленными.

**Критерии приёмки**
- `discover` на `WebWorkspace` возвращает ровно 27 файлов `.ts` (список зафиксирован
  константой `EXPECTED_TS`), файлы под `node_modules/` в нём отсутствуют, а без
  исключений — присутствуют (контрольная проверка: иначе тест проходил бы просто
  потому, что каталога нет);
- `*.spec.ts` и `*.d.ts` **присутствуют** в результате обхода;
- все списки отсортированы, пути POSIX-относительные;
- `test_fixture_web.py` проверяет конструкции по существу, а не по именам файлов.
  Проверка ищет форму **по всему корпусу** `.ts`: перенести конструкцию в соседний
  файл можно, удалить — нельзя. Поиск в конкретном файле дал бы тест, который
  переживёт исчезновение конструкции при переименовании файла.

**Проверка**
```bash
uv run pytest tests/test_discovery.py tests/test_fixture_web.py -q
```

## F03 — `docpipe/route.py`: нормализация маршрута

**Цель:** одна чистая функция, приводящая маршрут фронта и маршрут контроллера к общему
ключу.

**Создать:** `docpipe/route.py`, `tests/test_route.py`

**Зачем.** Две копии нормализации разойдутся на первом же частном случае и разойдутся
молча. Модуль лежит **не** под `web/`, потому что им пользуются обе стороны.

**Спецификация**

```python
@dataclass(frozen=True)
class RewriteRule:
    module: str
    strip_prefix: str = ""
    add_prefix: str = ""

@dataclass(frozen=True)
class RouteKey:
    http_method: str          # верхний регистр; "" — если сторона его не знает
    route: str                # нормализованный путь без ведущего/замыкающего '/'
    discriminator: str = ""   # имя списка для обращений к реестру (F07)

def normalize_route(raw: str, *, rewrite: RewriteRule | None = None) -> str: ...
def route_key(http_method: str, raw: str, *,
              rewrite: RewriteRule | None = None, discriminator: str = "") -> RouteKey: ...
def almost_equal(a: RouteKey, b: RouteKey) -> bool: ...   # различаются только числом {}
```

Порядок шагов `normalize_route` — фиксированный, менять нельзя:

| # | Шаг | Пример |
|---|---|---|
| 1 | отбросить схему и хост, если есть | `https://h/api/x` → `/api/x` |
| 2 | отбросить query и фрагмент | `api/items?listInnerName=models` → `api/items` |
| 3 | снять `strip_prefix`, затем дописать `add_prefix` модуля | `/pm/api/limits` → `/api/limits`; `/api/users` → `/admin/api/users` |
| 4 | заменить подстановки на `{}` | `` `api/ml/x/${id}` `` → `api/ml/x/{}`; `{id:guid}`, `{id?}`, `{*rest}` → `{}` |
| 5 | схлопнуть `//`, снять ведущий и замыкающий `/` | `//api/x/` → `api/x` |
| 6 | привести к нижнему регистру | `api/ML/Structure` → `api/ml/structure` |

**Направление шага 3: маршрут фронта приводится к тому, что видит бэкенд.** Правило
описывает работу прокси (`pathRewrite`), поэтому `strip_prefix` **снимается**,
а `add_prefix` **дописывается**; общий ключ живёт в пространстве имён бэкенда.
Обратное направление («снять оба») неосуществимо: правило заведено на модуль
фронта, а у маршрута контроллера модуля фронта нет, и выбрать для него правило
не из чего. Порядок внутри шага — сначала снять, потом дописать: у правила,
где заданы оба поля, это замена головы пути, а в обратном порядке дописанная
голова закроет собой ту, которую надо снять.

> **Ловушка. Шаг 2 обязан искать разделитель вне подстановки.** `[HttpGet("{id?}")]`
> — законная и частая форма шаблона ASP.NET. Поиск первого `?` в строке обрезает
> маршрут до `api/x/{id`, четвёртый шаг такую подстановку уже не распознаёт,
> и получается ключ, который выглядит правдоподобно и не совпадает ни с чем.
> Скобки считаются, разделитель берётся на нулевой глубине.

> **Ловушка. Префикс сравнивается по сегментам, а не по подстроке.** `pathRewrite`
> — регулярное выражение, и `^/pm` срезало бы `/pmloadrequests/x` до выдуманного
> `/loadrequests/x`. У PM.Front в прокси существуют оба контекста — и `/pm/api`,
> и `/pm/pmloadrequests`, — то есть обе формы в репозитории есть, а различает их
> только граница сегмента. Регистр при сравнении складывается **с обеих сторон**:
> сложить только у пути значило бы сломать сравнение тому, кто написал `/PM`
> в конфигурации.

> **Ловушка. `add_prefix` не дублируется.** Литерал, уже написанный с префиксом,
> дал бы `/admin/admin/api/x` — сразу две находки, «вызов без эндпоинта» и «эндпоинт
> без вызывающего», и обе выглядели бы дефектом. Так же ведёт себя боевой декоратор
> `SetApiUrl`: базу, уже присутствующую в URL, он не добавляет.

> **Ловушка. Ведущая подстановка шаблона — это база, а не сегмент.**
> `` `${this.baseUrl}/saveAlternative` `` даёт `{}/savealternative`, что не совпадёт
> ни с чем. Подстановка **в начале** строки обрабатывается не здесь: значение базы
> разрешает F07 и передаёт сюда уже склеенный литерал. Если разрешить не удалось —
> вызов невосстановлен, и это отдельная категория, а не мусорный ключ.

> **Ловушка. Шаг 6 идёт последним.** Если привести к нижнему регистру раньше шага 3,
> сравнение префикса `/PM` с `strip_prefix: "/pm"` перестанет работать у того, кто
> написал префикс с заглавной.

**Критерии приёмки**
- таблица из шести шагов покрыта тестами по одному случаю на строку **и** двумя
  комбинированными;
- `almost_equal` истинна для `api/ml/structure/getforupdate` и
  `api/ml/structure/getforupdate/{}`, ложна для разных сегментов, для разных
  глаголов и различителей и **ложна для совпавших целиком ключей**: «почти»
  исключает «точно», иначе реализация, перебирающая кандидатов через
  `almost_equal` до проверки на равенство, сложит настоящие связи в корзину
  «почти совпало» и молча занизит их число;
- `discriminator` кладётся в ключ **как написан**, без приведения регистра: дальше
  он сравнивается с `ref` записи реестра, а бизнес-слой сравнивает `ref` точным
  равенством (`business.resolve._key`);
- `normalize_route` — чистая функция: одинаковый вход даёт одинаковый выход, глобального
  состояния нет (проверяется вызовом дважды в перемешанном порядке);
- пустая строка и одиночный `/` дают `""`, а не падение.

**Проверка**
```bash
uv run pytest tests/test_route.py -q
```

## F04 — `web/parser.py`: TypeScript → `FileParseResult`

**Цель:** разбор одного `.ts` в структуру, из которой строятся символы.

**Создать:** `docpipe/web/__init__.py`, `docpipe/web/parser.py`,
`docpipe/web/queries/{declarations,members}.scm`, `tests/test_web_parser.py`
**Изменить:** `pyproject.toml`, `deploy/pyproject.toml`, `deploy/OFFLINE.md`,
оба `uv.lock`

> **Зависимость добавляется в ДВА `pyproject.toml`.** Состав поставки сверяется
> с составом разработки тестом `test_runtime_dependencies_match_the_repository`:
> забытая в `deploy/` зависимость — это отказ на целевой машине закрытого контура,
> и ловится он здесь, а не там. Заодно строка дописывается в таблицу пакетов
> `deploy/OFFLINE.md`: грамматика — расширение на C, и на зеркале без колёс
> её придётся собирать.

**Зачем.** Аналог `dotnet/parser.py`. Ошибка здесь не видна: файл разберётся, символы
появятся, но частью — и отчёт будет выглядеть исправным.

**Спецификация**

Версия API tree-sitter — **0.25+**: `Query(LANG, src)` + `QueryCursor(q).captures(node)`,
возвращающий `dict[str, list[Node]]`. Старые формы не работают.

Извлекается: классы, интерфейсы, перечисления, экспортируемые функции и константы;
декораторы, модификаторы, `extends`/`implements`, члены (методы, свойства, параметры
конструктора), JSDoc, `SourceSpan`, `parse_errors`.

**Импорты здесь НЕ извлекаются** — они нужны только резолву и заводятся в F05
вместе с ним. Это значит, что F05 правит и `parser.py` тоже: разбор — его дело,
а `resolve.py` занимается разрешением, а не чтением файлов второй раз.

Классы, интерфейсы и перечисления берутся **независимо от `export`**, функции
и константы — **только экспортируемые**, и второе выражается структурой запроса
(`(export_statement declaration: (lexical_declaration) @declaration)`), а не
проверкой в Python: иначе `lexical_declaration` поймает каждое `const` внутри
каждого тела метода.

Из декоратора берутся имя, позиционные аргументы и **литеральные** поля объекта.
`templateUrl` нужен шагу 2 (хэш шаблона входит в `impl_hash`), `standalone`
и `selector` — правилам, `@Action(LoadInnerDebts)` — цепочке NGXS. Поле
со значением-выражением не берётся вовсе: «поле есть, но неизвестно» и «поля нет»
обязаны различаться.

> **Ловушка. Декоратор — сосед объявления, а не потомок, и это инверсия правила C#.**
> У экспортируемого класса `decorator` лежит в `export_statement` **рядом**
> с `class_declaration`; у неэкспортируемого — внутри `class_declaration`. В Angular
> экспортируется всё, что имеет декоратор, поэтому реализация, перенесённая с .NET
> буквально, не классифицирует **ни одного** компонента и сервиса — при нулевом числе
> ошибок разбора. Собирать декораторы обязательно с обоих уровней.

> **Ловушка. Списки захватов `QueryCursor.captures()` не выровнены между собой.**
> На одном запросе `@method` пришёл в порядке `[innerDebtsSnapshot, get, post, …]`,
> а `@call` — в другом; `zip` даёт пары, которых в коде нет. Брать один ключ
> и спускаться от узла, а не сшивать списки.

> **Ловушка. Шаблонная строка разбирается на `string_fragment` и `template_substitution`.**
> Это не мешает, а помогает: «подстановка в начале строки — база, а не параметр пути» —
> проверяемое свойство дерева, а не эвристика.

> **Ловушка. JSDoc — сосед `export_statement`, а не объявления.** Комментарий стои́т
> перед словом `export`, то есть снаружи узла, от которого идёт поиск. Обход
> предыдущих соседей `class_declaration` найдёт JSDoc **только у неэкспортируемого**
> класса, а у экспортируемого не найдёт — и разница будет выглядеть как случайность
> в данных, а не как дефект. Лечится одним понятием: соседей ищем у «якоря» —
> самого объявления либо охватывающего его `export_statement`. Тот же якорь
> отдаёт и декораторы.

> **Ловушка. Три клаузы наследования устроены по-разному.**
> ```
> extends_clause        value: Base, type_arguments: <T>   ← двумя ПОЛЯМИ
> implements_clause     generic_type Holder<T>, type_identifier Other
> extends_type_clause   generic_type First<A>,  type_identifier Second
> ```
> У `extends` класса дженерик лежит отдельным узлом, у остальных — внутри типа.
> Единый обход по потомкам отдаст `Base` вместо `Base<T>` **только** у `extends`,
> и правило по базовому типу с дженериком сработает на `implements`, но не
> на `extends`. Половина набора работает, половина нет, причины не видно.

> **Предел нормализации `decl_hash`.** Схлопывание пробелов делает хэш нечувствительным
> к отступам и переносам, но не к запятой: `prettier`, разбивая длинный список
> параметров на строки, дописывает висящую запятую, и хэш меняется. Это то же
> свойство, что у .NET с `dotnet format`; чинить его нечем, кроме собственного
> форматтера, и переписывать документ раз в жизни файла дешевле.

**Критерии приёмки**
- на фикстуре разобраны оба класса с декораторами — и экспортируемый, и нет
  (тест утверждает **оба**, иначе ловушка не проверена);
- функциональный интерцептор (`export const X: HttpInterceptorFn = …`) распознан как
  символ, а не пропущен: в АС CF так объявлены интерцепторы и guard'ы;
- `parse_errors > 0` при синтаксически битом файле, и такой файл не роняет прогон;
- `impl_hash` не включает номера строк и пути — переформатирование файла его не меняет;
- разбор одного файла дважды даёт идентичный результат.

**Проверка**
```bash
uv run pytest tests/test_web_parser.py -q
```

## F05 — `web/resolve.py`: импорты, алиасы, бочки, замыкание

**Цель:** превратить `import { X } from '@shared/y'` в путь файла, а `extends Base` —
в резолвнутое имя.

**Создать:** `docpipe/web/resolve.py`, `tests/test_web_resolve.py`
**Изменить:** `docpipe/web/parser.py`, `docpipe/model.py` — извлечение импортов
и переэкспортов входит сюда, а не в F04: разбор одного файла делает парсер
(результат кэшируется), резолв только разрешает уже разобранное. Второй проход
по файлам в `resolve.py` разошёлся бы с кэшем и удвоил чтение дерева.

**Зачем.** Без алиасов `tsconfig` **ни один** импорт вида `@shared/…` не разрешится.
Ловушка усугубляется тем, что `extends` при этом сохранится сырой строкой и правила
по `base_type` **сработают** — то есть часть набора будет работать, а часть нет,
без видимой причины.

**Спецификация**

1. относительные импорты + правила разрешения: `.ts`, `/index.ts`;
2. алиасы из `tsconfig.json` (`compilerOptions.paths`), включая наследование
   `extends` между `tsconfig*.json`;
3. бочки: `index.ts` с `export * from './x'` — переэкспорт, из-за которого имя
   импортируется не оттуда, где объявлено;
4. замыкание наследования цепочкой — тем же способом, что в `dotnet/resolve.py`.

**Резолв идёт по файлам, а не по пространствам имён,** и это меняет устройство
модуля целиком. На .NET имя ищется по namespace и usings, поэтому переход
«базовый тип → символ» требует арности (один FQN — несколько типов). В TypeScript
единица изоляции — файл: пара «файл + имя» уникальна сама по себе, и арность
в переходе не нужна вовсе.

Отсюда же **FQN считается от пути файла**, а не от каталога: два файла одного
каталога законно объявляют одноимённый `Helper`, и FQN по каталогу склеил бы их
в один символ — один из двух исчез бы из документации молча.

> **Ловушка. `tsconfig.json` — это НЕ JSON.** И `ng new`, и `nx` генерируют его
> с комментариями (`/* To learn more about this file see: … */`), а руками туда
> дописывают `//` и висящие запятые. `json.loads` на таком файле бросает
> исключение — то есть не читается **ни один боевой `tsconfig`**, а вместе с ним
> не разрешается ни один импорт вида `@shared/…`. Комментарии вырезаются сканером,
> а не регулярным выражением: `//` внутри строки (`"url": "http://host"`)
> регулярное выражение приняло бы за начало комментария.

> **Ловушка. `paths` дочернего конфига замещает родительский целиком.** Так
> устроен TypeScript: `extends` сливает `compilerOptions` по ключам, и ключ
> `paths` заменяется, а не дополняется. Слияние выглядит логичнее и даёт набор
> алиасов, которого у компилятора нет, — то есть резолв, расходящийся со сборкой.

> **Ловушка. Побеждает шаблон алиаса с самым длинным префиксом до `*`.** При
> объявленных `@shared` и `@shared/*` импорт `@shared/x` обязан пойти по второму.
> Выбор «первый совпавший» даёт резолв, зависящий от порядка ключей в файле.

> **Ловушка. Алиас может указывать в `node_modules`.** В ML это
> `"exceljs": ["../node_modules/exceljs/dist/exceljs.bare"]`. Резолв обязан такие цели
> помечать внешними и **не** тянуть их в обход: иначе обход, из которого `node_modules`
> вырезали, вернётся туда через алиас. Путь у такой цели не возвращается вовсе —
> так её нельзя втянуть в обход даже случайно.

**Критерии приёмки**
- импорт через алиас, через бочку и относительный резолвятся на фикстуре;
- нерезолвнутое имя сохраняется сырым (как `base_types_raw` на .NET), а не теряется;
- замыкание считается транзитивно и не зацикливается на `A extends B extends A`;
- алиас в `node_modules` помечен внешним, **и файл цели в фикстуре существует** —
  иначе проверка проходит просто потому, что резолвить нечего;
- `tsconfig` с комментариями и висящими запятыми читается, а `//` внутри строки
  комментарием не считается;
- собственное объявление файла перекрывает импортированное имя;
- переименование при импорте (`import { Base as Api }`) сохраняет **оба** имени:
  под одним имя видно здесь, под другим объявлено в источнике;
- два одноимённых класса в одном каталоге дают **разные** FQN;
- порядок входных файлов на индекс не влияет.

**Проверка**
```bash
uv run pytest tests/test_web_resolve.py -q
```

## F06 — `web/modules.py`: что такое модуль на фронте

**Цель:** список модулей с идентификаторами, устойчивыми к переименованию проектов.

**Создать:** `docpipe/web/modules.py`, `tests/test_web_modules.py`

**Спецификация**

Порядок определения, сверху вниз, первое найденное выигрывает:

1. `angular.json` → каждый элемент `projects` даёт модуль; `root`/`sourceRoot` задают
   его границы (в ML `root: ""`, то есть модуль — весь workspace);
2. `nx.json` рядом с `apps/*/project.json` и `libs/*/project.json` → каждый
   `project.json` даёт модуль;
3. `package.json` вне корня — модуль, если ни того, ни другого нет;
4. иначе — корень репозитория одним модулем.

Правила применяются **по месту, а не глобально**: `angular.json` в корне не отменяет
nx-проекта в соседнем каталоге. Глобальное «первое сработавшее» схлопнуло бы
многопроектный репозиторий в один модуль.

**Ключ модуля — каталог-граница, а не файл объявления.** На .NET файл проекта
и модуль всегда один к одному, поэтому ключом служит путь `.csproj`. На фронте
один многопроектный `angular.json` объявляет несколько модулей, и ключ по файлу
склеил бы их в один — вместе с символами, потому что ключ модуля входит в ключ
символа. Граница — `sourceRoot`, при его отсутствии `root`; `id` = `module:<граница>`.
Имена проектов при этом не уникальны, и ключ по имени тоже не годится (на .NET
это уже стоило отдельного разбора — в ABP 39 повторов).

Файл принадлежит модулю с **самой длинной** подходящей границей: у workspace
с `sourceRoot: "src"` и вложенным nx-проектом файл подходит обоим.

В модуль складываются: версия `@angular/core` и `typescript` (в `target_frameworks`
— это ответ на тот же вопрос, что `net8.0` у .NET), имена всех зависимостей
(в `package_references` — по ним видно наличие `@ngxs/store` либо `@ngrx/store`),
путь `proxy.conf*` и путь `tsconfig`, от которого берутся алиасы. Последние два
в манифест не идут: они нужны разбору и человеку, заполняющему `url_rewrite`.

> **Ловушка. `*nx.json` в pathspec и в glob ловит любой файл, чьё имя кончается
> на `nx.json`.** На разведке первой строкой раздела встал
> `DuplicatedRecordsBugEvanx.json` из тестовых данных .NET. Сравнивать имя файла
> целиком.

> **Ловушка. `sourceRoot` в `project.json` задан относительно корня nx-workspace,
> а не относительно проекта.** Склейка с каталогом проекта даёт
> `apps/widget/apps/widget/src` — путь правдоподобный и несуществующий, а файлы
> модуля остаются ничьими и в манифест не попадают вовсе. Границей nx-проекта
> берётся каталог самого `project.json`.

> **Ловушка. `root: ""` — это весь репозиторий.** В ML именно так, и по `root`
> модулем оказался бы репозиторий целиком, вместе с шестью соседними фронтами
> и всем бэкендом. Поэтому `sourceRoot` выигрывает у `root`.

> **Битый файл объявления не роняет прогон.** `angular.json` с комментарием —
> норма (это JSONC, как и `tsconfig`), а отказ на одном файле стоил бы всего
> прогона.

**Критерии приёмки**

## F07 — `web/calls.py`: HTTP-вызовы, константы, обращения к реестру

**Цель:** из тела метода получить `WebCall` с маршрутом и честной оценкой уверенности.

**Создать:** `docpipe/web/calls.py`, `tests/test_web_calls.py`

**Зачем.** Это ядро требования «связь фронт↔бэк». Замер на боевом модуле: 79 вызовов,
26 литералов, 27 шаблонов, 21 «переменная».

**Спецификация**

**Задача делится на два шага, и это не косметика.** `extract_calls` записывает
**факты** о вызове и от конфигурации не зависит — его результат можно кэшировать.
`build_calls` интерпретирует их с учётом `web.url_rewrite` и `web.registry_calls`.
Иначе смена одной строки в `docpipe.yaml` требовала бы перечитать все исходники,
а кэш отдавал бы ключи, собранные по прежней настройке, — молча.

Из того же деления следует, что `RawCall.url` хранится **вместе с query-строкой**:
различитель обращения к реестру живёт именно там, а нормализация маршрута его
отбрасывает. Отбросить его при разборе — значит склеить все справочники в один
ключ ещё до того, как конфигурация успеет что-то сказать.

Вызов считается HTTP-вызовом только по **получателю**: `this.http`, `httpClient`,
`_http`, `this.httpService` и т. п. — список в константе модуля. Глагол берётся
из имени метода; `request(method, url)` не поддержан намеренно — первый аргумент
там не URL, и обработка «через раз» дала бы вызовы с маршрутом `get`.

> **Ловушка, стоившая целого прогона разведки.** Счётчик `.get(`/`.post(` без получателя
> меряет `Map.get`, `form.get('search')`, `headers.get(…)`, `queryParams.get(…)`.
> На боевом модуле таких 327 против 79 настоящих. Отношение «литералов ко всем
> вызовам», посчитанное по ним, бессмысленно, а выглядит убедительно.

Формы первого аргумента и `confidence`:

| Форма | `confidence` | Что делает реализация |
|---|---|---|
| строковый литерал | `high` | берёт как есть |
| шаблонная строка | `high` | фрагменты + `{}` вместо подстановок |
| `` `${this.baseUrl}/x` `` | `high`, если поле разрешено | подставляет литерал поля |
| `constUrl` — константа модуля | `high`, если разрешена | подставляет литерал |
| конкатенация `'api/x/' + id` | `medium` | литеральная часть + `{}` |
| переменная-параметр, поле без литерала | — | **невосстановлен**, с файлом и строкой |

**Разрешение констант обязательно, а не «потом».** Две формы:

```ts
export const auditUrl = '/integration/log/AuditJ';            // 10 вызовов одного сервиса
private readonly baseUrl: string = '/api/ml/debtsconsgroup';  // ещё шесть
```

Без них отчёт назовёт невосстановленными 27 % вызовов там, где настоящая дыра —
единицы, и доверие к числу пропадёт раньше, чем его успеют починить. Разрешаются только
инициализаторы-литералы в том же файле; всё остальное — невосстановлено.

> **Ловушка. Таблица литеральных полей — по классу, а не по файлу.** Два сервиса
> в одном файле законно объявляют `baseUrl` с разными значениями, и общая таблица
> подставит в вызов чужую базу — молча и правдоподобно. Константы уровня модуля,
> наоборот, общие для файла.

> **Ловушка. Конкатенация обходится слева направо.** `a + b + c` — это
> `(a + b) + c`, и обход дерева стеком без внимания к порядку даёт `{}api/x/`
> вместо `api/x/{}`: ключ, который не совпадёт ни с чем, но выглядит настоящим.

**Обращения к реестру.** Для маршрутов из `web.registry_calls` дополнительно
разбирается место различителя:

```ts
this.http.post('api/items/query', { listInnerName: 'OkkChain', … });  // in: body
`api/items?listInnerName=models`                                       // in: query
```

Результат кладётся в `RouteKey.discriminator`. Если маршрут в списке, а различитель
литералом не найден — вызов помечается `registry_unresolved`: это состояние, а не
ошибка, и оно печатается числом.

**Критерии приёмки**
- шесть форм таблицы разобраны на фикстуре, каждая своим тестом;
- `Map.get` и `form.get` в результат **не** попадают (отдельный тест с обоими);
- `auditUrl` и `this.baseUrl` разрешены; вызов с URL из параметра — невосстановлен
  и назван с файлом и строкой;
- обе формы обращения к реестру дают разные `RouteKey` при одном маршруте;
- сумма «восстановлено + невосстановлено» равна общему числу вызовов — проверяется
  тестом, потому что именно это делает число честным.

**Проверка**
```bash
uv run pytest tests/test_web_calls.py -q
```

## F08 — `web/routes.py`: дерево роутов и якорь страницы

**Цель:** сопоставить компоненту его полный маршрут.

**Создать:** `docpipe/web/routes.py`, `tests/test_web_routes.py`

**Спецификация**

Собираются три формы объявления ветки:

1. `component: X` — лист;
2. `loadComponent: () => import('./x').then(m => m.X)` и короткая форма `() => X`;
3. `children: [...importedArray]` — **spread импортированного массива**;
4. `loadChildren: () => import('./x.routes').then(m => m.ROUTES)`.

> **Ловушка. Форма 3 — не экзотика, а основная у АС CF.** В ML `loadChildren` — ноль,
> `RouterModule.forRoot/forChild` — ноль, а дерево собрано спредами из `routesPath/*.ts`.
> Разбор одного `app.routes.ts` даёт два пути из двадцати шести, и молча: ошибок разбора
> нет, узлы просто не появляются. Реализация обязана уметь **обе** межфайловые формы.

Полный путь склеивается из сегментов родителей; `path: '**'` и `redirectTo` страницами
не считаются. Компонент, до которого нельзя дойти по таблице, — не страница, а
переиспользуемый компонент. Компонент, до которого дойти можно, но путь собрать
не удалось, — `route_unresolved`, именованное число.

**Корневой считается таблица, на которую никто не ссылается** — ни спредом,
ни `loadChildren`. Опознавать корень по `provideRouter`/`RouterModule.forRoot`
нельзя: в боевом модуле их нет **вовсе**, а дерево при этом собрано. Без этого
правила каждая дочерняя таблица становится ещё и корнем, и один и тот же экран
появляется дважды: как `/forecast/daily` и как `/daily`.

**Таблица опознаётся по аннотации типа** (`: Routes`), а не по содержимому:
«массив объектов с ключом `path`» поймает любой конфиг меню, а таких в модуле
больше, чем таблиц роутов.

> **Ловушка. `() => import('./x').then(m => m.ROUTES)` — это ДВЕ стрелки.**
> Тело внешней — `import(…).then(…)`, у которого свойство называется `then`.
> Реализация, берущая первое попавшееся свойство при обходе, подставит `then`
> и в имя таблицы, и в имя компонента: правдоподобно и целиком неверно
> (`/models/loader/quiz` → компонент `then`). Брать надо тело **внутренней**
> стрелки.

> **`:id` нормализуется в `docpipe/route.py`, и туда пришлось дописать шаг.**
> Параметр Angular отличается от подстановки ASP.NET, а двоеточие встречается
> и внутри шаблона `{id:guid}` — различить их можно только по началу сегмента.
> Сделано посегментно, после замены фигурных форм.

**Критерии приёмки**
- на фикстуре собраны пути через спред **и** через `loadChildren`;
- `:id` превращается в `{}` через `docpipe/route.py`, а не своей копией;
- `**` и `redirectTo` не порождают страниц;
- ветка, собранная выражением, даёт `route_unresolved`, а не отсутствие узла.

**Проверка**
```bash
uv run pytest tests/test_web_routes.py -q
```

## F09 — сторона .NET: проверка склейки маршрутов

**Цель:** убедиться, что существующий `dotnet/endpoints.py` переживает боевые формы,
и назвать вслух то, чего он не разбирает.

**Изменить:** `tests/fixtures/WildSolution/**`, `tests/test_endpoints.py`,
при необходимости `docpipe/dotnet/endpoints.py`

**Зачем.** Разведка показала на боевом бэке: `[Route]` — 433, токенов `[controller]`
и `[action]` — **ноль**, `[HttpGet("…")]` с аргументом — 47, пустых `[HttpGet]` — 556,
`MapControllerRoute` — 1.

Чтение кода: `_member_template` уже берёт аргумент `Http*`, а при его отсутствии —
отдельный `[Route]` того же члена; `_combine` уже обрабатывает абсолютные шаблоны
`/` и `~/`. То есть **преобладающая форма уже поддержана**, и задача — не переписать,
а закрепить фикстурой и назвать пробел.

**Спецификация**

1. В `WildSolution` добавить контроллер с: пустым `[HttpGet]` + `[Route("state/byclient")]`
   на методе, вторым методом с `[HttpPost("insert")]`, третьим с абсолютным `~/…`,
   и четвёртым — пустым `[HttpGet]` **без** `[Route]` (маршрут равен маршруту класса).
2. Тест утверждает четыре получившихся маршрута целиком, а не по одному сегменту.
3. Конвенциональная маршрутизация (`MapControllerRoute`) и minimal API не разбираются
   — это записано в docstring модуля и остаётся так. Но `web link` (F13) обязан считать
   такие контроллеры отдельной категорией: иначе их вызовы попадут в «эндпоинт
   не найден» и будут выглядеть дефектом фронта.

**Признак конвенционального контроллера считается по манифесту**, а не по символам:
узел вида `controller`, у которого эндпоинтов **нет вовсе** либо есть эндпоинт
с **пустым** маршрутом. Оба случая означают одно — URL из атрибутов не собирается.
Считать это на стороне символов нельзя: `web/link.py` не имеет права импортировать
`docpipe/dotnet/**`, а манифест ему и так на входе.

**Критерии приёмки**
- четыре маршрута совпадают с ожидаемыми строками, и проверяются они **целиком**,
  а не по сегменту: ошибка склейки даёт правдоподобный путь, отличающийся одним
  куском, и посегментная проверка её пропустит;
- поведение `dotnet/endpoints.py` **не изменилось** (проверено: все четыре формы
  собираются существующим кодом; если правка потребовалась — это находка,
  и её надо дописать в план);
- контроллер без атрибутов маршрутизации даёт ноль эндпоинтов, а контроллер
  без `[Route]` на классе — эндпоинт с пустым маршрутом: оба признака проверены
  тестом, потому что по ним F13 и будет считать категорию.

**Проверка**
```bash
uv run pytest tests/test_endpoints.py tests/test_scan_e2e.py -q
```

## F10 — модели и схема 2.0

**Цель:** одна схема на два языка, без вранья в именах полей.

**Изменить:** `docpipe/model.py`, `schema/doc-tree.schema.json`, `tests/golden/doc-tree.json`,
`docs/manifest.md`, `README.md`, `docpipe/emit.py`, `docpipe/tree.py`, `docpipe/cli.py`,
`docpipe/dotnet/csproj.py`, `docpipe/materialize/build.py`, тесты, конструирующие `Module`

Золотой манифест перегенерируется командой из «Проверки»; сидкар
`tests/golden/doc-tree.run.json` в репозиторий не входит — его надо удалить.

**Спецификация**

1. `Module.csproj` → `Module.project_file`. Добавляется `Module.lang: Literal["cs","ts"]`
   — **обязательное, без значения по умолчанию**. Умолчание `"cs"` означало бы, что
   сборщик модулей фронта, забывший его выставить, отдаёт манифест, в котором все
   модули объявлены .NET-овскими, и заметить это нечем: остальные поля у такого
   модуля правильные.
2. `Symbol` переиспользуется как есть; отображение TypeScript на его поля:
   `namespace` — путь каталога модуля, `type_kind` расширяется **синтаксическими**
   видами, которых у C# нет: `function` и `const` (`interface` и `enum` уже есть).
3. Новые модели: `WebCall` (файл, строка, `RouteKey`, `confidence`, `via_action`),
   `RouteEntry` (путь, компонент, `route_unresolved`).
4. `schema_version` → `"2.0"`.

> **`component`, `service`, `guard` и прочее — это `DocNode.kind`, а не `type_kind`.**
> Первое — результат работы правил (`rules/web.yaml`, поле `kind:`), второе —
> форма объявления в исходнике. Сложить их в одно поле значит поручить решение
> классификации парсеру, то есть тому, кто правил не читает; заодно исчезнет
> разница между «в коде объявлен класс» и «мы решили считать его компонентом»,
> а на ней стои́т весь отчёт о нерешённых символах.

> **Ловушка. Это разовый сдвиг байтов всего .NET-манифеста.** Золотой файл
> перегенерируется **одной** правкой и в **отдельном** коммите, где нет ничего другого:
> иначе в диффе не отличить переименование поля от изменения поведения. Альтернатива —
> оставить `csproj` у TypeScript-модуля навсегда, и это имя будет врать в каждом отчёте.

> **`module_csproj` во front matter документа этой задачей НЕ переименовывается.**
> Ключ живёт в генерируемом блоке шага 2 и врёт ровно так же, как врало поле модели,
> — но его переименование перегенерирует **все** документы, включая боевые. Решение
> принимается в F14, когда появятся web-документы и цена станет очевидной;
> здесь важно, что вопрос назван, а не то, как он решён.

**Критерии приёмки**
- `docpipe schema --out` даёт схему с `project_file` и `lang`, `docpipe validate`
  на золотом манифесте проходит;
- дифф золотого файла содержит **только** переименование поля, добавление `lang`
  и `schema_version` — ни одного изменённого узла;
- `docs/manifest.md` описывает оба значения `lang`;
- `Module` без `lang` не создаётся (тест на `ValidationError`);
- `WebCall` переживает круг через JSON вместе с вложенным `RouteKey`, и лишнее
  поле **внутри ключа** тоже отвергается: `extra="forbid"` обязан действовать
  на всю глубину, иначе опечатка в имени различителя пройдёт молча.

**Проверка**
```bash
uv run docpipe schema --out schema/doc-tree.schema.json && git diff --stat schema/
uv run pytest tests/test_model.py tests/test_scan_e2e.py -q
```

## F13 — `docpipe web link`: сведение двух манифестов

Пять категорий, и только последняя — дефект:

|---|---|
| связь найдена точно | — |
| **почти совпало**: ключи различаются только числом `{}` | нет, инвентарь |
| эндпоинт без вызывающего | нет: его может звать другая система, мобильный клиент, интеграция |
| вызов без эндпоинта | нет по умолчанию: часть бэка на конвенциональной маршрутизации (F09) |
| один ключ объявлен двумя узлами бэкенда | **да**: это коллизия маршрутов, ломающая приложение |

> **Ловушка. Находка роняет прогон, только если её может починить автор документа.**
> Все категории печатаются всегда, кода возврата не меняют, пока не названы
> в `--fail-on`. Линт, красный с первого дня, выключат на второй.

> **Ловушка. Модуль без записи в `url_rewrite` — не то же самое, что модуль
> с пустым `strip_prefix`.** Первый печатается как ненастроенный: иначе забытая
> настройка выглядит как исправная связь, а расходиться будет ровно на префиксе.

**Критерии приёмки**
- на фикстуре найдены связи по литералу, по шаблону и по разрешённой константе;
- «почти совпало» ловит пару `…/getforupdate` ↔ `…/getforupdate/{}`;
- обращения к реестру не склеиваются: два вызова с разным `listInnerName` дают две
  связи;
- ненастроенный модуль назван;
- вывод детерминирован при перемешанном порядке входов.

**Проверка**
```bash
uv run pytest tests/test_web_link.py -q
```

## F14 — шаг 2 для web

**Цель:** документы фронта той же машиной, что и .NET.

**Создать:** `templates/web/{page,component,api-service,state}.md`
**Изменить:** `docpipe/materialize/build.py` (только в части `impl_hash` шаблона)

**Спецификация**

`doc_path` строится существующим механизмом (`docs_root` + `modules_dir` +
`doc_layout`). В `impl_hash` компонента входит **хэш содержимого `.html`-шаблона**;
`.scss` не входит. Путь шаблона попадает в узел — агент шага 3 его прочитает.

В генерируемый блок страницы добавляются: маршрут, вызываемые эндпоинты (из F13),
экшены стора.

> **Ловушка. Подсказки в шаблонах — только HTML-комментарии.** `is_section_empty` —
> самая дорогая функция шага 2: ошибка в сторону «не пусто» заставит агента счесть всё
> дерево написанным.

**Критерии приёмки**
- `materialize` на web-манифесте создаёт документы, `docs status` показывает `write`;
- правка `.html` переводит документ в `stale`, правка `.scss` — нет;
- `assemble(parse_document(t)) == t` байт в байт на новых шаблонах.

**Проверка**
```bash
uv run docpipe web scan --root tests/fixtures/WebWorkspace --out /tmp/web.json
uv run docpipe materialize /tmp/web.json --root /tmp/webdocs
uv run docpipe docs status /tmp/web.json --root /tmp/webdocs
uv run pytest tests/test_materialize_web.py -q
```

## F15 — бизнес-слой: якорь `page`

**Цель:** бизнес-документ ссылается на экран, а не на компонент.

**Изменить:** `docpipe/business/resolve.py`, `docpipe/business/lint.py`,
`docs/business-layer.md`

**Спецификация**

Новый вид якоря `page` с ключом-маршрутом. Ступень разрешения читает web-манифест.
`business_hash` считается по разрешённым фактам и **не содержит имён компонентов** —
переименование `LoaderQuizComponent` хэш не меняет, смена маршрута меняет.

Обращения к реестру связывают бизнес-документ со списком напрямую: вид `list` уже есть
в `REGISTRY_KIND`, новая пара в мост не нужна — нужен путь «страница → список», и он
идёт через `WebCall.discriminator`.

**Критерии приёмки**
- якорь `page: "/models/loader/quiz"` разрешается в узел web-манифеста;
- переименование компонента `business_hash` не меняет; смена маршрута — меняет;
- покрытие страниц бизнес-документами печатается числом и не роняет прогон.

**Проверка**
```bash
uv run pytest tests/test_business_web.py -q
```

|---|---|

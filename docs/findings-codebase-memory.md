# Разведка: codebase-memory-mcp как поставщик разбора

Дата: 19.08.2026. Версия `v0.10.8` (собрана 19.08.2026), лицензия MIT,
[DeusData/codebase-memory-mcp](https://github.com/DeusData/codebase-memory-mcp).
Прогон на четырёх репозиториях из `docspipe-examples/examples`.

Вопрос разведки один: закрывает ли этот движок **разбор**, чтобы нам осталась
платформенная часть — реестры, точки входа, швы. Ответ: закрывает наполовину,
и граница проходит не там, где обещает документация.

---

## Ограничения среды: пройдены

Это первый фильтр, и предыдущий кандидат (repowise) на нём отвалился.

| Требование | Факт |
|---|---|
| Лицензия | MIT |
| Установка | один файл, `ELF 64-bit, statically linked, stripped`, 293 МБ распакованный |
| Динамические зависимости | **ноль** (`ldd`: «не является динамическим исполняемым файлом») |
| Рантайм, Docker, ключ API | не требуются |
| Исходящие соединения за прогон | **ноль** (`ss -tnp` во время индексации четырёх репозиториев) |
| Сборка из исходников | C/C++ и zlib, `scripts/build.sh` |

Статическая линковка означает, что в контур несётся **один файл** и версия glibc
на целевой машине роли не играет. Если пронос бинаря невозможен по регламенту,
остаётся сборка из исходников: репозиторий на C, зависимости вендорены внутрь.

**Эмбеддер выключается режимом.** `--mode fast` — «filtered files, no
similarity/semantic»; разрешение вызовов работает во всех режимах, вектора
только в `full`/`moderate`. Все замеры ниже сделаны в `fast`, то есть без
эмбеддингов вообще.

Наблюдатель и UI выключаются: `config set auto_watch false`, `ui_enabled false`.
Каталог данных переносится через `CBM_CACHE_DIR`.

## Замеры

Режим `fast`, машина без GPU, 15,4 ГБ ОЗУ. Бюджет памяти движок берёт сам как
долю ОЗУ (`budget_mb=3861 total_ram_mb=15444 source=ram_fraction`).

| Репозиторий | Узлов | Рёбер | Время |
|---|---|---|---|
| eshoponweb | 2 558 | 6 535 | 7,9 с |
| wexflow | 23 159 | 113 034 | 17,5 с |
| squidex | 43 114 | 215 091 | 22,5 с |
| **abp** | **173 550** | **402 137** | **45,9 с** |

`abp` попадает ровно в целевой диапазон плана (100–200 тыс. узлов, 300–600 тыс.
рёбер) — и собирается за 46 секунд при бюджете 5 минут.

**Память — единственное число мимо цели.** Пик рабочего процесса на `abp` —
**6,9 ГБ** при нашем требовании ≤ 4 ГБ; после пика падает до 570 МБ, то есть
это переходный всплеск, а не рабочий уровень. На машине с 8 ГБ прогон `abp`
рискован. Ограничитель ищется в настройках, но `config list` его не показывает.

**Отсев и частичный разбор объявляются в ответе.** `not_indexed_files` с
причиной на каждый файл (`ignored-suffix`, `skip-list`, `fast-pattern`),
`parse_partial` с диапазонами строк, где конструкции могли потеряться. Это
ровно наше правило «отсев без причины запрещён», реализованное у них.

## Что движок делает хорошо

**Разрешение вызовов на C# аккуратное, ложных рёбер не наблюдалось.** Проверка
на `eshoponweb`, случай с декоратором:

```csharp
services.AddScoped<ICatalogViewModelService, CachedCatalogViewModelService>();
```

У интерфейса две реализации, и DI связывает его с `Cached…`, а не с
одноимённым `CatalogViewModelService`. Запрос всех рёбер `CALLS` в
`GetCatalogItems` дал ровно два, оба верные:

```
OnGet (Pages/Index.cshtml.cs)              → CachedCatalogViewModelService.GetCatalogItems
GetCatalogItems (Cached…Service.cs)        → CatalogViewModelService.GetCatalogItems
```

Ни одного ребра к однофамильцу. В исходниках резолвера
(`src/pipeline/lsp_resolve.h`) это заявлено прямо: «ambiguous tails return NULL
so the registry fallback stays in», «would fabricate a `CALLS` edge — so the
fallbacks stay off there». Разделение `CALLS` (цель доказана) и `USAGE` (цель
не доказана) — это наше правило Р6, реализованное на уровне вида ребра.

**Фронтовые вызовы HTTP извлекаются с нормализацией.** На `squidex`
шаблонные строки с интерполяцией сведены к маршруту с плейсхолдерами:

```
frontend/src/app/shared/services/apps.service.ts      → /api/apps/:appName/settings
frontend/src/app/shared/services/contents.service.ts  → /api/content/:appName/:schemaName/query
```

Это тот самый случай «первый аргумент — выражение», ради которого в нашем плане
заведено отдельное правило.

**Инкрементальность и поставка.** Git-детекция изменений, `detect_changes`,
артефакт `.codebase-memory/graph.db.zst` для переноса индекса без пересборки.

## Что движок не делает, и это остаётся нашим

### 1. Интерфейс не связывается с реализацией по DI

Главная находка. Движок **не читает регистрации контейнера**: грепом по
исходникам резолвера `AddScoped|AddSingleton|AddTransient|ServiceCollection`
— одно попадание, и то комментарий про FastAPI.

Следствие видно на `eshoponweb`. Цепочка обрывается на интерфейсе:

```
HandleAsync → GetTokenAsync (ApplicationCore/Interfaces/ITokenClaimsService.cs)
```

При этом `IdentityTokenClaimService.GetTokenAsync` — реализация из
`AddScoped<ITokenClaimsService, IdentityTokenClaimService>()` — не имеет
**ни одного** входящего ребра `CALLS` и с точки зрения графа не вызывается
никем.

Поведение непоследовательно: у `IEmailSender` рёбра пришли и на интерфейс,
и на реализацию (от разных вызывающих). То есть где тип получателя выводится
локально — цель настоящая; где получатель объявлен интерфейсом, ребро
останавливается на интерфейсе.

На АС CF получатель — почти всегда интерфейс, внедрённый конструктором.
Значит граф вызовов рвётся на **каждой** границе сервиса.

**Хорошая новость: сырьё для связывания в графе уже есть.** Регистрация видна
как ребро `USAGE`:

```
AddCoreServices → USAGE → EmailSender (Infrastructure/Services/EmailSender.cs)
Program.cs      → USAGE → IdentityTokenClaimService
```

То есть наша фича G04 сжимается с «написать разрешение вызовов .NET» до
«вывести ребро `binds` и переставить цель» — постобработка, а не парсер.
Плюс у нас уже есть `dotnet/di.py`, который это и делает.

### 2. Реестры, объявляющие точки входа, не связываются с кодом

Проверка на `wexflow` — репозиторий взят в примеры именно за то, что точки
входа объявлены в XML, как в АС CF:

```xml
<Workflow id="125" name="Workflow_Approval">
  <Tasks><Task id="1" name="Approval" … /></Tasks>
</Workflow>
```

Имя `Approval` диспетчеризуется в класс `Wexflow.Tasks.Approval`. В графе
**930 XML-узлов есть**, файлы проиндексированы, но ребра от workflow-XML
к классу задачи **нет ни одного**: все входящие рёбра `Approval` — структурные
`DEFINES` / `DEFINES_METHOD` плюс самоссылка.

Класс задачи выглядит недостижимым. Это ровно предсказанный планом случай
45 workflow АС CF, теперь измеренный на чужом репозитории. Общий движок этого
и не может: диалект реестра — свойство платформы, а не языка.

**Отсюда R03/R04 и G03 остаются целиком нашими.**

### 3. Эндпоинты .NET не извлекаются, и шов собирается только наполовину

На `squidex` — 257 атрибутов `[Route(` в `backend/src` и полноценный фронт
на Angular. В графе:

- `Route`-узлов всего **55**, и все — фронтовые;
- `Route`-узлов с путём внутри `backend` — **ноль**;
- у всех рёбер `HTTP_CALLS` цель пустая (`-`): маршрут есть, обработчик не найден.

То есть `HTTP_CALLS` означает «фронт зовёт такой маршрут», а не «фронт зовёт
этот метод контроллера». Вторая половина шва отсутствует, и присоединить её
изнутри движка нечем.

У нас эта половина уже сделана: разбор `[Route]`/`[HttpGet]` со сложением трёх
частей и `web link`. **G15 сводится к соединению, а не к извлечению.**

### 4. `HTTP_CALLS` даёт ложные срабатывания на регулярных выражениях

На `squidex` из 67 рёбер `HTTP_CALLS` заметная часть — литералы регулярок
из минифицированного JS, принятые за маршруты: `/bull/g`, `/tag/g`,
`/punctuation/g`, `/<self>/g`. Цель у них пустая.

Само по себе не смертельно (мусор виден и отфильтровывается по цели), но
показывает: извлечение маршрутов эвристическое, и наш отчёт о неполноте (G08)
обязан считать такие рёбра отдельной категорией, а не принимать на веру.

### 5. Узлов данных нет как понятия

В словаре узлов (`Project`, `Package`, `Folder`, `File`, `Module`, `Class`,
`Function`, `Method`, `Interface`, `Enum`, `Type`, `Route`, `Resource`)
таблицы, представления и процедуры отсутствуют. Ребро `WRITES` — про запись
в поле, не в базу. G05, G05b, G05c остаются нашими без изменений.

### 6. Граф read-only, своих узлов не добавить

`query_graph` — читающее подмножество openCypher (`MATCH`, `WHERE`, `RETURN`,
агрегаты). Мутаций нет, схему не расширить.

Это не блокер, но определяет архитектуру: **их граф — источник, наш индекс
собирается рядом**, а не поверх. Совпадает с уже существующей у нас границей
L1 → L2.

## Интерфейс интеграции

Важное практическое открытие: **MCP-протокол не обязателен.**

```
codebase-memory-mcp cli [--json] <tool> [args]   # один тул, затем выход
codebase-memory-mcp daemon start                 # тёплый демон, снимает старт с каждой команды
```

То есть движок вызывается из Python как подпроцесс с JSON на выходе — как
`git`, а не как сервис. Три пути получения данных, все рабочие:

1. `cli query_graph --project P --query "<Cypher>" --json` — точечные выборки;
2. артефакт `.codebase-memory/graph.db.zst` — снимок SQLite, переносимый;
3. MCP-сервер — когда спрашивает агент, а не наш пайплайн.

Для сборки индекса подходит первый: детерминированный, без демона, без сети.

Отдельно: `--tool-profile=analysis|scout` сужает набор тулов, а `--mode
cross-repo-intelligence --target-projects` заявлен как сведение `Route`
и каналов между проектами — проверить, чинит ли он шов, когда фронт и бэк
проиндексированы **разными** проектами (на `squidex` они в одном).

## Вывод

**Разбор общего вида забираем.** Символы, вызовы внутри языка, импорты,
наследование, реализация интерфейсов, инкрементальность — это дешевле и лучше,
чем мы напишем, и проходит ограничения среды.

**Платформенный слой остаётся наш целиком, и он же — вся ценность:**

| Наше | Почему движок не может |
|---|---|
| R01–R04 разведка и нормализованный реестр | диалект реестра — свойство платформы |
| G03 точки входа из реестра | литерала workflow в коде нет структурно |
| G04 связывание `binds` по DI | контейнер не читается; сырьё в графе есть |
| G05/G05b/G05c узлы данных | таблиц нет как вида узла |
| G06 грид-сервисы | вызов по имени через прокси кластера |
| G15 вторая половина шва | эндпоинты .NET не извлекаются |
| G07 достижимость, веерность, честная сдача | `trace_path` есть, правила Р6 нет |
| G08 отчёт о неполноте | категории наши, ложные `HTTP_CALLS` считать некому |
| G17 дрейф прозы и спецификаций | понятия не существует |

Формулировка «останется только приведение к общему формату» верна наполовину:
приведение к формату — да, и сверх него **связывание через DI**, без которого
граф вызовов на АС CF рвётся на каждой границе сервиса.

## Что проверить перед тем, как закладываться

1. **Ограничитель памяти.** 6,9 ГБ на `abp` против нашего требования ≤ 4 ГБ.
   Найти ключ или измерить на машине с 8 ГБ.
2. **Доля разрешённых вызовов.** Из соотношения `CALLS` к `USAGE`
   (на `abp` — 39 072 против 112 303) она **не выводится**: `USAGE` смешивает
   неразрешённые вызовы с обычными чтениями полей и констант. Наше требование
   «не менее 75 %» меряется только своим счётчиком мест вызова — то есть G08.
3. **Коллизии FQN.** На `abp` `Program` объявлен 65 раз, `IndexModel` — 62.
   Ложных рёбер на выборке не найдено, но выборка мала; нужен направленный тест.
4. **Режим `cross-repo-intelligence`** — чинит ли шов между отдельно
   проиндексированными фронтом и бэком.
5. **Устойчивость формата.** Схема их SQLite нигде не документирована,
   `get_graph_schema` отдаёт её в рантайме. Читать надо через Cypher
   и с проверкой версии, иначе привяжемся к недокументированному формату.

# Перемер на версии 0.6.0 (20.08.2026)

Всё, что записано выше, снято на **v0.10.8**. В боевой контур прошла только
версия **0.6.0**, и план требует перемерить протокол на ней **до** того, как
на него обопрётся хоть одно решение этапа (G01 п. 1, риск Р-7). Перемер сделан
на той же четвёрке репозиториев и отвечает на те же вопросы.

**Итог: 0.6.0 фильтр проходит.** JSON-CLI есть, `--mode fast` есть, граф
читается полностью, память и время радикально лучше. Условие переключения
на запасной вариант **не сработало**. Но форма чтения другая, чем записано
выше, и на пути к этому выводу лежат четыре ловушки, каждая из которых даёт
не ошибку, а тихий неверный ответ.

## Числа

Режим `fast`, чистый `CBM_CACHE_DIR` на каждый прогон, та же машина
(16 ГБ RAM, без GPU).

| Репозиторий | Узлов | Рёбер | `CALLS` | Время | Память |
|---|---|---|---|---|---|
| eshoponweb | 1 997 | 3 436 | 263 | 0,07 с | 45 МБ |
| wexflow | 11 430 | 28 919 | 7 389 | 1,06 с | 486 МБ |
| squidex | 30 499 | 97 096 | 29 863 | 1,92 с | 564 МБ |
| abp | 156 592 | 246 629 | 30 186 | 4,7 с | 1,24 ГБ |

Сравнение с v0.10.8 (числа из таблицы выше):

| Репозиторий | Узлов 0.6.0 / 0.10.8 | Рёбер 0.6.0 / 0.10.8 | Время 0.6.0 / 0.10.8 |
|---|---|---|---|
| eshoponweb | 1 997 / 2 558 (78 %) | 3 436 / 6 535 (53 %) | 0,07 с / 7,9 с |
| wexflow | 11 430 / 23 159 (49 %) | 28 919 / 113 034 (26 %) | 1,06 с / 17,5 с |
| squidex | 30 499 / 43 114 (71 %) | 97 096 / 215 091 (45 %) | 1,92 с / 22,5 с |
| abp | 156 592 / 173 550 (90 %) | 246 629 / 402 137 (61 %) | 4,7 с / 45,9 с |

**Рёбер меньше, но `CALLS` — не в той же пропорции.** На `abp` рёбер вызова
30 186 против 39 072 у v0.10.8, то есть **77 %**; проседают в основном
вспомогательные виды (`DEFINES`, `CONTAINS_*`, семантические).

**Память перестала быть риском.** 1,24 ГБ на `abp` против 6,9 ГБ у v0.10.8
при потолке среды 16 ГБ — запас двенадцатикратный. Риск Р-8 закрыт числом:
замер на целевом репозитории остаётся обязательным, но перспектива выхода
за потолок исчезла.

**Полный цикл движка на целевом масштабе — пять секунд, а не сорок шесть.**
Это заранее решает вопрос G09: инкрементальность почти наверняка не нужна.

**Режимы почти не различаются.** На `eshoponweb`: `fast` — 3 436 рёбер,
`moderate` — 3 526, `full` — 3 558 при 2 030 узлах. Разница — семантические
рёбра; `CALLS` во всех трёх одинаковы. Значит, `fast` берётся не как
компромисс, а как режим без лишнего.

## Как читается граф в 0.6.0

Через `query_graph` и подмножество openCypher, как и записано в плане, —
но с двумя условиями, без которых запрос **молча возвращает пустоту**.

**Ловушка 1: у обоих концов ребра обязана быть метка.**

```
MATCH (a)-[:CALLS]->(b) RETURN a.name, b.name              → 0 строк
MATCH (a:Method)-[:CALLS]->(b:Method) RETURN a.name, b.name → работает
```

Ошибки нет, есть пустой результат — то есть ответ, неотличимый от «таких
рёбер в графе нет». Именно на этой форме перемер едва не закончился выводом
«рёбра из 0.6.0 не читаются вовсе» и переключением на запасной вариант.

Проверка полноты: сумма по всем парам меток совпадает со счётчиком схемы
**точно** — на `eshoponweb` 237 (`Method→Method`) + 8 (`Method→Class`) +
16 (`Module→Method`) + 1 (`File→Method`) + 1 (`Module→Function`) = 263,
и `get_graph_schema` даёт 263. Ничего не теряется, если перебрать пары.

**Ловушка 2: неизвестное свойство возвращает пустую строку, а не ошибку.**

```
RETURN n.qualified_name, n.file_path   → значения есть
RETURN n.file, n.path, n.line, n.type  → пустые строки
```

Мост, спросивший не то имя поля, получит колонку пустых значений и решит,
что движок этого не знает.

**Ловушка 3: агрегатов и `labels()` нет.** `count(*)` не агрегирует (вернёт
столько строк, сколько узлов), `labels(n)` даёт пустую строку. Счётчики
берутся у `get_graph_schema` и `get_architecture`, а не запросом.

**Ловушка 4: `trace_path` сопоставляет по КОРОТКОМУ имени и молча выбирает
один узел.** Полное имя он не принимает вовсе (вернёт пустой ответ).
На `eshoponweb` `trace_path("GetTokenAsync")` даёт пустые `callers`
и `callees`, потому что нашёл объявление в интерфейсе, — при том что
у реализации входящих рёбер два. Для точного извлечения рёбер инструмент
непригоден; он для человека, а не для моста.

Отдельно про `search_graph`: он отдаёт узлы пачкой, с `qualified_name`,
`file_path`, `label` и степенями, а `include_connected` — соседей, но
**короткими именами и без направления**. Если бы Cypher не читал рёбра,
пришлось бы восстанавливать их отсюда, и это было измерено: имя соседа
уникально в 41–51 % случаев, встречная проверка («кандидат, который сам
называет вызывающего») поднимает разрешимость до 65–86 %. Числа приведены
затем, что они и есть цена ошибки в ловушке 1: та же работа, вдвое хуже
результат.

## Детерминизм: измерен, находка локализована

Два прогона `index_repository` с чистого кэша на одном входе, канонический
дамп (сортировка, только имена и пути):

| Репозиторий | Полный дамп | Проекция моста (объявления + `CALLS`/`INHERITS`) |
|---|---|---|
| eshoponweb | **расходится**: 5 строк из 5 433 | совпадает байт в байт (1 006 строк) |
| squidex | не мерялся целиком | совпадает байт в байт (48 248 строк) |
| abp | не мерялся целиком | совпадает байт в байт (67 545 строк) |

**Виновник назван.** Расходятся узлы вида `Module`, у которых
`qualified_name` собран без расширения файла: `…css.app.component`
соответствует и `app.component.css`, и `app.component.scss`, и в разных
прогонах побеждает разный файл. Пять пар на `eshoponweb`, все —
таблицы стилей.

Это **не** блокирующая находка: недетерминизм лежит целиком за пределами
того, что мост проецирует в наш индекс (объявления кода и рёбра вызовов).
Правило для моста: узлы `Module`, соответствующие таблицам стилей,
в индекс не идут, а числа расхождения — категория отчёта G08.

Чтение всего графа `abp` через Cypher (52 запроса по парам меток) занимает
**1,9 секунды**. Бюджет сборки этим не расходуется.

## DI-случай: разрешается ИНАЧЕ, и это меняет G04

Главный вопрос перемера. В v0.10.8 вызов через интерфейс останавливался
на интерфейсе, и G04 писалась как «довершить ребро по `binds`».

В 0.6.0 то же место разрешается **сразу в реализацию**:

```
AuthenticateEndpoint.HandleAsync → IdentityTokenClaimService.GetTokenAsync
UserController.CreateUserInfo    → IdentityTokenClaimService.GetTokenAsync
```

При этом `GetTokenAsync` объявлен в `ITokenClaimsService`, а поле имеет тип
интерфейса. То есть 0.6.0 доводит вызов до реализации **по имени**, а не
по типу.

Обратная сторона видна на случае с декоратором:

```
IndexModel.OnGet → CachedCatalogViewModelService.GetCatalogItems   есть
Cached….GetCatalogItems → CatalogViewModelService.GetCatalogItems  ПОТЕРЯНО
```

У v0.10.8 второе ребро было. У 0.6.0 `CatalogViewModelService.GetCatalogItems`
не имеет входящих рёбер вовсе: где кандидатов на имя несколько, движок
выбирает одного и про остальных молчит.

**Следствие для G04, и оно обязательное.** Механика «ребро остановилось
на интерфейсе — довести по `binds`» на 0.6.0 неприменима: доводить нечего,
цель уже конкретна. Вместо неё:

1. **проверять** выбор движка нашими `binds`: цель, которую он выбрал
   по имени, обязана совпасть с зарегистрированной реализацией. Расхождение
   — категория отчёта, а не тихая правка;
2. **дополнять** рёбрами к остальным зарегистрированным реализациям
   с пониженной уверенностью — ровно там, где движок выбрал одну из многих;
3. `USAGE`-рёбра от регистрации, на которые план рассчитывал как на «сырьё
   для связывания», в 0.6.0 отсутствуют: у `IdentityTokenClaimService`
   ни входящих, ни исходящих. Сырьё берётся у нашего `dotnet/di.py`,
   и только у него.

Уверенный выбор одной реализации из нескольких — это в точности «уверенное
неправильное ребро» из Р6, только чужое. Мерить его обязан G08.

## Ответы на вопросы, ради которых делался перемер

| Вопрос плана | Ответ на 0.6.0 |
|---|---|
| JSON-CLI есть? | да: `cli <tool> '<json>'`, один позиционный JSON |
| `--mode fast` есть? | да; `fast`/`moderate`/`full` различаются только семантическими рёбрами |
| Граф читается? | да, через Cypher с метками у обоих концов ребра |
| DI-случай разрешается так же? | **нет**: доводит до реализации по имени, теряет вторую при неоднозначности |
| Память? | 1,24 ГБ на `abp` — риск Р-8 снят |
| Детерминизм? | в проекции моста — байт в байт; расхождение только на `Module` таблиц стилей |

Условие переключения на запасной вариант не сработало ни по одному пункту.
Решение «движок берём» подтверждено для версии, которая реально запускается
в контуре.

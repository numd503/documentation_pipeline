# План реализации бизнес-слоя документации

Исполнительный план для агента-реализатора. Шаг 1 (`docs/parser-implementation-plan.md`)
закончен; шаг 2 (`docs/materialize-implementation-plan.md`) реализуется параллельно —
здесь он не переделывается. Факты о боевом репозитории, на которых стоит этот план, —
в [`findings-cashflow-registries.md`](findings-cashflow-registries.md).

---

## Как работать с этим планом

1. Задачи выполняются по графу зависимостей. Задача закрыта, только когда **её команда
   проверки проходит зелёной**.
2. Перед каждым коммитом: `uv run ruff check . && uv run ruff format --check . && uv run mypy docpipe && uv run pytest -q`.
3. **Ничего не додумывай.** Нет в спецификации — реализуй минимально необходимое для
   критериев приёмки.
4. Сообщения об ошибках и docstring — по-русски; имена в коде — по-английски.
5. При расхождении плана с реальностью — **править план**, а не молча обходить.

---

## Зачем этот слой

Шаги 1–3 строят техническую документацию: что за тип, что он делает, где лежит код.
Бизнес-документация — процессы, сущности, правила — из кода не выводится и пишется
аналитиками. Задача этого слоя: **связать одно с другим так, чтобы рефакторинг,
не меняющий бизнес-смысла, не ломал связь.**

Наивная схема — «аналитик ведёт список рёбер процесс ↔ тип» — разваливается по трём
причинам, и все три обязательны к пониманию, иначе реализация повторит ошибку:

1. **Связь ведёт сторона, которая не видит изменений.** Аналитика нет в PR, где
   переименовали класс. Связь рвётся в момент T, обнаруживается в T+3 месяца.
2. **Идентичность кода меняется от вещей без бизнес-смысла.** `doc_path` меняется даже
   при неизменном коде — достаточно поправить `rules/dotnet.yaml` и тип
   переклассифицируется. `node_id` меняется при переносе типа в другой namespace.
3. **Рёбер тысячи.** Столько связей не сопровождает никакой процесс.

## Ключевые решения

| Решение | Почему так |
|---|---|
| Стрелка одна: техника ссылается на бизнес, бизнес о технике не знает | Рефакторинг тогда физически не может сломать бизнес-документ. Худшее — висящий якорь на технической стороне, который чинит тот же PR, что его сломал |
| Якорь — «точка контракта», а не идентичность типа | Строка, которую обязан знать вызывающий, не меняется при рефакторинге: её изменение ломает внешних потребителей, то есть является бизнес-событием по определению |
| Реестры платформы — первичный источник якорей | В АС CF джобы, workflow и обработчики событий объявлены в XML и диспетчеризуются по данным. Литерала в C# не существует **структурно** — см. findings, ловушка 10 |
| Каталог — это множество `.md`-файлов, отдельного манифеста нет | Аналитик работает в IDE: один файл = один процесс, `git add` — и готово. Промежуточный манифест потребовал бы генерации перед каждой правкой |
| `business_hash` считается по **разрешённым фактам**, а не по объявленному тексту | Хэш по тексту менялся бы только когда аналитик сам правит документ, то есть не ловил бы ничего. Хэш по резолву ловит изменение кода |
| В `business_hash` нет имён C#-типов, путей и namespace | Прямое требование постановки: рефакторинг без смены бизнес-смысла не должен давать `review`. Та же логика, по которой `signature_hash` не включает строки |
| `entry` проверяется, `upstream` — никогда | Процесс может начинаться в зоне ответственности другой команды. Требовать доказательства чужого триггера — значит получить вечно красный линт и его отключение |
| Идентификатор бизнес-объекта неизменен, `doc_path` выводится из него | Отсюда бизнес-документы **не переезжают**, и вся машинерия автопереноса из шага 2 им не нужна |
| `docpipe/business/**` и `docpipe/registry/**` не импортируют `docpipe/dotnet/**` | Система полиязычна (.NET, Python, Angular). Бизнес-слой обязан быть языконезависимым с первого дня, иначе через год его придётся переписывать втрое |
| Флаги состояния из реестров не читаются | `Override`, `IsActive`, `JOBDISABLED` — политика поставки и состояние БД. Инструмент боевой БД не видит, а прочитанный флаг однажды прочтут как факт. Политика к тому же меняется независимо от кода |
| **Бизнес-сущности пишутся, а не генерируются** | Решение владельца, проверенное на боевых данных: 289 списков `Cashflow.Structure.xml` — это таблицы и их структура, а не каталог бизнес-сущностей. Полезен там **только** `DisplayName`. Сгенерировать 289 малозначимых сущностей — выстрел в ногу: их никто не прочтёт, а отчёт о непокрытом будет вечно красным |

## Шкала устойчивости якорей

Выбор якоря — главный рычаг всей конструкции. Уровень 1 предпочитается всегда,
когда он существует.

| Уровень | Якорь | Переживает | Ломается от |
|---|---|---|---|
| 1 | внешний контракт: имя grid-сервиса, `JOBTITLE`, `Id@Version` workflow, `список+EventType`, HTTP-маршрут, топик | переименование и перенос типов, разделение классов, смену namespace, смену правил классификации | изменения самого контракта — а это бизнес-событие |
| 2 | namespace или каталог | переименование, разделение и слияние типов | реорганизацию пространства имён (ловится линтом мёртвых правил) |
| 3 | идентичность типа (FQN, `node_id`) | почти ничего | переименование, перенос, смену модуля |

**Правило выбора, применимое к любому новому случаю:** якорь — то, что обязан знать
вызывающий. Если внешний код пишет строку — якорь строка. Если пишет тип — якорь тип.
Если это можно переименовать, не сломав никого снаружи, — это не якорь.

## Реестры

Реестр — файл в репозитории, который **уже** объявляет точки входа и читается
исполняющей системой. Его нельзя испортить незаметно: неверный реестр ломает работу.
Поэтому доверие к нему выше, чем к любому комментарию и к любой вики.

Конфигурация — данные, а не код. Файл `registries.yaml` рядом с `docpipe.yaml`:

```yaml
version: "1"
registries_version: "2026-07-29.1"

registries:
  - id: grid-services
    kind: grid_service
    path: sbt.cashflow.gridservice.subrepo/Sbt.CMS.GridService.Initializer/services.config
    format: xml
    item_xpath: "./dotNetServices/add"          # ТОЛЬКО прямые дети: см. ловушку 1
    fields:
      ref:      "@name"
      impl_fqn: "@class"
      assembly: "@assembly"
      team:     "@team"

  - id: jobs
    kind: job
    paths: ["sbt.cashflow.deployment/Sbt.Deployment.Db/Cashflow/Data/Items/Items*.xml"]
    format: xml
    item_xpath: "./Lists/List[@InnerName='JOBS']/Items/Item[@KeyField='JOBTITLE']"
    fields:
      ref:          "@KeyValue"
      contract_fqn: "@JOBCLASS"                 # интерфейс, не реализация
      assembly:     "@JOBASSEMBLY"
      disabled:     "@JOBDISABLED"
      schedule_raw: "@JOBSCHEDULE"

  - id: workflows
    kind: workflow
    paths: ["sbt.cashflow.deployment/Sbt.Deployment.Db/Cashflow/Data/Items/Items*.xml"]
    format: xml
    item_xpath: "./Lists/List[@InnerName='Workflows']/Items/Item[@KeyField='WorkflowTitle']"
    fields:
      title:      "@KeyValue"
      is_active:  "@IsActive"
      definition: "./File[@FieldInnerName='WorkflowDefinition']/@Path"
    follow:
      field: definition
      base:  sbt.cashflow.deployment/Sbt.Deployment.Db/Cashflow
      format: json
      fields:
        ref:       "Id"
        version:   "Version"
        data_type: "DataType"
      children:
        kind: workflow_step
        list: "Steps"
        fields:
          ref:       "Id"
          impl_type: "StepType"
          next:      "NextStepId"

  - id: structure
    kind: list
    path: sbt.cms.cashflow.subrepo/Sbt.CMS.Cashflow.Structure/Cashflow.Structure.xml
    format: xml
    item_xpath: "./Lists/List"
    fields:
      ref:         "@InnerName"
      table:       "@TableName"
      display_name: "@DisplayName"
    children:
      - kind: list_field
        item_xpath: "./Fields/*"                # Field* — по префиксу, не по перечню
        fields:
          ref:          "@InnerName"
          column:       "@ColumnName"
          display_name: "@DisplayName"
          required:     "@Required"
          lookup:       "@ListSource"
      - kind: list_event
        item_xpath: "./EventReceivers/EventReceiver"
        fields:
          ref:      "@EventType"
          impl_fqn: "@Class"
          assembly: "@Assembly"

  - id: kafka-topics
    kind: kafka_topic
    format: inline                              # источник не найден, ведётся вручную
    items: []
```

Требования к читателю:

- вывод **детерминирован**: все списки сортируются явным `sorted()` с явным ключом,
  порядок обхода файлов источником порядка не является;
- один нечитаемый файл или одна битая запись не роняют прогон: строка в отчёте,
  остальное читается;
- используется только подмножество XPath из `xml.etree.ElementTree`. `lxml` не вводится:
  закрытый контур, каждая новая зависимость — отдельное согласование.

## Разрешение якоря

Ступени по порядку, первая сработавшая выигрывает:

```
1. реестр            → confidence=registry, известны реализация, сборка, команда
2. литерал           → строка встречается в enrolled-файлах манифеста: confidence=literal, file:line
3. индекс символов   → только для kind=type: FQN существует в решении
4. не разрешён       → ошибка линта, если verify != false
```

> **Ловушка. Для `workflow`, `job`, `grid_service` и `list_event` ступень 2 заведомо
> пустая, и это не дефект.** Диспетчеризация идёт по данным, литерала в C# нет
> структурно. Реализация, считающая пустой литеральный поиск проблемой, даст вечно
> красный линт по всем 45 workflow, и его отключат.

> **Ловушка. Литеральный поиск идёт по `symbol.sources[].path` из манифеста, а не
> обходом файловой системы.** Иначе в результаты попадут вывод сборки (`artifacts/bin`),
> тесты и каталог самого инструмента.

> **Ловушка. Ступень 3 видит только задокументированные типы.** Настоящего индекса
> символов в манифесте нет — он строится при `scan` и не сохраняется (та же ловушка,
> что в B03). Поэтому «не разрешён» на этой ступени означает «не найден среди узлов
> документации», а не «типа не существует», и формулировать сообщение надо именно так.

### Словари видов расходятся

Аналитик пишет `table` и `kafka` — слова предметной области; реестр объявляет `list`
и `kafka_topic` — слова платформы. Мост между наборами один и лежит в
`resolve.REGISTRY_KIND`; расширять `ANCHOR_KINDS` и `RegistrySpec.kind` можно
независимо, но новая пара обязана попасть в эту таблицу, иначе якорь просто никогда
не разрешится и это будет выглядеть как «инструмент не нашёл».

| Якорь в документе | Вид записи реестра |
|---|---|
| `grid_service`, `job`, `workflow`, `workflow_step`, `list_event` | те же |
| `table` | `list` |
| `kafka` | `kafka_topic` |
| `http`, `type` | реестра нет: ступени 2 и 3 |

```markdown
  accepted: null

<!-- docpipe:generated:start -->

<!-- docpipe:generated:end -->

<!-- Что должно произойти в бизнесе, чтобы процесс начался. Технические подробности

<!-- docpipe:section:start steps -->

<!-- docpipe:section:start rules --><!-- --><!-- docpipe:section:end rules -->

<!-- docpipe:section:start notes --><!-- --><!-- docpipe:section:end notes -->
```

Зоны те же, что в шаге 2, и по той же причине: `docpipe:` — проекция, перезаписывается;
`docpipe_state:` — состояние, сохраняется; секции — авторские, **никогда** не затираются.
Подсказки — только HTML-комментарии: иначе `is_section_empty` сочтёт каждый новый
документ написанным.

### Идентификатор

```
bp.<домен>.<процесс>      процесс     bp.valuation.twinml-scoring
be.<домен>.<сущность>     сущность    be.valuation.user-task
cap.<домен>[.<под>]       возможность cap.valuation
```

Регекс: `^(bp|be|cap)\.[a-z0-9]+(-[a-z0-9]+)*(\.[a-z0-9]+(-[a-z0-9]+)*)+$`.

Три правила, каждое из которых иначе выстрелит через год:

1. **В идентификаторе нет команды, системы и технологии.** Не `bp.ml.kafka-eod`.
   Команды меняются, системы переименовывают, Kafka заменят. Идентификатор отражает,
   **что** делается.
2. **Идентификатор не меняется никогда.** Меняется `title`. Переосмысление процесса —
   это `status: deprecated` плюс новый идентификатор с `supersedes: [старый]`.
3. **Выведенный из употребления идентификатор не переиспользуется.**

`doc_path` выводится: `{business_root}/{kind}s/{сегменты id после префикса}.md`.
Так как идентификатор неизменен, документ не переезжает — механика автопереноса
из шага 2 бизнес-слою не нужна.

### Якорь

Якорь — **объект**, а не строка:

Имя `scope` то же, что у `ResolvedAnchor` из B03, намеренно: одна вещь — одно имя,
иначе сверка каталога с инвентаризацией превращается в перевод.

```python
{"kind": "list_event", "ref": "ItemAdded", "scope": "UserTasks"}
{"kind": "workflow", "ref": "TwinMLWorkflow", "version": 2}
{"kind": "job", "ref": "PM: Load limits"}
{"kind": "kafka", "ref": "pricing.eod.requested", "owner": "команда интеграции", "verify": false}
```

> **Ловушка. Не вводить строковую форму якоря как ключ.** Соблазн склеить
> `job:PM: Load limits` велик, но `JOBTITLE` содержит пробелы и двоеточия, а `KeyValue`
> workflow — кириллицу. Любой парсер такой строки — источник багов. Строка допустима
> только для показа человеку и **никогда** не разбирается обратно.

## `business_hash`

Считается по **результату разрешения** якорей, нормализованному до бизнес-видимых фактов.
Это ядро всей затеи: от состава хэша напрямую зависит, будет ли рефакторинг создавать
ложные тревоги.

| Вид якоря | Что входит в хэш | Что **не** входит и почему |
|---|---|---|
| `workflow` | `Id`, `Version`, отсортированные `Id` шагов и их `NextStepId` | `StepType` — переименование класса шага бизнес-смысла не меняет |
| `workflow_step` | `Id` шага, `NextStepId` | `StepType` |
| `job` | `JOBTITLE`, `Interval`, `FirstTime` | `JOBCLASS`, сборка, `JOBDISABLED` |
| `grid_service` | `name`, отсортированные имена публичных методов реализации | FQN класса: методы вызываются по имени через прокси и являются контрактом, класс — нет |
| `list_event` | `InnerName` списка, `EventType`, отсортированные **сборки** всех обработчиков пары | имена классов обработчиков: их переименование не меняет участников |
| `list` | отсортированные `(InnerName, ColumnName, тип поля, Required, DisplayName, ListSource)` | порядок полей, формы |
| `http` | метод и маршрут | имя контроллера и метода |
| `type` (контракт) | **ничего** — см. ниже | имя класса, namespace, путь, порядок свойств |
| `kafka` и всё с `verify: false` | **ничего** | нечего разрешать |

`upstream` в хэш не входит никогда: это чужая зона, и его правки — авторские.

> **Расхождение с реальностью, найдено на B05: `JOBDISABLED` из хэша убран.** Строка
> таблицы противоречила решению «флаги состояния из реестров не читаются» и ловушке 8:
> `JOBDISABLED` — политика поставки и состояние боевой БД, которой инструмент не видит.
> Читать флаг только ради хэша значило бы завести второй, негласный источник истины
> про то же самое. `registries.example.yaml` его и не читает — противоречие было
> внутри плана, а не между планом и кодом.

> **Расхождение с реальностью, найдено на B05: форма типа в хэш не входит.** Строка
> требовала «отсортированные (имя на проводе, нормализованный тип, обязательность)»,
> но этих данных в манифесте нет: `contracts[]` и `shape_hash` для DTO отложены
> намеренно (см. «Отложено намеренно»). Хуже того, вычислить форму по `symbol.members`
> нельзя даже приблизительно — проверено на парсере: `record Money(decimal Amount,
> string Currency)` даёт **ноль** членов, форма лежит в списке параметров. Реализация
> «по свойствам» дала бы пустую форму у каждой записи, одинаковый хэш у всех сразу
> и изменение контракта, прошедшее незамеченным. Поэтому `type` разрешается ступенью 3
> и вносит в хэш только свою идентичность. Строку возвращать вместе с `shape_hash`.

> **Ловушка. Имя на проводе не равно имени свойства.** `[JsonPropertyName]`,
> `[DataMember(Name=…)]`, `[JsonProperty]` переопределяют имя при сериализации. Хэш
> по именам свойств даст ложную тревогу ровно на том рефакторинге, который надо
> не замечать.

> **Ловушка. `record` с позиционными параметрами.** У `record R(Guid Id, decimal Sum)`
> объявлений свойств нет — форма лежит в списке параметров. Реализация, обходящая только
> `property_declaration`, даст пустую форму и одинаковый хэш у всех записей сразу.

## Решение для агента и статусы

| Условие | Решение | Причина |
|---|---|---|
| есть пустые секции | `write` | документ не наполнен |
| якорь не разрешается и `verify != false` | `broken` | `точка входа не найдена: workflow TwinMLWorkflow@2` |
| приёмки не было, а текст есть | `review` | текст не сверялся с реализацией |
| `business_hash` ≠ принятого | `review` | `состав изменился: добавлен шаг IndividualThresholds` |
| иначе | `skip` | — |

Статусы: `broken`, `empty`, `undeclared`, `drifted`, `current`.

Статуса `orphan` у бизнес-слоя нет: документы создаются людьми, а не выводятся из кода,
поэтому «лишний документ» — нормальное состояние, а не дефект.

> **Расхождение с реальностью, найдено на B10: статуса `missing` тоже нет.** Документ
> здесь **и есть файл** — каталог собирается обходом `.md`, — поэтому «файла нет»
> означает «документа нет», а не «документ потерян». Чтобы сообщить о ненаписанном,
> понадобился бы второй источник истины о том, какие документы должны существовать,
> то есть ровно то, от чего отказались решением «каталог — это множество файлов».
> Отвечает на этот вопрос отчёт линта о непокрытых точках входа: он считается
> по реестрам — единственному источнику, который действительно знает, чего не хватает.

`broken` у бизнес-слоя означает **неразрешённый якорь**, а не нечитаемый документ:
документ, который не разбирается, в каталог не попадает вовсе и виден проверкой
`catalog` в линте. Разделение важно: «не нашли точку входа» и «состав изменился» —
разные причины, требующие разных действий, и смешивать их в одном статусе нельзя.

## Линт

`docpipe business lint`. Восемь проверок, порядок фиксирован. Имена — значения
`--fail-on`; значение вне перечня — код 2, а не пустой фильтр.

**Дефекты каталога — код 1.** Это то, что автор документа может починить сам:

1. `unresolved` — **неразрешённый якорь** (`verify != false`) с указанием документа
   и ступеней, которые пробовались. Якорь, признанный неоднозначным (проверка 3),
   сюда не попадает: одна причина — одна находка.
2. `no-entry` — **процесс без `entry`**: либо не дописан, либо это не процесс.
3. `ambiguous-version` — **неоднозначная версия workflow**: ссылка без `version`
   при нескольких кандидатах. Кандидаты перечисляются, выбор не делается.
4. `unknown-capability` — **ссылка на необъявленную возможность**.
5. `team-mismatch` — **расхождение команд**: `@team` реестра против `ownership.yaml`
   по реализации.
6. `catalog` — **дубли и формат идентификаторов**, то есть всё, что каталог отбраковал
   при загрузке. Такие документы в `catalog.docs` не попадают, и увидеть их можно
   только здесь.

**Инвентарные факты — кода возврата не меняют**, пока их не назвали в `--fail-on`:

7. `registry-unlinked` — **запись реестра ссылается на тип, не найденный среди узлов
   документации.**
8. `uncovered` — **непокрытые точки входа**: записи реестров **видов из `ENTRY_KINDS`**,
   на которые не ссылается ни один бизнес-документ, со срезами по `team` и по виду.
   **Это главный отчёт всего линта:** он отвечает на вопрос «сколько ещё писать»
   и показывает, что именно. Списки (`list`) сюда не входят никогда: их 289, описывать
   их поштучно никто не будет, и попадание их в отчёт сделало бы его вечно красным.

Требование покрытия 100 % не ставится и не должно ставиться: у большей части кода
бизнес-смысла нет. Отчёт 8 считается только по записям реестров, то есть по точкам входа.

> **Расхождение с реальностью, найдено на B06: деления на две группы в плане не было,
> и без него линт красный с первого дня.** Исходная формулировка — «код 1 при находках» —
> вместе с отчётом о непокрытом означает ненулевой код на любом репозитории, где
> каталог не дописан, то есть всегда. Красный с первого дня линт выключают на второй,
> и вместе с ним пропадают шесть проверок, которые работают. Правило простое:
> **находка роняет прогон, только если её может починить автор документа.** Сколько
> точек входа ещё не описано — состояние работы, а не дефект.

> **Расхождение с реальностью, найдено на B06: диагноз «мёртвая запись реестра»
> поставить нечем.** Проверка требовала резолва `impl_fqn` «в индексе символов», но
> индекс строится при `scan` и **не сохраняется** — ровно то, что уже отмечено ловушкой
> в B03. Отличить «класса нет» от «класс не документируется» по манифесту нельзя,
> поэтому проверка переименована в `registry-unlinked` и говорит ровно то, что знает:
> «не найден среди узлов документации». Настоящий диагноз появится, когда индекс FQN
> начнёт сохраняться; это правка шага 1 (новое поле манифеста и версия схемы),
> и делать её внутри B06 значило бы протащить изменение формата под видом линта.
> До тех пор проверка остаётся инвентарным фактом: на фикстуре она срабатывает на
> двух записях из восьми, и обе — легальные (тип есть, документации у него нет).

## B01 — `registry/`: декларативный читатель

**Цель:** конфигурация описывает реестр, код не знает ни про АС CF, ни про Ignite.

**Создать:** `docpipe/registry/{__init__,model,config,reader}.py`,
`tests/test_registry_reader.py`, `tests/fixtures/registries/**`

**Спецификация**

```python
def load_registries(path: Path) -> list[RegistrySpec]: ...
def read_registry(spec: RegistrySpec, root: Path) -> RegistryResult: ...  # items, errors
```

Поддерживаются: `path` / `paths` (глоб), `item_xpath`, `fields`, вложенные `children`,
переход по ссылке `follow` (значение поля — путь к другому файлу, разбираемому своим
набором полей).

Выражение поля для XML бывает четырёх видов: `@attr`, `путь/@attr`, `путь` (текст
элемента) и `#tag` — имя самого элемента. Последнее нужно там, где вид записи закодирован
тегом, а не атрибутом: у полей списка структуры это `FieldText`, `FieldLookup`,
`FieldDateTime`, и вид поля входит в состав бизнес-сущности.

Форматы верхнего уровня — **`xml` и `inline`**. `json` бывает только целью `follow`:
способ найти записи в JSON-файле нигде не задан (для XML это `item_xpath`, аналога нет),
а придумать его — значит завести формат, которым никто не пользуется. Внутри `follow`
структура известна, поэтому вопроса не возникает.

Записи верхнего уровня сортируются, вложенные — **нет**, и стирать эту разницу «для
единообразия» нельзя. Верхний уровень приходит из нескольких файлов, и его порядок —
следствие обхода ФС. Порядок шагов workflow — данные: это цепочка `NextStepId`.

> **Ловушка. ElementTree не умеет выбирать атрибуты.** `find("./File[…]/@Path")`
> возвращает `None`. Суффикс `/@Attr` читатель обязан отрезать сам и делать
> `find(elem_path).get(attr)`. Без этого конфигурация выглядит рабочей и молча
> отдаёт пустые значения.

> **Ловушка. BOM.** Все XML читаются **байтами**; `read_text(encoding="utf-8")` уронит
> `ET.fromstring`. Та же ловушка, что у `.csproj`.

> **Ловушка. Один битый файл не роняет прогон.** Файлов реестров десятки, правились они
> годами разными командами. Ошибка разбора — строка в `RegistryResult.errors`.

> **Ловушка. `follow` требует явной базы.** Путь внутри реестра относителен к корню
> развёртывания, а не к файлу реестра и не к корню репозитория. Разделители — Windows.
> Реализация без `base` и без замены `\` на `/` даст путь, который выглядит настоящим.

> **Ловушка. Пустой реестр обязан сообщать о себе.** Реестр, не давший ни одной записи,
> внешне неотличим от «таких точек входа в системе нет». Сообщать нужно, только если
> файлы прочитаны, а записей нет **во всех**: ноль записей в отдельном файле — норма,
> глоб `Items*.xml` для джобов законно захватывает `Items-Workflows.xml`. К сообщению
> добавляется подсказка про `xmlns`: при объявленном пространстве имён поиск по голому
> имени тега не находит ничего и об этом не сообщает.

Номера строк у записей не хранятся: ElementTree позиций не отдаёт, а способы их достать
хрупки и завязаны на версию. Запись ссылается на файл — для отчётов этого достаточно.

**Критерии приёмки**
- на фикстуре `services.config` прочитаны ровно 3 сервиса; вложенный
  `<interceptors><add/></interceptors>` **не** попал в результат;
- на фикстуре `Items_Basic.xml` прочитаны только записи из `List[@InnerName='JOBS']`;
  посторонний справочник в результат не попал;
- `follow` по `Items-Workflows.xml` прочитал определение и его шаги;
- перестановка файлов в глобе не меняет результат ни на байт;
- файл с BOM читается; файл с битым XML даёт запись в `errors`, остальные — результат;
- `/@Attr` в описании поля возвращает значение атрибута, а не `None`;
- файл, попавший под глоб, но не содержащий нужного списка, ошибкой **не** является;
  реестр, пустой во всех файлах, — является;
- запись без `ref` пропускается с сообщением, а не молча;
- шаги workflow идут в порядке объявления, а не по алфавиту.

**Проверка**
```bash
uv run pytest tests/test_registry_reader.py -q
```

## B02 — четыре реестра АС CF

**Цель:** описать реальные реестры данными и разобрать их специфику.

**Создать:** `registries.example.yaml`, `docpipe/registry/parse.py`,
`tests/test_registry_cashflow.py`

**Спецификация** — раздел «Реестры» целиком. Сверх общего читателя нужны три разбора:

1. `JOBSCHEDULE` — **экранированный XML внутри атрибута**: разэкранировать, разобрать
   вторым `ET.fromstring`, взять `Interval` (секунды) и `FirstTime`.
2. `StepType` и `DataType` — assembly-qualified `"FQN, Сборка"`: резать по первой запятой
   **вне квадратных скобок**, иначе дженерик `Foo\`2[[…, Asm]], Asm` даст обрубок.
3. Вид поля списка структуры закодирован **именем элемента** (`FieldText`, `FieldLookup`,
   `FieldDateTime`), а не атрибутом, и входит в состав бизнес-сущности. Берётся
   выражением `#tag`.

> **Ловушка. ElementTree не понимает `Field*` в позиции тега.** Его подмножество XPath
> допускает `*` только как компонент целиком, поэтому «по префиксу» выражается как
> `./Fields/*` — все дети `<Fields>`. Это не слабее белого списка, а строже: перечень
> видов (`FieldText`, `FieldFile`, `FieldNumber`, `FieldBool`, `FieldDateTime`,
> `FieldLookup`, `FieldMultiLookup`, `FieldMultiUser`) заведомо неполон, и белый список
> молча потерял бы поле нового вида. Вид при этом не теряется — он приходит из `#tag`.

> **Решение владельца: флаги состояния не читаются вовсе.** `Override`, `IsActive`,
> `JOBDISABLED` описывают политику поставки и состояние БД, а не бизнес-смысл. Три довода,
> и каждого хватило бы: инструмент видит репозиторий и боевой БД не знает **никогда**,
> поэтому «джоб выключен» сказать не может; прочитанный флаг рано или поздно кто-нибудь
> прочтёт как факт; политика поставки меняется независимо от кода, и привязка к ней
> устаревала бы от правки процедуры развёртывания.
>
> Читается то, что описывает контракт: идентификатор, класс или интерфейс, сборка,
> команда, расписание, заголовок, версия, тип состояния. Оговорка «это объявлено
> в репозитории, а не наблюдается в бою» верна для любого значения отсюда —
> безусловно, без флагов. Закреплено тестом `test_state_flags_are_deliberately_not_read`.
>
> Следствие для workflow: читаются **все** версии, выбор за автором документа.
> Инструмент версию не выбирает и выбрать не может.

**Критерии приёмки**
- на фикстурах разобраны все четыре вида; количества совпадают с ожидаемыми;
- `JOBSCHEDULE` даёт `interval=60`, `first_time="2017-01-01"`;
- `StepType` с дженериком режется верно (тест на искусственной строке);
- две версии одного workflow в фикстуре дают две записи, обе с `is_active=true`;
- `EventReceiver` фикстуры даёт `(список, EventType, класс, сборка)`;
- поле `FieldSomethingNew`, отсутствующее в перечне видов, всё равно прочитано.

**Проверка**
```bash
uv run pytest tests/test_registry_cashflow.py -q
```

## B03 — `docpipe anchors`

**Цель:** инвентаризация точек входа со связью до кода и документов.

**Создать:** `docpipe/registry/anchors.py`, `tests/test_anchors_cli.py`
**Изменить:** `docpipe/cli.py`

**Спецификация**

Резолв идёт **по соглашению об именах полей**, а не разбором по видам реестра: поле
`impl_fqn`, `contract_fqn`, `impl_type` или `data_type` содержит имя типа. Новый реестр
достаточно описать, назвав поле так же, — код не трогается.

Порядок один для всех: сначала прямое совпадение по `symbol.fqn`, затем реализации
интерфейса. Индекс реализаций строится перебором `related` у каждого узла: обратного
ребра `implemented_by` в манифесте нет, `tree._relations` его намеренно не создаёт.

Виды якорей делятся на **точки входа** (`grid_service`, `job`, `workflow`, `list_event`,
`kafka_topic`, `http`) и остальные. Дети, являющиеся точками входа, поднимаются на верхний
уровень отдельными якорями со ссылкой на родителя в `scope`: **обработчик события — это
вход, а список, внутри которого он объявлен, — нет.** Поля списка и шаги workflow
остаются вложенными: они описывают устройство.

`--format json` — через `hashing.stable_json_dumps`, отсортировано по
`(kind, scope, ref, version)`.

> **Ловушка. `JOBCLASS` — интерфейс.** Резолв в узел напрямую даст «вне дерева» почти
> всегда: в наборе правил по умолчанию интерфейсы не документируются
> (`type_kind: ["class", "record"]`). Идти обязательно через реализации.

> **Ловушка. Дженерик не сопоставится без нормализации.** В манифесте `symbol.fqn`
> хранится без арности, в реестре — полное имя закрытого дженерика
> (`MapStep\`2[[…]]`). Отсюда `strip_generic_arity`.

> **Ловушка. «Не найден среди узлов» — это НЕ «мёртвая запись реестра».** Узлами
> становятся только enrolled и классифицированные типы, поэтому неразрешённая ссылка
> может означать и «тип не документируется». Отличить одно от другого можно лишь
> по индексу символов, которого в манифесте нет: он строится при `scan` и не сохраняется.
> Поэтому B03 сообщает «не найден среди узлов документации» и **не** называет запись
> мёртвой; диагноз «мёртвая» ставит B06, где индекс доступен.

> **Ловушка. Команда известна не у всех якорей.** `@team` объявлен только
> в `services.config`. Для джобов, workflow и обработчиков событий владелец берётся
> из `ownership.yaml` (M06) по реализации; до него `--team` их не отбирает, и это
> надо говорить прямо, а не выдавать пустой результат за отсутствие.

> **Ловушка. Направление «код → якорь» так же нужно, как и обратное.** `anchors list`
> идёт от реестра к коду, но отправная точка аналитика обычно другая: он знает
> свой класс и не знает, какой строкой его вызывают. Без обратного поиска
> остаётся глазами просматривать перечень на сотни записей — на боевом
> репозитории это не работает. Отсюда `anchors which`, и три решения в нём
> неочевидны: (1) ищутся и **вложенные** записи, потому что команда чаще владеет
> шагом workflow, чем процессом целиком, а шаги на верхний уровень не
> поднимаются; (2) печатается **готовый кусок `entry`** на языке каталога
> (`table`, а не `list`) — строка показа обратно не разбирается, и собирать её
> в поля глазами человек не обязан; (3) «не найдено» — код **0**, потому что
> точка входа есть не у всякого типа, и код 1 объявлял бы нормальное состояние
> дефектом.

> **Ловушка. Сужение до своей части обязано идти ДО проверки на неоднозначность.**
> Селектор `only` (`assembly` либо `team`) отбирает из уже найденного, а не
> участвует в поиске. Если проверять «несколько записей = неоднозначность»
> раньше сужения, чужой подписчик на общей паре объявится неоднозначностью
> в нашем документе, хотя наша запись там ровно одна. Три следствия, каждое
> из которых легко сделать неправильно: (1) промах селектора — **отдельное**
> состояние `selector_missed`, а не `unresolved`: якорь на месте, сузили
> в пустоту, чинится одной строкой, и находка обязана перечислить, кто сейчас
> на якоре; (2) `only.team` без `ownership.yaml` не сужает ничего и обязан
> сказать это находкой, потому что молча пустой набор неотличим от «наших
> записей на якоре нет»; (3) на **покрытие** сужение не влияет — пара остаётся
> покрытой целиком, иначе отчёт потребует документ на чужой обработчик, и линт
> станет красным с первого дня. `assembly` сравнивается точным равенством,
> а не префиксом: `Sbt.Cashflow.ML` как префикс поймал бы и `Sbt.Cashflow.MLOps`.

> **Ловушка. На одной паре «список + `EventType`» бывает несколько обработчиков.**
> Платформа вызывает всех подписчиков события, поэтому это не дубль и не ошибка
> чтения: обе записи обязаны дойти до разрешения отдельными якорями. Реализация,
> схлопывающая их по `ref` или берущая первую попавшуюся через `next()`, молча
> потеряет половину участников события — раздел «Реализация» при этом выглядит
> заполненным, и заметить пропажу нечем. Разделить подписчиков якорем **нельзя
> и не нужно**: класс в якорь не входит, иначе его переименование ломало бы
> бизнес-документ. Следствия: инвентаризация считает **записи реестра**, а не
> пары, поэтому `Точек входа` больше, чем различимых пар; в «Точках входа»
> генерируемого блока пара — одна строка, в «Реализации» — по строке на
> подписчика. Фикстура: `tests/fixtures/registries/Structure.xml`,
> `UserTasks + ItemAdded`.

**Критерии приёмки**
- на фикстурном манифесте и фикстурных реестрах инвентаризация даёт ожидаемые количества
  по видам;
- `--team Core` сужает вывод; `--kind job` сужает вывод; фильтры комбинируются;
- два вызова `--format json` совпадают байт в байт;

- `anchors explain` печатает реестр, файл, реализацию, узел и `doc_path` (номера строки

## B10 — `business status` и `business accept` ✅

**Цель:** замкнуть цикл: зафиксировать соответствие документа реализации.

**Создать:** `docpipe/business/status.py`, `tests/test_business_accept.py`
**Изменить:** `docpipe/cli.py`, `docpipe/business/build.py`

**Спецификация**

`accept` записывает `docpipe_state.accepted = {business_hash, entry, resolved_at: null}`
и пересобирает генерируемый блок. Времени в состоянии нет — иначе `accept`
неидемпотентен.

`entry` в состоянии — **снимок разрешённых фактов**, а не копия объявленных якорей.
Из него `status` считает разницу словами: «добавлен шаг NotifyStep», «шаг A: переход
был 'B', стал 'C'». Два хэша человеку, открывшему отчёт, не сообщают ничего — между
ними предлагается догадываться, а по разнице фактов сразу видно, надо ли править текст.

Приёмка идёт через ту же запись, что и `build`: `compose` принимает состояние
параметром. Отдельный путь записи был бы второй реализацией слияния зон, и разошлись
бы они на первом же документе с чужими ключами front matter.

Ненаполненный документ не принимается (код 1): приёмка означает «текст сверен
с реализацией», а сверять нечего. `--force` оставлен для документов, описанных
целиком в чужой системе — у них заполнен `external_ref`.

> **Ловушка. `accept` берёт хэш из свежего разрешения, а не из front matter.** Front
> matter — зеркало и мог отстать. Взяв значение оттуда, `accept` зафиксировал бы
> устаревший хэш, и документ навсегда остался бы `current`, будучи `drifted`.

**Критерии приёмки**
- `accept` дважды подряд не меняет файл ни на байт;
- после добавления шага в фикстурный workflow решение → `review` с перечислением
  добавленных шагов; повторный `accept` его снимает;
- после переименования класса шага решение остаётся `skip`;
- `accept` на пустом документе → код 1; с `--force` → принят;
- `business status --format json` двух вызовов совпадает байт в байт.

**Проверка**
```bash
uv run pytest tests/test_business_accept.py -q
```

## Сводка ловушек

Каждая однажды прошла бы критерии приёмки и сломалась бы в проде.

1. **`.//add` ловит интерцепторы** — только прямые дети `./dotNetServices/add`.
2. **`.//Item` ловит справочники** — якорить на `List[@InnerName='JOBS']`.
3. **`@KeyValue` без `@KeyField`** бессмыслен.
4. **ElementTree не выбирает атрибуты** — суффикс `/@Attr` резать самому.
5. **Путь в `follow` относителен к базе развёртывания**, разделители Windows.
6. **`JOBSCHEDULE`** — экранированный XML внутри атрибута.
7. **`StepType` / `DataType`** — резать по первой запятой вне скобок.
8. **Флаги состояния** (`Override`, `IsActive`, `JOBDISABLED`) **не читаются вовсе** —
   это политика поставки и состояние БД, а не бизнес-смысл.
9. **Инструмент видит репозиторий, а не боевую БД**, и обязан это оговаривать
   безусловно — для любого значения из реестра.
10. **Литеральная ступень пуста структурно** для диспетчеризуемых по данным якорей.
11. **BOM** во всех XML — читать байтами.
12. **Якорь — объект, не строка**; строковая форма только для показа.
13. **`business_hash` не содержит имён C#-типов** (кроме методов grid-сервиса —
    они и есть контракт).
14. **Имя на проводе ≠ имя свойства**; `record` хранит форму в параметрах.
15. **`JOBCLASS` — интерфейс**, резолв через реализации.
16. **Покрытие считается по реестрам**, а не по узлам манифеста.
17. **`--fail-on` с опечаткой — код 2**, а не пустой фильтр.
18. **Ни одной кросс-слойной ссылки руками** — только генерируемые блоки.
19. **`business_root` — параметр**, не константа.
20. **Расхождение `doc_path` и идентификатора — ошибка**, а не повод переносить файл.

## Отложено намеренно

**`business-map.yaml` — привязка кода к возможностям правилами.** Тот же движок
`ruleset.py` (задача M01 шага 2), предикаты `path_glob`, `namespace_prefix`, `module_glob`.
Нужен, когда потребуется грубое покрытие кода без точек входа. Пока не нужен: реестры
дают точки входа, а покрытие 100 % не требуется.

**`contracts[]` и `shape_hash` для DTO.** Расширение шага 1: DTO не становятся узлами
(исключение из `rules/dotnet.yaml` остаётся верным — три тысячи описаний property-bag'ов
не нужны), но их форма попадает в манифест и даёт межкомандный контроль контрактов.
Отложено потому, что сущностей, требующих описания, мало (см. решение
«бизнес-сущности пишутся, а не генерируются»), и межкомандный контроль контрактов
понадобится позже описания процессов.
Ценность появится, когда понадобится ловить изменение общего DTO командой A, задевающее
процессы команды B.

**Аннотации бизнес-идентификатора в коде** (`<business ref="…"/>` в XML-doc). Правила
и реестры не выражают трёх вещей: два процесса в одном каталоге, шаг процесса, явное
«здесь бизнес-смысла нет». Требует правки продуктового кода шести команд, поэтому
делается **последней** и только по замеру: сколько точек входа осталось неразрешёнными
после B06. Если 5 % — аннотировать 5 %; если 40 % — проблема в другом, и аннотации
её замаскируют.

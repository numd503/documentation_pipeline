# Прогон на реальном репозитории: eShopOnWeb

Первая проверка `docpipe` вне синтетической фикстуры. Репозиторий `examples/eshoponweb`
(Microsoft eShopOnWeb) — эталонный .NET-проект: заметно меньше АС CF, но структурно
богаче фикстуры.

Состояние на момент прогона: готовы T00–T04 (обход, конфигурация). Парсер ещё не написан,
поэтому классификация ниже сделана черновым скриптом поверх сырого tree-sitter —
это разведка, а не проверка готового кода.

---

## Что подтвердилось

**Главная ставка архитектуры сыграла.** Грамматика `tree-sitter-c-sharp` разобрала
**244 файла из 244 без единой ошибки**:

```
файлов: 244   объём: 270 KiB
время парсинга: 0.13s   (1948 файл/с, 2.1 MiB/с)
файлов с ошибками разбора: 0 из 244   всего ERROR-узлов: 0
```

Экстраполяция на масштаб АС CF: даже на 20 000 файлов полный парсинг займёт порядка
10 секунд. Отказ от Roslyn был верным решением — он потребовал бы `restore` и сборки,
то есть минут.

Обход файловой системы: **17 мс** на 254 файла.

## Что сломалось бы в текущей спецификации

### 1. Многострочные base list ломают `signature_hash`

Найден реальный случай в `src/PublicApi/AuthEndpoints/AuthenticateEndpoint.cs`:

```csharp
public class AuthenticateEndpoint : EndpointBaseAsync
    .WithRequest<AuthenticateRequest>
    .WithActionResult<AuthenticateResponse>
```

Текст элемента `base_list`, извлечённый как есть:

```python
'EndpointBaseAsync\n    .WithRequest<AuthenticateRequest>\n    .WithActionResult<AuthenticateResponse>'
```

План предписывал брать текст base list «как есть, без нормализации». Последствия:

- **`signature_hash` перестаёт быть устойчивым к переформатированию.** Переносы строк
  и отступы попадают в хэш; переформатирование файла меняет хэш и заставляет агента
  на шаге 3 перегенерировать документ. Это прямо противоречит заявленной цели.
- Правило `base_type: ["EndpointBaseAsync"]` не сработает — в строке лежит вся цепочка.
- В манифесте появляются литеральные `\n` — JSON становится нечитаемым.

**Исправление:** схлопывать последовательности пробельных символов в base list в один
пробел при извлечении, а при матчинге правил сравнивать по идентификатору до `<`
и после последней `.`.

### 2. Файлы без namespace

4 файла объявляют типы в глобальном namespace. FQN для них равен имени типа.
Спецификация T10 склеивает `namespace + "." + name`, что при пустом namespace дало бы
FQN с ведущей точкой. В плане это описано («пустые части пропускаются»), но случай
стоит вынести в тест — вживую он встречается.

### 3. DI-регистрации живут в top-level statements

3 файла `Program.cs` (`Web`, `PublicApi`, `BlazorAdmin`) написаны в стиле top-level
statements — без класса и метода:

```csharp
builder.Services.AddScoped<IBasketService, BasketService>();
```

Фикстура использует классический `static class Program` с методом. Реализация T13,
написанная под фикстуру и ищущая вызовы внутри `method_declaration`, **не найдёт
ни одной регистрации в современном .NET-проекте**. Поиск обязан идти по всему дереву
файла независимо от вложенности.

### Распределение синтаксических конструкций

| Конструкция | Файлов |
|---|---|
| file-scoped namespace (`namespace N;`) | 239 |
| block namespace (`namespace N { }`) | 1 |
| без namespace | 4 |
| top-level statements | 3 |
| `global using` | 0 |
| `using static` / алиасы | 0 |

Обе формы namespace обязательны к поддержке — редкая форма встречается ровно один раз,
и именно на ней всё сломается, если её не учесть.

## Что показала черновая классификация

Правила из `rules/dotnet.yaml` (в редакции плана), применённые к 247 объявлениям типов:

```
unclassified     199        <- 81%
excluded          30
service           12
controller         4
provider           1
repository         1
                 ---
страниц документации: 18    из 244 файлов
```

**Правила слишком узкие.** 18 страниц на проект такого размера — это не документация.
Ниже разбор того, что попало в 199 неклассифицированных.

### Паттерн REPR вместо контроллеров

10 типов `*Endpoint` — в `PublicApi` HTTP-поверхность построена не на контроллерах:

```
CatalogItemGetByIdEndpoint    : IEndpoint<IResult, GetByIdCatalogItemRequest, IRepository<CatalogItem>>
CreateCatalogItemEndpoint     : IEndpoint<IResult, CreateCatalogItemRequest, IRepository<CatalogItem>>
AuthenticateEndpoint          : EndpointBaseAsync.WithRequest<…>.WithActionResult<…>
```

Контроллеров при этом всего 4. **Свести HTTP-поверхность к контроллерам — значит потерять
две трети API.** Для АС CF набор паттернов будет другим, но вывод общий: правила
обязаны настраиваться под проект, и первый прогон на реальном коде нужен именно
для того, чтобы их набрать.

### 9 интерфейсов `*Service` учтены как «неклассифицированные»

`IBasketService`, `IOrderService`, `ICatalogItemService` и ещё шесть отсеклись
предикатом `type_kind: [class, record]` — это **правильно** по замыслу (документируем
реализацию, а не контракт). Но в статистике они попали в общую кучу с типами, про
которые правила действительно ничего не знают.

**Следствие для T20:** `docpipe stats` должен разделять «интерфейс, покрытый
реализацией» и «не подошло ни одно правило». Иначе цифра `unclassified` бесполезна
для настройки правил — а именно ради неё команда и существует.

### Прочие крупные группы

| Суффикс | Штук | Что это | Предложение |
|---|---|---|---|
| `*Model` | 36 | Razor Page models, view models | добавить в `exclude.name_regex` |
| `*Specification` | 11 | паттерн Ardalis.Specification | отдельный `kind`, если нужен |
| `*Endpoint` | 10 | REPR-эндпоинты | отдельный `kind` + извлечение маршрутов |
| `*Configuration` | 9 | EF Core `IEntityTypeConfiguration` | скорее исключить |
| `*Test` | 6 | тесты | отсекать вместе с тестовыми проектами |

### Тестовые проекты попадают в документацию

45 типов из 247 (18%) лежат в 4 проектах `tests/`:
`UnitTests`, `FunctionalTests`, `IntegrationTests`, `PublicApiIntegrationTests`.

Они прошли бы в манифест как обычные узлы. Нужен либо `exclude.path_glob: ["**/tests/**"]`,
либо — точнее — настройка `enrolled` в `docpipe.yaml`. Второе лучше: тестовые проекты
всё равно должны **парситься** (их символы участвуют в графе наследования), но узлов
документации порождать не должны. Это ровно тот случай, ради которого enrollment
отделён от scope.

## Коллизии имён: модульное дерево спасает

22 имени типов встречаются в нескольких файлах:

```
CatalogItem   : src/ApplicationCore/Entities/CatalogItem.cs
                src/BlazorShared/Models/CatalogItem.cs
Constants     : src/BlazorShared/Authorization/Constants.cs
                src/Web/Constants.cs
```

**Почти все дубли разнесены по разным модулям**, и раскладка разводит их
автоматически — хэш-суффикс не понадобится.

**Уточнение (2026-07-31).** Раньше здесь стоял вывод, что это подтверждает выбор
именно модульного дерева, а раскладка по видам сущностей дала бы массовые коллизии.
Вывод неверен, и ошибка поучительная: коллизии разводит не порядок сегментов,
а то, что **имя модуля вообще входит в путь**. Раскладки `{модуль}/{вид}` и
`{вид}/{модуль}` — перестановка одной тройки, и множество конфликтов у них общее
(проверено на ABP: одни и те же 19 путей на 47 узлов). Массовые коллизии дала бы
раскладка **без** модуля — `docs/<kind>/<slug>.md`, — а её никто не предлагал.
Подробнее — в `docs/parser-architecture.md`, §2.5.

Найдено 5 вложенных типов (`CatalogItem.CatalogItemDetails`, `LoginModel.InputModel`),
причём `InputModel` объявлен дважды в разных родителях — `containing_type` в FQN
обязателен, иначе они схлопнутся в один узел.

## Покрытие XML-документацией: 16 типов из 247

**6.5%.** Исходники почти не содержат `///`-комментариев.

Это ключевой факт для шага 3: **описания придётся выводить из структуры кода**
(имена, базовые типы, сигнатуры, DI-связи, маршруты), а не пересказывать существующие
комментарии. Что совпадает с требованием из `purpose.md` — «в документации содержится
описание, а не повторение кода», — но означает, что агент не сможет опереться
на подсказки в коде и нагрузка на него выше, чем можно было ожидать.

Стоит проверить эту цифру на АС CF до планирования шага 3: если там XML-doc покрыт
хорошо, задача агента становится принципиально проще.

## Итог: что менять в плане

| Приоритет | Что | Где |
|---|---|---|
| Высокий | Схлопывать пробелы в `base_types` | T06 |
| Высокий | Искать DI-вызовы по всему дереву, не внутри методов | T13 |
| Высокий | Разделить `unclassified` и «интерфейс покрыт реализацией» | T20 |
| Средний | Второй набор фикстур с находками из дикой природы | новая T01b |
| Средний | Тест на тип без namespace | T10 |
| Низкий | Расширить `exclude.name_regex` (`*Model`, `*Configuration`) | T14 |
| Низкий | Пример `enrolled` для отсечения `tests/` в `docpipe.yaml` | T21 |

Правила классификации под конкретный проект (`*Endpoint`, `*Specification`) намеренно
**не** зашиваются в дефолтный `rules/dotnet.yaml`: они специфичны для eShopOnWeb.
Для АС CF набор будет свой, и собирать его нужно по выводу `docpipe stats`.

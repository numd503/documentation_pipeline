# Парсер структуры документации (`docpipe`) — архитектура

Документ описывает шаг 1 пайплайна из [`purpose.md`](../purpose.md): детерминированное
построение дерева документации по исходному коду. Скоуп текущей версии — **только .NET (C#)**.

---

## 1. Что делает шаг и чего он не делает

**Делает:** читает исходники решения и производит один артефакт — манифест `doc-tree.json`,
описывающий, какие документы должны существовать, где они лежат, каким шаблоном описываются
и на какие места в коде ссылаются.

**Не делает:** не создаёт директории, не пишет `.md`, не вызывает LLM, не читает и не изменяет
уже существующую документацию.

Это сознательное разделение. Шаг 1 — чистая функция без сайд-эффектов: одинаковый вход даёт
байт-в-байт одинаковый выход. Создание иерархии директорий (шаг 2) и наполнение документов
агентом (шаг 3) — отдельные процессы, потребляющие манифест.

```
                     ┌─────────────────────────────────────┐
   исходники .NET ──▶│  Шаг 1: docpipe scan (детермин.)    │──▶ doc-tree.json
                     └─────────────────────────────────────┘         │
                                                                     ▼
                     ┌─────────────────────────────────────┐
                     │  Шаг 2: materialize (идемпотентно)  │──▶ docs/**/*.md (скелеты)
                     └─────────────────────────────────────┘         │
                                                                     ▼
                     ┌─────────────────────────────────────┐
                     │  Шаг 3: агент + tools (недетермин.) │──▶ наполненные документы
                     └─────────────────────────────────────┘
```

Граница между детерминированным и недетерминированным проходит строго по одной линии:
**классификация — правила, описание — агент.** Решение «этот класс — контроллер» принимает
правило из YAML. Решение «что этот контроллер делает» принимает агент.

## 2. Ключевые архитектурные решения

### 2.1 tree-sitter, а не Roslyn

Парсинг C# выполняется через `tree-sitter` + грамматику `tree-sitter-c-sharp` (обе ставятся
готовыми wheel-пакетами, компилятор не нужен).

| | tree-sitter | Roslyn |
|---|---|---|
| Зависимости | pip wheel | .NET SDK + `restore` + сборка |
| Работает на «сыром» checkout | да | нужен собирающийся солюшн |
| Скорость | секунды–десятки секунд | минуты |
| Устойчивость к сломанному коду | да | нет |
| Семантика (резолв символов) | нет | полная |

Для построения **структуры** семантика почти не нужна: классификация идёт по атрибутам,
именам базовых типов и конвенциям имён — это синтаксис. Недостающее (цепочки наследования
внутри решения) достраивается самостоятельно, см. §4.3.

.NET SDK в среде пайплайна не предполагается. Обогатитель на Roslyn не проектируется.

### 2.2 Индекс символов отделён от скоупа парсинга

Дорог только парсинг. Для корректной классификации нужен не весь манифест, а **индекс
символов всего решения**: FQN → вид типа, базовые типы, атрибуты, члены. Он на порядки
меньше и кэшируется.

Отсюда следует главное свойство системы: можно перепарсить один модуль, но резолв и
классификацию прогнать по **полному** графу символов — и получить тот же результат, что
даёт полный скан.

Без этого разделения частичный прогон молча ломается: `PricingController : BaseApiController`,
где базовый класс лежит в другом модуле, не будет классифицирован как контроллер.

### 2.3 Два режима работы

**Инкрементальный (по умолчанию, отдельного флага нет).** Обход и хэширование всех файлов
(без парсинга — это ~1–2 с на десятках тысяч файлов), репарс только изменённых. Результат
**по построению совпадает** с полным сканом. Это чистая оптимизация.

**Скоуп (`--scope src/Cf.Pricing.Api`).** Обход ограничен указанными директориями, узлы вне
скоупа переносятся из предыдущего манифеста, символы вне скоупа берутся из кэша. Требует
`--from-manifest`, без него команда отказывается работать.

Честная граница скоупа: если тип **вне** скоупа поменял базовый класс, сущности внутри
скоупа могли переклассифицироваться, и скоуп-режим этого не увидит. Поэтому:

- скоуп — инструмент дев-цикла (крутить правила, смотреть на один модуль);
- источник истины в CI — инкрементальный прогон по всему репозиторию.

Манифест, полученный в скоуп-режиме, помечен `partial.scope`, чтобы это было видно и
downstream, и ревьюеру.

### 2.4 Enrollment ≠ scope

Два похожих, но разных понятия — их легко перепутать:

- **scope** — «что я сейчас перепарсиваю». Влияет на скорость и на размер диффа.
- **enrollment** — «что вообще входит в документацию». Влияет на состав манифеста.

Неenrolled модули **всё равно парсятся** при полном прогоне (их символы нужны для графа
наследования), но узлов документации не порождают. Это позволяет внедрять документацию
по 2–3 модуля за раз, не теряя корректности классификации.

### 2.5 Размещение файлов ≠ навигация

Физическая раскладка задаётся `doc_layout` и по умолчанию группирует документы
по виду сущности (`docs/modules/<kind>/<csproj>/<slug>.md`):

```
docs/
  modules/gridservices/Cf.Pricing.Api/…     # сначала вид, потом проект
  modules/controllers/Cf.Pricing.Api/…
```

Выбор в пользу вида, а не проекта, сделан потому, что вопрос «покажи все
grid-сервисы» задают чаще, чем «покажи всё в этом проекте», а первый в раскладке
`module-first` требует обхода всего дерева. Обратный порядок остался под
`doc_layout: module-first`.

**Коллизии тут ни при чём, и это стоит проговорить прямо.** Соблазн считать
модульную раскладку «более безопасной» разбивается о то, что обе — перестановка
одной и той же тройки (модуль, вид, slug). Путь в каждой однозначно определяется
тройкой, поэтому множество узлов, спорящих за один файл, у них общее; на ABP это
одни и те же 19 путей на 47 узлов. Разводит их в обоих случаях хэш-суффикс.

Плата за `kind-first` ровно одна: модуль перестал быть префиксом пути, поэтому
`docs status МАНИФЕСТ docs/modules/Cf.Pricing.Api` больше не выбирает проект
целиком — его документы разложены по каталогам видов. Владение это не задевает:
оно считается по путям **исходников**, а не по `doc_path`, — но команде, которая
читает документацию попроектно, `module-first` подойдёт лучше.

**Генерируемых индексов `docs/_views/**` нет и не планируется.** Здесь они были обещаны
как слой читаемости; при проектировании шага 2 решение изменилось — документация просто
лежит в репозитории набором `.md`, а навигацию даёт файловое дерево и поиск. Раздел
оставлен как запись о том, что решение принято осознанно, а не забыто.

Манифест при этом по-прежнему содержит всё, что понадобилось бы такому слою — `domain`,
`endpoints`, `dependencies`, — и сделать представления снаружи можно в любой момент:
это чистая функция от манифеста, шаг 1 не затрагивается.

## 3. Карта модулей

```
docpipe/
├── cli.py                    точка входа (typer): scan / diff / stats / validate / schema
├── config.py                 docpipe.yaml: roots, enrolled, domains, пути к правилам
├── model.py                  все pydantic-модели + генерация JSON Schema
├── hashing.py                content_hash, signature_hash, stable_json_dumps, slugify
├── discovery.py              обход ФС, ignore-правила, применение scope
├── cache.py                  sqlite-кэш разобранных файлов (индекс символов)
├── dotnet/
│   ├── sln.py                разбор .sln → список проектов
│   ├── csproj.py             разбор .csproj → TFM, ProjectReference, PackageReference
│   ├── queries/*.scm         tree-sitter запросы (данные, не код)
│   ├── parser.py             файл .cs → FileParseResult (чистый синтаксис)
│   ├── resolve.py            usings→FQN, слияние partial, замыкание наследования
│   ├── endpoints.py          сборка HTTP-маршрутов контроллеров
│   └── di.py                 регистрации DI и сервисов Ignite
├── classify.py               движок правил: Symbol → kind + template
├── tree.py                   сборка дерева, slug'и, коллизии, связи, домены
├── emit.py                   детерминированная сериализация манифеста
└── diff.py                   сравнение двух манифестов
```

Правила и схемы лежат вне пакета, потому что они — конфигурация, а не код:

```
rules/dotnet.yaml             правила классификации
schema/doc-tree.schema.json   генерируется из pydantic-моделей
docpipe.yaml                  конфигурация запуска
```

## 4. Поток данных

```
  discovery ──▶ [пути .cs, .csproj, .sln]
       │
       ├──▶ csproj/sln ──────────────▶ граф модулей (TFM, зависимости)
       │
       └──▶ cache ──miss──▶ parser ──▶ FileParseResult ──▶ cache
                 │                            │
                 └──hit───────────────────────┤
                                              ▼
                                          resolve ──▶ SymbolIndex (FQN → Symbol)
                                              │        + замыкание наследования
                                              ▼
                             endpoints ──▶  classify  ◀── rules/dotnet.yaml
                                   di ──▶      │
                                              ▼
                                            tree ──▶ DocNode[]
                                              │
                                              ▼
                                            emit ──▶ doc-tree.json
                                                     doc-tree.run.json (метаданные прогона)
```

### 4.1 Discovery

Обход от `--root`, сужение по `roots` из конфигурации (складывается с `--scope`:
первый постоянен, второй задаётся на один прогон), отбрасывание по `exclude.path_glob`
из правил (`**/obj/**`, `**/bin/**`,
`**/*.g.cs`, `**/*.Designer.cs`, `**/Migrations/**`). Пути нормализуются в репо-относительные
POSIX. Результат сортируется — обход ФС никогда не используется как источник порядка.

### 4.2 Parser

Один файл → один `FileParseResult`. Чистый синтаксис, никакой межфайловой логики:
`usings`, `global usings`, объявления типов (namespace, модификаторы, type parameters,
base list как сырой текст, атрибуты с аргументами, XML-doc), члены типов, DI-регистрации.

Запросы вынесены в `.scm`-файлы — их можно править, не трогая код.

### 4.3 Resolve

Три задачи:

**Резолв имён в FQN.** Для каждого имени из base list, детерминированный порядок попыток:

1. содержит `.` → пробуем как готовый FQN;
2. охватывающий namespace и его предки (`A.B.C.X`, `A.B.X`, `A.X`, `X`);
3. каждый `using` в лексикографическом порядке (`using + "." + name`);
4. не найдено → остаётся сырым именем.

При нескольких совпадениях берётся лексикографически меньший FQN и ставится флаг
`ambiguous`. Порядок 2→3 соответствует семантике C#.

**Слияние partial.** Объявления с одинаковым FQN и модификатором `partial` сливаются в один
`Symbol` с несколькими записями в `sources`. Это не редкость в .NET, и это же закрывает
требование «ссылки до конкретной реализации» — их может быть несколько.

**Замыкание наследования.** Транзитивный обход base list по индексу символов.
Нерезолвнутые имена (внешние фреймворочные типы вроде `ControllerBase`) сохраняются в
замыкании как есть — правила матчатся именно по ним.

### 4.4 Classify

Движок правил из `rules/dotnet.yaml`. Предикаты:
`attribute`, `base_type` (прямые), `inherits` (транзитивное замыкание), `name_regex`,
`name_suffix`, `namespace_regex`, `path_glob`, `type_kind`, `modifier`,
`has_member_with_attribute`.

Семантика:

- вычисляются **все** правила; совпавшие собираются в `matched_rules`;
- победитель — с наибольшим `priority`, при равенстве — лексикографически меньший `id`;
- если не совпало ни одно правило, узел не создаётся (тип не документируется);
- `inherits` покрывает и интерфейсы: отдельного предиката `implements` нет намеренно —
  различение класс/интерфейс в base list без полной семантики ненадёжно.

Поле `matched_rules` — не декорация. На проекте такого размера классификация без следа
«почему» становится чёрным ящиком, который невозможно отлаживать.

### 4.5 Tree

Присвоение `doc_path`, доменов, связей.

**Slug.** Имя типа → kebab-case с корректным разбором аббревиатур
(`HTTPClientFactory` → `http-client-factory`). Type parameters отбрасываются.

**Коллизии.** Если несколько узлов дают один `doc_path`, суффикс `-{sha256(fqn)[:8]}`
получают **все** участники коллизии. Так добавление нового конфликтующего типа не сдвигает
путь у существующих непредсказуемым образом.

**Связи (`related`).** Интерфейс ↔ реализации выводятся из графа наследования и из
DI-регистраций. Это позволяет документировать реализацию, а не интерфейс, не теряя связь.

**Домены.** Опциональный `domains.yaml` (glob по пути csproj → домен). При отсутствии —
фолбэк на имя модуля. Отсутствие файла не ломает работу.

### 4.6 Emit

`doc-tree.json` не содержит **ни одного** недетерминированного поля. Метаданные прогона
(время, хост, длительность, статистика) пишутся в сидкар `doc-tree.run.json`. Благодаря
этому тест на детерминизм — обычный побайтовый diff, без логики исключения полей.

Сериализация: `sort_keys=True`, `ensure_ascii=False`, `indent=2`, завершающий перевод строки.

## 5. Формат манифеста

```jsonc
{
  "schema_version": "1.0",
  "ruleset_version": "2026-07-30.1",
  "parser": { "tree_sitter": "0.26.0", "grammar_c_sharp": "0.23.5" },
  "partial": null,                     // либо {"scope": ["src/…"], "outside_from_cache": true}
  "modules": [
    { "id": "module:src/Sample.Pricing.Api/Sample.Pricing.Api.csproj",
      "name": "Sample.Pricing.Api",
      "csproj": "src/Sample.Pricing.Api/Sample.Pricing.Api.csproj",
      "target_frameworks": ["net8.0"],
      "project_references": ["src/Sample.Common/Sample.Common.csproj"],
      "domain": "pricing", "enrolled": true }
  ],
  "nodes": [
    {
      "id": "type:src/Sample.Pricing.Api/Sample.Pricing.Api.csproj#Sample.Pricing.Api.Controllers.PricingController`0",
      "kind": "controller",
      "template": "controller",
      "title": "PricingController",
      "doc_path": "docs/modules/controllers/Sample.Pricing.Api/pricing-controller.md",
      "parent": "module:src/Sample.Pricing.Api/Sample.Pricing.Api.csproj",
      "module": "Sample.Pricing.Api",
      "domain": "pricing",
      "symbol": {
        "fqn": "Sample.Pricing.Api.Controllers.PricingController",
        "type_kind": "class",
        "modifiers": ["public", "sealed"],
        "base_types": ["Sample.Common.Web.BaseApiController"],
        "base_type_closure": ["Sample.Common.Web.BaseApiController", "ControllerBase"],
        "attributes": [{ "name": "Route", "args": ["api/v1/pricing"], "named_args": {} }],
        "xml_doc": "Handles pricing requests."
      },
      "sources": [
        { "path": "src/Sample.Pricing.Api/Controllers/PricingController.cs",
          "start": 12, "end": 48 }
      ],
      "members": [
        { "name": "GetAsync", "kind": "method", "line": 24,
          "attributes": [{ "name": "HttpGet", "args": ["{id:guid}"], "named_args": {} }] }
      ],
      "endpoints": [
        { "http_method": "GET", "route": "api/v1/pricing/{id:guid}",
          "member": "GetAsync", "line": 24 }
      ],
      "dependencies": [
        { "target": "Sample.Pricing.Api.Services.IPricingService",
          "via": "constructor", "confidence": "high" }
      ],
      "related": [
        { "target": "type:Sample.Pricing.Api.Services.PricingService", "relation": "uses" }
      ],
      "matched_rules": ["controller.aspnet"],
      "signature_hash": "sha256:…"
    }
  ]
}
```

Три поля заслуживают отдельного упоминания:

- **`sources` — список.** В .NET сплошь `partial class`; одна сущность живёт в нескольких файлах.
- **`matched_rules`** — аудит классификации.
- **`signature_hash`** — хэш нормализованных сигнатур (не файла целиком). Позволяет шагу 3
  перегенерировать только те документы, чей публичный контракт изменился. На большом проекте
  это разница между «агент обходит 4000 документов» и «агент обходит 30».

## 6. Гарантии детерминизма

Требование из `purpose.md` превращено в проверяемые свойства:

| Свойство | Как обеспечивается |
|---|---|
| Стабильный порядок | `sorted()` на всех обходах; сортировка по кодпоинтам, без локали |
| Стабильные пути | только репо-относительные, POSIX-разделители |
| Отсутствие времени | все метаданные прогона — в сидкар-файле |
| Стабильная сериализация | `sort_keys=True, ensure_ascii=False, indent=2` |
| Видимость смены грамматики | версии tree-sitter и грамматики записаны в манифест |
| Стабильные коллизии | суффикс от хэша FQN, никогда не порядок вставки |

Проверяется тремя тестами:

```
full(repo) == full(repo)                                     # двойной прогон, байт-в-байт
full(repo) == full(repo с перемешанным порядком листинга)    # независимость от ФС
full(repo) == incremental(repo, любое состояние кэша)        # инвариант режима A
scoped(prev, scope) == full(repo), если вне scope не менялось # инвариант режима B
```

Последний тест — то, что отделяет «частичное обновление работает» от «частичное обновление
тихо врёт». Он обязателен.

## 7. CLI

```
docpipe scan --root PATH [--config docpipe.yaml] [--rules rules/dotnet.yaml]
             [--out artifacts/doc-tree.json]
             [--scope DIR]... [--from-manifest FILE]
             [--no-cache] [--stats] [--dry-run] [--jobs N]

docpipe diff OLD.json NEW.json [--format text|json]
docpipe stats MANIFEST.json
docpipe validate MANIFEST.json
docpipe schema --out schema/doc-tree.schema.json
```

`scan --stats` печатает состояние решений — сколько типов решено документировать,
сколько решено не документировать и с какой причиной, и сколько осталось без решения —
**без** генерации манифеста. На проекте такого размера первый запуск почти наверняка
оставит несколько тысяч без решения, и правила придётся крутить именно по этой сводке.
Отчёт устроен так, что у настройки есть признак завершения: см. T23 в плане.
`docpipe stats MANIFEST.json` — то же по готовому манифесту, где остались только виды.

`docpipe diff` — не удобство: **вход шага 3 должен быть диффом, а не деревом целиком.**
Иначе агент каждый раз обходит всё, и экономия от `signature_hash` пропадает. Категории
диффа: `added`, `removed`, `reclassified`, `signature_changed`, `moved`.

## 8. Известные ограничения

Сформулированы явно, чтобы их не пришлось обнаруживать в проде:

1. **Динамические DI-регистрации** (сканирование сборок, конвенции через рефлексию)
   синтаксически не видны. Такие рёбра просто отсутствуют; в найденных проставляется
   `confidence`, и они не выдаются за полную картину.
2. **Внешние типы не резолвятся.** `ControllerBase` остаётся строкой. Для правил этого
   достаточно, для глубокого анализа — нет.
3. **Скоуп-режим слеп к изменениям вне скоупа** (§2.3). Компенсируется полным прогоном в CI.
4. **Условная компиляция.** `#if` не вычисляется; tree-sitter возвращает все ветки — оба
   варианта члена попадают в документацию. Хуже другое: директива **внутри выражения**
   (аргументы атрибута, fluent-цепочка) рвёт разбор, и объявление типа может исчезнуть
   из вывода целиком. Обойти это в рамках tree-sitter нельзя, поэтому `validate` отдельно
   проверяет комбинацию «ошибки разбора есть, объявлений нет» — см.
   [findings-abp.md](findings-abp.md). На ABP такой файл один из 7869 (0,01 %).
5. **Генераторы исходников** (source generators) не запускаются — их вывод не документируется.
6. **Апгрейд грамматики может изменить вывод.** Это легитимно и должно быть видно в диффе,
   поэтому версии зафиксированы в `pyproject.toml` и записаны в манифест.

## 9. Точки расширения

- **Новый вид сущности** — правило в `rules/dotnet.yaml` + шаблон. Код не трогается.
- **Новый предикат** — одна функция в `classify.py` + запись в реестре предикатов.
- **Новый язык** (Python, TypeScript) — новый пакет рядом с `dotnet/`, отдающий тот же
  `FileParseResult`. `resolve`/`classify`/`tree`/`emit` переиспользуются как есть.
- **Представление «для людей»** — чистая функция от манифеста, пишется снаружи; ни шаг 1,
  ни шаг 2 не затрагиваются (см. §2.5: в объём пайплайна это не входит).

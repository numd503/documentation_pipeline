Что значит «агент настройки» в этом репозитории: **сценарий для агента контура**,
который проводит человека от «репозиторий вижу впервые» до детерминированного
критерия «настройка закончена» и умеет вернуться, когда репозиторий изменился.
Состоит он из четырёх частей: скилл (маршрут и контрольные точки), MCP-инструменты
настройки (детерминированные ответы), протокол интервью (что спрашивать
и куда ложится ответ), критерий окончания. `docpipe` LLM не зовёт: модель живёт
только в сессии агента (правило Р12 плана графа), а её догадки входят
в пайплайн только через файлы настройки, которые человек прочитал и закоммитил
(Р10).

## 1. Главное

1. **Почти вся работа — не текст скилла, а детерминированный код `docpipe`.**
   Из 29 задач оценки (§9) скилл и протокол интервью — три. Остальное — то,
   без чего скиллу нечего звать: машинный вывод команд, находки, которых
   сейчас нет, место для причины у каждого решения, сервер инструментов,
   критерий окончания. Это следствие двух условий, и оба от силы модели
   не зависят: граница детерминизма (вопрос строится из находки, которую
   воспроизводит команда, а решает правило, а не агент в момент ответа)
   и обрезка вывода инструментов у агента. Сила модели решает другое:
   порядок шагов и суждение по находкам остаются скиллу (§5).
2. **Агент контура читает `.gigacode/`, а не `.qwen/`** (подтверждено 07.10):
   `.gigacode/skills/`, `.gigacode/agents/`, `.gigacode/settings.json`,
   `GIGACODE.md`/`AGENTS.md`. Скилл `recon` лежит в `.qwen/skills/`,
   `install.sh` пишет `.qwen/settings.json` — **на контуре оба сейчас
   невидимы**. Перенос доставки — первая задача, она не ждёт ничего (§9, S23a).
3. **Поверхность настройки — 158 ключей в 12 видах файлов**, из них 45 —
   в `docpipe.yaml`. У 34 ключей `docpipe.yaml` из 45 известен молчаливый
   отказ: ошибка даёт правдоподобный результат, а не сообщение. 11 ключей
   не проверяются ничем, кроме типа (§4).
4. **Решений человека — около шестидесяти.** Для двух третей уже есть
   детерминированная находка, из которой строится вопрос. Для шести —
   кандидатов в `di_methods`, `dispatch_interfaces`, `registry_calls`,
   `features`, окончаний имён проекта и команд-владельцев — находки нет,
   и вопрос пришлось бы строить из догадки (§6.2).
5. **«Спросить только о новом» сейчас невозможно.** Поле для причины есть
   у трёх файлов из шести (`rules.yaml` → `exclude.rules[].reason`,
   `pages.yaml`, `arch-registry.yaml` → `note`). У `enrolled`, `exclude`,
   `domains`, `url_rewrite`, `registry_calls`, `di_methods`,
   `dispatch_interfaces` нечем отличить «решили не трогать» от «ещё
   не смотрели» — ровно тот дефект, ради которого классификация разделила
   `undecided` и `not_documented` (§6.3).
6. **Восемь команд, которые нужны настройке, отвечают только текстом**,
   а подготовку входа шага 2 (`_prepare`) нельзя позвать без CLI. MCP-инструменту
   их нечем отдать агенту, кроме как разбором вывода для человека (§6.1).
7. **Справочники, которые ассистент будет читать первым, в 17 местах
   расходятся с кодом.** Пока настройку вёл человек, это стоило захода;
   у ассистента неверный справочник — уверенный неверный совет (§6.5).
8. **Масштаб — 29 задач**, больше шага 1 (T00–T26): самый крупный план
   репозитория. Решения приняты, ждёт только прогон на контуре —
   28 задач могут идти сейчас; первой — перенос доставки
   в `.gigacode/`, затем этап A, который чинит дефекты, которые есть
   и без ассистента (§9).
9. **Шов фронт↔.NET входит в первую версию** (Р-5), и три его формы
   нынешний формат не выражает: эндпоинты вне атрибутной маршрутизации,
   URL через обёртку, сгенерированный клиент. Найденную в них границу
   агенту некуда записать, поэтому формат расширяется (§8, S26–S28).

## 3. Агент контура: что известно о gigacode

gigacode — форк qwen code, поэтому **возможности** берутся по qwen code,
а **каталоги** у него свои. Источники: владелец (07.10.2026) — каталоги
`.gigacode/`, инструмент вопроса пользователю и уровень моделей; официальная
документация GigaCode CLI на gitverse.ru —
`gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/` разделы `skills`,
`mcp`, `subagents` (прочитаны 06.10), `memory` и `commands`; документация
qwen code по тегам (`github.com/QwenLM/qwen-code`, `qwenlm.github.io/qwen-code-docs`).
Публичной связи «версия GigaCode → версия qwen code» нет; по набору полей
документация GigaCode соответствует qwen code ≥ 0.19. Строка «ограничения»
ниже — со слов сторонних пользователей (репозиторий polisade-orchestrator,
`cli-capabilities.yaml`), не проверена.

| Что | qwen code | GigaCode по документации | Что это значит для нас |
|---|---|---|---|
| Каталог проекта | `.qwen/` | **`.gigacode/`** (подтверждено владельцем) | доставка в `.qwen/` на контуре мимо — и для `recon` уже сейчас |

**Уточнить на контуре** (на форму задач влияет, но не блокирует):

1. `gigacode --version` — какой qwen code под ним;
2. имя и ограничения инструмента вопроса: сколько вариантов, есть ли

3. включены ли доверенные папки, есть ли системный `settings.json`

**Порядок зависимостей**, которого придерживается любой сценарий (сведено
из README, `CASHFLOW.md`, `web.md`, `pages.md`, `ownership.md`):

```

  → enrolled и exclude обхода            ← иначе вопросы об отсеве — про чужой код
  → di_methods, dispatch_interfaces      ← ложатся в манифест, di_methods — в ключ кэша
  → правила и отсев .NET до undecided = 0
  → web.roots → web scan --stats → url_rewrite, registry_calls
  → правила web до undecided = 0 → web pages → pages.yaml
  → docs_root / modules_dir / doc_layout окончательно
  → materialize --dry-run → ownership (слой 10 → --lint → 50 → 100) → docs status
  → [graph: engine_path, тот же --root; arch-registry через скилл recon]
```

`enrolled` в README стоит вторым шагом, после отсева, а в бандле поставки —
«первым делом»; спрашивать о нём надо первым, иначе вопросы «документировать
ли эти 120 типов» задаются про код, который документировать не будут.
Чек-лист §10 `CASHFLOW.md` по зависимостям не упорядочен.

## 5. Принципы, из которых следует план

**Факты и проверки — в инструментах, порядок и суждение — в скилле.**
Граница проходит не по силе модели, а по тому, что обязано воспроизводиться.
Находка, из которой строится вопрос («120 типов в `*.Migrations`»), и проверка,
которой закрывается шаг (`undecided` = 0), должны давать одно и то же на одном
и том же репозитории — это `docpipe`. Порядок фаз, выбор, о какой группе
спросить первой, толкование находки и формулировка вопроса — работа модели:
агент контура уровня GLM-5.3 Flash / Qwen3.8-Flash-Next-262k (07.10.2026)
справится с ней по скиллу, и переносить её в детерминированный автомат
«следующий шаг» — платить большой задачей за то, что модель и так умеет.
Остаётся одна оговорка: проверочный прогон на машине разработки идёт
на более сильной модели и переоценивает агента — S24 читается с этой поправкой.

**Вопрос строится из находки, и у каждого вопроса есть адрес.** Форма
из шага 5 скилла `recon`: находка с числом и примером → варианты → «от ответа
зависит…» → файл и ключ, куда ложится ответ, → поле для причины. Вопрос
без адреса — анкета, ответ без поля для причины — то же безымянное число,
ради которого переделывался отчёт классификации.

**Ответ человека — в файле настройки, а не в памяти агента.** Повторная
настройка читает прошлые решения из файлов, поэтому второй источник
(журнал решений рядом с настройкой) отстанет так же, как отставало зеркало
`business_hash`. Место для причины — в самих файлах (решение Р-2, §8).

**Контрольная точка — команда, а не мнение агента.** Каждый шаг
скилла заканчивается вызовом, результат которого проверяется числом:
`config check` без отказов, `undecided` = 0, `docs status` без необъяснимых
`missing`/`broken`.

**Ответ инструмента — сводка с адресом продолжения.** Агрегаты, первые N
примеров и ключ, по которому взять следующую страницу. Выгрузка на тысячу
строк будет обрезана агентом молча, и «таких нет» станет неотличимо от
«не показали» — та же ловушка, что `head -30` в `CASHFLOW.md` §1а.

**Ничего специфичного для АС CF.** Вопросы скилла общие («платформа,
управляемая метаданными?», «у каждого фронта свой префикс прокси?»), значения
АС CF в него не попадают. Сейчас этому мешает поставка: `install.sh:27`
раскладывает бандл АС CF на любой репозиторий.

## 8. Решения до плана

Все шесть приняты владельцем 07.10.2026.

**Р-1. Принято 07.10: ассистент пишет прямо в файлы настройки** в рабочем
дереве; ревью — `git diff`, решение — коммит человека. Довод владельца
сильнее исходного: правка лежит там, откуда её читает прогон, поэтому агент
может тут же позвать инструмент ещё раз и увидеть, как правка изменила
результат, — цикл «правило → прогон → разница» без переноса черновика.
Р10 соблюдается: в пайплайн входит закоммиченное. Черновик рядом
с боевым файлом остаётся только у `arch-registry`, где у записи есть
провенанс. Риск — комментарии: файлы бандла густо прокомментированы,
PyYAML их не сохраняет, поэтому запись — текстовыми правками (прецедент —
`tools/migrate_rules.py`), а не перезаписью модели, и сразу после записи —
проверка файла инструментом.

**Р-2. Принято 07.10: причина решения — в самих файлах настройки**, второй
формой записи рядом с короткой (`enrolled: ["src/**"]` продолжает работать,
рядом допускается `{glob, reason}`), плюс явный список отрицательных решений
там, где решение — «не брать». Журнал решений отдельным файлом отвергнут:
второй источник отстанет. Совместимость обязательна: копия настройки лежит
на АС CF, как в случае краткой формы `exclude`.

**Р-3. Принято 07.10: отдельный сервер `docpipe setup serve`** на общем
протокольном модуле; изоляция ошибок чинится в обоих. Уточнение к доводу:
`docpipe graph serve` — наш сервер (`docpipe/graph/mcp.py`) над нашим
индексом `graph.db`, а не сервер `codebase-memory-mcp`; движок зовётся только
подпроцессом в `graph build`, его собственный MCP-сервер не используется
(правило Р13). Вывод от этого не меняется: настройке индекс не нужен, сервер
настройки от графа не зависит и читает `docpipe.yaml`. Разведка, которую
сейчас отдаёт `docpipe_overview`, в сервере настройки — своим инструментом.

**Р-4. Принято 07.10: один скилл `setup` с фазами** в справочных файлах
рядом (`dotnet.md`, `web.md`, `link.md`, `docs.md`, `ownership.md`); фаза
`py` добавится файлом. **Открыто: нужен ли второй скилл для ревью.**
Онбординг, ревью и расширение области различаются входом, а не фазами:

- онбординг начинается с пустой настройки: область (Р-6) → фазы по §4;
- расширение — с кода, который человек назвал: что о нём уже решено
  и каким правилом (Р-6, п. 5);
- ревью — с существующей, и вопросов у него два: что появилось в области
  с прошлого раза (S15) и **верны ли прежние решения** — правило отсева,
  которое стало съедать вдвое больше, протухшие правила `pages.yaml`,
  мёртвые правила владения, модуль из `url_rewrite`, которого больше нет,
  отсев по пути, который накрыл новый каталог.

Рекомендация: один скилл с тремя входами, вход выбирается по состоянию
настройки и по просьбе человека; делить на два — если на прогонах S24 модель путает вход (скилл
выбирается по `description`, и у ревью своя формулировка — «проверить
настройку после изменений в репозитории»). Второй вопрос ревью требует
базы сравнения — прошлого манифеста или прошлого отчёта об остатке
(`docpipe diff` между манифестами есть); где она хранится, решает план.

**Р-5. Принято 07.10 с дополнением: в первую версию входит шов фронт↔.NET.**
Граница: .NET, Angular, **связь между ними**, документы и владение. По словам
владельца, шов — один из важнейших факторов, и это ровно та работа, которую
стоит отдать агенту: архитектурную границу детерминированно найти трудно,
а проверить найденную — легко. Встроенное сопоставление HTTP есть
(`web link`, источник связи для документов решён 06.10), настраивается
`web.url_rewrite` и `web.registry_calls`. Цикл фазы: находка `web link`
(вызовы без эндпоинта, эндпоинты без вызывающего, модули без правила,
«почти совпало») → агент читает код по обе стороны: прокси, интерцептор,
база URL в `environment`, обёртки вызовов → правило → прогон → разница.

Три формы шва нынешним форматом **не выражаются**, и найденную в них границу
агенту некуда записать — значит, в пайплайн она не войдёт (Р10):

| Форма | Почему не выражается | Источник |
|---|---|---|
| эндпоинты вне атрибутной маршрутизации: `MapControllerRoute`, minimal API (`app.MapGet`) | `endpoints.py` разбирает только атрибуты; `web link` лишь перечисляет такие контроллеры (`conventional_controllers`) | `frontend-analysis.md` §2.5, `web.md` |
| URL из переменной или через обёртку (`this.urls.save`, свой `ApiService.get(path)`) | вызов остаётся невосстановленным; объявить «первый аргумент этого метода — путь» нечем — аналог `di_methods` для HTTP | `frontend-analysis.md` §5.4 |
| сгенерированный клиент OpenAPI | связь через посредника, которого разбор не видит | `frontend-analysis.md` §6.3 |

Поэтому формат расширяется — ровно под формы, найденные на открытых
репозиториях (squidex, abp), и как первый случай общего формата правил
связей (`backlog.md`, «Правила связей между языками»), чтобы Python позже лёг
в него же. Задачи S26–S28.

**Р-6. Принято 07.10: остановку решает человек, проверяемо — состояние.**
Позиция владельца: настройка — взаимодействие человека и агента; человек
знает, какой код принадлежит ему и команде, задаёт область и направление
разведки и решает, когда остановиться; агент итеративно разбирает участки
кода, которые в области остаются необъяснёнными.

1. **Область — существующими ключами**, отдельного понятия нет: `roots`,
   `enrolled`, `exclude`, `web.roots` и отсев по пути с причиной в обеих
   секциях `rules.yaml`. У фронта аналога `enrolled` нет
   (`web/modules.py:152`), но и не нужен: `web.roots`, `exclude`
   и `path_glob` с причиной в секции `web` выражают то же. Всё вне области
   печатается одной строкой с числами: молча суженная область неотличима
   от «всё объяснено».
2. **По каждой находке — решение, «принятого остатка» нет.** Находка
   объяснена, когда по ней есть решение — документируем или нет, и почему.
   Эндпоинт, который никто не зовёт, — это тоже вопрос «документируем ли»,
   а не остаток. Где решению негде лечь, это пробел формата, а не повод
   для отдельного списка.
3. **Цикл**: агент берёт крупнейший кластер необъяснённого — по порядку фаз
   §4, внутри фазы по размеру, — разбирается в коде, пишет правило (Р-1),
   перезапускает инструмент и показывает разницу: сколько объяснено и не
   появилось ли нового. Человеку — вопросы там, где решение его.
4. **Проверяемый критерий**: в области нет находки без решения и нет
   дефектов. Потолка «допустимого числа» нет. В CI — `--fail-on-unexplained`
   по области: новый код в области даёт новую находку, и это вход ревью.
5. **Расширение области** — третий вход скилла (Р-4): человек называет
   код, который хочет покрыть; агент показывает, входит ли он в область
   и **какие правила и с какими причинами** о нём уже решили (S30), человек
   решение меняет, агент правит правило и показывает разницу.

Находки и где лежит решение по каждой:

| Находка | Решение | Где лежит |
|---|---|---|
| модуль или каталог без решения о включении | берём / не берём, причина | `enrolled`, `exclude` второй формой (Р-2); фронт — `web.roots`, `path_glob` с причиной |
| группа `undecided` | вид / не документируем, причина | `rules.yaml` |
| вызов без эндпоинта | правило шва (префикс, обёртка, реестр) или адресат вне репозитория — документируем как внешнюю зависимость или нет, причина | `url_rewrite`, `registry_calls`, правила шва (S28) |
| эндпоинт без вызывающего | вход извне — документируем как точку входа / не документируем, причина | правила шва (S28), ключ — маршрут или глоб маршрутов |
| страница без маршрута, обёртка, раздел без маршрута | `pages.yaml` с причиной | `pages.yaml` |
| узел без владельца | правило владения | `ownership.yaml` |
| файл с ошибкой разбора | не документируем, причина — или правка исходника | `path_glob` с причиной |

Две строки таблицы — эндпоинт без вызывающего и вызов во внешний адрес —
сейчас решению места не дают. Обе ложатся в правила шва: правило связи
описывает не только пару концов, но и конец, у которого пары в репозитории
нет и не будет, — с причиной. Это ровно «сколько концов осталось без пары»
из `purpose.md`. Решение «не документируем» по отдельному эндпоинту — это
решение на уровне маршрута, а единица документа — тип; рекомендация для
плана: документ контроллера помечает такой эндпоинт, а не теряет его.

**Дефекты — не решения, а починка**: отказ `config check`, `broken`
в `docs status`, `missing`, который не исчезает после `materialize`
(раскладка разошлась или файл не прочитан, см. `shadowed_docs`), ошибки
загрузки файлов настройки.

Формулировка в `purpose.md` («Настройка с ассистентом», критерий) поправлена
07.10 по этому решению.

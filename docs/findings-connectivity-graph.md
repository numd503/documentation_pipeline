# Граф связности: пригоден ли `doc-tree.json` для поиска пути между компонентами

Разведка под новую фичу, которой в планах нет. Постановка: пользователь знает два
компонента (сервис, контроллер, провайдер — что угодно), не знает, связаны ли они,
и выполняет команду, которая по `doc-tree.json` находит цепочку между ними либо
честно сообщает, что связи нет.

Вопрос разведки — **не** «как это написать», а «хватает ли данных, чтобы ответ был
верным». Ниже — измерения на двух реальных репозиториях и вывод.

## Короткий ответ

**В текущем виде манифест для этой задачи не годится, и провал будет тихим.**
Наивная реализация запустится, отработает и на подавляющем большинстве пар вернёт
«связь не найдена» — при том, что связь в коде есть. Это худший из возможных
исходов: отрицательный ответ выглядит как валидный результат, а не как отказ.

Причина одна и она структурная: **манифест — это отфильтрованный срез, а не граф.**
В него попадает 7 % разобранных символов, и вырезаны ровно те узлы, через которые
проходят пути — интерфейсы.

Данные при этом **есть**: 53–72 % целей рёбер лежат в индексе символов и теряются
при записи манифеста. То есть задача решаема, но не чтением `doc-tree.json` в его
нынешнем составе.

## Как измерялось

```bash
uv run docpipe scan --root examples/eshoponweb --out eshop.json
uv run docpipe scan --root examples/abp       --out abp.json
```

Набор правил — `rules/dotnet.yaml` по умолчанию, `enrolled: ["**"]`. Граф строился
неориентированным (вопрос «связаны ли», а не «кто кого вызывает»), связность —
обходом в ширину по компонентам. Скрипты разовые, в репозиторий не входят.

## Итог в цифрах

| | eShopOnWeb | ABP |
|---|---|---|
| символов в индексе | 253 | 8966 |
| узлов в манифесте | 18 (**7,1 %**) | 694 (**7,7 %**) |
| интерфейсов в индексе | 16 | 853 |
| **интерфейсов, ставших узлами** | **0** | **0** |
| рёбер `dependencies` | 47 | 966 |
| из них ведут в узел манифеста | 3 (6,4 %) | 17 (**1,8 %**) |
| рёбер `related` | 12 | 2832 |
| из них ведут в узел манифеста | 0 (**0 %**) | 0 (**0 %**) |
| пар узлов со связью, «в лоб» | 2,6 % | **0,02 %** |
| пар узлов со связью, с переходом через интерфейс | 22,9 % | 16,2 % |
| изолированных узлов при этом | 22 % | **48 %** |

Строка «0,02 %» и есть приговор наивной реализации: на ABP из 240 471 пары узлов
путь находится для 39.

## Что в манифесте вообще есть для связности

Четыре источника рёбер, и ни один не задумывался как граф:

- **`node.dependencies[]`** — параметры конструктора и DI-регистрации;
- **`node.related[]`** — `implements` на интерфейсы;
- **`module.project_references[]`** — ссылки между проектами;
- **`symbol.base_type_closure[]`** — транзитивное замыкание наследования.

Дальше — почему каждого из них по отдельности не хватает.

## Шесть причин, по которым наивная реализация врёт

### 1. Середина пути вырезана: интерфейсов среди узлов ноль

Типовая цепочка в .NET — `Controller -> IService -> Service`. Обе стороны ссылаются
на интерфейс: контроллер параметром конструктора, реализация — ребром `implements`.

Интерфейс узлом **не становится никогда**: все правила классификации в
`rules/dotnet.yaml` требуют `type_kind: ["class", "record"]`. Проверено — 0 из 16
на eShopOnWeb, 0 из 853 на ABP.

Отсюда `related` со стопроцентной надёжностью ведёт в пустоту: **2832 ребра на ABP,
0 из них ведут в узел.** Это не редкий случай, а инвариант набора правил
по умолчанию.

Переход через интерфейс — не оптимизация, а единственный механизм, который вообще
даёт связность: он поднимает долю связанных пар с 0,02 % до 16,2 % на ABP
и с 2,6 % до 22,9 % на eShopOnWeb. Реализация, которая ходит только по узлам,
не найдёт почти ничего.

Обратный индекс (интерфейс -> его реализации) в репозитории уже есть —
`registry/anchors.py::build_index`, поле `implementors`. Он строится перебором
`related` у каждого узла ровно потому, что ребра `implemented_by` в манифесте нет.
Это готовая точка переиспользования, а не то, что нужно писать заново.

### 2. Цель ребра — FQN, а FQN не ключ

`Dependency.target` и `Relation.target` — строки FQN. Но FQN типы не различает:
на ABP 18 FQN стоят за более чем одним узлом (71 узел суммарно), а ключом символа
является тройка «модуль + FQN + арность» — об этом отдельный раздел в `CLAUDE.md`.

Значит переход «ребро -> узел» принципиально **один-ко-многим**, и выбор кандидата
обязан быть детерминированным и объяснимым. Иначе цепочка будет меняться между
прогонами на одном и том же коде — а поиск пути, дающий разные ответы, хуже
отсутствующего.

### 3. Рёбер из методов нет вовсе — только конструкторы

`tree._constructor_dependencies` разбирает **только** члены с `kind == "constructor"`.
На ABP в индексе 3484 конструктора и **18 828 методов**; параметры методов,
типы возвращаемых значений, свойства (10 780), локальные `GetRequiredService<T>()`,
`new`, статические вызовы и фабрики не дают ребра ни одного.

Это объясняет 48 % изолированных узлов на ABP даже после перехода через интерфейс.
Связь «A влияет на B» в коде существует, в манифесте её нет.

### 4. У `dependencies` смешаны два разных смысла и два направления

`via` бывает `constructor` и `di`, и читаются они противоположно:

- `constructor`: `target` — то, что тип **потребляет**;
- `di`: `target` — интерфейс, под которым тип **зарегистрирован**, то есть то,
  чем тип является, а не то, что он использует (см. docstring
  `tree._di_dependencies`).

Сложить их в один список рёбер и пойти обходом — значит получить путь, который
на человеческом языке не читается никак. Для ответа «влияют ли друг на друга»
направление придётся восстанавливать по `via`, а не по факту наличия ребра.

Отдельно: DI-рёбер почти нет — **8 из 966 на ABP**. Динамическая регистрация
(маркерные интерфейсы `ITransientDependency`, сканирование сборок) синтаксически
не видна и в манифест не попадает принципиально. Опираться на `via: di` как
на источник связности нельзя.

### 5. Словарь связей наполовину мёртвый

В `model.py` объявлено больше, чем производится:

| Объявлено | Производится |
|---|---|
| `DependencyVia = constructor \| di \| inheritance` | `inheritance` — **никогда** |
| `RelationKind = implements \| implemented_by \| uses` | только `implements` |

Проверено грепом по всему `docpipe/`. Реализация, написанная по схеме, будет
ждать `implemented_by` и `uses` и не получит их ни разу. Схема здесь описывает
намерение, а не данные, — и это именно та ловушка, которая проходит все критерии
приёмки и ломается в проде.

### 6. Уровень модулей отвечает «да» всегда

Соблазн взять запасной уровень: не нашли путь по узлам — поищем по
`project_references`. Ссылки резолвятся хорошо (18 из 18 и 2383 из 2383), граф
почти связный: на ABP крупнейшая компонента — 631 модуль из 671, 88,4 % пар.

Но для **узлов** это даёт **100 % пар в одной компоненте модулей** на обоих
репозиториях. То есть ответ на уровне модулей — всегда «связаны», для любой пары.
Как запасной уровень он бесполезен: он не отвечает на вопрос, он его отменяет.

Годится он ровно на одно — как отрицательный признак: если модули двух компонентов
лежат в **разных** компонентах графа модулей, связи гарантированно нет, и искать
дальше не нужно. На ABP это отсекает 11,6 % пар модулей.

## Чего конкретно не хватает

По убыванию влияния на результат:

1. **Символы, не ставшие узлами.** Манифест хранит только узлы; 53,2 % целей
   рёбер на eShopOnWeb и **72,4 % на ABP** — это типы, которые парсер разобрал
   и положил в индекс, а запись манифеста выбросила. Из них подавляющее
   большинство — интерфейсы (635 из 699 на ABP). **Данные не отсутствуют,
   они не доезжают.**
2. **Рёбра из методов и свойств.** Крупнейший неиспользованный источник связей;
   требует правки шага 1, а не только формата.
3. **Обратные рёбра.** `implemented_by` для интерфейсов, `used_by` для
   потребителей. Восстановимы обходом на стороне читателя, но тогда каждый
   потребитель манифеста строит их заново.
4. **Идентичность цели ребра.** `target` должен быть `node_id`/ключом символа,
   а не FQN, — иначе переход всегда неоднозначен.

## Что предлагается

Три варианта, от дешёвого к правильному.

**A. Только чтение манифеста, ничего не менять в шаге 1.** Команда строит граф
из `dependencies` + `related` + обратного индекса реализаций. Дёшево, ломать
нечего. Потолок — измерен: 16–23 % пар, половина узлов изолирована, а на суженном
`enrolled` (см. ниже) — 3,6 %. **Годится как прототип, но не как ответ
пользователю:** «связь не найдена» будет означать «мы не знаем», а постановка
требует честного «связи нет».

**B. Добавить в манифест транзитные символы.** Отдельная секция графа рядом
с `nodes[]`: узлы-посредники (в первую очередь интерфейсы), которые сами
документами не становятся, но нужны для пути. Закрывает причины 1 и 2, не трогает
состав документации и не ломает шаги 2 и 3. Это минимальное изменение,
после которого ответ становится осмысленным.

**C. Отдельный артефакт `doc-graph.json`.** Граф как самостоятельный выход шага 1,
со своими ключами (ключ символа, не FQN), обеими сторонами рёбер и видом связи.
Правильно по составу и не смешивает «что документировать» с «что с чем связано» —
это разные вопросы, и класть их в один файл значит связать их изменения.

Рекомендация — **B как первый шаг, C как форма**, если граф начнёт расти: секция
внутри манифеста добавляет полю `nodes[]` соседа, но не меняет его смысл, а вынос
в отдельный файл всегда можно сделать потом. Обратный порядок дороже.

Отдельно и независимо от выбора: **рёбра из параметров методов** (причина 3) дают
больше связности, чем любая работа с форматом, и не требуют её вовсе.

## Подводные камни для реализации

**Ответ «связи нет» обязан отличаться от «мы не смогли посмотреть».** Это главное
требование, и оно прямо следует из цифр выше. Если 62 % рёбер ведут в тупик,
а половина узлов изолирована, то честная формулировка — «путь не найден, при этом
N рёбер на пути оборвались на типах вне документации». Молчаливое «нет» здесь —
ложь с вероятностью, которую мы измерили.

**Суженный `enrolled` обрушивает связность.** Проверено: на eShopOnWeb с
`enrolled` только по `Web` и `PublicApi` доля связанных пар падает с 22,9 %
до **3,6 %**, изолированных узлов становится 75 %. Реализации живут в
`Infrastructure`, он не enrolled, узлов не даёт, цепочки рвутся. **На АС CF
`enrolled` будет узким** — то есть это не крайний случай, а рабочий режим.

**Компонент нельзя назвать просто именем.** На ABP 17,1 % узлов имеют
неуникальный `title` (`HomeController` — 8 штук, `MyProjectNameBrandingProvider` —
20). Пара `(module, title)` тоже не спасает: 47 узлов под 19 неуникальными парами.
Команда обязана принимать уточнение и при неоднозначности показывать кандидатов,
а не выбирать молча первого.

**Порядок обхода не может быть источником порядка.** Общее правило репозитория
действует и здесь: при нескольких кратчайших путях выбор обязан идти по явному
ключу сортировки. Иначе одна и та же команда на одном и том же манифесте даёт
разные цепочки, и первым, что сломается, будут тесты.

**Циклы в графе есть.** `compute_closures` уже защищается от циклов наследования
на битом коде; в графе зависимостей циклы легальны (взаимная регистрация через
интерфейсы). Обход обязан помнить посещённое.

**Длина пути должна быть ограничена.** При 694 узлах и переходе через интерфейсы
связность даёт компоненту в 279 узлов; путь из 15 хопов формально существует,
но как ответ на вопрос «влияют ли друг на друга» он бессмысленен. Предел глубины
нужен и он должен быть виден в выводе.

## Побочная находка: ошибка в `docs/manifest.md`

Пример модуля в `manifest.md` показывает

```json
"project_references": ["module:src/Sample.Common/Sample.Common.csproj"]
```

— с префиксом `module:`. В данных префикса нет, это путь к `.csproj`:

```json
"project_references": ["eShopOnWeb/src/BlazorShared/BlazorShared.csproj"]
```

Docstring `Module` в `model.py` описывает поле верно («пути, сравнимые с полем
`csproj` другого модуля»), ошибка только в справочнике. На этом уже споткнулся
первый заход этой самой разведки: граф модулей по примеру из документации дал
0 % разрешённых рёбер вместо 100 %. Правится одной строкой.

**Проверено:**

```

uv run ruff format --check  → 4 files already formatted
uv run mypy docpipe         → Success: no issues found in 2 source files
uv run pytest -q            → no tests ran (ожидаемо, тестов ещё нет)
```

### Трудности и отклонения от плана

**1. Typer схлопывает единственную команду в корневую.**
`uv run docpipe version` падал с `Got unexpected extra argument(s) (version)`.
Причина: при одной зарегистрированной команде typer делает её корневой, и слово
`version` разбирается как лишний позиционный аргумент.
Решение: пустой `@app.callback()` переводит приложение в многокомандный режим.
План обновлён — этот пункт добавлен в T00, иначе агент-реализатор упрётся в то же самое.

**2. `ruff format --check` форматирует Python-блоки внутри markdown.**
Проверка падала на `docs/parser-implementation-plan.md`: ruff переписывал компактные
псевдо-сигнатуры вида `def f(a,\n b) -> X: ...` в свой стиль. Это документация, а не код.
Решение: `extend-exclude = ["docs", "examples"]` в `[tool.ruff]`.
План обновлён.

**3. hatchling не находил пакет автоматически.**
Добавлен явный `[tool.hatch.build.targets.wheel] packages = ["docpipe"]`.
План обновлён.

**4. `.gitignore` уже существовал** со строкой `examples/` (туда склонированы `abp` и
`eshoponweb` для финальной проверки). Строка сохранена, остальные правила дописаны.

### Замечание на будущее

`uv run docpipe ...` пересобирает и переустанавливает пакет на каждом вызове
(`Built docpipe @ file:///...`). Это ~0.5 с накладных расходов на команду. На тестах
не сказывается (они импортируют модуль напрямую), но при ручной отладке CLI заметно.

**Создано:** 15 файлов в `tests/fixtures/SampleSolution/` (1 `.sln`, 2 `.csproj`, 12 `.cs`),

**Проверено:**


Дополнительно, разовой проверкой вне тестов: **все 12 файлов `.cs` парсятся
tree-sitter с `err=0`**, `root_node.has_error == False`. Это важно было проверить
до T06: если бы фикстура не разбиралась, вся дальнейшая работа строилась бы на песке.

### Отклонение от плана

**Тест сделан строже, чем требовал план.** План просил проверить только количество
(`.cs` ровно 12, `.csproj` 2, `.sln` 1). Вместо этого зафиксирован точный отсортированный
список путей и добавлены три содержательных теста:

- `test_generated_file_is_present_but_will_be_excluded` — файл под `obj/` существует;
- `test_partial_class_lives_in_two_files` — обе половинки содержат `partial class`;
- `test_cross_module_inheritance_chain` — цепочка `PricingController` →
  `BaseApiController` (другой модуль) → `ControllerBase` на месте.

Причина: проверка на количество не ловит подмену состава. Если кто-то удалит
`PricingService.Calculations.cs` и добавит любой другой `.cs`, счётчик сойдётся,
а тесты T10 и T18 начнут проверять не то, что задумано.

### Трудность: `.gitignore` мог тихо убить фикстуру (T01)

Файл `obj/Debug/net8.0/Sample.Generated.g.cs` нужен, чтобы проверять правила исключения.
Любой стандартный .NET-шаблон `.gitignore` содержит `obj/` и `bin/` — добавь его кто-нибудь
позже, и файл исчезнет из репозитория, а тесты T04/T14 продолжат проходить, ничего не
проверяя. Проверено `git check-ignore` (сейчас не игнорируется), в `.gitignore` добавлен
явный запрет-предупреждение.


Все 7 пар из таблицы плана проходят без правок алгоритма. Сверх плана добавлены тесты:
идемпотентность `slugify` (повторное применение к результату ничего не меняет),
невозможность пустого slug, независимость `stable_hash` от порядка ключей,
чувствительность `stable_hash` к порядку элементов списка.

### Отклонений от плана нет

Алгоритм реализован ровно как в спецификации. Регекс границ CamelCase
`(?<=[a-z0-9])(?=[A-Z])|(?<=[A-Z])(?=[A-Z][a-z])` корректно обрабатывает аббревиатуры.

### Кириллица в именах типов — вопрос закрыт

**Итог: действий не требуется.** Владелец проекта подтвердил, что в сигнатурах АС CF
кириллицы нет (в комментариях — есть, но они не затрагиваются).

`slugify` применяется ровно в одном месте — имя типа → имя файла в `doc_path`.
Проверено на парсере, что во всех остальных местах кириллица доходит до манифеста
без изменений:

| Что | Кириллица | Куда попадает |
|---|---|---|
| XML-doc `///` | сохраняется | `symbol.xml_doc` |
| Обычные комментарии | не извлекаются | никуда |
| Namespace, FQN, `node.id` | сохраняется | идентификаторы узлов |
| Аргументы атрибутов | сохраняется | `endpoints[].route` |
| Имя модуля в пути | сохраняется | `docs/modules/Расчёты/…` |
| Имя типа → имя файла | **схлопывается в `unnamed`** | только имя `.md`-файла |

Имя модуля идёт в путь сырым, а имя типа — через `slugify`, и это обосновано:
имя модуля берётся из имени файла `*.csproj`, то есть валидно для ФС по построению;
имя типа берётся из идентификатора, который валидным быть не обязан.

Разбор ниже сохранён на случай, если кириллические имена типов всё же обнаружатся
в каком-нибудь модуле.

### Разбор (справочно)

Проверка на реалистичных именах (вне тестов):

```
PricingController    -> 'pricing-controller'      OAuth2Handler   -> 'o-auth2-handler'
FXRateProvider       -> 'fx-rate-provider'        HTTPSProxy      -> 'https-proxy'
IRepository`1        -> 'i-repository-1'          GridGainService -> 'grid-gain-service'
DTOMapper            -> 'dto-mapper'              ApiV2Controller -> 'api-v2-controller'
ЦенаСервис           -> 'unnamed'   ← проблема
Сервис               -> 'unnamed'   ← проблема, коллизия с предыдущим
```

**Любое имя без ASCII-букв схлопывается в `unnamed`.** Корректность при этом не страдает:
разрешение коллизий в T15 добавит хэш-суффикс, и пути останутся уникальными. Но
читаемость теряется полностью — вместо осмысленного имени получится
`unnamed-a1b2c3d4.md`.

В C# кириллические идентификаторы легальны. Насколько это актуально для АС CF — вопрос
к владельцу проекта. Варианты, если понадобится:

1. **Оставить как есть** — коллизии разрешаются хэшем, имена нечитаемы. Ноль работы.
2. **Транслитерация** (`Сервис` → `servis`) — детерминированно, читаемо, нужна таблица
   соответствий на ~66 символов.
3. **Разрешить Unicode в именах файлов** — читаемо, но рискованно для кросс-платформенных
   путей, git на macOS (нормализация NFD/NFC) и внешних инструментов документации.

Реализован вариант 1, как и предписывал план. К нему возвращаться не нужно, пока
`docpipe stats` на реальном репозитории не покажет узлы со slug `unnamed`.


### Отклонения от плана

**1. Типизированные псевдонимы вместо голых `str`.** План описывал
`Symbol.type_kind: str`. Вместо этого заведены псевдонимы `TypeKind`, `MemberKind`,
`Lifetime`, `Confidence`, `DependencyVia`, `RelationKind` и используются на всех
уровнях единообразно. Причина: `type_kind` участвует в правилах классификации (T14),
и опечатка вида `"klass"` иначе всплыла бы только на проде в виде пустой выборки.
Есть тест `test_literal_fields_reject_typos`.

**2. Добавлен `extra="forbid"`.** Плана не нарушает, но не был им предписан.
Ловит опечатки при загрузке чужого манифеста (`--from-manifest` в T18) вместо
молчаливого игнорирования поля. Совместимость вперёд при этом не теряется:
`schema_version` объявлен как `Literal["1.0"]`, то есть несовместимость версий
и так фиксируется явно.

Обе модели `frozen=True` — как и предписывал план.

### Трудность: `Final` для константы со значением `Literal`

`SCHEMA_VERSION = "1.0"` выводился mypy как `str` и не подходил полю
`Literal["1.0"]`:

```
model.py:252: error: Incompatible types in assignment
  (expression has type "str", variable has type "Literal['1.0']")
```

Лечится явной аннотацией `SCHEMA_VERSION: Final[Literal["1.0"]] = "1.0"`.
Мелочь, но mypy strict её не пропускает, а агент-реализатор потратит на это время.

### Замечание: состав `$defs` в схеме

В сгенерированную схему попали 11 моделей:
`Attribute, Dependency, DocNode, Endpoint, Member, Module, ParserVersions,
PartialInfo, Relation, SourceSpan, Symbol`.

**`RawDeclaration`, `FileParseResult`, `DiRegistration`, `RunMeta` отсутствуют — и это
правильно.** Схема описывает `Manifest`, а перечисленные модели из него недостижимы:
первые три относятся к уровню парсера и живут только в кэше (T09), `RunMeta` — это
сидкар-файл. Если понадобится валидировать содержимое кэша, схему для
`FileParseResult` нужно будет генерировать отдельной командой.

### Найденный баг в спецификации: `fnmatch` не понимает `**`

Самая содержательная находка на текущий момент. План предписывал
«использовать `fnmatch` по POSIX-пути» и приводил один пример. Проверка показала:

```
fnmatch("src/A/obj/x/y.cs", "**/obj/**")  -> True
fnmatch("obj/y.cs",         "**/obj/**")  -> False   ← дыра
fnmatch("src/A/Sample.g.cs", "**/*.g.cs") -> True
fnmatch("Sample.g.cs",       "**/*.g.cs") -> False   ← дыра
```

`fnmatch` транслирует `*` в `.*` без учёта разделителей, поэтому шаблон `**/obj/**`
требует наличия `/` перед `obj`. Следствие: **файлы в корневых `obj/`, `bin/` и
сгенерированные файлы в корне репозитория молча просачивались бы в документацию.**
Наивная реализация по плану прошла бы все приведённые в нём критерии приёмки
и содержала бы эту дыру.

Исправлено функцией `matches_glob`: при неудаче и префиксе `**/` пробуется второй
прогон с отброшенным префиксом. Покрыто параметризованным тестом на 9 случаев.
План обновлён — добавлены и описание ловушки, и требование использовать
`matches_glob` в T14 (`exclude.path_glob` там сравнивается так же).

### Отклонения от плана

**1. `os.walk` вместо `Path.rglob`.** План предписывал `rglob`. Заменено, чтобы
получить отсечение каталогов: из каждого glob с суффиксом `/**` выводится glob
каталога (`**/obj/**` → `**/obj`), и в совпавшие каталоги обход не заходит вовсе.
На реальном репозитории это разница между полным обходом `.git`/`node_modules`
и мгновенным пропуском — а заявленные в архитектуре «1–2 секунды на десятках тысяч
файлов» без этого недостижимы.

Отсечение — чистая оптимизация и на результат влиять не может: если каталог совпал
с dir-глобом, любой файл под ним совпал бы и с исходным шаблоном. Это зафиксировано
тестом `test_pruning_does_not_change_result`, который сравнивает обход с отсечением
и без.

Побочная выгода: `os.walk(followlinks=False)` не разыменовывает симлинки из коробки.
Симлинк на дерево исходников иначе породил бы дубли символов с одинаковыми FQN.
Есть тест.

**2. Контрольный тест «без исключений».** Добавлен
`test_discover_without_excludes_sees_generated_file`: с пустым списком исключений
находится ровно 12 файлов. Без него тест на исключения проходил бы и в случае,
если бы файла просто не было на диске, — то есть проверял бы пустоту.

### Замечание: enrollment в этой задаче не реализован

`DocpipeConfig.enrolled` объявлен, но пока никем не читается — он применяется в T15
при сборке дерева, а не при обходе. Это соответствует замыслу: неenrolled модули
**должны** парситься, их символы нужны для графа наследования. Обход их не фильтрует.

## Внеплановый прогон на реальном репозитории (после T04)

По запросу владельца запущено то, что готово, на `examples/eshoponweb` (254 файла `.cs`,
10 проектов, 2 решения). Полный отчёт — [`findings-eshoponweb.md`](findings-eshoponweb.md),
здесь только выводы для реализации.

**Подтвердилось главное:** tree-sitter разобрал **244 файла из 244 без единой ошибки**
за 0.13 с (1948 файл/с). Отказ от Roslyn обоснован. Обход ФС — 17 мс.

**Три бага в спецификации, все внесены в план:**

1. **Многострочные `base_list`** (T06). Реальный случай:
   `class AuthenticateEndpoint : EndpointBaseAsync\n .WithRequest<…>\n .WithActionResult<…>`.
   План предписывал брать текст «как есть» — тогда `signature_hash` начинает зависеть
   от форматирования файла, и переформатирование заставляет агента на шаге 3
   перегенерировать документ впустую. Плюс правила по `base_type` перестают совпадать.
   Исправление: `re.sub(r"\s+", " ", text).strip()`.

2. **DI-регистрации в top-level statements** (T13). Все три `Program.cs` в eShopOnWeb
   написаны без класса и метода. Реализация, написанная под фикстуру (где `Program` —
   обычный статический класс) и ищущая вызовы внутри `method_declaration`,
   **не нашла бы ни одной регистрации в реальном проекте**. Обход обязан идти
   по всему дереву файла.

3. **`unclassified` смешивает разное** (T20). 9 интерфейсов `*Service` отсекаются
   предикатом `type_kind: [class, record]` — это правильно по замыслу, но в статистике
   они попадают в кучу с типами, про которые правила ничего не знают. Введена
   отдельная категория `interface_covered`.

**Наблюдения, не требующие правок кода:**

- Правила из плана дали 18 страниц на 244 файла (81% неклассифицировано). Это ожидаемо:
  дефолтный ruleset намеренно консервативен, а набирать правила нужно по `docpipe stats`
  на конкретном проекте. В eShopOnWeb HTTP-поверхность построена на паттерне REPR
  (10 типов `*Endpoint`), контроллеров всего 4.
- 22 имени типов дублируются, но почти все разнесены по модулям — модульная раскладка
  дерева разводит их без хэш-суффиксов. Подтверждает выбор структуры.
- Только **16 типов из 247 имеют XML-doc** (6.5%). Для шага 3 это значит, что описания
  придётся выводить из структуры кода, а не из комментариев. Стоит замерить ту же
  цифру на АС CF до планирования шага 3.
- 239 файлов с file-scoped namespace против 1 с блочным — редкая форма встречается
  ровно один раз, и именно на ней всё сломается, если её не поддержать.
- 45 типов (18%) лежат в тестовых проектах. Отсекать через `enrolled` в `docpipe.yaml`,
  а не через `exclude`: тестовые проекты должны парситься ради графа наследования,
  но узлов документации не порождать.

### Зачем отдельное решение, а не расширение SampleSolution

Критерии приёмки T04–T20 завязаны на точные количества в `SampleSolution`
(11 файлов, 10 символов, 6 узлов). Расширение той фикстуры потребовало бы

### Покрытые случаи

Все восемь найдены прогоном на eShopOnWeb, все ломают реализацию, написанную
только под `SampleSolution`:

| Случай | Что ломается без обработки |
|---|---|
| Многострочный `base_list` | `signature_hash`, правила `base_type` |
| Top-level statements в `Program.cs` | теряются **все** DI-регистрации |
| Тип без namespace | FQN с ведущей точкой |
| Блочный `namespace N { }` | namespace не определяется |
| `global using` / `using static` / алиас | резолв FQN |
| Вложенные типы с общим именем | два узла схлопываются в один |
| Два `Constants` в одном модуле | коллизия `doc_path` |
| Тестовый проект | тесты попадают в документацию |

Тесты фикстуры проверяют **наличие конструкций**, а не только файлов. Иначе
случайное «упрощение» фикстуры оставило бы тесты T06/T13 зелёными и бессмысленными.

### Уточнение контракта, найденное при написании фикстуры

Схлопывания пробелов (`\s+` → ` `), которое я внёс в план после прогона на eShopOnWeb,
**оказалось недостаточно**. На реальной строке получалось:

```
'EndpointBaseAsync .WithRequest<AuthenticateRequest> .WithActionResult<…>'
```

Пробел перед точкой остаётся, и это не канонический C#. Нужен второй шаг —
`re.sub(r"\s*\.\s*", ".", text)`. Итог совпадает с тем, как база была бы записана
в одну строку. План обновлён.

### Побочно: контракт сопоставления имён базовых типов (T14)

Фикстура вскрыла, что правило «последний сегмент после точки» неверно.
Для `Sample.Common.Web.BaseApiController` значим последний сегмент,
для `EndpointBaseAsync.WithRequest<A>.WithActionResult<B>` — **первый**
(последний даёт бессмысленное `WithRequest`).

Различаются по признаку «точка после первого `<`». Функция `base_type_candidates`
с таблицей проверенных случаев внесена в T14. Условие с `<` существенно: без него
`Sample.Common.Web.BaseApiController` порождал бы кандидата `Sample`, и правило
`base_type: ["Sample"]` совпадало бы со всем подряд.

Это тот случай, когда фикстура окупилась до написания кода, который она проверяет.

### Решения, которые стоит знать

**Запрос `.scm` только находит узлы объявлений.** Имя, модификаторы, базы и атрибуты
берутся обходом потомков, а namespace и `containing_type` — обходом предков.
Запросом второе выразить нельзя: tree-sitter не умеет подниматься вверх по дереву.
Файл `declarations.scm` остаётся местом, где перечислены виды объявлений, — добавить
новый вид можно, не трогая код.

**`span` начинается с атрибутов**, а не с `public`: `attribute_list` — потомок
объявления. Это желаемое поведение, ссылка в документации ведёт на объявление целиком.
Зафиксировано тестом, чтобы случайная «починка» не сдвинула ссылки.

**Квалифицированные имена атрибутов приводятся к простому**
(`System.ComponentModel.Description` → `Description`): правила классификации пишутся
по простому имени.

**`verbatim_string_literal` — единый лист** без потомка `string_literal_content`,
в отличие от обычной строки. `@` и кавычки снимаются вручную, `""` разворачивается в `"`.
Внесено в план.

### Четыре бага в уже написанном коде — исправлены здесь же

1. **`.slnx` не искался вовсе** (T04, T05). ABP мигрировал на новый XML-формат решений
   целиком: **30 файлов `.slnx` и ноль `.sln`**. `discovery` знал только про `.sln`,
   то есть нашёл бы там ноль решений. Теперь `sln_files` собирает оба расширения,
   а `parse_sln` выбирает разбор по суффиксу. Проверка: 651 проект из 30 решений,
   все существуют на диске.

2. **`module:{name}` — не уникальный id** (T05). Имена проектов повторяются **39 раз**,
   включая три разных `MyCompanyName.MyProjectName.csproj`. Разные модули склеились бы
   в один, и часть документации исчезла бы молча. Теперь `id = "module:" + путь к csproj`.
   Выбран путь, а не суффикс-разрешитель коллизий: путь уникален по построению и
   считается локально из одного файла, тогда как суффикс потребовал бы глобального
   прохода и менял бы id существующих модулей при добавлении нового.

3. **`ProjectReference` сопоставлялись по `.stem`** (T05) — та же проблема: ребро графа
   уходило бы в произвольный из одноимённых модулей. Теперь `Include` разрешается
   в репо-относительный путь. На ABP разрешаются **2383 ссылки из 2383**,
   на eShopOnWeb — 18 из 18.

4. **`$(TargetFrameworks)` попадал в манифест** (T05) как строка, неотличимая
   от настоящей платформы. Значения с `$(` отбрасываются.

### Три правки плана — на задачи, которые ещё не написаны

5. **`#if` прячет члены типа от прямого обхода** (T07 — следующая задача). Члены под
   `#if` не являются прямыми детьми `declaration_list`, они уходят под `preproc_if`
   и `preproc_else`. Реализация «перебрать детей тела» потеряла бы их молча.
   `#region`, в отличие от `#if`, контейнером не является — асимметрию легко не заметить.
   В спецификацию T07 добавлено требование спускаться вглубь с остановкой на вложенных
   типах и тест с ожиданием четырёх членов там, где наивная реализация вернёт два.

6. **`#if` внутри аргументов атрибута уничтожает объявление** (T20). Директива рвёт
   выражение, а атрибут — потомок объявления, поэтому ломается и оно: остаток файла
   переразбирается как top-level statements, и `class_declaration` пропадает.
   Так теряется `CmsKitWebUnifiedModule` в ABP. Обойти в рамках tree-sitter нельзя,
   поэтому `validate` обязан ловить комбинацию «`parse_errors > 0` и ноль объявлений».
   Воспроизведено один в один в фикстуре `WildSolution/…/Modules/ConditionalModule.cs`
   (8 ошибок, 0 объявлений — те же числа, что на настоящем файле).

7. **FQN не является уникальным ключом символа** (T15). План задавал
   `id = "type:" + fqn` и разрешение коллизий `doc_path` суффиксом `-{sha256(fqn)[:8]}`.
   На 9075 объявлениях ABP: по `fqn` — **255 коллизий**, по `module + fqn` — 108,
   по `module + fqn + арность` — 3. Причин две: перегрузка по арности дженерика
   (112 групп, рекорд — шесть арностей у одного имени) и одинаковые FQN в разных
   сборках. Хэш от FQN не разводит ничего там, где FQN совпадает: внутри одного модуля
   195 групп дают одинаковый slug, и в 105 из них FQN тоже одинаков. Ключ и суффикс
   переопределены в T15; фикстура с тремя арностями одного имени — в
   `WildSolution/…/Services/CrudAppService.cs`.

### Трудности прогона

**Минимальное воспроизведение потери объявления не удалось получить сразу.** Синтетический
пример с `#if` в аргументах атрибута парсился с ошибками, но объявление **выживало** —
терялось только на настоящем файле. Бисекция показала, что восстановление грамматики
зависит от того, что идёт за атрибутом: на упрощённом теле класса она справляется,
на реальном (с ещё одним `#if` внутри метода) — нет. Точный порог — внутреннее свойство
tree-sitter, гоняться за ним смысла нет. Вывод для плана сформулирован так, чтобы
не зависеть от порога: признаком считается пара «ошибки есть и объявлений нет», а фикстура
скопирована с реального файла, а не сочинена.

**Тест на фикстуру пришлось писать по тексту файла, а не по дереву.** Разбор сломан,
узла `attribute_list` в дереве нет, поэтому наличие конструкции проверяется по исходнику,
а последствие — по дереву. Обе половины нужны: без первой тест сломается, если файл
«починят», без второй — если грамматика научится восстанавливаться.

ни одной пустой сигнатуры. Разбор замедлился с 5,0 до 5,6 с (1406 файлов/с) —
плата за второй запрос по дереву.

### Отклонения от плана

**1. `event_field_declaration` — отдельный узел, план его не упоминал.** В грамматике
события объявляются двумя разными узлами: `event_declaration` — только форма
с `add`/`remove`, а обычное `public event EventHandler Changed;` — это
`event_field_declaration`. Реализация строго по плану потеряла бы обычную форму,
которой в ABP вдвое больше. План исправлен, узлов в `members.scm` шесть.

**2. Поле с несколькими объявителями даёт несколько членов.** План предписывал брать
имя первого `variable_declarator`; тогда в `private int _a = 1, _b = 2;` поле `_b`
пропало бы молча. На ABP таких полей 0 из 1652 — то есть правило плана ничего бы
не сломало на практике, — но корректная обработка стоит трёх строк, и молчаливая
потеря данных того не стоит. План исправлен.

**3. Список видов членов сужен явно.** `indexer_declaration`, `operator_declaration`,
`conversion_operator_declaration`, `destructor_declaration`, `delegate_declaration`
не извлекаются: в `MemberKind` таких значений нет. На 3000 файлов ABP их суммарно 20
против 14 000 обычных членов. Раньше это просто не оговаривалось, теперь записано
в план вместе с инструкцией, что менять при необходимости.

### Решения, которые стоит знать

**Владелец члена ищется обходом вверх, а не перебором детей тела.** Это следствие
находки ABP: члены под `#if` живут под `preproc_if`/`preproc_else` и прямыми детьми
`declaration_list` не являются. Запрос находит их на любой глубине, а ближайший
предок-тип сам разводит вложенные типы — отдельной логики «остановиться на вложенном
типе» не понадобилось. Тест на пять членов (`One`, `Two`, `TwoOld`, `Region`, `Three`)
ловит наивную реализацию: она вернёт три.

**Сигнатура режется по узлам, а не поиском `{` в тексте.** Терминаторы —
`block`, `arrow_expression_clause`, `accessor_list`, `;`. Текстовый поиск сломался бы
на `void M(string s = "{")` и на инициализаторах коллекций. Атрибуты отбрасываются,
хотя и являются потомками узла: для правил есть отдельное поле `attributes`,
а в сигнатуре они шумят. Ограничения `where T : class` и `: base(x)` стоят до тела
и в сигнатуру входят — это желаемое поведение.

**Срез текста берётся относительно самого узла** (`member.text[start - member.start_byte : …]`),
поэтому в функцию не нужно тащить исходник файла целиком.

### Замечание: тяжёлый хвост у сигнатур полей

`{` инициализатора коллекции лежит **внутри** `variable_declaration`, а не отдельным
потомком, поэтому обрезка по узлам его не отсекает и инициализатор входит в сигнатуру.
Обычно это полезно — значение `const` часть контракта, и его изменение должно менять
`signature_hash`. Но хвост тяжёлый: медиана сигнатуры поля 52 символа, p99 — 187,
максимум **1283** (поле с ASCII-графикой в инициализаторе). Всего сигнатур длиннее
200 символов — 460 из 37 262 (1,2 %).

Решено оставить как есть и записать в план требование к шагу 3 усекать сигнатуру
при выводе. Альтернатива — резать поле по `=` — теряет значения констант ради
1,2 % случаев.

### Замечание: покрытие XML-doc у членов

1703 члена из 37 262 (**4,6 %**) имеют `<summary>`. У типов было 3,8 %. Третье
подтверждение подряд: описания на шаге 3 придётся выводить из кода.

На реальном коде: **33 368 директив** на ABP (1223 уникальных пространства имён)

(1278 файлов/с) — цена третьего прохода запросом по дереву.

### Отклонения от плана

**1. Понадобился запрос по всему дереву, а не перебор детей `compilation_unit`.**
Директива `using` может лежать **внутри блочного namespace** — в ABP таких 8.
Перебор детей корня их не увидел бы. Заодно проверено, что ложных срабатываний

а `using (…) { }` — `using_statement`; узлом `using_directive` не является ни то,
ни другое. План исправлен, добавлен `usings.scm`.

**2. Узел имени бывает третьего типа — `alias_qualified_name`.** План называл только
`qualified_name` и `identifier`. Форма `using global::AutoMapper;` (в ABP две штуки)
даёт `alias_qualified_name` с текстом `global::AutoMapper`. Префикс снимается:
это квалификатор глобального пространства имён, а не часть имени, и без снятия
резолв на T10 такой namespace не нашёл бы. Прочие extern-алиасы
(`using MyLib::Some.Namespace;`) оставлены как есть — без разрешения алиасов сборок
они всё равно не резолвятся, а врать в манифесте хуже.

### Решения, которые стоит знать

**Имя берётся как последний именованный потомок.** У алиаса перед именем стоит ещё
`identifier` самого алиаса, поэтому «первый `identifier` или `qualified_name`»
дал бы имя алиаса. Алиасы всё равно отбрасываются, но правило «последний» корректно
для всех форм разом и не зависит от порядка проверок.

**`global` и `static` — анонимные узлы**, в `named_children` они не попадают,
поэтому различение идёт по `{child.type for child in directive.children}`.

**Ловушка с `using global::X;`.** Реализация, ищущая подстроку `global` в тексте
директивы, отнесла бы её в `global_usings` — хотя прямым потомком `global` здесь
не является. Зафиксировано отдельным тестом.

### Замечание: global usings в реальных репозиториях

В ABP и eShopOnWeb — **ноль** `global using` (формы: 33 374 обычных, 58 алиасов,
10 `using static`). Фича из C# 10, и обе кодовые базы её не используют: ABP целится
в том числе в netstandard2.0. Проверить эту форму можно только на фикстуре — ещё один
довод в пользу того, что `WildSolution` собирается вручную, а не копированием
из реального репозитория.

### Ограничение, которое стоит помнить на T10

Алиасы отбрасываются целиком, поэтому тип, на который ссылаются через алиас,
на T10 не разрешится. В ABP таких директив 58 на 33 368 (0,17 %). Лечится только
полноценной таблицей алиасов на файл; пока не окупается.

## T09 — `cache.py`: sqlite-кэш разобранных файлов ✅

**Создано:** `docpipe/cache.py`, `tests/test_cache.py`.

**Проверка**

```
uv run pytest -q                    197 passed
uv run ruff check .                 All checks passed
uv run ruff format --check .        26 files already formatted
uv run mypy docpipe                 Success: no issues found in 11 source files
```

### Замер на ABP — ради этого задача и делалась

| | время | попаданий | промахов |
|---|---|---|---|
| холодный прогон | 8,19 с | 0 | 7869 |
| тёплый прогон | **0,79 с** | 7869 | 0 |

Ускорение **10,3×**, результаты обоих прогонов побитово идентичны (сравнение всех 7869
`FileParseResult`). Размер БД — 8,0 МБ на 17,5 МБ исходников.

Оставшиеся 0,79 с — это чтение и хэширование всех файлов, то есть неустранимый пол
инкрементального режима. Совпадает с оценкой «~1–2 с на десятках тысяч файлов»
из §2.3 архитектуры.

### Отклонения от плана

**1. Битая БД пересоздаётся, а не роняет прогон.** В плане этого не было. Кэш —
расходный материал: оборванная запись, обрезанный файл или посторонний файл с тем же
именем не должны стоить отказа команды с советом «удалите каталог». Открытие проверяется
запросом `SELECT count(*) FROM sqlite_master`, на `sqlite3.DatabaseError` файл удаляется
и создаётся заново. Отдельно проверено, что пустой файл (0 байт) — валидная пустая БД
и пересоздавать его не нужно.

**2. `put` не коммитит.** План API коммит не описывал. Коммит на каждую запись — это
десятки тысяч fsync на большом репозитории. Коммит перенесён в `close()`; записи видны
через `get` в том же соединении, поэтому внутри прогона поведение не меняется, а на
аварийном завершении теряется кэш, но не результат.

**3. Уровень сжатия `zlib` задан явно.** Значение по умолчанию менялось между версиями
Python, а payload хочется иметь воспроизводимым побайтово.

Все три внесены в план.

### Решения, которые стоит знать

**Попадание определяется хэшем содержимого, `mtime` не используется вовсе.** Время
модификации меняется при checkout и при переносе репозитория, не меняя ни байта в файле:
кэш на `mtime` то промахивался бы там, где не должен, то попадал бы там, где нельзя.
Это то же требование, что и к манифесту, — результат обязан зависеть только от содержимого.

**`prune` считает разницу в Python, а не через `NOT IN (…)`.** Список путей измеряется
тысячами, а число параметров в запросе sqlite ограничено.

**Payload — `model_dump_json` от pydantic, а не `stable_json_dumps`.** Побайтовая
стабильность payload на корректность не влияет (сверяется `content_hash`, не payload),
а родная сериализация модели гарантирует точный round-trip. `stable_json_dumps`
используется только для строки версий в `meta`, где нужно сравнение на равенство.

### Ошибка, найденная своим же тестом

Первая версия `test_round_trip_keeps_full_structure` клала БД в
`sample_solution.parent / "tmp-cache"` — то есть **внутрь `tests/fixtures/`**. Тесты
проходили, но каталог фикстур засорялся. Замечено по `git status` сразу после прогона.
Исправлено на `tmp_path`. Вывод на будущее: любой тест, который что-то пишет, обязан
писать в `tmp_path`, даже если путь строится от фикстуры.

### Отклонения от плана

**1. Ключ индекса — не FQN.** План задавал `dict[str, Symbol]` с ключом-FQN. На ABP это
255 коллизий: 112 групп перегрузки по арности дженерика и 155 пар одинакового FQN
в разных сборках. Ключом стал `symbol_key(модуль, FQN, арность)` — тот же формат, что
у id узла на T15. Добавлена функция `index_by_fqn`: она возвращает **список** ключей,
потому что один FQN законно принадлежит нескольким типам (на ABP таких FQN 261).

**2. Namespace и usings проверяются последовательно, а не скопом.** План предписывал
собрать совпадения из namespace и usings вместе и при количестве >1 ставить `ambiguous`.
Это пометило бы неоднозначным обычный случай, когда тип виден и по namespace, и по using,
хотя в C# ближнее имя просто перекрывает дальнее. Реализовано как в C#: сначала
полностью квалифицированное имя, затем namespace и его префиксы от длинного к короткому
(побеждает первое совпадение), и только при неудаче — usings, где несколько совпадений
действительно означают неоднозначность. Результат — 1 неоднозначность на 8966 символов
вместо шума.

**3. `strip_generics` удаляет сбалансированные группы, а не всё от первого `<`.**
`A.B<C<D>>.E` — это вложенный тип `E` внутри generic-типа `B`, его FQN равен `A.B.E`.
Обрезка по первому `<` дала бы `A` и потеряла бы тип.

Все три внесены в план.

### Ошибка, которую нашёл собственный тест

Первая версия брала для резолва usings **только своего файла**. Тест
`test_global_using_participates_in_resolution` был написан под это поведение — и в момент
написания утверждения стало видно, что оно неверное: `global using` действует на весь
проект, а не на файл, где объявлен, и обычно все они лежат в одном `GlobalUsings.cs`.
То есть реализация не резолвила бы **ни один** тип, видимый исключительно через них.

Исправлено: набор видимых usings файла = собственные плюс все `global_usings` его модуля.
Границу модуля пересекать нельзя — проекты изолированы, на это добавлен отдельный тест.

Показательно, что на реальных репозиториях эта ошибка не проявилась бы никак: в ABP
и eShopOnWeb `global using` нет вовсе. Нашлась она только потому, что тест писался
формулировкой ожидания, а не подгонкой под вывод.

### Решения, которые стоит знать

**Базовые типы резолвятся до слияния, каждое объявление со своими usings.** Половинки
`partial class` лежат в разных файлах, и usings у них разные; резолв после слияния
применил бы к одной половине контекст другой.

**`base_types` хранит FQN, а не ключи символов.** По ним матчатся правила классификации
(`base_type: ["EndpointBaseAsync"]`), и ключ с модулем и арностью там был бы нечитаем.
Обратный переход даёт `index_by_fqn`.

**Атрибуты дедуплицируются вручную.** Поля `args` и `named_args` — список и словарь,
поэтому модель нехэшируема и `set` не работает.

**Пустой префикс namespace обязателен** при переборе: глобальное пространство имён видно
из любого места, и тип без namespace должен находиться.

### Главное отклонение: `[Route]` на методе

Разведка перед реализацией (по установившейся привычке смотреть на реальный код раньше,
чем писать) сразу дала цифру: в ABP **245 из 356** HTTP-атрибутов идут вместе
с отдельным `[Route]` на том же методе:

```csharp
[Route("api/abp/multi-tenancy")]
public class AbpTenantController
{
    [HttpGet]
    [Route("tenants/by-name/{name}")]
    public Task<TenantDto> FindTenantByNameAsync(string name) { }
```

План предписывал брать шаблон метода только из аргумента `Http*`. По этому плану **всем**
методам `AbpTenantController` достался бы один и тот же маршрут — маршрут типа. Таблица
эндпоинтов выглядела бы правдоподобно и была бы бесполезной, а на фикстуре все критерии
приёмки прошли бы: в `SampleSolution` шаблон записан прямо в `[HttpGet("{id:guid}")]`.

Исправлено: шаблон метода = аргумент `Http*`, при его отсутствии — аргумент `[Route]`
на том же члене. Случая, когда аргументы есть у обоих, ни в ABP, ни в eShopOnWeb нет
ни разу, поэтому приоритета достаточно простого.

### Прочие отклонения

**Токены сравниваются без учёта регистра.** План называл ровно `[controller]` и `[action]`;
ASP.NET их регистр не различает. Значение подставляется с исходным регистром имени.

**Сортировка дополнена третьим ключом** — `member`. По `(route, http_method)` два метода
с одинаковым маршрутом и глаголом (в ABP есть: `[HttpPost]` + `[MapToApiVersion]` на двух
перегрузках) остались бы в порядке обхода.

Заодно исправлен пример в критериях приёмки: он показывал GET первым, хотя по собственному
правилу сортировки `api/v1/Pricing` — префикс `api/v1/Pricing/{id:guid}`, и первым идёт POST.

### На реальном коде

| | ABP | eShopOnWeb |
|---|---|---|
| типов с эндпоинтами | 97 | 4 |
| эндпоинтов | 356 | 26 |
| с непустым маршрутом | 346 | 26 |
| глаголы | GET 226, POST 68, PUT 34, DELETE 26, PATCH 2 | GET 14, POST 12 |

Подстановка токенов проверена на eShopOnWeb: `[Route("[controller]/[action]")]` даёт
`Manage/ChangePassword`.

### Пустой маршрут — это не ошибка

10 эндпоинтов ABP получили пустой `route`: у контроллера нет `[Route]`, у метода нет
шаблона, то есть путь задаётся **конвенциональной** маршрутизацией в конфигурации
приложения. Атрибутов для него не существует, вывести путь неоткуда.

Эндпоинт всё равно выдаётся: то, что метод обрабатывает GET, — факт, и он полезен шагу 3.
Записано в план как явно не поддерживаемый случай, чтобы пустой маршрут не приняли за баг.

### Что решено не разбирать

- **конвенциональная маршрутизация** — задаётся не на типе;
- **minimal API** (`app.MapGet`) — не привязан к типу;
- **`[Route]` без `Http*`** (11 членов в ABP) — маршрут без ограничения по глаголу,
  а `Endpoint.http_method` обязателен.

### Отклонения от плана

**1. `typeof(...)` — не запасной вариант, а обычная форма записи.** План её не упоминал
вовсе. Разведка показала: в ABP и eShopOnWeb так записаны **47 регистраций из 267** —
больше, чем двумя типами-аргументами (34+13):

```csharp
context.Services.TryAddTransient(typeof(IKernelAccessor<>), typeof(KernelAccessor<>));
```

Имена типов здесь названы так же явно, как в `<…>`, поэтому `confidence` остаётся `high`.
Без этой ветки 47 полностью определённых регистраций были бы потеряны.

**2. Регистрация без единого имени типа пропускается.** План предписывал брать
«`service_type` из текста». Текстом там оказывается тело лямбды
(`sp => sp.GetRequiredService<X>()`), переменная (`AddSingleton(builder)`) или приведение
типа — в поле `service_type` манифеста попал бы мусор. Такую регистрацию нельзя связать
с символом, то есть документации она ничего не даёт. Таких вызовов 50 из 267.

**3. Узлы вызовов приходят в `di.py` снаружи.** План говорил «создать `di.py`, изменить
`parser.py`», не уточняя границу. Прямое обращение `di.py` к грамматике потребовало бы
импортировать `_LANGUAGE` из `parser.py`, который сам импортирует `di.py`, — цикл.
Запрос выполняет `parser.py` (ему и принадлежит вся работа с tree-sitter), а `di.py`
получает список узлов и занимается только смыслом.

Все три внесены в план вместе с тестами.

### Решения, которые стоит знать

**Запрос сужен до `function: (member_access_expression)`.** Это отсекает вызовы без
получателя (`Foo()`), которых в файле подавляющее большинство, и заодно даёт бесплатную
проверку: `AddScoped<IFoo, Foo>()` без `services.` регистрацией не считается.

**Имя метода лежит в поле `name` у `member_access_expression`** и бывает двух видов:
`identifier` или `generic_name`. `type_argument_list` принадлежит `generic_name`,
а **не** `invocation_expression` — на этом легко ошибиться.

**Открытые дженерики сохраняются как есть** (`IKernelAccessor<>`). Резолвом занимается
T15, и в план ему добавлено требование снимать generic-часть при сопоставлении с символом:
`KernelAccessor<>` не совпадёт с именем символа `KernelAccessor` буквально.

### Замечание: маркерные интерфейсы

Основной способ регистрации в ABP — не вызов, а наследование от `ITransientDependency`
(696 типов) или `ISingletonDependency` (167). Вызовов `Add*` там всего 182 на 8966 типов.
Синтаксически это не регистрация, и в `di.py` ему делать нечего — ловится правилом
классификации по базовому типу на T14. Записано в findings-abp.md ещё при прогоне;
здесь подтверждено цифрами.

## Стресс-тест на четырёх репозиториях (после T13)

По запросу владельца прогон всего написанного (T04–T13) на двух новых репозиториях —

### Один настоящий баг — исправлен

**Безымянные члены.** Три члена на двух репозиториях получили пустое имя: при
восстановлении после ошибки грамматика отдаёт `field_declaration` без имени — обломок
выражения из-под `#if`. Один случай оказался иным: `extension(char) { … }` — **члены-расширения
C# 14** из .NET 10, которых грамматика 0.23 ещё не знает.

Безымянный член превратился бы в безымянный раздел документации. Исправлено фильтрацией
в `_member_names`; после правки безымянных членов на всех четырёх репозиториях ноль.

### Одна ошибка в разборе проектов — исправлена

**`ProjectReference` через подстановки MSBuild.** В OpenTelemetry разрешались
**2 ссылки из 109**: все остальные записаны как `$(RepoRoot)\src\X\X.csproj`.
Хуже того, старый код склеивал такое значение с каталогом проекта и получал
правдоподобный, но выдуманный путь `test/X/$(RepoRoot)/src/…`.

Значение `$(RepoRoot)` вычисляется функцией MSBuild — воспроизводить это здесь нечем.
Но имя файла в ссылке записано буквально. Добавлен проход `csproj.resolve_references`:
дорезолвливает по имени файла и **только при единственном совпадении** (имена проектов
уникальны не везде — в ABP 39 повторов).

| | до | после |
|---|---|---|
| OpenTelemetry | 2 / 109 | **108 / 109** |
| остальные три | без изменений | без изменений |

Оставшаяся одна — `@(TrimmerRootAssembly->'%(Path)')`, преобразование item-группы,
а не путь. Правильно осталась неразрешённой.

### Две находки осознанно не исправлены

**`TargetFramework` через цепочку props-файлов: 70 модулей из 70 без TFM.** Все проекты
OpenTelemetry пишут `<TargetFrameworks>$(TargetFrameworksForLibraries)</TargetFrameworks>`,
а переменная определена в `build/Common.props`, который не импортируется ни из
`Directory.Build.props`, ни из `.csproj` — цепочка идёт через ещё два файла, и значение
содержит ещё одну подстановку. Достать это можно только полным вычислением свойств MSBuild.

План с самого начала объявляет это границей подхода, и граница подтвердилась. Вывод:
`target_frameworks` — метаданные, а не опора; ни одно правило на них не завязано.
Требование к T20: сообщать о модулях без TFM, чтобы пустое поле не приняли за свойство кода.

**Связанные исходники: 5 % типов вне модулей.** OpenTelemetry и semantic-kernel подключают
общий код через `<Compile Include="$(RepoRoot)\src\Shared\Guard.cs" Link="…" />`. Такой файл
лежит вне каталога любого проекта, и правило «ближайший `.csproj` вверх» не находит модуля:
39 файлов и 50 типов (5,0 %) в OpenTelemetry, 131 файл и 205 типов (4,8 %) в semantic-kernel.

Исправление ломает предположение «файл принадлежит одному модулю» — связанный файл
компилируется в несколько сборок сразу, — то есть меняет сигнатуру `build_symbol_index`
и порождает вопрос, в каком модуле показывать документ. Вместо тихой переделки сданных
задач заведена **T05b** с замерами и с проверкой, которую нужно сделать до реализации:
есть ли этот приём в целевом репозитории вообще.

### Известное ограничение подтвердилось в новых местах

Все 170 файлов с ошибками разбора на четырёх репозиториях — одна и та же причина,
найденная ещё на ABP: директива препроцессора внутри выражения. Стресс-тест добавил три
новых места: **модификатор объявления** (`public` / `#else` / `internal`), **базовый список**

Доля пострадавших файлов зависит от мультиплатформенности: 0 % в eShopOnWeb (один TFM),

Проверено, что причина именно в директивах: удаление из файла всех строк, начинающихся

Ни одного повтора `doc_path` и ни одного повтора id. **315 узлов из 828 на ABP получили

### Два бага, найденных проверкой на реальном коде

Проверка была простая: прогнать регулярку «похоже ли это на имя типа» по всем
`target` рёбер-конструкторов. Она сразу дала 219 подозрительных значений.

**1. Инициализатор конструктора ломал разбор параметров.** Сигнатура конструктора
намеренно включает `: base(...)` (это решение T07), а первая версия искала закрывающую
скобку через `rfind(")")` — то есть скобку инициализатора. Из
`public C(IOptions o) : base(o)` получался «параметр» `IOptions o) : base(o`.

На ABP так ломался **каждый пятый конструктор**: 217 рёбер из 1016. Исправлено поиском
**парной** скобки счётчиком глубины. После правки доля `low`-confidence на ABP упала
с 456 до 259 — сломанные имена перестали быть «нерезолвимыми».

**2. Тривия внутри сигнатуры (правка T07).** Оставшиеся два случая оказались другой
природы:

```csharp
[Obsolete("use another")]
#pragma warning disable CS0809 // Obsolete member overrides non-obsolete member
public override PropagationContext Extract<T>(…)
```

`#pragma` между атрибутом и модификатором становится **потомком** объявления, а не
соседом, и сигнатура начиналась с него. Комментарий на той же строке после схлопывания
пробелов сливался в общую строку. Второй вид — комментарий внутри списка параметров:
там `//` съедал бы остаток сигнатуры, потому что после схлопывания границы строки уже нет.

Замер до правки: **252 испорченные сигнатуры** на четырёх репозиториях (0,37 % от 68 828).
Мало по доле, но каждая портит и `signature_hash`, то есть заставляет шаг 3
перегенерировать документ впустую.

Исправлено вырезанием байтовых диапазонов узлов `comment` и `preproc_*` — именно
диапазонов, а не поиском `//` в тексте: `//` встречается внутри строковых литералов
(`"otpauth://totp/…"`, реальный случай из eShopOnWeb). После правки — **ноль**
на всех четырёх.

### Отклонения от плана

**Регистрация типа на самого себя ребра не даёт.** План говорил «DI-регистрации, где
`impl_type` соответствует символу», не оговаривая случай `AddTransient<ValuationWorkflow>()`,
где сервис и реализация — один тип. Петля в графе зависимостей — артефакт формы записи,
а не факт о коде, и в документе она читалась бы как «зависит от самого себя».

Побочно вскрылся пробел: **время жизни (`scoped`/`singleton`/`transient`) до манифеста
не доходит** — `Dependency` его не хранит, а `DocNode` не хранит `DiRegistration`.
Для самозарегистрированного типа это единственное, что регистрация сообщала. Вопрос
к шаблонам шага 2, отмечен здесь, чтобы не потерялся.

**`target` DI-ребра резолвится в FQN** тем же способом, что и параметры конструктора.
План не уточнял, что класть в `target`; сервис, записанный простым именем, в манифесте
выглядел бы иначе, чем тот же тип в рёбрах конструктора.

### Решения, которые стоит знать

**Домены проверяются в лексикографическом порядке ключей.** Словарь пришёл из YAML,
и порядок записи в файле источником решения быть не может — перестановка строк меняла бы
манифест. То же правило, что и для приоритетов правил на T14.

**`build_tree` вынесен в `conftest.py`.** Начиная с T15 почти каждой проверке нужен
готовый манифест целиком, а не его половина; повторять сборку в каждом тестовом модуле
означало бы четыре расходящиеся копии пайплайна.

значение из того же плана. Проверка падала бы на нём, ничего не проверив.

на быстрой фикстуре оба укладываются в одну секунду и дают одинаковый `generated_at`.
Первая версия теста на этом упала.

**2. `RunMeta.parse_error_files` добавлен сейчас, а не на T20.** План требует, чтобы
`validate` падал по списку файлов с ошибками разбора и без объявлений, а `stats` —
это `dict[str, int]`, куда список путей не положить. Поле заведено сразу: сидкар пишется
здесь, и возвращаться к `emit.py` на T20 ради одного поля незачем.

### Решения, которые стоит знать

**Оркестрация живёт в `emit.py`, а не в `cli.py`.** План говорил «создать `emit.py`,
изменить `cli.py`», не уточняя границу. Шестьдесят строк пайплайна в обработчике команды
означали бы, что сквозной прогон нельзя вызвать из теста без `CliRunner`.

**`_parse_one` — функция уровня модуля.** Иначе `ProcessPoolExecutor` не сможет её
сериализовать. Результаты после сбора **обязательно** пересортировываются по пути:
при `--jobs > 1` порядок завершения задач случаен, а от порядка `results` зависит
слияние `partial`-объявлений на T10.

**Золотой файл содержит версии грамматики**, поэтому апгрейд `tree-sitter` его ломает.
Это желаемое поведение: изменение вывода парсера должно быть видно в диффе, а не
проскакивать незамеченным.

## T17 — Тесты детерминизма ✅

**Создано:** `tests/test_determinism.py` — девять тестов.

**Проверка**

```
uv run pytest -q                    382 passed
uv run ruff check .                 All checks passed
uv run ruff format --check .        40 files already formatted
uv run mypy docpipe                 Success: no issues found in 17 source files
```

Требование из `purpose.md` стало проверяемым свойством. Сравнение везде побайтовое:
манифест не содержит недетерминированных полей, поэтому не нужно ни одного «сравнить,
игнорируя такие-то поля» — ради этого метаданные прогона и вынесены в сидкар.

### Отклонения от плана

**1. Монкипатчить нужно `discovery.os.walk`, а не `Path.rglob`.** `rglob` в `discovery`
нет: обход идёт через `os.walk`, потому что только так можно отсекать каталоги правкой
`dirnames` на месте (решение T04). Разворачивать при этом нужно **оба** списка —
и `dirnames`, и `filenames`: порядок каталогов влияет на порядок файлов.

**2. При подмене версии грамматики манифесты нельзя сравнивать целиком.** Версии лежат
в самом манифесте (поле `parser`), поэтому оно законно изменится. Сравниваются `modules`
и `nodes`; именно они и не должны поменяться от того, что кэш очистился.

### Что добавлено сверх плана

**Перенос репозитория** (две проверки). Две копии фикстуры в разных каталогах дают
побайтово равные манифесты, а кэш, наполненный из одной копии, годится для другой.
Это прямая проверка правила «пути только репо-относительные»: абсолютный путь ломал бы
документацию при любом различии в расположении рабочих копий у разработчика и в CI —
причём незаметно, потому что у автора-то всё сходится.

**Удаление файла.** Инкрементальный прогон после удаления обязан совпасть с полным:
кэш не должен воскрешать удалённый файл. За это отвечает `prune`, и до этого теста
он не был покрыт на уровне сквозного прогона.

**Все списки в манифесте отсортированы** — отдельный тест обходит модули и узлы
и проверяет каждое поле-список. Явная сортировка здесь не стиль, а условие
воспроизводимости, и проверять её точечно в каждой задаче ненадёжно.

**Обратимость JSON.** Манифест — контракт с шагом 2; запись и чтение обязаны быть
обратимы, иначе расхождение всплывёт у потребителя, а не здесь.

## Раздел о настройке в README (после T17)

По запросу владельца README дополнен разделом «Как этим пользоваться» и пошаговой
инструкцией «Настройка под конкретный проект». Каждая команда оттуда прогнана руками.

### Два бага, найденных при написании инструкции

**1. Аргументы primary constructor попадали в базовые типы.** Рецепт «посмотреть частые
базовые типы среди неклассифицированных» на semantic-kernel выдал `(output)` — 266 раз
и `(fixture)` — 159. Причина:

```csharp
public class MyTests(ITestOutputHelper output) : BaseTest(output), IDisposable
```

Тип с primary constructor передаёт аргументы базовому классу прямо в списке баз, и
`(output)` лежит там отдельным узлом `argument_list`. `_base_types` брал все
`named_children` и записывал его как базовый тип. Мусор расползался дальше по замыканию
наследования и попадал в `signature_hash`.

На четырёх репозиториях таких записей было **425**. Исправлено фильтром по типу узла;
после правки — ноль на всех четырёх.

Показательно, что баг нашёлся не тестом и не прогоном, а попыткой **воспользоваться**
собственным результатом: в таблице «частые базовые типы» строка `(output)` бросается
в глаза сразу, а в манифесте на 5 МБ её никто бы не заметил.

**2. Ошибки пользователя печатались traceback'ом.** Опечатка в `--rules` или несуществующий
`--root` роняли команду с трассировкой на полстраницы — ровно в тот момент, когда человек
первый раз пробует запустить всё руками. Заменено на сообщение и код возврата 2,
с тремя тестами.

### `tools/unclassified.py` — временный инструмент

Написан потому, что инструкция «смотрите на `unclassified` и добавляйте правила»
невыполнима: в манифест попадают только **классифицированные** типы, а для настройки
нужно ровно обратное. Счётчик в сидкаре говорит «7142», но не говорит, какие правила писать.

Скрипт печатает пять срезов по непокрытым типам: модули, окончания имён, базовые типы
с учётом замыкания, атрибуты, namespace. На ABP он сразу показывает
`ITransientDependency` (997 типов — больше, чем покрывает весь набор по умолчанию),
на semantic-kernel — что половина непокрытого это тесты и примеры, то есть вопрос
к `enrolled`, а не к правилам.

Требование внесено в план T20: `--stats` должен печатать эти же срезы, а скрипт при
реализации — удалить, а не оставлять рядом.

### Замечание про кэш

При проверке инструкции обнаружилось, что прогон на фикстуре создаёт
`tests/fixtures/SampleSolution/.docpipe/cache/`. Это ожидаемое поведение (`cache_dir`
относителен корню сканирования), и `.gitignore` его ловит, но для чужого дерева
поведение неочевидно. Описано в README вместе с `--no-cache`.

## Исключение тестов из дерева (по запросу владельца)

Требование: типы, чьё имя оканчивается на `Test`, в дерево документации попадать
не должны.

### Замер показал, что одного правила по имени мало

Прямолинейное `exclude.name_regex: ["^.*Tests?$"]` отсеивает **ноль** узлов на всех
четырёх проверочных репозиториях. Причина простая, но неочевидная: класс
`PricingServiceTests` не оканчивается ни на `Service`, ни на `Controller`, поэтому
и так не проходит ни одно правило классификации и узлом не становится.

Реальный шум идёт из другого места — вспомогательные типы **внутри** тестовых проектов
названы как продуктовые и классифицируются на общих основаниях:

```
AuditTestController                            -> controller
AuthorizationTestPermissionDefinitionProvider  -> provider
```

На ABP таких **104 узла из 828**. Отсекает их только `path_glob` по каталогам тестов.

### Что сделано

В `exclude` добавлено и то, и другое:

```yaml
path_glob: ["**/test/**", "**/tests/**", "**/*Test/**", "**/*Tests/**"]
name_regex: ["^.*Tests?$"]
```

Правило по имени оставлено, хотя сегодня оно ничего не ловит: оно фиксирует намерение
и сработает, когда в набор добавят более широкое правило — например, по атрибуту `[Fact]`
или по `type_kind`.

Эффект: ABP 828 → 694 узла, OpenTelemetry 10 → 7, semantic-kernel 69 → 67,
eShopOnWeb без изменений (его тестовые типы и так не классифицировались).

### Что проверено отдельно

**Форма `Tests` важнее формы `Test`**: в ABP 777 против 54, в semantic-kernel 829 против 17.
Правило `name_suffix: ["Test"]` не поймало бы `PricingServiceTests` вовсе —
`"PricingServiceTests".endswith("Test")` ложно. Поэтому регулярное выражение с `s?`.

**Ложных срабатываний по пути нет.** `**/*Tests/**` не цепляет `Contest/` и `Testing/` —
проверено и тестом, и на глобах напрямую.

**Три типа остались осознанно**: `AbpTestBaseWithServiceProvider`,
`BloggingTestAppBrandingProvider`, `ProcessTestController`. Все три лежат в `src/`
(это отгружаемая библиотека для тестов, демо-приложение и хост интеграционных тестов),
и ни один не оканчивается на `Test`. Поведение соответствует правилу.

### Замечание, которое стоит держать в голове для АС CF

В предметных областях, где «тест» — бизнес-понятие, правило по имени опасно.
Для финансового моделирования это не гипотеза: `StressTest` и `BackTest` — настоящие
сущности предметной области, а не юнит-тесты. Предупреждение вписано и в сам
`rules/dotnet.yaml`, и в README, и в план.

На фикстуре `scoped.nodes == full.nodes` для скоупа по каждому из двух модулей

### Баг, найденный собственным тестом: удалённый тип воскресал

Первая реализация брала из кэша всё, «чего не нашли обходом». Файл, удалённый **внутри**
скоупа, обходом уже не находится, но в кэше ещё лежит — и восстанавливался как «файл вне
скоупа». Тип оставался в дереве после удаления.

Исправлено отбором по **принадлежности пути скоупу**, а не по списку найденных файлов.
Разница видна только на удалении, поэтому тест на него обязателен и внесён в план.

### Открытие, которое сделал второй упавший тест

Ожидалось, что при холодном кэше скоуп-прогон «потеряет часть данных»: у контроллера
оборвётся замыкание наследования. Реальность жёстче — **узел исчезает целиком**.

Правило `controller.aspnet` смотрит на `ControllerBase`, до которого два шага через
`Sample.Common`. Без кэша цепочка обрывается на `BaseApiController`, ни одно правило
не совпадает, новый узел не порождается, а старый выброшен при слиянии как «в скоупе».
Тип просто пропадает из документации.

Это меняет требование к команде: предупреждение о ненайденных в кэше файлах — не
удобство, а необходимое условие. Добавлено в stderr и в статистику сидкара
(`restored_from_cache`, `missing_from_cache`).

### Отклонения от плана

**1. Отбор файлов вне скоупа — по пути, а не по «остальным».** См. выше; формулировка
плана «для всех остальных файлов из кэша» допускала оба прочтения, и неверное давало
воскрешение удалённых типов. Формулировка исправлена.

**2. `cache.prune` в скоуп-режиме не вызывается.** План этого не оговаривал. `prune`
удаляет из кэша всё, чего нет в списке найденных файлов, — то есть в скоуп-режиме снёс бы
весь кэш вне скоупа, ровно то, ради чего он здесь и нужен. Следующий скоуп-прогон
работал бы уже вслепую.

**3. Модули вне скоупа берутся из `previous`.** План не описывал, как файл вне скоупа
привязывается к проекту: обход туда не заходит, `.csproj` не найден. Список путей
к проектам собирается объединением найденного и `previous.modules[*].csproj`.

### Решение, которое стоит знать

**Узел «в скоупе», если в скоупе хотя бы один его источник.** Половинки `partial class`
могут лежать по разные стороны границы; правило «все источники в скоупе» оставило бы
такой тип неперестроенным, а правило «любой» перестраивает его целиком. Проверено
на `PricingService`, у которого два файла.

### Проверка на реальном сценарии

Дифф проверялся не на искусственном изменении кода, а на том, ради чего он нужен:

природу, значит скрыть главное: шагу 3 нужно переписать документ, а не перенести файл.

на узел, у которого изменилось всё сразу.

понадобится распознавать переименования, у него есть `signature_hash`: у переименованного
типа он тот же, что был у исчезнувшего.

**Код возврата всегда 0.** Команда предназначена для конвейера, где по её выводу решают,
что перегенерировать, а не для гейта в CI. Наличие изменений — не ошибка.

**Пустой результат печатается строкой «Изменений нет».** Пустой вывод неотличим от

### Отклонения от плана

**1. Счётчики живут в `docpipe/stats.py`, а не в `tree.py`.** План называл `tree.py`,
но там сборка узлов, и сто строк статистики её бы заслонили. Заодно `stats.py`
понадобился обеим командам — `scan --stats` и `stats MANIFEST`.

**2. `emit.run` возвращает `ScanResult`.** `--stats` нужен индекс символов, которого
в `(Manifest, RunMeta)` нет. Вместо расширения кортежа до тройки — что переписало бы
все вызовы в тестах — добавлен `run()`, возвращающий манифест, метаданные и статистику,
а `scan()` остался обёрткой над ним.

**3. Отдельная функция `classify_with_reason` не понадобилась.** План предлагал расширить
возврат `classify` до `Classification | Literal["excluded"] | None` либо завести вторую
функцию. Публичный `is_excluded`, сделанный ещё на T14, закрывает это без изменения
сигнатур.

### Решения, которые стоит знать

**`--stats` и `--dry-run` ничего не пишут.** Обе команды зовут в цикле настройки правил,
где перезаписывать манифест на каждой итерации незачем, а `--dry-run` вдобавок
сравнивает с тем самым файлом, который перезаписал бы.

**`stats MANIFEST` не может показать `unclassified`.** В манифест попадают только узлы,
то есть уже классифицированное. Посчитать непокрытое можно лишь имея индекс символов,
поэтому для настройки нужен именно `scan --stats`. В docstring команды это сказано прямо,
чтобы отсутствие колонки не приняли за баг.

**`validate` читает сидкар.** Список файлов со сломанным разбором лежит в
`<manifest>.run.json`: он про прогон, а не про результат, и в манифесте ему не место.
Если сидкара нет, проверка просто пропускает этот пункт.

**Предупреждение и ошибка разведены.** Тип, объявленный в нескольких файлах без `partial`
(на ABP таких три), — предупреждение: слияние в один документ там допустимо. Повтор
`id` или `doc_path` — ошибка: это молчаливая потеря документа.

`docpipe.example.yaml` не загрузился с первого раза:

Причина: секция, у которой **все записи закомментированы**, разбирается YAML как `None`,

артефактом — третий раз за проект (первые два: `(output)` в базовых типах и traceback
на опечатке в `--rules`).

**Файл назван `docpipe.example.yaml`, а не `docpipe.yaml`.** Конфигурация не подхватывается
автоматически — путь всегда задаётся флагом `--config`. Файл с именем `docpipe.yaml`
в корне репозитория выглядел бы действующим, и настройки в нём молча не применялись бы:
худший вид ошибки, тот, который выглядит как успех. Суффикс `.example.` снимает
двусмысленность бесплатно.

Автоподхват не добавлялся: он в плане не предусмотрен и порождает вопрос «почему прогон
изменился, я же ничего не менял».

### Что проверяет smoke-тест

Не дублирует тесты отдельных команд, а закрывает то, что между ними: все шесть команд
живы одновременно, `--help` каждой отвечает, коды возврата означают обещанное
(0 — успех, 1 — манифест не прошёл проверку, 2 — ошибка вызова), сквозной сценарий
«прогон → validate → stats → скоуп → diff» отрабатывает целиком, и **пример
конфигурации из репозитория действительно работает** — проверяется сам файл,
а не его копия. Пример, который не запускается, хуже отсутствующего: он выглядит рабочим.

| | покрытие |

| **semantic-kernel, все типы** | **52,5 %** |
| **semantic-kernel, узлы дерева** | **93,4 %** |

52 % по репозиторию. Это не совпадение — правила отбирают публичную поверхность API,
а её документируют лучше остального. То есть классификация попутно работает фильтром
качества входных данных для шага 3.

Обе цифры внесены в `CASHFLOW.md` с указанием мерить **оба** числа на АС CF:
по всем типам и по узлам готового манифеста.

### Что показала подобранная конфигурация о самом инструменте

- **Публичные интерфейсы для библиотеки — главный артефакт.** 57 интерфейсов, включая

- **`interface_covered` исчезает**, если интерфейсы классифицируются напрямую. Категория

## T22 — Поставка в репозиторий АС CF (после T21)

По запросу владельца: инструмент должен лежать **внутри** боевого репозитория,

Окружение поставки — **17 пакетов против 40** в разработке. Не `uv sync --no-dev`

Плата за это — второй манифест, который может разъехаться с первым; сверка вынесена
в `tests/test_deploy_bundle.py`.

### Каталог инструмента внутри сканируемого дерева: нужен третий вид исключений

Инструмент, положенный в `docs/ml/docspipe`, — это чужой код внутри репозитория,
который docpipe обязан не читать. Ни `enrolled`, ни `exclude` из `rules/dotnet.yaml`
для этого не годятся: первое управляет составом документации, второе — классификацией,
и оба оставляют файл прочитанным. Обход же зашивался константой `DEFAULT_EXCLUDE`
в `emit.py`, и настроить его было нечем.

Добавлено поле `exclude` в `DocpipeConfig` и `exclude_globs(config)` в `emit.py`.
Два решения, каждое против конкретной молчаливой ошибки:

- **шаблоны складываются со встроенными, а не замещают их.** При замещении строка
  `exclude: ["docs/**"]` вернула бы `obj/` и `bin/` в документацию — и никак бы себя
  не проявила, кроме раздутого манифеста;
- **тест фиксирует ловушку `"docs"` без `/**`.** Такой шаблон совпадает с самим
  каталогом, но не с файлами под ним. Команда отрабатывает, манифест строится,
  каталог как сканировался, так и сканируется.

Понятий стало три, и в README, `docpipe.example.yaml` и плане T04 они теперь
разведены таблицей: enrolled — «что документируем», `exclude` в правилах — «что
не документируем, но читаем», `exclude` в конфигурации — «куда не заходим»
(символ исчезает из индекса, наследование через него рвётся).

### Дефект, вскрывшийся при первой же установке

**Поле `out` в `docpipe.yaml` не читалось никогда.** У флага `--out` было значение
по умолчанию `artifacts/doc-tree.json`, поэтому `settings.out` не использовался ни
разу за весь проект, а `docpipe.example.yaml` описывал его как рабочее.

В разработке это незаметно: конфигурация лежит рядом с местом запуска, и оба пути
совпадают. На боевом репозитории конфигурация лежит в `docs/ml/docspipe/cashflow-docspipe/`,
запуск идёт из корня, и манифест уехал бы в `artifacts/` рядом с корнем — то есть
в рабочее дерево продукта.

Исправлено: тип параметра `Path | None`, значение по умолчанию убрано,
`destination = out or Path(settings.out)`. Требование внесено в план T16.

Пятый раз за проект дефект найден не тестом, а попыткой воспользоваться собственным
артефактом по назначению. Закономерность устойчивая: тесты проверяют то, что автор
предполагал, а применение — то, что он предположить не догадался.

  заякорено с обеих сторон, поэтому `StressTestRun` под него не подпадает — «Test»
  в середине имени безопасен. Опасность оказалась в другом месте: шаблоны путей
  `**/*Test/**` и `**/*Tests/**` отсекают любой каталог с таким окончанием, включая
  предметный `StressTest/`. Сужены до `**/*.Test(s)/**` — точка перед Test оставляет
  только тестовые проекты по конвенции .NET;
- **маркерных интерфейсов DI нет** (одно вхождение `IDependency` на репозиторий) —
  правило `cf.injected-service` оставлено выключенным;
- **две команды из §1 отвечают не на тот вопрос, который кажется.** `grep -rl "^#if"`
  не видит директив с отступом, а искать надо не их, а `#if` внутри выражения —
  единственный ответ даёт `parse_error_files` после прогона. В команде про типы
  `*Test` стоял `head -30`, то есть ответ «около тридцати» мог быть усечением.
  Обе команды в плане поправлены.

## T22 — доработка поставки под закрытый контур

Первая попытка установки в АС CF провалилась: `uv sync` упирался в
`invalid peer certificate` и тянул пакеты не оттуда. Разбор показал три
независимые причины — исправлены все.

### Лок из поставки за пределами PyPI бесполезен

`uv.lock` ссылается на файлы `files.pythonhosted.org` **поимённо и с хэшами**:
162 URL и 16 записей `registry = "https://pypi.org/simple"`. Настройка индекса
готовый лок не перенаправляет — с `--frozen` uv идёт ровно по записанным адресам.
То есть флаг `--index-url` в такой конфигурации не помогает вообще, и это
неочевидно: выглядит как «зеркало настроено, но не используется».

Лечится только пересборкой: `uv lock` против настроенного индекса. Проверено, что
uv в этом случае **пере**решает зависимости, а не падает на несовпадении источника,
поэтому удалять лок перед пересборкой не нужно — записанные версии останутся, если
зеркало их отдаёт.

Установщик получил `--index URL`, который и записывает адрес, и влечёт пересборку.

### Настройки uv — файлом рядом с пакетом, а не переменными окружения

Проверено экспериментально: `uv.toml` из каталога, указанного в `--project`,
подхватывается и `lock`, и `sync`, и `run`, из любого текущего каталога. Это лучше
переменных окружения — настройка переживает смену терминала и не требует помнить
её при каждом вызове.

В `uv.toml` поставки три строки, каждая против конкретного отказа:

- `[[index]] default = true` — **вместо** PyPI, а не в дополнение. С `default = false`
  uv всё равно ходил бы на pypi.org за тем, чего нет в зеркале;
- `native-tls = true` — системное хранилище сертификатов. Причина
  `invalid peer certificate` именно в этом: прокси подписывает соединения
  сертификатом внутреннего УЦ, которого нет в наборе, вшитом в uv;
- `python-downloads = "never"` — иначе uv, не найдя интерпретатор, уходит за
  сборкой Python на github.com и упирается в тот же прокси, но сообщение будет уже
  про загрузку Python. С этой строкой ошибка честная.

Две ловушки, обе проверены на месте:

- **порядок ключей в TOML.** Ключи верхнего уровня обязаны стоять до первой таблицы
  `[[index]]`, иначе TOML отнесёт их к ней. Это не синтаксическая ошибка — настройка
  просто перестаёт действовать. Закреплено тестом;
- **`native-tls` объявлен устаревшим** в пользу `system-certs`, и свежий uv на него
  ругается. Переименовать нельзя: неизвестный ключ uv.toml не игнорирует, а падает
  с ошибкой разбора, то есть `system-certs` сломает установку на старом uv, а
  `native-tls` перестанет работать, только когда его выпилят совсем. Оставлено
  старое имя с объяснением в комментарии.

### Сборка пакета оказалась необязательной

`uv sync` собирает `docpipe` через `hatchling` — ещё один пакет, который зеркало
может не отдавать. Режим `--no-install-project` ставит только пять зависимостей:
15 пакетов вместо 17, ни сборочного бэкенда, ни шага сборки.

Расплата — нет консольной команды `docpipe`. Поэтому `run.sh` переведён на
`python -m docpipe` с `PYTHONPATH` на каталог поставки: это работает в **обоих**
режимах, и выбор режима перестал влиять на то, как инструмент вызывают. Проверено
сквозным прогоном в обеих установках — манифест одинаковый.

### Запуск не должен ходить в сеть

`run.sh` переведён на `uv run --no-sync`. Без этого каждый запуск сверялся бы
с индексом и падал бы там, где индекс недоступен, — на команде, которая
с зависимостями ничего не делает. Окружение поднимает установщик, и это его работа.

### Дефект, который был бы обнаружен только при обновлении

Установщик копировал `deploy/uv.lock` поверх целевого безусловно. На машине, где
лок уже пересобран против внутреннего зеркала, обновление инструмента вернуло бы
ссылки на pypi.org — и рабочая установка сломалась бы **после** успешного
обновления, то есть в момент, никак с обновлением не связанный по виду.

Теперь установщик отличает свой лок по строке `registry = "https://pypi.org/simple"`:
чужой сохраняется, а вместо копирования запускается пересборка против того же
зеркала. Обе строки — в локе и в скрипте — закреплены тестом, иначе смена формата
записи в uv.lock тихо вернёт прежнее поведение.

### Диагностика вместо чужого стектрейса

При неудаче установщик печатает три причины в порядке частоты, каждую с готовой
командой и подставленным путём репозитория, и сообщает, что скопированные файлы
на месте. Ошибка uv остаётся выше — она нужна, — но человеку больше не приходится
по ней догадываться, что настраивать.

## T22 — сборка окружения внутри контура и переход на `$WORK`

Продолжение разбора установки на боевой машине. Выяснилось два обстоятельства,
каждое из которых меняет процедуру.

### Зеркало может отдавать не всё

Настройки индекса недостаточно: часть пакетов внутреннее зеркало не проксирует
вовсе. Значит, набор зависимостей нужно **подбирать** внутри контура, а не
переносить готовым.

Написан `deploy/OFFLINE.md` — процедура из семи шагов: клонировать, разложить
поставку без сети (`--skip-sync`), настроить `uv.toml`, итеративно подобрать
`uv lock`, проверить, зафиксировать результат обратно в `deploy/` клона.

Три вещи, которые в такой процедуре неочевидны и потому вынесены явно:

- **подбор идёт в установленной поставке, а не в `deploy/`.** `uv lock` собирает
  метаданные пакета, а `deploy/pyproject.toml` объявляет `packages = ["docpipe"]` —
  рядом с ним пакета нет, и команда падает раньше, чем доходит до зависимостей.
  В `$BUNDLE` лежит и то и другое, и это ровно тот каталог, где инструмент потом
  работает: подбираем там, где проверяем;
- **свобода по пакетам разная.** `tree-sitter` ниже 0.25 не заработает — там
  сменился API запросов, это не вкусовщина. Версия `tree-sitter-c-sharp` попадает
  в манифест и в ключ кэша, то есть её смена законна, но обнуляет кэш и может
  изменить вывод. Для остальных ограничения почти безразличны. Сведено в таблицу,
  иначе подбор превращается в угадывание, какую строку можно трогать;
- **проверка зеркала — до подбора и отдельным пустым проектом.** Иначе
  `invalid peer certificate` неотличим от «пакета нет в зеркале», и человек
  правит `pyproject.toml` там, где надо править `SSL_CERT_FILE`.

Для случая, когда пакета нет вовсе: `uv export` → `pip download` на машине
с доступом → `find-links` плюс `offline = true` в `uv.toml`. Обе настройки
проверены на этом uv; `offline = true` заодно работает проверкой полноты набора —
недостача видна сразу и по имени пакета, а не по таймауту.

Установщик научился брать `deploy/uv.toml`, если он есть: после одного подбора
`--index` больше не нужен ни на одной машине периметра. Сам файл добавлен
в `.gitignore` — адрес внутреннего зеркала за периметр не нужен, а `git pull`
его не тронет.

**Сверка манифестов ослаблена до имён пакетов.** Тест сравнивал `dependencies`
целиком, но на закрытом контуре ограничения версий расходятся законно — их
подстраивают под то, что отдаёт зеркало, и возвращают в `deploy/`. Сравнение
имён по-прежнему ловит то, ради чего тест писался: забытую при добавлении
зависимость.

### Обновление не должно требовать сети

Установщик пересобирал лок при каждом обновлении поверх установки с внутренним
зеркалом. Это лишнее: если состав зависимостей не менялся, пересобирать нечего,
а требование связи с зеркалом на ровном месте — это отказ там, где можно было
обойтись. Теперь `pyproject.toml` поставки сравнивается с установленным, и
пересборка идёт только при расхождении.

### Пути через `$WORK`

В целевой системе задана переменная `$WORK` = `/home/work/<логин>`. Все пути
в `CASHFLOW.md`, `deploy/README.md`, `install.sh` и `docpipe.yaml` переведены
на неё: `/home/work/$USER` неверен там, где логин и имя каталога различаются,
и молча уводит установку не туда. На сами скрипты это не влияет — `install.sh`
берёт репозиторий аргументом, `run.sh` вычисляет пути от своего расположения.

## B01 — декларативный читатель реестров ✅

Первая задача бизнес-слоя. Разведка репозитория АС CF (см.
`docs/findings-cashflow-registries.md`) показала, что точки входа объявлены не в
коде: джобы, workflow и обработчики событий лежат строками в XML и исполняются
универсальными раннерами, получающими имя типа из данных. Читатель этих файлов —
вход всего бизнес-слоя, и он не зависит ни от шага 2, ни от .NET вообще.

Создано: `docpipe/registry/{__init__,model,config,reader}.py`,
`tests/test_registry_reader.py` (36 тестов), `tests/fixtures/registries/**`.

### Что решено по ходу

**Формат `json` на верхнем уровне не реализован.** План перечислял `xml`, `json`,
`inline`, но способ найти записи в JSON-файле нигде не задан: для XML это
`item_xpath`, для JSON аналога не описано. Придумывать его — значит завести формат,
которым никто не пользуется. JSON читается только как цель `follow`, где структура
известна (`Steps` у workflow-core). План поправлен.

**Номера строк у записей не хранятся.** ElementTree позиций не отдаёт, а способы их
достать (подмена `TreeBuilder`, работа с expat напрямую) хрупки и завязаны на версию.
Записи ссылаются на файл; этого хватает для отчётов, а B03 при необходимости найдёт
строку поиском по якорю. План B03 поправлен: `explain` печатает файл, не строку.

**Записи верхнего уровня сортируются, вложенные — нет.** Разница принципиальная и
её легко стереть «для единообразия». Записи верхнего уровня приходят из нескольких
файлов, и их порядок — следствие обхода ФС. Порядок шагов workflow — **данные**:
это цепочка `NextStepId`, и сортировка по `ref` её порвёт. Правило записано как
комментарий в `read_registry` и закреплено тестом
`test_children_keep_declaration_order`, который проверяет, что порядок шагов
фикстуры **не** совпадает с алфавитным.

### Ловушки, подтверждённые на фикстурах

- **`.//add` ловит интерцепторы.** У `<interceptors><add type="…"/></interceptors>`
  нет `@name`, поэтому обход по `.//add` дал бы либо падение, либо фантомный сервис.
  Только прямые дети.
- **`.//Item` ловит справочники.** В `Items_Basic.xml` рядом с `JOBS` лежат
  справочники БД; якорь на `List[@InnerName='JOBS']` обязателен.
- **ElementTree не выбирает атрибуты.** `find("./File[…]/@Path")` возвращает `None`.
  Суффикс `/@Attr` читатель отрезает сам. Без этого описание реестра выглядит
  рабочим и молча отдаёт пустые значения — худший вид отказа.
- **База для `follow` задаётся явно.** Путь в реестре отсчитывается от корня
  развёртывания, а не от каталога файла реестра. Тест
  `test_follow_base_is_not_the_registry_directory` проверяет именно удвоенный путь
  `deployment/Data/Items/Data/Items/Workflows/…`, который получается при наивной
  склейке и выглядит настоящим.
- **BOM.** Фикстура `Items-Workflows.xml` сохранена с BOM намеренно, и это закреплено
  отдельным тестом `test_fixture_still_has_bom`: «чистка» фикстуры иначе оставит
  проверку чтения байтами бессмысленной.

### Что добавилось сверх плана

**Отчёт о пустом реестре.** Реестр, не давший ни одной записи, внешне неотличим от
«таких точек входа в системе нет», и это самая дорогая из возможных ошибок настройки.
Сообщение выдаётся, только если файлы прочитаны, но записей нет **во всех** —
ноль записей в отдельном файле нормально: глоб `Items*.xml` для реестра джобов
законно захватывает `Items-Workflows.xml`, где списка `JOBS` нет. К сообщению
добавляется подсказка про пространство имён: при объявленном `xmlns` поиск по голому
имени тега не находит ничего и об этом не сообщает.

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy docpipe && uv run pytest -q
                                                   # 534 passed
```

## B02 — четыре реестра АС CF ✅

Реестры описаны данными: `registries.example.yaml` в корне, зеркало по фикстурам —
`tests/fixtures/registries/registries.yaml`. Кода добавилось мало: `parse.py` на два
разбора и одно выражение в читателе.

Создано: `registries.example.yaml`, `docpipe/registry/parse.py`,
`tests/fixtures/registries/registries.yaml`, `tests/test_registry_cashflow.py`
(26 тестов).

### Пример и фикстура не должны разъехаться

Описание реестров поставляется как пример с боевыми путями, а проверяется на фикстурах
с другими путями. Это готовое место для расхождения: поправят одно, забудут другое,
и обнаружит это настройщик на боевом репозитории — там, где отладка дороже всего.

Поэтому `test_example_matches_fixture` сравнивает два описания целиком, **исключая
ровно три поля**: `path`, `paths` и `follow.base`. Всё остальное — `item_xpath`, состав
полей, вложенные записи — обязано совпадать.

### `#tag`: вид поля лежит в имени элемента

Обнаружено при реализации. Вид поля списка (`FieldText`, `FieldLookup`, `FieldDateTime`)
записан **тегом**, а не атрибутом, и при этом входит в состав бизнес-сущности —
он нужен в `business_hash` (B05). Читатель такого не умел.

Добавлено четвёртое выражение поля — `#tag`. Три строки в `_extract_xml`, план B01
поправлен.

Заодно выяснилось, что формулировка плана «читать по префиксу `Field*`» **невыразима**:
подмножество XPath в ElementTree допускает `*` только как компонент целиком, `Field*`
в позиции тега не поддерживается. Получилось `./Fields/*` — все дети `<Fields>`. Это
не слабее белого списка, а строже: перечень видов заведомо неполон, и белый список
молча потерял бы поле нового вида. Вид при этом не теряется — приходит из `#tag`.
План поправлен.

### `parse_schedule`: экранирование делает не тот, на кого думаешь

`JOBSCHEDULE` записан как `&lt;JobSchedule Interval=&quot;60&quot; /&gt;`, и «разэкранировать»
звучит как отдельная работа. На деле разэкранирование выполняет **первый** разбор XML:
в поле приходит уже `<JobSchedule …/>`. Остаётся второй `fromstring`, и именно его
легко не заметить, приняв значение за обычную строку.

`Interval` — в секундах (подтверждено на АС CF). Отсюда вывод, который записан в docstring
и понадобится B08: `Interval=60` у отчётного джоба — это опрашивающий цикл, а не
«отчёты формируются раз в минуту». Различать опрос и расписание — дело сборщика
документа; разбор отдаёт число.

Мусор не роняет инвентаризацию: пустая строка, число, обрезанный тег дают `None`.

### `split_type_name`: запятая вне скобок

`StepType` и `DataType` записаны как `"FQN, Сборка"`. Наивный `split(",")[0]` на закрытом
дженерике `MapStep`2[[System.String, mscorlib],[System.Int32, mscorlib]], Sbt.Sample`
даёт `MapStep`2[[System.String` — обрубок, который не найдётся ни в одном индексе
символов и будет выглядеть как отсутствующий тип. Резать надо по первой запятой **вне
квадратных скобок**; фикстура `Sample.v2.json` такой шаг содержит намеренно, и есть
отдельный тест, показывающий, что наивная резка даёт другой результат.

Из остатка берётся только первый сегмент: полное отображаемое имя сборки содержит
`Version=`, `Culture=`, `PublicKeyToken=`, а сопоставляется всё это с именем проекта.

### Что добавилось в описание сверх плана

- **`override`** у джобов и workflow. `Override="false"` означает, что при развёртывании
  запись не перезаписывает существующую строку в БД, то есть расписание и признак
  активности для неё — «объявлено при установке», а не факт. Без этого поля документ
  уверенно сообщал бы неверную периодичность;
- **`error_behavior`** у workflow: `DefaultErrorBehavior` описывает, что происходит при
  сбое шага, и это бизнес-значимо.

## B03 — `docpipe anchors`: инвентаризация точек входа ✅

Первый артефакт бизнес-слоя, полезный сам по себе. Отвечает на вопрос «сколько
в системе точек входа и что их реализует» — таблицы, которой в АС CF, по-видимому,
не существует, а без неё объём работы по каталогу процессов остаётся догадкой.

Создано: `docpipe/registry/anchors.py`, `tests/test_anchors_cli.py` (24 теста).
Изменено: `docpipe/cli.py` (под-typer `anchors` с `list` и `explain`),
`docpipe/registry/parse.py` (`strip_generic_arity`).

### Резолв по соглашению об именах, а не по видам реестра

Соблазн был написать `if kind == "job": …`. Вместо этого поле, содержащее имя типа,
называется одним из четырёх имён — `impl_fqn`, `contract_fqn`, `impl_type`, `data_type`, —
и резолв идёт по имени поля. Новый реестр достаточно описать, назвав поле так же.

Порядок один для всех: прямое совпадение по `symbol.fqn`, затем реализации интерфейса.
Отдельная ветка «для джобов идти через интерфейс» не понадобилась — она получается сама,
а `via` в результате говорит, что именно сработало. Индекс реализаций строится перебором
`related` у каждого узла: обратного ребра `implemented_by` в манифесте нет,
`tree._relations` его намеренно не создаёт (интерфейс мог не стать узлом).

### Обработчик события — вход, список — нет

Структурное решение, которое стоило продумать. Записи реестра структуры — это списки,
а точками входа являются объявленные на них обработчики. Поэтому дети, чей вид входит
в `ENTRY_KINDS`, поднимаются на верхний уровень отдельными якорями со ссылкой на
родителя в `scope` (`UserTasks/ItemAdded`), а поля списка и шаги workflow остаются
вложенными: они описывают устройство, а не вход.

Правило сформулировано через множество видов, а не через `if kind == "list"`. Побочная
выгода: на боевом `Cashflow.Structure.xml` поля списков (их тысячи) не заливают вывод.

### «Не найден среди узлов» — это НЕ «мёртвая запись»

План B03 говорил «мёртвая запись реестра выводится в отчёт». По манифесту такой диагноз
поставить **нельзя**: узлами становятся только enrolled и классифицированные типы,
поэтому неразрешённая ссылка одинаково выглядит и когда типа нет, и когда он просто
не документируется. Различает их только индекс символов, а он строится при `scan`
и никуда не сохраняется.

Формулировка исправлена везде: B03 сообщает «не найден среди узлов документации» и
печатает почему; диагноз «мёртвая запись» ставит B06, где индекс доступен. План поправлен.

### Дженерики

`StepType` закрытого дженерика приходит как `MapStep`2[[System.String, mscorlib],…], Asm`,
а `symbol.fqn` в манифесте хранится без арности (она вынесена в `type_parameters`
и приписывается только к `id` узла). Без нормализации ни один дженерик-шаг не сопоставился
бы. Добавлен `strip_generic_arity` — резать по первой обратной кавычке достаточно:
в сегментах namespace она встречаться не может.

### Что сказано прямо, а не обойдено

**Команда известна не у всех якорей.** `@team` объявлен только в `services.config`;
у джобов, workflow и обработчиков событий владелец должен браться из `ownership.yaml`
(M06), которого ещё нет. `--team` их поэтому не отбирает. Это записано в план, чтобы
пустой результат не приняли за отсутствие.

### Флаги состояния убраны из описания реестров (решение владельца)

`Override`, `IsActive`, `JOBDISABLED` больше не читаются. Три довода, каждого хватило бы:
инструмент видит репозиторий и боевой БД не знает никогда, поэтому «джоб выключен»
сказать не может; прочитанный флаг рано или поздно кто-нибудь прочтёт как факт; политика
поставки меняется независимо от кода, и привязка к ней устаревала бы от правки процедуры
развёртывания.

Оговорка «объявлено в репозитории, а не наблюдается в бою» верна для любого значения
из реестра безусловно — она и заменяет флаги. Закреплено тестом
`test_state_flags_are_deliberately_not_read`; атрибуты в фикстурах при этом оставлены,
они описывают реальность файлов.

## M03 — обратимый разбор документа ✅

Сделан вне очереди шага 2: B04 разбирает бизнес-документы этим же кодом, и
дублировать разбор нельзя — форматы зон разъехались бы, а обнаружилось бы это

Создано: `docpipe/materialize/{__init__,model,document}.py`,

### Инвариант

`assemble(parse_document(t)) == t` байт в байт — проверено на 14 документах:
с front matter и без, CRLF, без завершающего перевода строки и с тремя, с BOM,
с юникодом, с чужими ключами, с маркерами в непривычных пробелах.

Держится он на двух решениях, каждое из которых легко нарушить «упрощением»:
сегмент хранит **и** тело, **и** полный исходный текст с маркерами (иначе сборка
нормализует маркер к каноническому виду); строки бьются своим выражением, а не
`splitlines(keepends=True)` — последний режет ещё и по `\v`, `\f`, ` `,
и строка документа могла бы разъехаться там, где переводом строки не пахнет.

### Маркер внутри блока кода: ограничение подтвердилось, тест был неверен

Первая версия теста утверждала, что маркер внутри ```-блока не считается маркером.
Это неверно: разбор построчный, о блоках кода не знает, и такой маркер **делает
документ структурно испорченным**. План это и описывал — обходной путь один, отступ
в четыре пробела. Тест переписан на честное поведение: голый маркер в блоке кода даёт
`DocumentError`, маркер с отступом — обычный текст. План дополнен явной формулировкой.

### Валидация состояния — не здесь

План требовал отказа, если `docpipe_state` «не проходит валидацию». Типизированно
это здесь невозможно: у шага 2 в принятом состоянии два хэша и список членов,
у бизнес-слоя — `business_hash`, а разбор общий. Проверяется общее: `docpipe`
и `docpipe_state`, если они есть, — словари. Схему валидирует модель своего слоя.
План поправлен.

## B04 — каталог бизнес-документов ✅

Создано: `docpipe/business/{__init__,model,catalog}.py`,
`tests/test_business_catalog.py` (32 теста), `tests/fixtures/business/**`.

### Поправка владельца: сущности пишутся, а не генерируются

Я предположил, что 289 списков `Cashflow.Structure.xml` — готовый каталог
бизнес-сущностей. Владелец проверил на боевых данных: это таблицы и их структура,
полезен там **только** `DisplayName`, и сгенерировать 289 малозначимых сущностей —
выстрел в ногу. Их никто не прочтёт, а отчёт о непокрытом станет вечно красным.

Решение записано в план: документ `be.*` заводится поштучно и только когда сущность
нужна процессу; реестр структуры даёт **справку**, а не заготовку. Отчёт о непокрытом
считается только по `ENTRY_KINDS`, и `list` в него не входит никогда.

Ценность реестра структуры при этом подтвердилась в другом: `list_event` — отличная
точка входа, на боевых данных их 176.

### Каталог — это множество файлов

Отдельного манифеста бизнес-слоя нет. Аналитик работает в IDE, и один файл на процесс
с `git add` дешевле промежуточного артефакта, который пришлось бы пересобирать перед
каждой правкой.

Документом каталога считается `.md`, у которого `docpipe.schema` начинается
с `business/`. **Именно по схеме, а не по наличию ключа `docpipe`:** формат зон общий
с шагом 2, и отбор по ключу перепутал бы слои в обе стороны. В фикстурах на это стоит
отдельный документ с `schema: materialize/1`, лежащий внутри дерева каталога.

### Что решено по ходу

**`doc_path_for(doc_id, business_root)` — без параметра `kind`.** План передавал вид
документа отдельно, но он однозначно задан префиксом идентификатора. Два источника
истины про вид разошлись бы, и документ уехал бы не в тот каталог. Соответствие
префикса и объявленного `kind` проверяется отдельной проверкой. План поправлен.

**`scope` вместо `list:` и `workflow:`.** В примере плана область якоря называлась
по виду родителя. У `ResolvedAnchor` из B03 это `scope`; одна вещь — одно имя, иначе
сверка каталога с инвентаризацией превращается в перевод. План поправлен.

**Не всякая ошибка выбрасывает документ.** Документ с нерезолвящейся `capability`
структурно исправен — не разрешается только ссылка, и выбросить его значило бы
спрятать целый процесс из всех отчётов из-за опечатки в одном поле. Выбрасываются
только документы, чью **идентичность** установить нельзя: неверный формат
идентификатора, расхождение с путём, несоответствие вида префиксу.

**Ошибки собираются, а не бросаются на первой.** Аналитик правит документы пачкой,
и увидеть все проблемы сразу дешевле, чем по одной за прогон.

`SCHEMA_VERSION` 1.0 → 1.1, `CACHE_VERSION` 1 → 2.

### Граница нормализации оказалась уже, чем звучал критерий

Критерий приёмки говорил: «переформатирование файла (лишние пробелы, переносы строк)
не меняет `impl_hash`». Первая версия теста проверяла это на
`Compute( int x )` против `Compute(int x)` — и упала.

Причина в самой спецификации: `re.sub(r"\s+", " ", …)` схлопывает
**последовательности** пробельных символов, но не удаляет одиночный пробел,
вставленный там, где его не было. Отступы, переносы строк и пустые строки покрыты;
смена правил расстановки пробелов вокруг скобок — нет.

Усиливать нормализацию не стал: правила пришлось бы выдумывать, а агрессивная
нормализация схлопывает и значимые различия. Вместо этого граница зафиксирована
явно — отдельным тестом `test_normalisation_boundary_is_whitespace_runs`, записью
в `docs/manifest.md` и в план. Практическое следствие: смена настроек форматтера
даст **разовую** волну «реализация изменилась» по всему дереву; событие однократное
и снимается приёмкой.

Это тот случай, когда тест был сильнее спецификации, и правильный выход — не
подгонять реализацию под тест и не ослаблять тест молча, а записать границу.

### Вторая граница: XML-doc

`SourceSpan` не включает XML-doc — комментарий является предшествующим соседом
объявления, а не его потомком. Поэтому правка XML-doc `impl_hash` не меняет.
Записано тестом и в справочнике: менять устройство span ради этого не нужно,
но знать об этом шагу 3 придётся.

### Проверено парами

Смысл двух хэшей теряется, если проверять их порознь, поэтому критерии
сформулированы парами:

- изменение тела метода — `impl_hash` меняется, `signature_hash` **нет**;
- изменение типа возврата — меняются **оба**;
- перестановка файлов `partial`-типа — не меняется ничего;
- правка любой половины `partial` — `impl_hash` меняется.

## M04 — шаблоны и образцы ✅

Создано: `templates/README.md`, семь скелетов, четыре образца,
`docpipe/materialize/template.py`, `tests/test_materialize_template.py` (42 теста).

### Комплект скелетов сверяется с набором правил

Тест читает `rules/dotnet.yaml` и сравнивает множество значений `template`
с множеством имён файлов. Добавить вид сущности теперь значит дописать правило
**и** завести скелет: иначе прогон упадёт с явной ошибкой вместо молчаливой
потери документов.

### Что проверяется при загрузке и почему

- **генерируемый блок есть и пуст** — скелет объявляет его место, а не
  содержимое; положенный туда текст затрётся при первом прогоне, и человек
  решит, что инструмент сломан;
- **каждая секция пуста по `is_section_empty`** — самая дорогая проверка
  во всём шаге 2: подсказка обычным текстом сделала бы каждый новый документ
  «уже написанным», и агент обошёл бы дерево впустую;
- **есть секция `notes`** — при реклассификации должна остаться хотя бы одна
  секция-приёмник;
- **нет front matter** — он собирается целиком по манифесту;
- **ключи подстановки из белого списка** — `{{ tema }}` иначе осталась бы
  текстом в каждом документе дерева.

### Маркер с неверным именем ловится счётом, а не разбором

Неочевидное следствие устройства M03: маркер, имя которого не по образцу
`[a-z][a-z0-9_]*`, разбором **не распознаётся** и молча становится обычным
текстом. Ошибки при этом нет — документ структурно корректен, просто секции
в нём нет.

Поймать это можно только сравнением: число вхождений `docpipe:section:(start|end)`
в тексте против удвоенного числа разобранных секций. Проверка добавлена.

Граница при этом такая: если испорчен **только один** из пары маркеров, ошибку
даёт уже разбор документа, и его сообщение точнее — оно указывает на строку.
Счёт ловит случай, когда испорчены оба (`Notes`, `my-notes`), — то есть когда
человек последовательно назвал секцию не по образцу. Оба случая закреплены
тестами.

### Образцов четыре, а не семь, и это решение

Постановка требует шаблоны сервиса, провайдера, воркфлоу и контроллера — они
и заполнены, на реальных типах `SampleSolution`, включая эндпоинты и связи
из золотого манифеста.

Для `ignite-service` и `ignite-compute` образцов **нет**: специфика кластера
на боевом репозитории не проверена (`CASHFLOW.md` §3.2), и придуманный образец
врал бы агенту про то, чего никто не видел. Отсутствие закреплено тестом, чтобы
образец не появился «за компанию».

Отдельный тест сверяет состав секций образца с составом секций его скелета:
иначе образец учил бы структуре, которой скелет не создаёт.

### Проверка


## M07 — `plan.py`: план, статусы, решения ✅

Создано: `docpipe/materialize/plan.py`, `tests/test_materialize_plan.py` (23 теста).

### Два «действия» названы по-разному

План предупреждал, что статус и действие путают. Оказалось, что путают и два

узла, а не отсутствие места.

там, где узла нет.

### `docs/materialize.md` — справочник, а не пересказ плана

По образцу `docs/manifest.md`: что лежит в файле, какие зоны, какие статусы,
какие команды, как выглядит цикл. Обоснования остались в плане — дублировать их
значило бы завести два места, которые разойдутся.

Все команды из справочника прогнаны на тестовом решении: `scan` → `materialize` →
`docs status` → `docs accept` → `docs owners --lint` → `anchors list`.

### CLAUDE.md: семь правил шага 2

Реализовывать дальше будет более слабый агент, поэтому в раздел жёстких правил
добавлено то, что ломается **молча**: зоны документа и инвариант обратимости;
различение слоёв по `docpipe.schema`; `is_section_empty`; сравнение по
нормализованному тексту; отказ вместо самолечения; `accept` берёт хэши
из манифеста; приёмка идёт через тот же план и ту же запись.

### CASHFLOW: §9 про шаг 2

Три вещи, специфичные для боевого репозитория: `docs_root` и `docs_scan_exclude`
с каталогом самого инструмента; обязательный первый прогон с `--dry-run` как
первая оценка объёма; таблица «что смотреть в первом отчёте `docs status`».
Три пункта добавлены в чек-лист.

## T23 — решения вместо неклассифицированного ✅

Задача пришла не из плана, а из работы на боевом репозитории: `./run.sh stats` дал
около 4100 неклассифицированных, и по отчёту было нельзя понять, что из этого требует
правила, а что вообще не должно документироваться. Замечание было сформулировано так:
«их надо либо классифицировать, либо отметить, что классификация не нужна,
соответственно и отчёт должен это отражать».

### Почему отчёт не мог сказать «готово»

Причина оказалась механической, а не стилистической.

Состояние «решено не документировать» в модели было — счётчик `excluded`, — но
безымянное: ни по какому решению, ни зачем. Разбивка по причинам, которая есть
в README («на ABP `name_regex` — 508 из 996»), была добыта ручными замерами, инструмент
её не показывал.

Хуже второе. Секция `exclude` умела ровно четыре условия, и решение «типы с атрибутом
`[GenerateCode]` не документируем» выразить было **нечем**. На АС CF это 1478 типов,
которые оставались в `unclassified` навсегда, сколько бы раз человек их ни просмотрел.
То есть счётчик смешивал «ещё не смотрели» с «посмотрели и решили, что не надо»,
потому что второе физически некуда было положить.

### Что сделано

Три исхода, и все три — решения: `<kind>` (документируем), `not_documented`
(не документируем, с причиной), `undecided` (решения нет). Плюс два состояния, которые
решением человека не являются и потому стоят отдельно: `not_enrolled` — решено уровнем
выше, в `docpipe.yaml`; `interface_covered` — решил инструмент.

`exclude` стал списком правил с обязательным `reason` и условием из тех же десяти
предикатов. Нового кода это почти не потребовало: движок в `ruleset.py` (M01) generic,
а таблица предикатов в `classify.py` уже содержала `attribute`, `namespace_regex`
и `inherits`. Ровно та дырка, из-за которой 1478 типов были неотсеиваемы, закрылась
переиспользованием того, что уже было.

`require_public` оставлен полем. Отрицания в движке нет намеренно, и «не public» через
предикаты не выражается; но довод не только технический — это глобальный переключатель
«документируем ли внутреннюю кухню», а не решение о группе типов. В отчёте он участвует
псевдоправилом `exclude.require_public` с приоритетом ниже всех остальных.

### Что оказалось важнее, чем выглядело

**Появился признак завершения, а с ним и смысл в CI.** `--fail-on-undecided` даёт код 1,
пока есть типы без решения. Пока «не решено» было счётчиком «неклассифицировано»,
он был большим всегда, и новый тип в репозитории в нём не выделялся: +1 к 7142 не видно.
Это и есть настоящая причина, по которой замечание было верным.

**Совместимость оказалась обязательной, а не любезной.** Копия набора правил уже лежит
на боевом репозитории АС CF, и правка, требующая одновременной миграции, означала бы,
что настройку там надо переделывать. Поэтому краткая форма из четырёх полей
разворачивается в правила с зарезервированными id `exclude.<поле>` и общими причинами,
а формы складываются: `rules:` можно дописать рядом с полями, ничего в них не меняя.
Развёрнутый набор АС CF так и оставлен в краткой форме — переведён только эталонный
`rules/dotnet.yaml`, а в набор АС CF добавлены закомментированные заготовки по трём
крупным группам из его отчёта.

### Ловушки

**Атрибуция при нескольких совпавших решениях.** Побеждает больший `priority`, при равном —
меньший `id` (`pick_winner`), и никогда порядок в файле: иначе перестановка двух правил
в YAML меняла бы цифры, которые идут в журнал и в CI. Правила краткой формы получили
отрицательные приоритеты (`path_glob` −1, `name_regex` −2, `type_kind_deny` −3,
`require_public` −4), чтобы решение человека забирало атрибуцию себе, а порядок между
собой повторял порядок проверок прежней реализации — иначе замеры «по какой причине
отсеяно» из findings перестали бы сходиться.

**Правило-заглушка.** `when: {}` отвергается при загрузке само — условие обязано быть
словарём с одним ключом, это проверка из M01. А вот `path_glob: ["**"]` с причиной
«разберусь потом» синтаксически законно, и запретить его нельзя: законные широкие
решения существуют. Видно только в таблице причин, по неправдоподобно большому
счётчику у одного решения. Поэтому таблица сортируется по убыванию счётчика,
а не по id.

**Отчёт для человека, а не для парсера.** Пришлось написать `plural`: «1 правил»
в отчёте выглядит дефектом инструмента. Строка «решение не принято» остаётся на месте
и при нуле, с подписью «решены все символы»: исчезнув, она заставила бы выяснять,
всё решено или отчёт сломался.

**Таблица видов перестала печатать `total`.** Сумма видов меньше числа символов, потому
что служебные категории ушли в блок решений, — и итог в этой таблице читался бы как
ошибка. По манифесту (`docpipe stats`) итог печатается: там он равен сумме.

### Проверка

Главный критерий — **манифест по фикстуре отличается от эталонного ровно одной строкой,
`ruleset_version`**. Перевод эталонного набора в форму с причинами не изменил ничего
по существу, и это проверено побайтовым сравнением, а не рассуждением. Отдельный тест
`test_reference_set_migration_changed_nothing` держит то же самое иначе: состав отсева
на `SampleSolution` и `WildSolution` у краткой формы и у формы с причинами совпадает.

Ключи сидкара переименованы: `unclassified` → `undecided`, `excluded` →
`not_documented`, добавлен агрегат `documented`. Ничего, кроме документации, эти ключи
не читало — проверено grep по `.sh`, `.yaml`, `.json`; README при этом показывал ключ
`classified`, которого инструмент никогда не выдавал, и теперь пример стал правдой.

909 тестов (+22).

## T24 — `docpipe symbols` ✅

Задача пришла с того же боевого репозитория, из следующего шага цикла настройки.
После T23 отчёт по одному проекту выглядел так:

```
Вне области            24170
РЕШЕНИЕ НЕ ПРИНЯТО         6
  модули:  6  Sbt.Cashflow.Grid.Services.AutoConclusionService
  окончания имён:  4 (прочее), 1 Factory, 1 Converter
```

И дальше двигаться нечем: известно, что осталось шесть символов и что четыре
не опознаются по имени, но **что это за символы — не известно**. Формулировка была
такая: «отладка каждого проекта будет занимать время, и надо иметь инструмент,
который позволит удобно это смотреть».

### Признак, который уже был

До T20 роль такого инструмента играл разовый скрипт `tools/unclassified.py`; его
удалили, когда появился `scan --stats`. Здесь повторилось то же самое: для работы
по инструкции понадобился скрипт поверх внутренних функций `docpipe`, которого
в инструменте нет. Это и есть признак нехватки команды, а не нехватки скрипта.

### Что сделано

`docpipe symbols` печатает сами символы с фильтрами по состоянию решения, модулю,
namespace, правилу и виду. На символ — семь строк: вид и модификаторы, путь со
строкой объявления, прямые базы, замыкание наследования, атрибуты, публичные члены
и принятое решение с причиной.

Показываются не все поля, а решающие — те, по которым пишется предикат. Полный дамп
заставляет листать вывод вместо того, чтобы принять решение; для остального есть
`--format json`.

Публичные члены попали в вывод не для полноты: имена методов grid-сервиса — это
контракт (их вызывают по имени через прокси), и на АС CF вид сущности опознаётся
по ним там, где имя типа не говорит ничего. Ровно тот случай, что в отчёте выглядит
как «4 (прочее)».

### Что оказалось важным

**Одна реализация решения на отчёт и на выборку.** Две разошлись бы на первой новой
категории, и тогда `--stats` говорит «шесть без решения», а `symbols` показывает
пять — доверять нельзя ни одному. Решение вынесено в `stats.decide`, `collect_stats`
переписан на неё; счётчики от этого не изменились (проверено существующими тестами
до правки строк), а согласованность закреплена отдельным тестом.

**`--rule` работает в обе секции сразу.** Спрашивают его, чтобы проверить только что
написанное правило, и помнить, в какой оно секции, человек не должен. Побочно вышло
полезное: на классифицированных он показывает правила, которые совпали, но не
победили, — `--rule service` находит `RiskComputeService`, ставший `ignite_service`.
До этого такой аудит делался через `jq` по `matched_rules` в манифесте.

**Индекс символов пришлось вернуть из прогона.** `ScanResult` получил поле `index`:
спрашивать «что осталось без решения» у манифеста бессмысленно, туда по определению
попадает только решённое.

### Побочно исправлено

Обрезка срезов переехала из подсчёта в вывод, и появился `--top`. На репозитории
с сотнями проектов топ-15 модулей выглядел полным списком — то есть половина работы
была не видна; теперь обрезанный срез помечается остатком («и ещё 476»).

Заодно `_top` перестал пользоваться `most_common(15)`: тот при равных счётчиках
сохраняет порядок вставки, то есть порядок обхода индекса. Формально это нарушало
жёсткое правило проекта про явный `sorted()` с явным ключом, и на срезе с длинным
хвостом единичных счётчиков могло проявиться. Теперь сортировка явная: по убыванию,
при равенстве по имени.

932 теста (+23).

## T25 — вызов через CLI вместо скрипта-обёртки ✅

Замечание с боевой машины: «мне не нравится, что есть какой-то скрипт типа `run.sh`,
который по сути дублирует функционал CLI… если нужно объявить какие-то переменные
окружения, то лучше это будет просто списком переменных, а не скриптом, который надо
разбирать».

### Чем скрипт мешал

Он завёл свой набор режимов — `stats`, `scan`, `dry-run`, `validate`, `diff`,
`symbols`, `--` — поверх тех же команд `docpipe`. Два следствия, оба выяснились
на практике:

- **инструкция перестала совпадать с тем, что человек набирает.** Читая
  «`./run.sh stats`», он не находит там ни одного своего флага, а чтобы узнать,
  какие пути подставляются, обязан прочитать bash;
- **каждая новая команда требовала строки в `case`.** В T24 `symbols` пришлось
  добавлять в двух местах. Обёртка, перечисляющая команды, разъезжается с CLI
  по умолчанию — это вопрос времени, а не аккуратности.

### Что в нём было по существу

Три вещи, каждая из которых иначе даёт отказ именно на закрытом контуре:
`uv run --no-sync` (без него каждый вызов сверяется с индексом и падает там, где
индекса нет), `python -m docpipe` с `PYTHONPATH` (при установке
с `--no-install-project` консольной команды нет вовсе) и `cd $CF_ROOT` перед вызовом
(`out` в конфигурации задан от текущего каталога, а не от `--root`).

Всё переехало в инструкцию: пять строк `export` и одна строка `alias`. После этого
команды в документации выглядят так, как их набирают:

```bash
docpipe scan --root . --config $BUNDLE/docpipe.yaml --stats
docpipe symbols --root . --config $BUNDLE/docpipe.yaml --module <проект>
```

`--rules` из инструкций убран заодно: путь к `rules.yaml` прописан в `docpipe.yaml`,
и дублировать его флагом значило бы иметь два источника истины.

### Ловушка, которую пришлось закрыть

Требование `--no-sync` осталось без исполнителя. Пока был скрипт, флаг лежал
в коде и проверялся тестом по этому коду; теперь единственный носитель — текст
инструкции. Поэтому тест проверяет её: `--no-sync` обязан присутствовать
в `deploy/README.md`, `cashflow-docspipe/README.md` и в шапке `docpipe.yaml`.
Без этого флаг тихо выпадет при следующей правке документации, а обнаружится
на машине без доступа к индексу — то есть в худшем возможном месте.

Третьим носителем сделана финальная подсказка `install.sh`: она печатает тот же
список переменных и алиас, поэтому рабочий вызов человек получает сразу после
установки, не открывая README.

### Что осталось на боевой машине

`install.sh` файлы копирует, но не удаляет, поэтому уже установленный `run.sh`
там останется до ручного удаления. Работать он продолжит — команды CLI, которые
он зовёт, не менялись.

934 теста (+2: инструкция проверяется вместо скрипта).

## T26 — один набор правил в поставке ✅

Замечание с боевой машины: «настроечный файл при обновлении не затирается,
рядом кладётся `rules.yaml.new` — тогда зачем тот, что уровнем выше? Можно же
оставить только те, что в `cashflow-docspipe`».

Замечание верное, и оно лучше того, что предлагал я. За полчаса до этого я
разбирал ту же копию и предлагал её **переименовать** — в
`rules/dotnet.reference.yaml`, чтобы её нельзя было подхватить по умолчанию.
Это лечило симптом; вопрос «а зачем она вообще» я не задал, хотя механизм
`keep_configured` с `.new` описан в этом же журнале двумя разделами выше.

### Почему копия не нужна

Она отвечала на вопрос «что настроено под АС CF». Но на него уже отвечают две
вещи: пометки «АС CF» прямо в наборе и `rules.yaml.new`, который приносит новую
версию при обновлении. Третий ответ был лишним с самого начала.

После T23 он к тому же испортился: эталон переехал в форму с причинами, набор
АС CF остался в краткой, и `diff` между ними распух до 68 строк даже без
комментариев — показывал форму записи, а не настройку.

### Почему она была вредна

Значение `rules` по умолчанию — `rules/dotnet.yaml` **относительно текущего
каталога**. Прогон из каталога инструмента без `--config` брал эталонный набор
и завершался успешно: манифест построен не теми правилами, ни предупреждения,
ни намёка. Воспроизвёл на копии раскладки, чтобы не рассуждать.

Из `$CF_ROOT`, как написано в инструкции, ловушка не срабатывает — там `rules/`
нет и прогон падает с «файл не найден». То есть она ждала ровно того, кто зайдёт
в каталог инструмента, а туда заходить логично: там лежит настройка.

### Про остаток на уже установленных машинах

Установщик по правилу не удаляет ничего, поэтому оставшийся `rules/dotnet.yaml`
там останется — вместе с ловушкой. Промолчать было нельзя, поэтому добавлено
предупреждение в stderr с объяснением и командой `rm -r`. Тест проверяет обе
половины: что сказали и что **не** удалили.

Тесты установщика впервые прогоняют его по-настоящему (`--skip-sync`, сеть не
нужна) и смотрят на получившееся дерево, а не на текст скрипта. Проверка «ровно
два `.yaml` в дереве» переживёт любую перестановку строк в `install.sh` —

## B06 — `docpipe business lint` ✅

Создано: `docpipe/business/lint.py`, `tests/test_business_lint.py`.
Изменено: `docpipe/cli.py`, `docpipe/config.py`, `docpipe/business/catalog.py`,

### Главная правка плана: «код 1 при находках» делал линт бесполезным

План требовал ронять прогон на любой находке и одновременно печатать отчёт
о непокрытых точках входа. Вместе это означает ненулевой код на любом репозитории,
где каталог не дописан, — то есть всегда, и в первый день особенно. Красный
с первого дня линт выключают на второй, и вместе с ним пропадают шесть проверок,
которые работают.

Правило, по которому проведена граница: **находка роняет прогон, только если её может
починить автор документа.** Якорь не разрешается, процесс без входа, неоднозначная
версия, необъявленная возможность, расхождение команд, битый идентификатор — код 1.
Сколько точек входа ещё не описано и какие записи реестров не нашли своего узла —
состояние работы, а не дефект: печатаются всегда, код возврата не меняют, пока
не названы в `--fail-on`. На фикстуре это видно прямо: находок восемь, код 0.

### Диагноз «мёртвая запись реестра» поставить нечем

Проверка 2 требовала резолва `impl_fqn` «в индексе символов». Индекса нет: он
строится при `scan` и не сохраняется — ровно то, что уже отмечено ловушкой в B03,
только там из этого сделали вывод «диагноз поставит B06», а B06 нечем.

Отличить «класса нет» от «класс не документируется» по манифесту нельзя. Поэтому
проверка называется `registry-unlinked` и говорит ровно то, что знает: «не найден
среди узлов документации». На фикстуре она срабатывает на двух записях, и обе
легальные: `BlockFilesService` и реализация `ILoadLimitsJob` намеренно оставлены
без документации. Назови их линт мёртвыми — первое же, что сделал бы настройщик,
это удалил бы рабочий сервис из `services.config`.

Настоящий диагноз появится, когда индекс FQN начнёт сохраняться. Это правка шага 1:
новое поле манифеста и версия схемы. Делать её внутри B06 значило бы протащить
изменение формата под видом линта, поэтому она записана в план как отдельная работа.

Неоднозначный якорь (`SampleWorkflow` без версии) не разрешается, и наивная
реализация выдала бы про него две строки: «не разрешён» и «неоднозначная версия».

пропускает.

### Настоящая ошибка: зеркало `business_hash` ломало чтение документа

Первая версия писала текущий хэш в `docpipe:` рядом с остальной проекцией —
по образцу шага 2, где так лежат `signature_hash` и `impl_hash`. Прогон прошёл,
файлы записались, и следующий же `build` показал `1 validation error for
BusinessDoc: business_hash`. `BusinessDoc` объявлен с `extra="forbid"`, и загрузка
падала на собственном выводе инструмента: каталог из трёх документов стал каталогом
из нуля, а три строки ошибок ушли в stderr.

Поле можно было бы добавить в модель, но правильный ответ — не писать его вовсе.
Единственный хранимый хэш — **принятый**, и он лежит в `docpipe_state`. Зеркало
текущего завело бы второй источник, который обязан отстать: документ правят руками
чаще, чем пересобирают. `accept`, взявший значение оттуда, зафиксировал бы устаревший
хэш, и документ навсегда остался бы `current`, будучи `drifted`, — ровно та ловушка,
которая в плане описана для B10. Пересчитать хэш дешевле, чем сверять два.

### `build` не создаёт документов

Скелет в `compose` не передаётся вовсе: функция пересобирает документ поверх его
текущего текста. Создание — отдельное действие (`business new`).

Это то же решение, из-за которого у бизнес-слоя нет статуса `orphan`:
бизнес-документы создаются людьми, а не выводятся из кода. Совмести создание
со сборкой — и каталог начал бы расти сам, а `build` перестал бы быть безопасной
операцией, которую можно звать в CI.

### Один сборщик входных данных на все команды

`_business_context` читает манифест, реестры, каталог и владение один раз и отдаёт
`BusinessInputs`. Первая версия `lint` собирала это сама, и при добавлении `build`
получилось бы две сборки: разойдись они в наборе реестров — `build` собирал бы
документ по одному набору, а `status` сравнивал бы с другим, и документ навсегда
остался бы «изменившимся». Ошибка при этом выглядела бы как дефект хэша.

### Мелочи генерируемого блока

Разделы идут фиксированным порядком, раздел без данных печатается со словом «Нет.»:
пропущенный раздел читается как «инструмент не умеет», а «Нет.» — как факт.

Агрегат состояния workflow выводится из реестра, поэтому объявленный `contracts`
с тем же `ref` не повторяется — одна и та же строка дважды выглядит как две
разные вещи. Направления печатаются по-русски: `state` в тексте документа для
аналитика не значит ничего.

Без правил владения шаги не пропадают из раздела «Участники», а идут строкой
`(не задан)`. Пустой раздел выглядел бы как «шагов нет», то есть как факт о процессе,
хотя это факт об отсутствии настройки.

### Что осталось незакрытым

`templates/business/**` в поставку АС CF **не входит**: `install.sh` копирует
`templates/*.md` и `templates/examples/*.md`, подкаталога `business` в глобе нет.

не найдёт скелета. Чинится в B11 вместе с остальной поставкой.

### Граница пакета держится тем же способом, что и с .NET

`docpipe/materialize/**` не импортирует `docpipe/business/**`. Обратный индекс
«узел → бизнес-документы» строится в `cli._with_business_links` и кладётся
в `BuildContext` как данные. Проверяется обходом AST — тем же, что запрещает
импорт `docpipe.dotnet`; общая часть двух проверок вынесена в `_imports_of`.

Импорт проверил бы только то, что модуль загружается, а не то, что зависимости нет.

### Отдельное поле `business_root` вместо «непустого индекса»

Раздел «Бизнес-контекст» появляется, только когда каталог задан. Отличать это
по непустому индексу нельзя: тогда раздел возникал бы у всех узлов сразу при
первом же бизнес-документе в репозитории — то есть структура технического
документа менялась бы от появления чужого файла. Поэтому в контексте два поля:
`business_root` отвечает на «каталог задан», `business_links` — на «этот узел
упомянут». Узел без упоминаний получает «Нет.», а не отсутствие раздела.

### Неготовый бизнес-слой не роняет шаг 2

Реестры могут быть описаны раньше, чем появится первый бизнес-документ, а каталог
может быть временно битым. Отказ материализовать техническую документацию из-за
этого был бы наказанием не за то: шаг 2 самостоятелен, бизнес-слой к нему
пристёгивается. Ошибка идёт строкой в stderr, раздел не собирается, остальное
пишется.

Золотое дерево не изменилось: `business_root` по умолчанию `None`.

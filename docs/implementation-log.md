```
pyyaml==6.0.3              pytest==9.1.1

```

**Проверено:**

```
uv sync                     → без ошибок
uv run docpipe version      → 0.1.0
uv run ruff check .         → All checks passed
uv run ruff format --check  → 4 files already formatted
uv run mypy docpipe         → Success: no issues found in 2 source files
uv run pytest -q            → no tests ran (ожидаемо, тестов ещё нет)
```

### Трудности и отклонения от плана

**1. Typer схлопывает единственную команду в корневую.**
`uv run docpipe version` падал с `Got unexpected extra argument(s) (version)`.
Причина: при одной зарегистрированной команде typer делает её корневой, и слово
`version` разбирается как лишний позиционный аргумент.
Решение: пустой `@app.callback()` переводит приложение в многокомандный режим.
План обновлён — этот пункт добавлен в T00, иначе агент-реализатор упрётся в то же самое.

**2. `ruff format --check` форматирует Python-блоки внутри markdown.**
Проверка падала на `docs/parser-implementation-plan.md`: ruff переписывал компактные
псевдо-сигнатуры вида `def f(a,\n b) -> X: ...` в свой стиль. Это документация, а не код.
Решение: `extend-exclude = ["docs", "examples"]` в `[tool.ruff]`.
План обновлён.

**3. hatchling не находил пакет автоматически.**
Добавлен явный `[tool.hatch.build.targets.wheel] packages = ["docpipe"]`.
План обновлён.

**4. `.gitignore` уже существовал** со строкой `examples/` (туда склонированы `abp` и
`eshoponweb` для финальной проверки). Строка сохранена, остальные правила дописаны.

### Замечание на будущее

`uv run docpipe ...` пересобирает и переустанавливает пакет на каждом вызове
(`Built docpipe @ file:///...`). Это ~0.5 с накладных расходов на команду. На тестах
не сказывается (они импортируют модуль напрямую), но при ручной отладке CLI заметно.

**Создано:** 15 файлов в `tests/fixtures/SampleSolution/` (1 `.sln`, 2 `.csproj`, 12 `.cs`),


Дополнительно, разовой проверкой вне тестов: **все 12 файлов `.cs` парсятся
tree-sitter с `err=0`**, `root_node.has_error == False`. Это важно было проверить
до T06: если бы фикстура не разбиралась, вся дальнейшая работа строилась бы на песке.

### Отклонение от плана

**Тест сделан строже, чем требовал план.** План просил проверить только количество
(`.cs` ровно 12, `.csproj` 2, `.sln` 1). Вместо этого зафиксирован точный отсортированный
список путей и добавлены три содержательных теста:

- `test_generated_file_is_present_but_will_be_excluded` — файл под `obj/` существует;
- `test_partial_class_lives_in_two_files` — обе половинки содержат `partial class`;
- `test_cross_module_inheritance_chain` — цепочка `PricingController` →
  `BaseApiController` (другой модуль) → `ControllerBase` на месте.

Причина: проверка на количество не ловит подмену состава. Если кто-то удалит
`PricingService.Calculations.cs` и добавит любой другой `.cs`, счётчик сойдётся,
а тесты T10 и T18 начнут проверять не то, что задумано.

### Трудность: `.gitignore` мог тихо убить фикстуру (T01)

Файл `obj/Debug/net8.0/Sample.Generated.g.cs` нужен, чтобы проверять правила исключения.
Любой стандартный .NET-шаблон `.gitignore` содержит `obj/` и `bin/` — добавь его кто-нибудь
позже, и файл исчезнет из репозитория, а тесты T04/T14 продолжат проходить, ничего не
проверяя. Проверено `git check-ignore` (сейчас не игнорируется), в `.gitignore` добавлен
явный запрет-предупреждение.


Все 7 пар из таблицы плана проходят без правок алгоритма. Сверх плана добавлены тесты:
идемпотентность `slugify` (повторное применение к результату ничего не меняет),
невозможность пустого slug, независимость `stable_hash` от порядка ключей,
чувствительность `stable_hash` к порядку элементов списка.

### Отклонений от плана нет

Алгоритм реализован ровно как в спецификации. Регекс границ CamelCase
`(?<=[a-z0-9])(?=[A-Z])|(?<=[A-Z])(?=[A-Z][a-z])` корректно обрабатывает аббревиатуры.

### Кириллица в именах типов — вопрос закрыт

**Итог: действий не требуется.** Владелец проекта подтвердил, что в сигнатурах АС CF
кириллицы нет (в комментариях — есть, но они не затрагиваются).

`slugify` применяется ровно в одном месте — имя типа → имя файла в `doc_path`.
Проверено на парсере, что во всех остальных местах кириллица доходит до манифеста
без изменений:

| Что | Кириллица | Куда попадает |
|---|---|---|
| XML-doc `///` | сохраняется | `symbol.xml_doc` |
| Обычные комментарии | не извлекаются | никуда |
| Namespace, FQN, `node.id` | сохраняется | идентификаторы узлов |
| Аргументы атрибутов | сохраняется | `endpoints[].route` |
| Имя модуля в пути | сохраняется | `docs/modules/Расчёты/…` |
| Имя типа → имя файла | **схлопывается в `unnamed`** | только имя `.md`-файла |

Имя модуля идёт в путь сырым, а имя типа — через `slugify`, и это обосновано:
имя модуля берётся из имени файла `*.csproj`, то есть валидно для ФС по построению;
имя типа берётся из идентификатора, который валидным быть не обязан.

Разбор ниже сохранён на случай, если кириллические имена типов всё же обнаружатся
в каком-нибудь модуле.

### Разбор (справочно)

Проверка на реалистичных именах (вне тестов):

```
PricingController    -> 'pricing-controller'      OAuth2Handler   -> 'o-auth2-handler'
FXRateProvider       -> 'fx-rate-provider'        HTTPSProxy      -> 'https-proxy'
IRepository`1        -> 'i-repository-1'          GridGainService -> 'grid-gain-service'
DTOMapper            -> 'dto-mapper'              ApiV2Controller -> 'api-v2-controller'
ЦенаСервис           -> 'unnamed'   ← проблема
Сервис               -> 'unnamed'   ← проблема, коллизия с предыдущим
```

**Любое имя без ASCII-букв схлопывается в `unnamed`.** Корректность при этом не страдает:
разрешение коллизий в T15 добавит хэш-суффикс, и пути останутся уникальными. Но
читаемость теряется полностью — вместо осмысленного имени получится
`unnamed-a1b2c3d4.md`.

В C# кириллические идентификаторы легальны. Насколько это актуально для АС CF — вопрос
к владельцу проекта. Варианты, если понадобится:

1. **Оставить как есть** — коллизии разрешаются хэшем, имена нечитаемы. Ноль работы.
2. **Транслитерация** (`Сервис` → `servis`) — детерминированно, читаемо, нужна таблица
   соответствий на ~66 символов.
3. **Разрешить Unicode в именах файлов** — читаемо, но рискованно для кросс-платформенных
   путей, git на macOS (нормализация NFD/NFC) и внешних инструментов документации.

Реализован вариант 1, как и предписывал план. К нему возвращаться не нужно, пока
`docpipe stats` на реальном репозитории не покажет узлы со slug `unnamed`.

### Отклонения от плана

**1. Типизированные псевдонимы вместо голых `str`.** План описывал
`Symbol.type_kind: str`. Вместо этого заведены псевдонимы `TypeKind`, `MemberKind`,
`Lifetime`, `Confidence`, `DependencyVia`, `RelationKind` и используются на всех
уровнях единообразно. Причина: `type_kind` участвует в правилах классификации (T14),
и опечатка вида `"klass"` иначе всплыла бы только на проде в виде пустой выборки.
Есть тест `test_literal_fields_reject_typos`.

**2. Добавлен `extra="forbid"`.** Плана не нарушает, но не был им предписан.
Ловит опечатки при загрузке чужого манифеста (`--from-manifest` в T18) вместо
молчаливого игнорирования поля. Совместимость вперёд при этом не теряется:
`schema_version` объявлен как `Literal["1.0"]`, то есть несовместимость версий
и так фиксируется явно.

Обе модели `frozen=True` — как и предписывал план.

### Трудность: `Final` для константы со значением `Literal`

`SCHEMA_VERSION = "1.0"` выводился mypy как `str` и не подходил полю
`Literal["1.0"]`:

```
model.py:252: error: Incompatible types in assignment
  (expression has type "str", variable has type "Literal['1.0']")
```

Лечится явной аннотацией `SCHEMA_VERSION: Final[Literal["1.0"]] = "1.0"`.
Мелочь, но mypy strict её не пропускает, а агент-реализатор потратит на это время.

### Замечание: состав `$defs` в схеме

В сгенерированную схему попали 11 моделей:
`Attribute, Dependency, DocNode, Endpoint, Member, Module, ParserVersions,
PartialInfo, Relation, SourceSpan, Symbol`.

**`RawDeclaration`, `FileParseResult`, `DiRegistration`, `RunMeta` отсутствуют — и это
правильно.** Схема описывает `Manifest`, а перечисленные модели из него недостижимы:
первые три относятся к уровню парсера и живут только в кэше (T09), `RunMeta` — это
сидкар-файл. Если понадобится валидировать содержимое кэша, схему для
`FileParseResult` нужно будет генерировать отдельной командой.

### Найденный баг в спецификации: `fnmatch` не понимает `**`

Самая содержательная находка на текущий момент. План предписывал
«использовать `fnmatch` по POSIX-пути» и приводил один пример. Проверка показала:

```
fnmatch("src/A/obj/x/y.cs", "**/obj/**")  -> True
fnmatch("obj/y.cs",         "**/obj/**")  -> False   ← дыра
fnmatch("src/A/Sample.g.cs", "**/*.g.cs") -> True
fnmatch("Sample.g.cs",       "**/*.g.cs") -> False   ← дыра
```

`fnmatch` транслирует `*` в `.*` без учёта разделителей, поэтому шаблон `**/obj/**`
требует наличия `/` перед `obj`. Следствие: **файлы в корневых `obj/`, `bin/` и
сгенерированные файлы в корне репозитория молча просачивались бы в документацию.**
Наивная реализация по плану прошла бы все приведённые в нём критерии приёмки
и содержала бы эту дыру.

Исправлено функцией `matches_glob`: при неудаче и префиксе `**/` пробуется второй
прогон с отброшенным префиксом. Покрыто параметризованным тестом на 9 случаев.
План обновлён — добавлены и описание ловушки, и требование использовать
`matches_glob` в T14 (`exclude.path_glob` там сравнивается так же).

### Отклонения от плана

**1. `os.walk` вместо `Path.rglob`.** План предписывал `rglob`. Заменено, чтобы
получить отсечение каталогов: из каждого glob с суффиксом `/**` выводится glob
каталога (`**/obj/**` → `**/obj`), и в совпавшие каталоги обход не заходит вовсе.
На реальном репозитории это разница между полным обходом `.git`/`node_modules`
и мгновенным пропуском — а заявленные в архитектуре «1–2 секунды на десятках тысяч
файлов» без этого недостижимы.

Отсечение — чистая оптимизация и на результат влиять не может: если каталог совпал
с dir-глобом, любой файл под ним совпал бы и с исходным шаблоном. Это зафиксировано
тестом `test_pruning_does_not_change_result`, который сравнивает обход с отсечением
и без.

Побочная выгода: `os.walk(followlinks=False)` не разыменовывает симлинки из коробки.
Симлинк на дерево исходников иначе породил бы дубли символов с одинаковыми FQN.
Есть тест.

**2. Контрольный тест «без исключений».** Добавлен
`test_discover_without_excludes_sees_generated_file`: с пустым списком исключений
находится ровно 12 файлов. Без него тест на исключения проходил бы и в случае,
если бы файла просто не было на диске, — то есть проверял бы пустоту.

### Замечание: enrollment в этой задаче не реализован

`DocpipeConfig.enrolled` объявлен, но пока никем не читается — он применяется в T15
при сборке дерева, а не при обходе. Это соответствует замыслу: неenrolled модули
**должны** парситься, их символы нужны для графа наследования. Обход их не фильтрует.

## Внеплановый прогон на реальном репозитории (после T04)

По запросу владельца запущено то, что готово, на `examples/eshoponweb` (254 файла `.cs`,
10 проектов, 2 решения). Полный отчёт — [`findings-eshoponweb.md`](findings-eshoponweb.md),
здесь только выводы для реализации.

**Подтвердилось главное:** tree-sitter разобрал **244 файла из 244 без единой ошибки**
за 0.13 с (1948 файл/с). Отказ от Roslyn обоснован. Обход ФС — 17 мс.

**Три бага в спецификации, все внесены в план:**

1. **Многострочные `base_list`** (T06). Реальный случай:
   `class AuthenticateEndpoint : EndpointBaseAsync\n .WithRequest<…>\n .WithActionResult<…>`.
   План предписывал брать текст «как есть» — тогда `signature_hash` начинает зависеть
   от форматирования файла, и переформатирование заставляет агента на шаге 3
   перегенерировать документ впустую. Плюс правила по `base_type` перестают совпадать.
   Исправление: `re.sub(r"\s+", " ", text).strip()`.

2. **DI-регистрации в top-level statements** (T13). Все три `Program.cs` в eShopOnWeb
   написаны без класса и метода. Реализация, написанная под фикстуру (где `Program` —
   обычный статический класс) и ищущая вызовы внутри `method_declaration`,
   **не нашла бы ни одной регистрации в реальном проекте**. Обход обязан идти
   по всему дереву файла.

3. **`unclassified` смешивает разное** (T20). 9 интерфейсов `*Service` отсекаются
   предикатом `type_kind: [class, record]` — это правильно по замыслу, но в статистике
   они попадают в кучу с типами, про которые правила ничего не знают. Введена
   отдельная категория `interface_covered`.

**Наблюдения, не требующие правок кода:**

- Правила из плана дали 18 страниц на 244 файла (81% неклассифицировано). Это ожидаемо:

  на конкретном проекте. В eShopOnWeb HTTP-поверхность построена на паттерне REPR
  (10 типов `*Endpoint`), контроллеров всего 4.
- 22 имени типов дублируются, но почти все разнесены по модулям — модульная раскладка
  дерева разводит их без хэш-суффиксов. Подтверждает выбор структуры.
- Только **16 типов из 247 имеют XML-doc** (6.5%). Для шага 3 это значит, что описания
  придётся выводить из структуры кода, а не из комментариев. Стоит замерить ту же
  цифру на АС CF до планирования шага 3.
- 239 файлов с file-scoped namespace против 1 с блочным — редкая форма встречается
  ровно один раз, и именно на ней всё сломается, если её не поддержать.
- 45 типов (18%) лежат в тестовых проектах. Отсекать через `enrolled` в `docpipe.yaml`,
  а не через `exclude`: тестовые проекты должны парситься ради графа наследования,
  но узлов документации не порождать.

### Зачем отдельное решение, а не расширение SampleSolution

Критерии приёмки T04–T20 завязаны на точные количества в `SampleSolution`
(11 файлов, 10 символов, 6 узлов). Расширение той фикстуры потребовало бы

### Покрытые случаи

Все восемь найдены прогоном на eShopOnWeb, все ломают реализацию, написанную
только под `SampleSolution`:

| Случай | Что ломается без обработки |
|---|---|
| Многострочный `base_list` | `signature_hash`, правила `base_type` |
| Top-level statements в `Program.cs` | теряются **все** DI-регистрации |
| Тип без namespace | FQN с ведущей точкой |
| Блочный `namespace N { }` | namespace не определяется |
| `global using` / `using static` / алиас | резолв FQN |
| Вложенные типы с общим именем | два узла схлопываются в один |
| Два `Constants` в одном модуле | коллизия `doc_path` |
| Тестовый проект | тесты попадают в документацию |

Тесты фикстуры проверяют **наличие конструкций**, а не только файлов. Иначе
случайное «упрощение» фикстуры оставило бы тесты T06/T13 зелёными и бессмысленными.

### Уточнение контракта, найденное при написании фикстуры

Схлопывания пробелов (`\s+` → ` `), которое я внёс в план после прогона на eShopOnWeb,
**оказалось недостаточно**. На реальной строке получалось:

```
'EndpointBaseAsync .WithRequest<AuthenticateRequest> .WithActionResult<…>'
```

Пробел перед точкой остаётся, и это не канонический C#. Нужен второй шаг —
`re.sub(r"\s*\.\s*", ".", text)`. Итог совпадает с тем, как база была бы записана
в одну строку. План обновлён.

### Побочно: контракт сопоставления имён базовых типов (T14)

Фикстура вскрыла, что правило «последний сегмент после точки» неверно.
Для `Sample.Common.Web.BaseApiController` значим последний сегмент,
для `EndpointBaseAsync.WithRequest<A>.WithActionResult<B>` — **первый**
(последний даёт бессмысленное `WithRequest`).

Различаются по признаку «точка после первого `<`». Функция `base_type_candidates`
с таблицей проверенных случаев внесена в T14. Условие с `<` существенно: без него
`Sample.Common.Web.BaseApiController` порождал бы кандидата `Sample`, и правило
`base_type: ["Sample"]` совпадало бы со всем подряд.

Это тот случай, когда фикстура окупилась до написания кода, который она проверяет.

### Решения, которые стоит знать

**Запрос `.scm` только находит узлы объявлений.** Имя, модификаторы, базы и атрибуты
берутся обходом потомков, а namespace и `containing_type` — обходом предков.
Запросом второе выразить нельзя: tree-sitter не умеет подниматься вверх по дереву.
Файл `declarations.scm` остаётся местом, где перечислены виды объявлений, — добавить
новый вид можно, не трогая код.

**`span` начинается с атрибутов**, а не с `public`: `attribute_list` — потомок
объявления. Это желаемое поведение, ссылка в документации ведёт на объявление целиком.
Зафиксировано тестом, чтобы случайная «починка» не сдвинула ссылки.

**Квалифицированные имена атрибутов приводятся к простому**
(`System.ComponentModel.Description` → `Description`): правила классификации пишутся
по простому имени.

**`verbatim_string_literal` — единый лист** без потомка `string_literal_content`,
в отличие от обычной строки. `@` и кавычки снимаются вручную, `""` разворачивается в `"`.
Внесено в план.

### Четыре бага в уже написанном коде — исправлены здесь же

1. **`.slnx` не искался вовсе** (T04, T05). ABP мигрировал на новый XML-формат решений
   целиком: **30 файлов `.slnx` и ноль `.sln`**. `discovery` знал только про `.sln`,

   а `parse_sln` выбирает разбор по суффиксу. Проверка: 651 проект из 30 решений,
   все существуют на диске.

2. **`module:{name}` — не уникальный id** (T05). Имена проектов повторяются **39 раз**,
   включая три разных `MyCompanyName.MyProjectName.csproj`. Разные модули склеились бы
   в один, и часть документации исчезла бы молча. Теперь `id = "module:" + путь к csproj`.
   Выбран путь, а не суффикс-разрешитель коллизий: путь уникален по построению и
   считается локально из одного файла, тогда как суффикс потребовал бы глобального
   прохода и менял бы id существующих модулей при добавлении нового.

3. **`ProjectReference` сопоставлялись по `.stem`** (T05) — та же проблема: ребро графа
   уходило бы в произвольный из одноимённых модулей. Теперь `Include` разрешается
   в репо-относительный путь. На ABP разрешаются **2383 ссылки из 2383**,
   на eShopOnWeb — 18 из 18.

4. **`$(TargetFrameworks)` попадал в манифест** (T05) как строка, неотличимая
   от настоящей платформы. Значения с `$(` отбрасываются.

### Три правки плана — на задачи, которые ещё не написаны

5. **`#if` прячет члены типа от прямого обхода** (T07 — следующая задача). Члены под
   `#if` не являются прямыми детьми `declaration_list`, они уходят под `preproc_if`
   и `preproc_else`. Реализация «перебрать детей тела» потеряла бы их молча.
   `#region`, в отличие от `#if`, контейнером не является — асимметрию легко не заметить.
   В спецификацию T07 добавлено требование спускаться вглубь с остановкой на вложенных
   типах и тест с ожиданием четырёх членов там, где наивная реализация вернёт два.

6. **`#if` внутри аргументов атрибута уничтожает объявление** (T20). Директива рвёт
   выражение, а атрибут — потомок объявления, поэтому ломается и оно: остаток файла
   переразбирается как top-level statements, и `class_declaration` пропадает.
   Так теряется `CmsKitWebUnifiedModule` в ABP. Обойти в рамках tree-sitter нельзя,
   поэтому `validate` обязан ловить комбинацию «`parse_errors > 0` и ноль объявлений».
   Воспроизведено один в один в фикстуре `WildSolution/…/Modules/ConditionalModule.cs`
   (8 ошибок, 0 объявлений — те же числа, что на настоящем файле).

7. **FQN не является уникальным ключом символа** (T15). План задавал

   На 9075 объявлениях ABP: по `fqn` — **255 коллизий**, по `module + fqn` — 108,
   по `module + fqn + арность` — 3. Причин две: перегрузка по арности дженерика
   (112 групп, рекорд — шесть арностей у одного имени) и одинаковые FQN в разных
   сборках. Хэш от FQN не разводит ничего там, где FQN совпадает: внутри одного модуля
   195 групп дают одинаковый slug, и в 105 из них FQN тоже одинаков. Ключ и суффикс
   переопределены в T15; фикстура с тремя арностями одного имени — в

### Трудности прогона

**Минимальное воспроизведение потери объявления не удалось получить сразу.** Синтетический
пример с `#if` в аргументах атрибута парсился с ошибками, но объявление **выживало** —
терялось только на настоящем файле. Бисекция показала, что восстановление грамматики
зависит от того, что идёт за атрибутом: на упрощённом теле класса она справляется,
на реальном (с ещё одним `#if` внутри метода) — нет. Точный порог — внутреннее свойство
tree-sitter, гоняться за ним смысла нет. Вывод для плана сформулирован так, чтобы
не зависеть от порога: признаком считается пара «ошибки есть и объявлений нет», а фикстура
скопирована с реального файла, а не сочинена.

**Тест на фикстуру пришлось писать по тексту файла, а не по дереву.** Разбор сломан,
узла `attribute_list` в дереве нет, поэтому наличие конструкции проверяется по исходнику,
а последствие — по дереву. Обе половины нужны: без первой тест сломается, если файл
«починят», без второй — если грамматика научится восстанавливаться.

**1. `event_field_declaration` — отдельный узел, план его не упоминал.** В грамматике
события объявляются двумя разными узлами: `event_declaration` — только форма
с `add`/`remove`, а обычное `public event EventHandler Changed;` — это
`event_field_declaration`. Реализация строго по плану потеряла бы обычную форму,
которой в ABP вдвое больше. План исправлен, узлов в `members.scm` шесть.

**2. Поле с несколькими объявителями даёт несколько членов.** План предписывал брать
имя первого `variable_declarator`; тогда в `private int _a = 1, _b = 2;` поле `_b`
пропало бы молча. На ABP таких полей 0 из 1652 — то есть правило плана ничего бы
не сломало на практике, — но корректная обработка стоит трёх строк, и молчаливая
потеря данных того не стоит. План исправлен.

**3. Список видов членов сужен явно.** `indexer_declaration`, `operator_declaration`,
`conversion_operator_declaration`, `destructor_declaration`, `delegate_declaration`
не извлекаются: в `MemberKind` таких значений нет. На 3000 файлов ABP их суммарно 20
против 14 000 обычных членов. Раньше это просто не оговаривалось, теперь записано
в план вместе с инструкцией, что менять при необходимости.

### Решения, которые стоит знать

**Владелец члена ищется обходом вверх, а не перебором детей тела.** Это следствие
находки ABP: члены под `#if` живут под `preproc_if`/`preproc_else` и прямыми детьми
`declaration_list` не являются. Запрос находит их на любой глубине, а ближайший
предок-тип сам разводит вложенные типы — отдельной логики «остановиться на вложенном
типе» не понадобилось. Тест на пять членов (`One`, `Two`, `TwoOld`, `Region`, `Three`)
ловит наивную реализацию: она вернёт три.

**Сигнатура режется по узлам, а не поиском `{` в тексте.** Терминаторы —
`block`, `arrow_expression_clause`, `accessor_list`, `;`. Текстовый поиск сломался бы
на `void M(string s = "{")` и на инициализаторах коллекций. Атрибуты отбрасываются,
хотя и являются потомками узла: для правил есть отдельное поле `attributes`,
а в сигнатуре они шумят. Ограничения `where T : class` и `: base(x)` стоят до тела
и в сигнатуру входят — это желаемое поведение.

**Срез текста берётся относительно самого узла** (`member.text[start - member.start_byte : …]`),
поэтому в функцию не нужно тащить исходник файла целиком.

### Замечание: тяжёлый хвост у сигнатур полей

`{` инициализатора коллекции лежит **внутри** `variable_declaration`, а не отдельным
потомком, поэтому обрезка по узлам его не отсекает и инициализатор входит в сигнатуру.
Обычно это полезно — значение `const` часть контракта, и его изменение должно менять
`signature_hash`. Но хвост тяжёлый: медиана сигнатуры поля 52 символа, p99 — 187,
максимум **1283** (поле с ASCII-графикой в инициализаторе). Всего сигнатур длиннее
200 символов — 460 из 37 262 (1,2 %).

Решено оставить как есть и записать в план требование к шагу 3 усекать сигнатуру
при выводе. Альтернатива — резать поле по `=` — теряет значения констант ради
1,2 % случаев.

### Замечание: покрытие XML-doc у членов

1703 члена из 37 262 (**4,6 %**) имеют `<summary>`. У типов было 3,8 %. Третье
подтверждение подряд: описания на шаге 3 придётся выводить из кода.


Оба критерия приёмки совпали: `PricingController.cs` даёт три `usings` и пустые

На реальном коде: **33 368 директив** на ABP (1223 уникальных пространства имён)
и 884 на eShopOnWeb. Ни одного подозрительного имени. Разбор 5,6 → 6,2 с
(1278 файлов/с) — цена третьего прохода запросом по дереву.

### Отклонения от плана

**1. Понадобился запрос по всему дереву, а не перебор детей `compilation_unit`.**
Директива `using` может лежать **внутри блочного namespace** — в ABP таких 8.
Перебор детей корня их не увидел бы. Заодно проверено, что ложных срабатываний
внутри методов нет: `using var s = …` — это `local_declaration_statement`,
а `using (…) { }` — `using_statement`; узлом `using_directive` не является ни то,
ни другое. План исправлен, добавлен `usings.scm`.

**2. Узел имени бывает третьего типа — `alias_qualified_name`.** План называл только
`qualified_name` и `identifier`. Форма `using global::AutoMapper;` (в ABP две штуки)
даёт `alias_qualified_name` с текстом `global::AutoMapper`. Префикс снимается:
это квалификатор глобального пространства имён, а не часть имени, и без снятия
резолв на T10 такой namespace не нашёл бы. Прочие extern-алиасы
(`using MyLib::Some.Namespace;`) оставлены как есть — без разрешения алиасов сборок
они всё равно не резолвятся, а врать в манифесте хуже.

### Решения, которые стоит знать

**Имя берётся как последний именованный потомок.** У алиаса перед именем стоит ещё
`identifier` самого алиаса, поэтому «первый `identifier` или `qualified_name`»
дал бы имя алиаса. Алиасы всё равно отбрасываются, но правило «последний» корректно
для всех форм разом и не зависит от порядка проверок.

**`global` и `static` — анонимные узлы**, в `named_children` они не попадают,
поэтому различение идёт по `{child.type for child in directive.children}`.

**Ловушка с `using global::X;`.** Реализация, ищущая подстроку `global` в тексте
директивы, отнесла бы её в `global_usings` — хотя прямым потомком `global` здесь
не является. Зафиксировано отдельным тестом.

### Замечание: global usings в реальных репозиториях

В ABP и eShopOnWeb — **ноль** `global using` (формы: 33 374 обычных, 58 алиасов,
10 `using static`). Фича из C# 10, и обе кодовые базы её не используют: ABP целится
в том числе в netstandard2.0. Проверить эту форму можно только на фикстуре — ещё один
довод в пользу того, что `WildSolution` собирается вручную, а не копированием
из реального репозитория.

### Ограничение, которое стоит помнить на T10

Алиасы отбрасываются целиком, поэтому тип, на который ссылаются через алиас,
на T10 не разрешится. В ABP таких директив 58 на 33 368 (0,17 %). Лечится только
полноценной таблицей алиасов на файл; пока не окупается.

## T09 — `cache.py`: sqlite-кэш разобранных файлов ✅

**Создано:** `docpipe/cache.py`, `tests/test_cache.py`.

**Проверка**

```
uv run pytest -q                    197 passed
uv run ruff check .                 All checks passed
uv run ruff format --check .        26 files already formatted
uv run mypy docpipe                 Success: no issues found in 11 source files
```

### Замер на ABP — ради этого задача и делалась

| | время | попаданий | промахов |
|---|---|---|---|
| холодный прогон | 8,19 с | 0 | 7869 |
| тёплый прогон | **0,79 с** | 7869 | 0 |

Ускорение **10,3×**, результаты обоих прогонов побитово идентичны (сравнение всех 7869
`FileParseResult`). Размер БД — 8,0 МБ на 17,5 МБ исходников.

Оставшиеся 0,79 с — это чтение и хэширование всех файлов, то есть неустранимый пол
инкрементального режима. Совпадает с оценкой «~1–2 с на десятках тысяч файлов»
из §2.3 архитектуры.

### Отклонения от плана

**1. Битая БД пересоздаётся, а не роняет прогон.** В плане этого не было. Кэш —
расходный материал: оборванная запись, обрезанный файл или посторонний файл с тем же
именем не должны стоить отказа команды с советом «удалите каталог». Открытие проверяется
запросом `SELECT count(*) FROM sqlite_master`, на `sqlite3.DatabaseError` файл удаляется
и создаётся заново. Отдельно проверено, что пустой файл (0 байт) — валидная пустая БД
и пересоздавать его не нужно.

**2. `put` не коммитит.** План API коммит не описывал. Коммит на каждую запись — это
десятки тысяч fsync на большом репозитории. Коммит перенесён в `close()`; записи видны
через `get` в том же соединении, поэтому внутри прогона поведение не меняется, а на
аварийном завершении теряется кэш, но не результат.

**3. Уровень сжатия `zlib` задан явно.** Значение по умолчанию менялось между версиями
Python, а payload хочется иметь воспроизводимым побайтово.

Все три внесены в план.

### Решения, которые стоит знать

**Попадание определяется хэшем содержимого, `mtime` не используется вовсе.** Время
модификации меняется при checkout и при переносе репозитория, не меняя ни байта в файле:
кэш на `mtime` то промахивался бы там, где не должен, то попадал бы там, где нельзя.
Это то же требование, что и к манифесту, — результат обязан зависеть только от содержимого.

**`prune` считает разницу в Python, а не через `NOT IN (…)`.** Список путей измеряется
тысячами, а число параметров в запросе sqlite ограничено.

**Payload — `model_dump_json` от pydantic, а не `stable_json_dumps`.** Побайтовая
стабильность payload на корректность не влияет (сверяется `content_hash`, не payload),
а родная сериализация модели гарантирует точный round-trip. `stable_json_dumps`
используется только для строки версий в `meta`, где нужно сравнение на равенство.

### Ошибка, найденная своим же тестом

Первая версия `test_round_trip_keeps_full_structure` клала БД в
`sample_solution.parent / "tmp-cache"` — то есть **внутрь `tests/fixtures/`**. Тесты
проходили, но каталог фикстур засорялся. Замечено по `git status` сразу после прогона.
Исправлено на `tmp_path`. Вывод на будущее: любой тест, который что-то пишет, обязан
писать в `tmp_path`, даже если путь строится от фикстуры.

Разница 88 % против 39 % объясняется составом: в eShopOnWeb большинство баз — внешние

`ITransientDependency`).

### Отклонения от плана

**1. Ключ индекса — не FQN.** План задавал `dict[str, Symbol]` с ключом-FQN. На ABP это
255 коллизий: 112 групп перегрузки по арности дженерика и 155 пар одинакового FQN
в разных сборках. Ключом стал `symbol_key(модуль, FQN, арность)` — тот же формат, что
у id узла на T15. Добавлена функция `index_by_fqn`: она возвращает **список** ключей,
потому что один FQN законно принадлежит нескольким типам (на ABP таких FQN 261).

**2. Namespace и usings проверяются последовательно, а не скопом.** План предписывал
собрать совпадения из namespace и usings вместе и при количестве >1 ставить `ambiguous`.
Это пометило бы неоднозначным обычный случай, когда тип виден и по namespace, и по using,
хотя в C# ближнее имя просто перекрывает дальнее. Реализовано как в C#: сначала
полностью квалифицированное имя, затем namespace и его префиксы от длинного к короткому
(побеждает первое совпадение), и только при неудаче — usings, где несколько совпадений
действительно означают неоднозначность. Результат — 1 неоднозначность на 8966 символов
вместо шума.

**3. `strip_generics` удаляет сбалансированные группы, а не всё от первого `<`.**
`A.B<C<D>>.E` — это вложенный тип `E` внутри generic-типа `B`, его FQN равен `A.B.E`.
Обрезка по первому `<` дала бы `A` и потеряла бы тип.

Все три внесены в план.

### Ошибка, которую нашёл собственный тест

Первая версия брала для резолва usings **только своего файла**. Тест
`test_global_using_participates_in_resolution` был написан под это поведение — и в момент
написания утверждения стало видно, что оно неверное: `global using` действует на весь
проект, а не на файл, где объявлен, и обычно все они лежат в одном `GlobalUsings.cs`.
То есть реализация не резолвила бы **ни один** тип, видимый исключительно через них.

Исправлено: набор видимых usings файла = собственные плюс все `global_usings` его модуля.
Границу модуля пересекать нельзя — проекты изолированы, на это добавлен отдельный тест.

Показательно, что на реальных репозиториях эта ошибка не проявилась бы никак: в ABP
и eShopOnWeb `global using` нет вовсе. Нашлась она только потому, что тест писался
формулировкой ожидания, а не подгонкой под вывод.

### Решения, которые стоит знать

**Базовые типы резолвятся до слияния, каждое объявление со своими usings.** Половинки
`partial class` лежат в разных файлах, и usings у них разные; резолв после слияния
применил бы к одной половине контекст другой.

**`base_types` хранит FQN, а не ключи символов.** По ним матчатся правила классификации
(`base_type: ["EndpointBaseAsync"]`), и ключ с модулем и арностью там был бы нечитаем.
Обратный переход даёт `index_by_fqn`.

**Атрибуты дедуплицируются вручную.** Поля `args` и `named_args` — список и словарь,
поэтому модель нехэшируема и `set` не работает.

**Пустой префикс namespace обязателен** при переборе: глобальное пространство имён видно
из любого места, и тип без namespace должен находиться.

**1. Переход «базовый тип -> символ» идёт по паре (FQN, арность).** План описывал обход

если половинки `partial` резолвят одно имя по-разному (usings у файлов разные),
побеждает первая по порядку файлов.

Оба отклонения внесены в план, включая тест, который проваливает реализация без арности:
`IService<T> : IOneArg`, `IService<T,K> : ITwoArgs`, `User : IService<int,string>` →
в замыкании `User` должен быть `ITwoArgs`.

### Главное отклонение: `[Route]` на методе

Разведка перед реализацией (по установившейся привычке смотреть на реальный код раньше,
чем писать) сразу дала цифру: в ABP **245 из 356** HTTP-атрибутов идут вместе
с отдельным `[Route]` на том же методе:

```csharp
[Route("api/abp/multi-tenancy")]
public class AbpTenantController
{
    [HttpGet]
    [Route("tenants/by-name/{name}")]
    public Task<TenantDto> FindTenantByNameAsync(string name) { }
```

План предписывал брать шаблон метода только из аргумента `Http*`. По этому плану **всем**
методам `AbpTenantController` достался бы один и тот же маршрут — маршрут типа. Таблица
эндпоинтов выглядела бы правдоподобно и была бы бесполезной, а на фикстуре все критерии
приёмки прошли бы: в `SampleSolution` шаблон записан прямо в `[HttpGet("{id:guid}")]`.

Исправлено: шаблон метода = аргумент `Http*`, при его отсутствии — аргумент `[Route]`
на том же члене. Случая, когда аргументы есть у обоих, ни в ABP, ни в eShopOnWeb нет
ни разу, поэтому приоритета достаточно простого.

### Прочие отклонения

**Токены сравниваются без учёта регистра.** План называл ровно `[controller]` и `[action]`;
ASP.NET их регистр не различает. Значение подставляется с исходным регистром имени.

**Сортировка дополнена третьим ключом** — `member`. По `(route, http_method)` два метода
с одинаковым маршрутом и глаголом (в ABP есть: `[HttpPost]` + `[MapToApiVersion]` на двух
перегрузках) остались бы в порядке обхода.

Заодно исправлен пример в критериях приёмки: он показывал GET первым, хотя по собственному
правилу сортировки `api/v1/Pricing` — префикс `api/v1/Pricing/{id:guid}`, и первым идёт POST.

### На реальном коде

| | ABP | eShopOnWeb |
|---|---|---|
| типов с эндпоинтами | 97 | 4 |
| эндпоинтов | 356 | 26 |
| с непустым маршрутом | 346 | 26 |
| глаголы | GET 226, POST 68, PUT 34, DELETE 26, PATCH 2 | GET 14, POST 12 |

Подстановка токенов проверена на eShopOnWeb: `[Route("[controller]/[action]")]` даёт
`Manage/ChangePassword`.

### Пустой маршрут — это не ошибка

10 эндпоинтов ABP получили пустой `route`: у контроллера нет `[Route]`, у метода нет
шаблона, то есть путь задаётся **конвенциональной** маршрутизацией в конфигурации
приложения. Атрибутов для него не существует, вывести путь неоткуда.

Эндпоинт всё равно выдаётся: то, что метод обрабатывает GET, — факт, и он полезен шагу 3.
Записано в план как явно не поддерживаемый случай, чтобы пустой маршрут не приняли за баг.

### Что решено не разбирать

- **конвенциональная маршрутизация** — задаётся не на типе;
- **minimal API** (`app.MapGet`) — не привязан к типу;
- **`[Route]` без `Http*`** (11 членов в ABP) — маршрут без ограничения по глаголу,
  а `Endpoint.http_method` обязателен.

### Отклонения от плана

**1. `typeof(...)` — не запасной вариант, а обычная форма записи.** План её не упоминал
вовсе. Разведка показала: в ABP и eShopOnWeb так записаны **47 регистраций из 267** —
больше, чем двумя типами-аргументами (34+13):

```csharp
context.Services.TryAddTransient(typeof(IKernelAccessor<>), typeof(KernelAccessor<>));
```

Имена типов здесь названы так же явно, как в `<…>`, поэтому `confidence` остаётся `high`.
Без этой ветки 47 полностью определённых регистраций были бы потеряны.

**2. Регистрация без единого имени типа пропускается.** План предписывал брать
«`service_type` из текста». Текстом там оказывается тело лямбды
(`sp => sp.GetRequiredService<X>()`), переменная (`AddSingleton(builder)`) или приведение
типа — в поле `service_type` манифеста попал бы мусор. Такую регистрацию нельзя связать
с символом, то есть документации она ничего не даёт. Таких вызовов 50 из 267.

**3. Узлы вызовов приходят в `di.py` снаружи.** План говорил «создать `di.py`, изменить
`parser.py`», не уточняя границу. Прямое обращение `di.py` к грамматике потребовало бы
импортировать `_LANGUAGE` из `parser.py`, который сам импортирует `di.py`, — цикл.
Запрос выполняет `parser.py` (ему и принадлежит вся работа с tree-sitter), а `di.py`
получает список узлов и занимается только смыслом.

Все три внесены в план вместе с тестами.

### Решения, которые стоит знать

**Запрос сужен до `function: (member_access_expression)`.** Это отсекает вызовы без
получателя (`Foo()`), которых в файле подавляющее большинство, и заодно даёт бесплатную
проверку: `AddScoped<IFoo, Foo>()` без `services.` регистрацией не считается.

**Имя метода лежит в поле `name` у `member_access_expression`** и бывает двух видов:
`identifier` или `generic_name`. `type_argument_list` принадлежит `generic_name`,
а **не** `invocation_expression` — на этом легко ошибиться.

**Открытые дженерики сохраняются как есть** (`IKernelAccessor<>`). Резолвом занимается
T15, и в план ему добавлено требование снимать generic-часть при сопоставлении с символом:
`KernelAccessor<>` не совпадёт с именем символа `KernelAccessor` буквально.

### Замечание: маркерные интерфейсы

Основной способ регистрации в ABP — не вызов, а наследование от `ITransientDependency`
(696 типов) или `ISingletonDependency` (167). Вызовов `Add*` там всего 182 на 8966 типов.
Синтаксически это не регистрация, и в `di.py` ему делать нечего — ловится правилом
классификации по базовому типу на T14. Записано в findings-abp.md ещё при прогоне;
здесь подтверждено цифрами.

## Стресс-тест на четырёх репозиториях (после T13)

По запросу владельца прогон всего написанного (T04–T13) на двух новых репозиториях —

### Один настоящий баг — исправлен

**Безымянные члены.** Три члена на двух репозиториях получили пустое имя: при
восстановлении после ошибки грамматика отдаёт `field_declaration` без имени — обломок
выражения из-под `#if`. Один случай оказался иным: `extension(char) { … }` — **члены-расширения
C# 14** из .NET 10, которых грамматика 0.23 ещё не знает.

Безымянный член превратился бы в безымянный раздел документации. Исправлено фильтрацией
в `_member_names`; после правки безымянных членов на всех четырёх репозиториях ноль.

### Одна ошибка в разборе проектов — исправлена

**`ProjectReference` через подстановки MSBuild.** В OpenTelemetry разрешались
**2 ссылки из 109**: все остальные записаны как `$(RepoRoot)\src\X\X.csproj`.
Хуже того, старый код склеивал такое значение с каталогом проекта и получал
правдоподобный, но выдуманный путь `test/X/$(RepoRoot)/src/…`.

Значение `$(RepoRoot)` вычисляется функцией MSBuild — воспроизводить это здесь нечем.
Но имя файла в ссылке записано буквально. Добавлен проход `csproj.resolve_references`:
дорезолвливает по имени файла и **только при единственном совпадении** (имена проектов
уникальны не везде — в ABP 39 повторов).

| | до | после |
|---|---|---|
| OpenTelemetry | 2 / 109 | **108 / 109** |
| остальные три | без изменений | без изменений |

Оставшаяся одна — `@(TrimmerRootAssembly->'%(Path)')`, преобразование item-группы,
а не путь. Правильно осталась неразрешённой.

### Две находки осознанно не исправлены

**`TargetFramework` через цепочку props-файлов: 70 модулей из 70 без TFM.** Все проекты
OpenTelemetry пишут `<TargetFrameworks>$(TargetFrameworksForLibraries)</TargetFrameworks>`,
а переменная определена в `build/Common.props`, который не импортируется ни из
`Directory.Build.props`, ни из `.csproj` — цепочка идёт через ещё два файла, и значение
содержит ещё одну подстановку. Достать это можно только полным вычислением свойств MSBuild.

План с самого начала объявляет это границей подхода, и граница подтвердилась. Вывод:
`target_frameworks` — метаданные, а не опора; ни одно правило на них не завязано.
Требование к T20: сообщать о модулях без TFM, чтобы пустое поле не приняли за свойство кода.

**Связанные исходники: 5 % типов вне модулей.** OpenTelemetry и semantic-kernel подключают
общий код через `<Compile Include="$(RepoRoot)\src\Shared\Guard.cs" Link="…" />`. Такой файл
лежит вне каталога любого проекта, и правило «ближайший `.csproj` вверх» не находит модуля:
39 файлов и 50 типов (5,0 %) в OpenTelemetry, 131 файл и 205 типов (4,8 %) в semantic-kernel.

Исправление ломает предположение «файл принадлежит одному модулю» — связанный файл
компилируется в несколько сборок сразу, — то есть меняет сигнатуру `build_symbol_index`
и порождает вопрос, в каком модуле показывать документ. Вместо тихой переделки сданных
задач заведена **T05b** с замерами и с проверкой, которую нужно сделать до реализации:
есть ли этот приём в целевом репозитории вообще.

### Известное ограничение подтвердилось в новых местах

Все 170 файлов с ошибками разбора на четырёх репозиториях — одна и та же причина,
найденная ещё на ABP: директива препроцессора внутри выражения. Стресс-тест добавил три
новых места: **модификатор объявления** (`public` / `#else` / `internal`), **базовый список**
и **шаблон в pattern matching**.

Доля пострадавших файлов зависит от мультиплатформенности: 0 % в eShopOnWeb (один TFM),
0,5 % в ABP, 2,2 % в semantic-kernel и **8,7 %** в OpenTelemetry, который таргетит
от `netstandard2.0` до `net10.0`.

Проверено, что причина именно в директивах: удаление из файла всех строк, начинающихся

- **`.slnx` — не экзотика.** Три репозитория из четырёх его содержат, semantic-kernel

- **`ambiguous`** — одна неоднозначность на 14 221 символ, и та настоящая.

Проверка была простая: прогнать регулярку «похоже ли это на имя типа» по всем
`target` рёбер-конструкторов. Она сразу дала 219 подозрительных значений.

**1. Инициализатор конструктора ломал разбор параметров.** Сигнатура конструктора
намеренно включает `: base(...)` (это решение T07), а первая версия искала закрывающую
скобку через `rfind(")")` — то есть скобку инициализатора. Из
`public C(IOptions o) : base(o)` получался «параметр» `IOptions o) : base(o`.

На ABP так ломался **каждый пятый конструктор**: 217 рёбер из 1016. Исправлено поиском
**парной** скобки счётчиком глубины. После правки доля `low`-confidence на ABP упала
с 456 до 259 — сломанные имена перестали быть «нерезолвимыми».

**2. Тривия внутри сигнатуры (правка T07).** Оставшиеся два случая оказались другой
природы:

```csharp
[Obsolete("use another")]
#pragma warning disable CS0809 // Obsolete member overrides non-obsolete member
public override PropagationContext Extract<T>(…)
```

`#pragma` между атрибутом и модификатором становится **потомком** объявления, а не
соседом, и сигнатура начиналась с него. Комментарий на той же строке после схлопывания
пробелов сливался в общую строку. Второй вид — комментарий внутри списка параметров:
там `//` съедал бы остаток сигнатуры, потому что после схлопывания границы строки уже нет.

Замер до правки: **252 испорченные сигнатуры** на четырёх репозиториях (0,37 % от 68 828).
Мало по доле, но каждая портит и `signature_hash`, то есть заставляет шаг 3
перегенерировать документ впустую.

Исправлено вырезанием байтовых диапазонов узлов `comment` и `preproc_*` — именно
диапазонов, а не поиском `//` в тексте: `//` встречается внутри строковых литералов
(`"otpauth://totp/…"`, реальный случай из eShopOnWeb). После правки — **ноль**
на всех четырёх.

### Отклонения от плана

**Регистрация типа на самого себя ребра не даёт.** План говорил «DI-регистрации, где
`impl_type` соответствует символу», не оговаривая случай `AddTransient<ValuationWorkflow>()`,
где сервис и реализация — один тип. Петля в графе зависимостей — артефакт формы записи,
а не факт о коде, и в документе она читалась бы как «зависит от самого себя».

Побочно вскрылся пробел: **время жизни (`scoped`/`singleton`/`transient`) до манифеста
не доходит** — `Dependency` его не хранит, а `DocNode` не хранит `DiRegistration`.
Для самозарегистрированного типа это единственное, что регистрация сообщала. Вопрос
к шаблонам шага 2, отмечен здесь, чтобы не потерялся.

**`target` DI-ребра резолвится в FQN** тем же способом, что и параметры конструктора.
План не уточнял, что класть в `target`; сервис, записанный простым именем, в манифесте
выглядел бы иначе, чем тот же тип в рёбрах конструктора.

### Решения, которые стоит знать

**Домены проверяются в лексикографическом порядке ключей.** Словарь пришёл из YAML,
и порядок записи в файле источником решения быть не может — перестановка строк меняла бы
манифест. То же правило, что и для приоритетов правил на T14.

**`build_tree` вынесен в `conftest.py`.** Начиная с T15 почти каждой проверке нужен
готовый манифест целиком, а не его половина; повторять сборку в каждом тестовом модуле
означало бы четыре расходящиеся копии пайплайна.

значение из того же плана. Проверка падала бы на нём, ничего не проверив.

на быстрой фикстуре оба укладываются в одну секунду и дают одинаковый `generated_at`.
Первая версия теста на этом упала.

**2. `RunMeta.parse_error_files` добавлен сейчас, а не на T20.** План требует, чтобы
`validate` падал по списку файлов с ошибками разбора и без объявлений, а `stats` —
это `dict[str, int]`, куда список путей не положить. Поле заведено сразу: сидкар пишется
здесь, и возвращаться к `emit.py` на T20 ради одного поля незачем.

### Решения, которые стоит знать

**Оркестрация живёт в `emit.py`, а не в `cli.py`.** План говорил «создать `emit.py`,
изменить `cli.py`», не уточняя границу. Шестьдесят строк пайплайна в обработчике команды
означали бы, что сквозной прогон нельзя вызвать из теста без `CliRunner`.

**`_parse_one` — функция уровня модуля.** Иначе `ProcessPoolExecutor` не сможет её
сериализовать. Результаты после сбора **обязательно** пересортировываются по пути:
при `--jobs > 1` порядок завершения задач случаен, а от порядка `results` зависит
слияние `partial`-объявлений на T10.

**Золотой файл содержит версии грамматики**, поэтому апгрейд `tree-sitter` его ломает.
Это желаемое поведение: изменение вывода парсера должно быть видно в диффе, а не
проскакивать незамеченным.

## T17 — Тесты детерминизма ✅

**Создано:** `tests/test_determinism.py` — девять тестов.

**Проверка**

```
uv run pytest -q                    382 passed
uv run ruff check .                 All checks passed
uv run ruff format --check .        40 files already formatted
uv run mypy docpipe                 Success: no issues found in 17 source files
```

Требование из `purpose.md` стало проверяемым свойством. Сравнение везде побайтовое:
манифест не содержит недетерминированных полей, поэтому не нужно ни одного «сравнить,
игнорируя такие-то поля» — ради этого метаданные прогона и вынесены в сидкар.

### Отклонения от плана

**1. Монкипатчить нужно `discovery.os.walk`, а не `Path.rglob`.** `rglob` в `discovery`
нет: обход идёт через `os.walk`, потому что только так можно отсекать каталоги правкой
`dirnames` на месте (решение T04). Разворачивать при этом нужно **оба** списка —
и `dirnames`, и `filenames`: порядок каталогов влияет на порядок файлов.

**2. При подмене версии грамматики манифесты нельзя сравнивать целиком.** Версии лежат
в самом манифесте (поле `parser`), поэтому оно законно изменится. Сравниваются `modules`
и `nodes`; именно они и не должны поменяться от того, что кэш очистился.

### Что добавлено сверх плана

**Перенос репозитория** (две проверки). Две копии фикстуры в разных каталогах дают
побайтово равные манифесты, а кэш, наполненный из одной копии, годится для другой.
Это прямая проверка правила «пути только репо-относительные»: абсолютный путь ломал бы
документацию при любом различии в расположении рабочих копий у разработчика и в CI —
причём незаметно, потому что у автора-то всё сходится.

**Удаление файла.** Инкрементальный прогон после удаления обязан совпасть с полным:
кэш не должен воскрешать удалённый файл. За это отвечает `prune`, и до этого теста
он не был покрыт на уровне сквозного прогона.

**Все списки в манифесте отсортированы** — отдельный тест обходит модули и узлы
и проверяет каждое поле-список. Явная сортировка здесь не стиль, а условие
воспроизводимости, и проверять её точечно в каждой задаче ненадёжно.

**Обратимость JSON.** Манифест — контракт с шагом 2; запись и чтение обязаны быть
обратимы, иначе расхождение всплывёт у потребителя, а не здесь.

## Раздел о настройке в README (после T17)

По запросу владельца README дополнен разделом «Как этим пользоваться» и пошаговой
инструкцией «Настройка под конкретный проект». Каждая команда оттуда прогнана руками.

### Два бага, найденных при написании инструкции

**1. Аргументы primary constructor попадали в базовые типы.** Рецепт «посмотреть частые
базовые типы среди неклассифицированных» на semantic-kernel выдал `(output)` — 266 раз
и `(fixture)` — 159. Причина:

```csharp
public class MyTests(ITestOutputHelper output) : BaseTest(output), IDisposable
```

Тип с primary constructor передаёт аргументы базовому классу прямо в списке баз, и
`(output)` лежит там отдельным узлом `argument_list`. `_base_types` брал все
`named_children` и записывал его как базовый тип. Мусор расползался дальше по замыканию
наследования и попадал в `signature_hash`.

На четырёх репозиториях таких записей было **425**. Исправлено фильтром по типу узла;
после правки — ноль на всех четырёх.

Показательно, что баг нашёлся не тестом и не прогоном, а попыткой **воспользоваться**
собственным результатом: в таблице «частые базовые типы» строка `(output)` бросается
в глаза сразу, а в манифесте на 5 МБ её никто бы не заметил.

**2. Ошибки пользователя печатались traceback'ом.** Опечатка в `--rules` или несуществующий
`--root` роняли команду с трассировкой на полстраницы — ровно в тот момент, когда человек
первый раз пробует запустить всё руками. Заменено на сообщение и код возврата 2,
с тремя тестами.

### `tools/unclassified.py` — временный инструмент

Написан потому, что инструкция «смотрите на `unclassified` и добавляйте правила»
невыполнима: в манифест попадают только **классифицированные** типы, а для настройки
нужно ровно обратное. Счётчик в сидкаре говорит «7142», но не говорит, какие правила писать.

Скрипт печатает пять срезов по непокрытым типам: модули, окончания имён, базовые типы
с учётом замыкания, атрибуты, namespace. На ABP он сразу показывает
`ITransientDependency` (997 типов — больше, чем покрывает весь набор по умолчанию),
на semantic-kernel — что половина непокрытого это тесты и примеры, то есть вопрос
к `enrolled`, а не к правилам.

Требование внесено в план T20: `--stats` должен печатать эти же срезы, а скрипт при
реализации — удалить, а не оставлять рядом.

### Замечание про кэш

При проверке инструкции обнаружилось, что прогон на фикстуре создаёт
`tests/fixtures/SampleSolution/.docpipe/cache/`. Это ожидаемое поведение (`cache_dir`
относителен корню сканирования), и `.gitignore` его ловит, но для чужого дерева
поведение неочевидно. Описано в README вместе с `--no-cache`.

## Исключение тестов из дерева (по запросу владельца)

Требование: типы, чьё имя оканчивается на `Test`, в дерево документации попадать
не должны.

### Замер показал, что одного правила по имени мало

Прямолинейное `exclude.name_regex: ["^.*Tests?$"]` отсеивает **ноль** узлов на всех
четырёх проверочных репозиториях. Причина простая, но неочевидная: класс
`PricingServiceTests` не оканчивается ни на `Service`, ни на `Controller`, поэтому
и так не проходит ни одно правило классификации и узлом не становится.

Реальный шум идёт из другого места — вспомогательные типы **внутри** тестовых проектов
названы как продуктовые и классифицируются на общих основаниях:

```
AuditTestController                            -> controller
AuthorizationTestPermissionDefinitionProvider  -> provider
```

На ABP таких **104 узла из 828**. Отсекает их только `path_glob` по каталогам тестов.

### Что сделано

В `exclude` добавлено и то, и другое:

```yaml
path_glob: ["**/test/**", "**/tests/**", "**/*Test/**", "**/*Tests/**"]
name_regex: ["^.*Tests?$"]
```

Правило по имени оставлено, хотя сегодня оно ничего не ловит: оно фиксирует намерение
и сработает, когда в набор добавят более широкое правило — например, по атрибуту `[Fact]`
или по `type_kind`.

Эффект: ABP 828 → 694 узла, OpenTelemetry 10 → 7, semantic-kernel 69 → 67,
eShopOnWeb без изменений (его тестовые типы и так не классифицировались).

### Что проверено отдельно

**Форма `Tests` важнее формы `Test`**: в ABP 777 против 54, в semantic-kernel 829 против 17.
Правило `name_suffix: ["Test"]` не поймало бы `PricingServiceTests` вовсе —
`"PricingServiceTests".endswith("Test")` ложно. Поэтому регулярное выражение с `s?`.

**Ложных срабатываний по пути нет.** `**/*Tests/**` не цепляет `Contest/` и `Testing/` —
проверено и тестом, и на глобах напрямую.

**Три типа остались осознанно**: `AbpTestBaseWithServiceProvider`,
`BloggingTestAppBrandingProvider`, `ProcessTestController`. Все три лежат в `src/`
(это отгружаемая библиотека для тестов, демо-приложение и хост интеграционных тестов),
и ни один не оканчивается на `Test`. Поведение соответствует правилу.

### Замечание, которое стоит держать в голове для АС CF

В предметных областях, где «тест» — бизнес-понятие, правило по имени опасно.
Для финансового моделирования это не гипотеза: `StressTest` и `BackTest` — настоящие
сущности предметной области, а не юнит-тесты. Предупреждение вписано и в сам
`rules/dotnet.yaml`, и в README, и в план.

## T18 — Скоуп-режим ✅

**Создано:** `docpipe/merge.py`, `tests/test_scoped.py`; в `emit.scan` добавлены
параметры `scope` и `previous`, в CLI — флаги `--scope` и `--from-manifest`.


### Главный инвариант выполняется, в том числе на ABP

На фикстуре `scoped.nodes == full.nodes` для скоупа по каждому из двух модулей
и для обоих сразу. `PricingController` при скоупе по `Sample.Pricing.Api` сохраняет
`kind == "controller"` и полное замыкание `["ControllerBase", "Sample.Common.Web.BaseApiController"]`,
хотя модуль `Sample.Common` в этом прогоне не парсился вовсе.

Замер на ABP (671 проект, 7869 файлов):

| | |
|---|---|
| полный прогон | 10,2 с |
| скоуп по одному модулю | **2,1 с** |
| разобрано файлов | 301 |
| восстановлено из кэша | 7568 |
| узлов совпало с полным прогоном | 694 из 694 |

### Баг, найденный собственным тестом: удалённый тип воскресал

Первая реализация брала из кэша всё, «чего не нашли обходом». Файл, удалённый **внутри**
скоупа, обходом уже не находится, но в кэше ещё лежит — и восстанавливался как «файл вне
скоупа». Тип оставался в дереве после удаления.

Исправлено отбором по **принадлежности пути скоупу**, а не по списку найденных файлов.
Разница видна только на удалении, поэтому тест на него обязателен и внесён в план.

### Открытие, которое сделал второй упавший тест

Ожидалось, что при холодном кэше скоуп-прогон «потеряет часть данных»: у контроллера
оборвётся замыкание наследования. Реальность жёстче — **узел исчезает целиком**.

Правило `controller.aspnet` смотрит на `ControllerBase`, до которого два шага через
`Sample.Common`. Без кэша цепочка обрывается на `BaseApiController`, ни одно правило
не совпадает, новый узел не порождается, а старый выброшен при слиянии как «в скоупе».
Тип просто пропадает из документации.

Это меняет требование к команде: предупреждение о ненайденных в кэше файлах — не
удобство, а необходимое условие. Добавлено в stderr и в статистику сидкара
(`restored_from_cache`, `missing_from_cache`).

### Отклонения от плана

**1. Отбор файлов вне скоупа — по пути, а не по «остальным».** См. выше; формулировка
плана «для всех остальных файлов из кэша» допускала оба прочтения, и неверное давало
воскрешение удалённых типов. Формулировка исправлена.

**2. `cache.prune` в скоуп-режиме не вызывается.** План этого не оговаривал. `prune`
удаляет из кэша всё, чего нет в списке найденных файлов, — то есть в скоуп-режиме снёс бы
весь кэш вне скоупа, ровно то, ради чего он здесь и нужен. Следующий скоуп-прогон
работал бы уже вслепую.

**3. Модули вне скоупа берутся из `previous`.** План не описывал, как файл вне скоупа
привязывается к проекту: обход туда не заходит, `.csproj` не найден. Список путей
к проектам собирается объединением найденного и `previous.modules[*].csproj`.

### Решение, которое стоит знать

**Узел «в скоупе», если в скоупе хотя бы один его источник.** Половинки `partial class`
могут лежать по разные стороны границы; правило «все источники в скоупе» оставило бы
такой тип неперестроенным, а правило «любой» перестраивает его целиком. Проверено
на `PricingService`, у которого два файла.

### Проверка на реальном сценарии

Дифф проверялся не на искусственном изменении кода, а на том, ради чего он нужен:
**правке правил**. Настроенный набор для ABP (правило по `IAbpModule` и по

```
Всего изменений: 1790 (added: 1324, reclassified: 142, removed: 324)
```

828 узлов превратились в 1694. Ровно это и происходит при настройке под проект,
и по диффу видно, что именно изменилось: 1324 типа стали документироваться,
142 сменили вид, 324 ушли под новые правила исключения.

### Решения, которые стоит знать

**На узел приходится одно изменение, самое существенное.** Смена вида почти всегда
влечёт и смену `doc_path` — вид входит в путь. Сообщать «переехал» там, где тип сменил
природу, значит скрыть главное: шагу 3 нужно переписать документ, а не перенести файл.
Порядок проверок — `reclassified` → `moved` → `signature_changed`, есть тест
на узел, у которого изменилось всё сразу.

**Переименование — это `added` + `removed`, а не одно изменение.** Идентификатор узла
построен от FQN, и связать два имени между собой на этом уровне нечем. Если шагу 3
понадобится распознавать переименования, у него есть `signature_hash`: у переименованного
типа он тот же, что был у исчезнувшего.

**Код возврата всегда 0.** Команда предназначена для конвейера, где по её выводу решают,
что перегенерировать, а не для гейта в CI. Наличие изменений — не ошибка.

**Пустой результат печатается строкой «Изменений нет».** Пустой вывод неотличим от
«команда не отработала», и на глаз это не проверить.

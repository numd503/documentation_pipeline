# Команды `docpipe setup`: справочник

Команды для настройки `docpipe` на репозиторий с ассистентом. Обоснования —
в [`setup-implementation-plan.md`](setup-implementation-plan.md) (S01–S32),
ключи конфигурации — в [`configuration.md`](configuration.md). Здесь — что
команды делают, что печатают и как читать ответ. Справочник дополняет каждая
задача плана, которая добавляет команду или вид кандидатов.

## Общее для всех команд

- **Файлов настройки не пишут** (Р-1 плана). Значение в `docpipe.yaml`
  вносит агент своими средствами, ревью — `git diff`, решение — коммит
  человека. Команды пишут только кэш разбора (`cache_dir` под `--root`),
  как `scan`.
- **`--format text|json`**. Неизвестное значение — код 2 с перечнем
  допустимых. JSON — с фиксированным порядком ключей и полем
  `schema_version`; ключи латиницей, русские подписи — только в тексте.
- **Ответ — страница с продолжением**: `--limit` (по умолчанию 20, `0` —
  все) и `--offset`, в отчёте всегда `total` и `offset`. Агент контура
  обрезает длинный вывод, и без `total` «таких нет» неотличимо от «не
  показали». Текст кончается строкой «Показаны 1–20 из 45. Дальше:
  --offset 20.».
- **Коды возврата**: 0 — отчёт построен (в том числе пустой), 2 —
  неверный аргумент или вход не читается (конфигурация, файл правил).
- **Пути входов** (`rules` и прочие) разрешаются так же, как у `scan`:
  от текущего каталога, затем от каталога `--config`.

## `setup candidates KIND`

```bash
uv run docpipe setup candidates di-methods --root . --config docpipe.yaml
uv run docpipe setup candidates di-methods --root . --format json --limit 5
```

Кандидаты в ключ настройки — факты, из которых агент строит вопрос
человеку. Значение команда не предлагает: она считает, по чему его
выбирают. Виды:

| `KIND` | Ключ | Задача плана |
|---|---|---|
| `di-methods` | `di_methods` | S11 |

### `di-methods`

Методы `Add*`/`TryAdd*`, похожие на самодельную обёртку регистрации DI
(`AddSingletonAs<X>().As<I>()`). Без ключа `di_methods` такая обёртка даёт
ноль регистраций молча — на squidex 67 вместо 421.

Отбор: нестандартное имя (`AddScoped`, `AddSingleton`, `AddTransient`,
`AddHostedService` и их `Try…` известны и без настройки) и не меньше двух
вызовов с типом — тип-аргументом или `typeof`. Порядок —
`(-round(receiver_overlap, 2), -calls_with_types, method)`.

| Поле | Что значит |
|---|---|
| `method` | имя метода |
| `calls` | все вызовы, включая лямбда-форму без типа |
| `calls_with_types` | вызовы с типом-аргументом или `typeof` |
| `files` | в скольких файлах вызывается |
| `receivers` | три самых частых получателя: `[имя, вызовов]` |
| `receiver_overlap` | доля вызовов, у которых получатель тот же, на котором в этом репозитории зовут стандартные `Add*` |
| `declared_in` | файл объявления метода-расширения (`static`, `this ` в сигнатуре), если он в репозитории; иначе `null` |
| `configured` | уже перечислен в `di_methods` |
| `examples` | до трёх `файл:строка`, сначала вызовы с типом |

Над списком — база пересечения: `standard_calls` (число стандартных
регистраций) и `standard_receivers` (их три частых получателя).

Как читать:

- **Высокое пересечение и много вызовов с типом** — почти наверняка
  обёртка: её зовут на той же коллекции сервисов, что и `AddScoped`.
- **Нулевое пересечение** — метод другого объекта: `AddField` на `schema`,
  `AddDays` на дате (у последнего и типа нет, в список он не попадает).
- **Стандартных регистраций нет** (`standard_calls: 0`) — пересечение
  нулевое у всех и ничего не говорит; отчёт пишет это строкой, порядок
  задаёт только число вызовов с типом.
- **`declared_in: null` — не довод против.** Главная обёртка часто
  объявлена в пакете, а объявленные в репозитории
  `AddXxx(this IServiceCollection …)` нередко агрегаторы, а не обёртки.
- **`calls` больше `calls_with_types`** — часть вызовов записана лямбдой
  (`AddSingletonAs(_ => new X())`). Регистрацией такой вызов не станет
  и с ключом: это ограничение разбора регистраций, а не находки
  (`configuration.md`, `di_methods`).

Получатель — последний идентификатор выражения: `services`, `Services`
у `builder.Services`. Получатель-вызов пишется со скобками: у
`services.AddMvc().AddX()` это `AddMvc()`, потому что объект там —
результат вызова, а не коллекция сервисов. Форма, которую разбор
не называет (`items[0]`, `base`), — пустая строка, в тексте `—`.

# Страница как единица документации: план (P01–P16)

Шаг `web` (F01–F19) даёт дерево узлов «один класс — один документ». На боевом
модуле это 1500 документов, из которых человеку нужны десятки: экран, его
состояние, его логика, его вызовы к бэкенду. Этот план превращает **страницу**
в единицу документации и делает её состав управляемым.

Три требования, из которых он собран:

1. **автоматический обход страниц** — есть (F08 + повышение), но список вызовов
   у страницы завышен в разы, и это надо чинить первым;
2. **страницу можно добавить и снять руками** — иначе инструмент диктует состав
   документации, а решение принимает человек;
3. **документ страницы содержит подразделы** — состояние, логика, данные, —
   то есть поглощает то, что сегодня лежит отдельными файлами.

Предшественники: [`frontend-implementation-plan.md`](frontend-implementation-plan.md)
(шаг `web`), [`frontend-analysis.md`](frontend-analysis.md) (аналитика фронта),
[`findings-cashflow-frontend.md`](findings-cashflow-frontend.md) (разведка).

---

## Что показал боевой прогон

`docpipe web pages` на `Sbt.CMS.Cashflow.ML` (16.08.2026): **12 страниц**,
у всех внешние шаблоны, ни одной записи с невосстановленным маршрутом.

```
/                                    RoutesComponent          layout, помечен отчётом
/models/list                         ViewComponent            4 члена, 0 зависимостей, 0 вызовов
/forecast/{}                         ForecastComponent        45 членов, 13 зависимостей, 51 вызов
├── …/conclusion/view                AutoconclusionsPageComponent
├── …/forecasts                      NewForecastPageComponent
├── …/models                         ForecastModelsComponent
│   ├── …/models/loader              LoaderComponent          214 членов
│   └── …/loader/quiz                QuizPageComponent
├── …/questionnaires/list            ListComponent
└── …/structuring                    StructuringPage          2 члена, 0 вызовов, 3 дочерние
    ├── …/create и …/edit            StructuringCreatePage    один компонент на двух маршрутах
    └── …/view                       StructuringViewPage
```

**Цифра, из-за которой этот план начинается не с агрегата.** 61 уникальный
эндпоинт на 12 страниц, и **43 из них видны ровно у четырёх страниц каждый**:

```
25 эндпоинтов видны ровно у: ForecastComponent, ListComponent, LoaderComponent, StructuringCreatePage
17 эндпоинтов видны ровно у: ForecastComponent, RoutesComponent, StructuringCreatePage, StructuringViewPage
```

Такого совпадения интересов не бывает. Это гранулярность обхода: страница
внедряет `StructuringService`, и в её список попадают **все** методы сервиса,
а не те два, которые она зовёт. Обход отвечает на вопрос «до чего страница
дотягивается», а документу нужен ответ на «что она вызывает». Пока разница
не устранена, любой агрегат будет собран вокруг неверного списка.

---

## Решения, из которых следует всё остальное

**Страница — это маршрут, а не класс.** Уже действующее правило (F08, F15):
якорь бизнес-документа пишется на `/forecast/{}/structuring/view`, а не на
`StructuringViewPage`. Отсюда ключ ручного правила, ключ агрегата и ключ
переезда — маршрут.

**Вызов принадлежит странице, если страница его делает, а не если может.**
Принадлежность считается по цепочке вызовов методов (`this.service.byId(…)`,
`dispatch(new X())` → `@Action(X)` → `this.service.…`), а не по внедрению
в конструктор. Это ровно то различие, которое даёт 51 против ожидаемых 5–7.

**Узел поглощается страницей, только если достижим единственной страницей.**
`StructuringCreateService`, до которого не дотягивается никто, кроме
`/forecast/{}/structuring/create`, — раздел документа страницы.
`ItemsService`, до которого дотягиваются восемь страниц, — самостоятельный
документ, на который страницы ссылаются. Порога здесь нет и быть не может:
«общий» — это «второй потребитель появился», а не «потребителей больше N».

**У поглощения обязано быть своё состояние решения.** Поглощённый узел —
это «документируем внутри страницы», а не `undecided` и не «не документируем».
Прецедент — `interface_covered` (`stats.py`): решение инструмента, названное
отдельно, чтобы не засорять главный сигнал настройки.

**Ручное правило без причины запрещено, а не сработавшее — находка.**
Обе половины обязательны. Первая — то же правило, что у `exclude` в наборе
правил: «не документируем 4820» без причины бессмысленно. Вторая важнее:
файл ручных правил гниёт молча. Компонент переименовали — правило перестало
совпадать, страница тихо исчезла из документации, и никакой отчёт об этом
не сказал.

**Хэш агрегата включает хэши поглощённых узлов.** Иначе правка сервиса, целиком
живущего внутри страницы, не помечает документ страницы устаревшим — и агент
шага 3 не переписывает раздел, который стал ложью.

## P01 — вызов → член сервиса

**Цель:** знать, в каком методе сервиса записан каждый HTTP-вызов.

**Изменить:** `docpipe/model.py`, `docpipe/web/tree.py`, `docs/web.md`
**Создать:** `tests/test_web_call_member.py`

**Спецификация**

У `WebCall` уже есть `file` и `line`; у `Symbol.members` — `line` и `end_line`.
Значит атрибуция считается **без единой строки нового разбора**: вызов
принадлежит члену, чей диапазон его накрывает.

Новое поле `WebCall.member: str` — имя члена. Пустая строка означает «вызов
записан вне члена» (в теле фабрики, в поле модуля), и это состояние, а не
неизвестность.

> **Ловушка. Вложенные диапазоны.** Стрелка в поле класса
> (`load = () => this.http.get(…)`) — тоже член со своим диапазоном, и он
> вложен в… ничего, а вот метод, содержащий локальную функцию с вызовом,
> накрывает его целиком. Побеждает **самый узкий** накрывающий диапазон;
> перебор в порядке объявления даст первый попавшийся.

> **Ловушка. Диапазон члена может быть однострочным** (`line == end_line`),
> и сравнение обязано быть нестрогим с обеих сторон. Проверено на фикстуре:
> у `type` в классе экшена `line: 4, end_line: 4`.

**Критерии приёмки**
- у каждого вызова `AuditService` проставлен метод, в котором он записан;
- вызов внутри локальной функции внутри метода отнесён к методу, а не к файлу;
- вызов вне членов даёт `member: ""`, а не имя ближайшего члена;
- манифест остаётся детерминированным (двойной прогон, `cmp`).

**Проверка**
```bash
uv run pytest tests/test_web_call_member.py -q
uv run docpipe web scan --root tests/fixtures/WebWorkspace --out /tmp/web.json
```

## P02 — компонент → методы внедрённых зависимостей

**Цель:** знать не «страница внедряет `ModelService`», а «страница зовёт
`ModelService.byId` и `ModelService.save`».

**Создать:** `docpipe/web/usage.py`, `tests/test_web_usage.py`
**Изменить:** `docpipe/model.py`, `docpipe/web/tree.py`, `docpipe/web/queries/`

**Спецификация**

Новый факт `MemberUsage(receiver, method, line, member)`: `this.models.byId(id)`
даёт получателя `models`, метод `byId` и член, из которого зван. Получатель
резолвится по параметрам конструктора (`private models: ModelService`) в FQN
через тот же индекс, что и `_dependencies`.

В узел кладётся `uses: list[Usage]` — `target` (FQN узла), `member` (метод
цели), `via` (член источника). Это ребро графа вызовов; на нём стоит всё
дальнейшее.

> **Ловушка. Получатель — не всегда `this`.** Локальная переменная
> (`const s = this.models; s.byId(…)`), деструктуризация, `inject(ModelService)`
> в поле. Разрешать надо **только** то, что резолвится однозначно; остальное
> идёт в `unresolved` и печатается числом. Догадка здесь стоит дороже пропуска:
> ложное ребро втянет в страницу чужой сервис и породит неверный раздел
> документа.

> **Ловушка. Вызовы из шаблона не видны.** `(click)="save()"` вызывает метод
> компонента, а `*ngIf="service.ready$ | async"` — обращается к сервису прямо
> из `.html`. Грамматика Angular-шаблонов в этот план не входит (см. конец),
> поэтому ограничение обязано быть **названо в отчёте**, а не обнаружено потом
> по расхождению цифр.

> **Ловушка. Цепочки и опциональный доступ.** `this.a.b().c()` и `this.a?.b()`
> — одно ребро `a.b`, а не два и не ноль. Проверяется тестом на обеих формах.

**Критерии приёмки**
- у `DetailComponent` фикстуры ребро `ModelService.byId`, и только оно;
- `Map.get`, `FormGroup.get`, `headers.get` рёбер не дают (те же приманки,
  на которых считался счётчик вызовов в F07);
- нерезолвящийся получатель попадает в счётчик, а не в рёбра;
- число рёбер на фикстуре зафиксировано в тесте.

**Проверка**
```bash
uv run pytest tests/test_web_usage.py -q
```

## P03 — цепочка NGXS

**Цель:** соединить страницу с её состоянием — и через него с сервисами,
которые сегодня не видны вовсе.

**Создать:** `docpipe/web/store.py`, `tests/test_web_store.py`
**Изменить:** `docpipe/web/tree.py`, `docpipe/model.py`

**Спецификация**

Названный пробел F14: цепочка «компонент диспатчит → стейт обрабатывает →
сервис зовёт» не собирается ничем, и поле `WebCall.via_action`, заведённое
в F10, остаётся пустым на каждом прогоне.

Хорошая новость, проверенная на фикстуре: **звено уже лежит в манифесте**.
У члена `DebtState.load` записан атрибут `Action` с позиционным аргументом
`LoadInnerDebts`. Значит связывание идёт по имени класса экшена, резолвя его
через таблицу импортов файла стейта, — надёжнее, чем по строке `type`, которую
разбор полей не берёт вовсе.

Собираются три ребра:

| Форма в коде | Ребро |
|---|---|
| `this.store.dispatch(new LoadInnerDebts(id))` | страница → экшен |
| `@Action(LoadInnerDebts) load(…)` | экшен → стейт (член стейта) |
| `@Select(DebtState.items)`, `store.select(DebtState.items)`, `selectSnapshot` | страница → селектор стейта |

Дальше работает P02: `DebtState.load` зовёт `InnerDebtService.byClient`, и вызов
внутри этого метода известен из P01.

> **Найдено при реализации: тип экшена живёт на ребре, а не на вызове.**
> План требовал заполнить `WebCall.via_action` у вызова `InnerDebtService.byClient`.
> Так делать нельзя: этот вызов записан в сервисе, и тот же метод зовут
> и обработчик экшена, и компонент напрямую. Пометив вызов, инструмент
> утверждал бы, что до него **всегда** доходят через стор. Поэтому тип экшена
> несёт ребро (`Usage.action`), а `WebCall.via_action` остаётся за вызовом,
> записанным **внутри** обработчика, — форма редкая, но настоящая.

> **Ловушка. Один экшен обрабатывают несколько стейтов.** В NGXS это законно
> и встречается: `@Action(LoadInnerDebts)` может стоять в двух стейтах.
> Ребро — список, а не одно значение; реализация «первый попавшийся»
> потеряет половину состояния страницы молча.

> **Ловушка. `dispatch` принимает массив.** `dispatch([new A(), new B()])`
> и `dispatch(new A())` — одна форма для разбора, два ребра. Разбор,
> берущий первый аргумент как объект, на массиве даст ноль.

> **Ловушка. Экшен без обработчика — состояние, а не ошибка.** Экшен, который
> диспатчат, а обрабатывает только `@@Init`-подписка или эффект вне стейта,
> обработчика не имеет. Такое ребро обрывается, и это печатается числом.

**Критерии приёмки**
- `ListComponent` фикстуры связан с `DebtState` через `LoadInnerDebts`;
- ребро диспатча несёт строку типа экшена (`[Inner Debt] Load`), а вызов,
  записанный внутри обработчика, — `via_action`;
- `dispatch` с массивом даёт два ребра;
- экшен, обработанный двумя стейтами, даёт два ребра;
- число оборванных цепочек — именованный счётчик прогона.

**Проверка**
```bash
uv run pytest tests/test_web_store.py -q
uv run docpipe web scan --root tests/fixtures/WebWorkspace --stats
```

## P04 — точный список эндпоинтов страницы

**Цель:** заменить достижимость вызовами и **измерить разницу**.

**Изменить:** `docpipe/web/pages.py`, `docpipe/cli.py`, `tests/test_web_pages.py`

**Спецификация**

Граф: страница → (P02) методы сервисов → (P01) вызовы в этих методах;
плюс страница → (P03) экшен → член стейта → снова P02/P01. Эндпоинт попадает
в список страницы, только если до него есть путь **по вызовам**.

Старая величина не выбрасывается, а становится второй колонкой отчёта:

```
/forecast/{}   ForecastComponent
  вызывает         7 эндпоинтов
  дотягивается до  51   ← внедрено 13 сервисов; разница не дефект, а мера того,
                          сколько чужого приезжало в документ до P01–P03
```

`--depth` остаётся для достижимости и получает предупреждение в справке: это
инвентарь, а не состав страницы.

> **Ловушка. Ноль вызовов после P04 значит другое, чем до него.** До — «обход
> не видит цепочку». После — «страница действительно не ходит за данными сама»
> (её данные приходят через `@Input` от родителя или из платформенного грида).
> Заметка обязана смениться, иначе она будет объяснять несуществующую причину.

**Критерии приёмки**
- на фикстуре у страницы, зовущей один метод сервиса с пятью эндпоинтами,
  в списке один эндпоинт;
- обе величины печатаются рядом и обе названы;
- на боевом модуле разница зафиксирована в журнале числом (ожидание:
  `ForecastComponent` 51 → единицы);
- `/models/list` (`ViewComponent`, ноль зависимостей) разобран отдельно
  и объяснён: платформенный грид или `@Input` от родителя.

**Проверка**
```bash
uv run pytest tests/test_web_pages.py -q
uv run docpipe web pages artifacts/doc-tree.web.json --depth 2
```

## P05 — доработки отчёта

**Цель:** закрыть три мелочи, найденные на боевом прогоне.

**Изменить:** `docpipe/web/pages.py`, `docpipe/cli.py`, `tests/test_web_pages.py`

**Спецификация**

1. **Колонка «дочерних страниц»** — факт, а не эвристика: у страницы считается,
   сколько других страниц имеет её маршрут строгим префиксом сегментов.
   `StructuringPage` (2 члена, 0 вызовов, 3 дочерние) — контейнер;
   `ForecastComponent` (7 дочерних, 45 членов, свои вызовы) — экран с детьми,
   и никакая эвристика по числу членов их не разделила бы.
2. **CSV теряет глубину и посредника** у вызова — колонки добавляются;
   человек размечает страницы по этому файлу, и «через кого» ему нужнее всего.
3. **`SetApiUrl` в зависимостях шести страниц** — разобрать и назвать причину.
   Гипотеза: это декоратор-функция, попавшая в узлы и оттуда в разбор
   параметров конструктора. Лечится либо правилом отсева, либо `_parameter_types`
   — выбор делается **после** воспроизведения, а не до.

**Критерии приёмки**
- у контейнера в отчёте видно число дочерних страниц; у листа — ноль;
- сегментное сравнение: `/forecast/{}` не считается префиксом `/forecaster`;
- CSV содержит глубину и посредника;
- причина `SetApiUrl` названа в журнале, поведение изменено осознанно.

**Проверка**
```bash
uv run pytest tests/test_web_pages.py -q
uv run docpipe web pages artifacts/doc-tree.web.json --format csv
```

## P06 — `pages.yaml`: ручное добавление и снятие

**Цель:** состав страниц — решение человека, а не только вывод инструмента.

**Создать:** `docpipe/web/overrides.py`, `pages.example.yaml`,
`tests/test_web_overrides.py`
**Изменить:** `docpipe/config.py`, `docpipe/web/tree.py`, `docpipe/cli.py`

**Спецификация**

```yaml
version: "1"
pages:
  add:
    - route: "/forecast/{}/structuring/print"
      component: "src/app/structuring/print/print.component.PrintPage"
      reason: "Экран открывается из окна печати, маршрут задаётся в рантайме"
    - route: "/models/list"
      component: "src/app/models/view/view.component.ViewComponent"
      reason: "Страница платформы: маршрут в таблице роутов не объявлен"
  remove:
    - route: "/"
      reason: "Layout с router-outlet, собственного экрана нет"
    - component: "src/app/legacy/legacy.module.LegacyBannerComponent"
      reason: "Баннер, вставляется в шапку; экраном не является"
```

**Ручная страница — это запись маршрута из другого источника**, а не второй
механизм. Добавление порождает синтетическую `RouteEntry` с
`source: "pages.yaml"`, `table: "manual"`, и дальше работает всё существующее:
повышение вида, якорь бизнес-слоя, отчёт, покрытие. Отдельная ветка кода
для «ручных» страниц разошлась бы с автоматической на первом же различии.

Снятие не удаляет узел, а отменяет повышение: класс остаётся `component`
и попадает в `--not-pages` с ручной причиной. Документ у него остаётся —
компонент документируется как компонент.

Порядок применения фиксирован: автоматика → добавления → снятия. Снятие
сильнее добавления, потому что это последнее слово человека.

> **Ловушка. Правило, которое ни на что не легло, обязано быть находкой.**
> Компонент переименовали — правило `add` перестало совпадать, и страница
> тихо исчезла из документации: ни ошибки, ни предупреждения, а в отчёте
> просто на одну строку меньше. Каждое неприменившееся правило печатается
> и считается; `--fail-on-stale-overrides` включает отказ для CI. То же
> касается `add` на маршрут, который инструмент теперь находит сам, — правило
> стало лишним, и об этом надо сказать.

> **Ловушка. Ключ снятия — маршрут ИЛИ компонент, и оба обязаны быть
> однозначны.** У layout маршрут пустой (`/`), и он один; у компонента,
> стоящего на двух маршрутах (`StructuringCreatePage` — `create` и `edit`),
> снятие по маршруту снимет одну страницу из двух. Неоднозначное правило —
> отказ на загрузке, а не выбор наугад.

> **Ловушка. `component` в правиле — это FQN, зависящий от пути файла.**
> Он ломается при переносе файла, и это осознанная цена: другого стабильного
> способа указать на класс у инструмента нет. Именно поэтому неприменившееся
> правило обязано быть громким — оно будет случаться.

**Критерии приёмки**
- добавленная руками страница неотличима от найденной автоматически везде,
  кроме `source: pages.yaml` в обосновании;
- снятая страница остаётся узлом `component` и печатается в `--not-pages`
  с ручной причиной;
- правило без `reason` отвергается на загрузке;
- неприменившееся правило печатается всегда и роняет прогон только
  с `--fail-on-stale-overrides`;
- неоднозначное снятие — отказ с перечислением того, что подошло;
- порядок правил в файле на результат не влияет (тест переворачивает списки).

**Проверка**
```bash
uv run pytest tests/test_web_overrides.py -q
uv run docpipe web scan --root . --pages pages.yaml --out artifacts/doc-tree.web.json
uv run docpipe web pages artifacts/doc-tree.web.json --not-pages
```

## P07 — принадлежность узла странице

**Цель:** решить, что живёт внутри документа страницы, а что остаётся
самостоятельным документом.

**Создать:** `docpipe/web/ownership_graph.py`, `tests/test_web_absorption.py`
**Изменить:** `docpipe/model.py`, `docpipe/web/tree.py`

**Спецификация**

По графу вызовов (P04) для каждого узла считается множество страниц, которые
до него дотягиваются. Ровно одна — узел **поглощается** этой страницей
(`absorbed_by: <id страницы>`). Две и больше, или ноль — узел остаётся
самостоятельным документом.

Данные боевого модуля объясняют, почему правило такое: 43 эндпоинта из 61
достижимы ровно с четырёх страниц. Попытка «приписать сервис главной странице»
продублировала бы `ItemsService` восемь раз, и восемь копий разошлись бы
на первой же правке.

> **Ловушка. Поглощение меняется от появления второй страницы.** Завели второй
> экран, зовущий `StructuringCreateService`, — сервис перестал быть
> эксклюзивным и переехал из раздела в собственный документ. Это законно
> и обязано быть **видно в отчёте переезда** (P10), иначе первый же такой
> случай выглядит как пропажа текста.

> **Ловушка. Циклы.** `A` зовёт `B`, `B` зовёт `A`; страница дотягивается
> до обоих. Обход обязан быть по посещённым, иначе прогон не завершится.

> **Ловушка. Стейт эксклюзивен реже, чем кажется.** Стейт NGXS — глобальный
> синглтон, и до одного стейта дотягиваются все страницы, которые его селектят.
> Поглощаться будут в основном сервисы и утилиты одной страницы; стейты
> останутся общими и попадут в раздел ссылкой. Это не дефект правила — это
> устройство NGXS, и документ обязан отражать его, а не притворяться.

**Критерии приёмки**
- сервис, который зовёт одна страница, помечен `absorbed_by`;
- сервис, который зовут две страницы, не помечен ни одной;
- узел, до которого не дотягивается ни одна страница, остаётся самостоятельным;
- цикл не вешает прогон;
- результат детерминирован при перестановке узлов манифеста.

**Проверка**
```bash
uv run pytest tests/test_web_absorption.py -q
```

## P09 — агрегатный документ

**Цель:** документ страницы с подразделами, в которых лежит состояние
и логика.

**Изменить:** `templates/page.md`, `docpipe/materialize/build.py`,
`docpipe/materialize/plan.py`, `docs/materialize.md`
**Создать:** `tests/test_materialize_page_aggregate.py`

**Спецификация**

Разделы шаблона страницы:

| Раздел | Что в нём | Кто пишет |
|---|---|---|
| Зачем эта страница | назначение экрана | агент |
| Что на экране | блоки интерфейса | агент |
| **Состояние** | стейты, селекторы, экшены страницы | генерируемый блок + агент |
| **Логика** | методы страницы и поглощённых сервисов | генерируемый блок + агент |
| **Данные** | эндпоинты с методом сервиса, через который зовутся | генерируемый блок |
| Что можно сделать | действия пользователя | агент |
| **Состав** | поглощённые узлы; общие сервисы — ссылками | генерируемый блок |
| **Дочерние страницы** | ссылки на документы дочерних маршрутов | генерируемый блок |

Генерируемый блок и зоны работают как раньше: инвариант
`assemble(parse_document(t)) == t` остаётся, разделы агента не затираются
никогда.

> **Ловушка. Хэш агрегата.** `impl_hash` страницы обязан включать `impl_hash`
> поглощённых узлов, иначе правка сервиса, живущего внутри страницы,
> не пометит документ устаревшим, и раздел «Логика» останется ложью.
> `signature_hash` включает **состав** поглощённого: узел ушёл или пришёл —
> документ устарел, даже если код остальных не менялся.

> **Ловушка. Раздел «Состав» — не список всего, до чего дотянулись.** Общие
> сервисы идут ссылками на их документы, а не текстом: копия разойдётся
> с оригиналом на первой правке. Это то же правило, по которому бизнес-слой
> ссылается на технический, а не пересказывает его.

**Критерии приёмки**
- документ страницы содержит все восемь разделов, пустые — с подсказками
  в HTML-комментариях (иначе `is_section_empty` сочтёт их написанными);
- правка поглощённого сервиса делает документ страницы `stale`;
- правка общего сервиса делает `stale` его собственный документ, а не страницу;
- приёмка (`docs accept`) фиксирует оба хэша и не открывает файл на запись
  при «без изменений».

**Проверка**
```bash
uv run pytest tests/test_materialize_page_aggregate.py -q
uv run docpipe materialize artifacts/doc-tree.web.json --root .
uv run docpipe docs status artifacts/doc-tree.web.json --root .
```

## P13 — вторая ветка дерева документации

**Цель:** документы фронта лежат отдельной веткой, а не вперемешку с бэкендом.

**Изменить:** `docpipe/config.py`, `docpipe/web/tree.py`,
`docpipe/materialize/plan.py`, `docpipe/cli.py`, `docpipe.example.yaml`,
поставка, `docs/{configuration,pages,web,materialize}.md`
**Создать:** `tests/test_web_docs_tree.py`

**Спецификация**

Новый ключ `web.modules_dir` — каталог **внутри** `docs_root`, рядом
с `modules_dir`:

```
docs/modules/...   бэкенд, единица документации — класс
docs/front/...     фронт,  единица документации — страница
```

Пустое значение (умолчание) значит «та же ветка, что у бэкенда»: конфигурации,
написанные до появления ключа, обязаны давать те же пути.

> **Ловушка. Ветка — каталог внутри `docs_root`, а не путь целиком.** Ровно
> тот же довод, что и у `modules_dir`: обход документов идёт от `docs_root`
> и накрывает обе ветки разом, поэтому инвариант «`materialize` пишет туда,
> где ищет `docs status`» держится структурно. Отдельным путём его можно
> развести, и тогда каждый документ фронта навсегда `missing`.

> **Ловушка. Сверка префикса знает только один корень.** `layout_drift`
> сравнивает пути манифеста с `docs_root + modules_dir`; манифест фронта,
> собранный со второй веткой, не прошёл бы её никогда — прогон падал бы
> на каждом запуске. Префикс выбирается по манифесту (`expected_root`),
> и по нему же выбирается **имя ключа в сообщении**: отправлять чинить
> `modules_dir` там, где человек правил `web.modules_dir`, — это отказ,
> который дороже отсутствия отказа.

> **Ловушка. Очередь шага 3 несёт префикс отдельным полем.** Взятый
> из `modules_root`, он сообщил бы внешнему исполнителю путь, которого нет
> ни у одного документа очереди.

**Критерии приёмки**
- при `web.modules_dir: "front"` все узлы фронта под `docs/front/`,
  узлы бэкенда — под `docs/modules/` при той же конфигурации;
- пустое значение даёт прежние пути (проверяется отдельно);
- `docs status` находит документы во второй ветке: `missing` нет;
- манифест, собранный с одной раскладкой, роняет прогон с другой, и сообщение
  называет тот ключ, который правил человек;
- `worklist` кладёт в очередь префикс фронта;
- `web.modules_dir` обязан быть репо-относительным.

**Проверка**
```bash

uv run docpipe web scan --root . --config docpipe.yaml --out artifacts/doc-tree.web.json
uv run docpipe materialize artifacts/doc-tree.web.json --root .
```

## P16 — раздел: единица документации без маршрута

**Цель:** `inner-debt`, `leasing`, `invest-portfolio` документируются как одна
вещь, а не двумя десятками отдельных файлов каждый.

**Спецификация**

Раздел — функциональность, которую открывают из меню с нескольких экранов
и у которой нет своего URL. Ни страницей, ни поглощённым узлом он быть
не может: якорь страницы — маршрут, а по графу вызовов раздел «общий».

Поэтому раздел **объявляется человеком** в `pages.yaml` (`features:`),
границей служит каталог, а узел раздела синтетический — без символа.

> **Ловушка. Граница — сегмент пути, а не подстрока.** `…/leasing` иначе
> накрывает `…/leasing-report`, и чужие узлы уезжают в чужой документ.

> **Ловушка. Раздел «зовёт своих».** Вызовы сервиса, к которому внутри
> раздела никто не обращается (его зовут снаружи), пропали бы из раздела
> «Данные» — при том, что своего документа у сервиса больше нет. Узлу раздела
> дописываются синтетические рёбра на собственные члены с вызовами. Копировать
> сами вызовы нельзя: тот же вызов пришёл бы в отчёт дважды.

> **Ловушка. Состав документа — не то же, что участники обхода.** Внутри
> агрегата живут узлы, которых никто не зовёт: экшены, модели, DTO. Список
> «что описано в этом документе» строится по `absorbed_by`, иначе документ
> молча не упомянет половину того, что в него уехало.

**Критерии приёмки**
- всё под каталогом раздела уходит в его документ, включая экшены и DTO;
- объявленное сильнее выведенного: узел, который поглощала страница, уходит
  в раздел;
- страница внутри каталога остаётся страницей;
- пустой раздел — находка `feature-empty`;
- якорь `feature: inner-debt` разрешается, факты несут стейты и эндпоинты,
  имён классов в них нет;
- покрытие разделов считается линтом и кода возврата не меняет;
- в документе есть «Откуда открывается» со ссылками на страницы.

**Проверка**
```bash
uv run pytest tests/test_web_features.py -q
uv run docpipe web scan --root . --pages pages.yaml --out artifacts/doc-tree.web.json
uv run docpipe web pages artifacts/doc-tree.web.json
```

| разбор `.html` как языка | отдельная грамматика Angular-шаблонов; вызовы из шаблона останутся невидимыми, и это ограничение называется в отчёте (P02) |

| транзитивное поглощение через общий сервис | сервис, общий для двух страниц, не тянет за собой свои эксклюзивные утилиты в обе; они остаются при нём |
| автоматическое удаление осиротевших документов | инструмент документы не удаляет; он их называет (P10) |
| эвристика «это layout, выкинуть» | решение принимает человек через `pages.yaml` (P06); угаданная не-страница молча выкидывает экран из документации |
| наполнение разделов текстом | это шаг 3; здесь готовится структура и генерируемый блок |

## Фикстуры

Все новые случаи идут в `tests/fixtures/WebWorkspace`, не в `SampleSolution`:
числа в критериях приёмки T04–T20 завязаны на неё.

Что нужно дописать в `WebWorkspace`:

| Случай | Для задачи |
|---|---|
| сервис с двумя методами, у каждого свой вызов | P01, P02 |
| `dispatch` с массивом экшенов | P03 |
| один экшен, обработанный двумя стейтами | P03 |
| сервис, который зовут две страницы (общий) | P07 |
| сервис, который зовёт одна страница (поглощаемый) | P07 |
| страница-контейнер с дочерними маршрутами | P05 |
| компонент, снятый со страниц через `pages.yaml` | P06 |

Инвариант фикстур сохраняется: тест проверяет наличие **конструкций**,
а не только файлов, иначе «упрощение» фикстуры оставит тесты зелёными
и бессмысленными.

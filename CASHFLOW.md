# Настройка docpipe на репозитории АС CF

Рабочий документ: что проверить и что решить, прежде чем запускать `docpipe` на боевом
репозитории. Всё здесь — следствие прогонов на четырёх открытых .NET-проектах
(eShopOnWeb, ABP, OpenTelemetry, semantic-kernel), см. [`docs/findings-stress.md`](docs/findings-stress.md).

Общая инструкция по настройке — в [`README.md`](README.md), раздел «Настройка под
конкретный проект». Здесь только то, что специфично для АС CF или требует решения
человеком.

---

## 1. Диагностика: восемь команд перед первым запуском

Выполнить в корне репозитория АС CF. Каждая отвечает на вопрос, от которого зависит
настройка. Ответы стоит выписать — они понадобятся на шаге 3.

```bash
CF=/путь/к/репозиторию/АС-CF

# 1. Масштаб: сколько кода и проектов
find $CF -name '*.cs' -not -path '*/obj/*' -not -path '*/bin/*' | wc -l
find $CF -name '*.csproj' | wc -l

# 2. Формат решений: .sln, .slnx или оба
find $CF -name '*.sln' | wc -l
find $CF -name '*.slnx' | wc -l

# 3. Дубли имён проектов
find $CF -name '*.csproj' -printf '%f\n' | sort | uniq -d

# 4. Связанные исходники: общий код, подключённый ссылкой на файл
grep -rl "Compile Include" --include=*.csproj $CF | wc -l

# 5. Подстановки MSBuild в целевых платформах
grep -rho 'TargetFrameworks\?>[^<]*' --include=*.csproj $CF | grep -c '\$('

# 6. Плотность условной компиляции
grep -rl "^#if" --include=*.cs $CF | wc -l

# 7. Маркерные интерфейсы: регистрация в DI наследованием, а не вызовом
grep -rho ': *I[A-Za-z]*Dependency' --include=*.cs $CF | sort | uniq -c | sort -rn | head

# 8. Типы, чьё имя оканчивается на Test, но которые могут быть предметными
grep -rho 'class [A-Za-z]*Tests\?\b' --include=*.cs $CF | sort -u | head -30
```

### Что означают ответы

| № | Ответ | Что делать |
|---|---|---|
| 1 | больше ~5000 файлов | ставить `--jobs 4`; ориентир по времени — ниже, в §6 |
| 2 | есть `.slnx` | ничего, поддерживаются оба формата |
| 3 | список непуст | ничего, идентификаторы строятся от путей. Но `doc_path` использует **имя** модуля — проверить §5 |
| 4 | больше нуля | **часть типов не попадёт в документацию**, см. §4.1 |
| 5 | больше нуля | `target_frameworks` будут пусты у части модулей, см. §4.2 |
| 6 | заметная доля от общего числа | будут потери типов при разборе, см. §4.3 |
| 7 | список непуст | **обязательно** добавить правило по базовому типу, см. §3.3 |
| 8 | есть `StressTest`, `BackTest` и подобное | **сузить правило исключения тестов**, см. §2 |

## 2. Первое решение: тесты и предметные «тесты»

В наборе по умолчанию тесты отсекаются двумя правилами:

```yaml
name_regex: ["^.*Tests?$"]
path_glob:  ["**/test/**", "**/tests/**", "**/*Test/**", "**/*Tests/**"]
```

**Для финансового моделирования правило по имени опасно.** `StressTest`, `BackTest`,
`ScenarioTest` — это могут быть настоящие сущности предметной области, а не юнит-тесты.
Команда №8 из диагностики покажет, есть ли такие.

Если есть — убрать `^.*Tests?$` и положиться на путь:

```yaml
name_regex:
  # - "^.*Tests?$"        # убрано: StressTest и BackTest — предметные сущности
path_glob:
  - "**/*.Tests/**"       # только каталоги тестовых проектов
  - "**/test/**"
```

Проверить результат: в манифесте не должно остаться типов из тестовых проектов,
но `StressTest` остаться должен.

```bash
jq -r '.nodes[] | select(.title | test("Test")) | "\(.title)\t\(.symbol.sources[0].path)"' \
  artifacts/doc-tree.json
```

**Важно понимать разницу.** Исключённый тип всё равно **разбирается**: его символ нужен
графу наследования. Если продуктовый класс наследуется от базового класса, лежащего
в тестовом проекте (так бывает), цепочка не порвётся.

## 3. Правила классификации: что описать для АС CF

### 3.1 Четыре шаблона из постановки

В [`purpose.md`](purpose.md) названы Service, Provider, Workflow, Controller. Первые
правила для них уже есть в `rules/dotnet.yaml` и работают по конвенции имён
(`*Service`, `*Provider`, `*Workflow`) и по наследованию (`ControllerBase`).

Проверить на реальном коде, что конвенция соблюдается:

```bash
uv run python tools/unclassified.py $CF
```

Раздел «Окончания имён» покажет, какие суффиксы в АС CF реально используются. Если
вместо `*Service` там `*Handler` или `*Processor` — правила нужно переписать под них,
а не наоборот.

### 3.2 Ignite / GridGain: главная особенность АС CF

В наборе по умолчанию есть два правила, написанных «вслепую» по Apache Ignite .NET:

```yaml
- id: ignite.service
  when: { all: [ { type_kind: ["class", "record"] },
                 { inherits: ["IService", "Apache.Ignite.Core.Services.IService"] } ] }

- id: ignite.compute
  when: { all: [ { type_kind: ["class", "record"] },
                 { inherits: ["IComputeFunc", "IComputeJob", "IComputeTask"] } ] }
```

**Их нужно проверить на настоящем коде.** GridGain — коммерческая сборка на базе
Apache Ignite, и namespace-ы могут отличаться. Что выяснить:

```bash
# какие Ignite-интерфейсы реально реализуются
grep -rhoE ': *I(Service|ComputeFunc|ComputeJob|ComputeTask|CacheEntryProcessor)[<,) ]' \
  --include=*.cs $CF | sort | uniq -c | sort -rn

# как называются пакеты
grep -rho 'PackageReference Include="[^"]*Ignite[^"]*"' --include=*.csproj $CF | sort -u
grep -rho 'PackageReference Include="[^"]*GridGain[^"]*"' --include=*.csproj $CF | sort -u

# полные namespace-ы, чтобы правило совпадало и по короткому, и по полному имени
grep -rho 'using [A-Za-z.]*Ignite[A-Za-z.]*;' --include=*.cs $CF | sort | uniq -c | sort -rn
```

Дальше добавить найденные имена в `inherits`. Предикат `inherits` смотрит на **всё
замыкание наследования**, поэтому сработает и на классе, который наследуется от вашего
собственного `CfComputeBase`, а тот уже реализует `IComputeFunc`.

> **`IService` — слишком общее имя.** В ABP, где Ignite нет вовсе, правило
> `ignite.service` сработало на одном типе: там оказался свой интерфейс с тем же
> коротким именем. Правило сравнивает и короткое имя, и полное, поэтому короткое
> лучше убрать, оставив полное:
>
> ```yaml
> inherits: ["Apache.Ignite.Core.Services.IService"]   # без голого "IService"
> ```
>
> То же касается `IComputeJob` и подобных, если в АС CF есть свои интерфейсы
> с такими именами. Проверяется просто: после прогона посмотреть, что попало
> в `ignite_service`, и убедиться, что это действительно сервисы кластера.
>
> ```bash
> jq -r '.nodes[] | select(.kind | startswith("ignite")) | "\(.kind)\t\(.title)"' \
>   artifacts/doc-tree.json
> ```

Отдельно стоит подумать о видах сущностей, которых нет в наборе по умолчанию:
задачи на кластере, кэши, слушатели событий, continuous queries. Каждая — своё правило
и свой шаблон.

### 3.3 Регистрация в DI: вызовом или маркером

`docpipe` находит регистрации вида `services.AddScoped<IFoo, Foo>()`, включая
`typeof(...)`-форму и top-level statements в `Program.cs`.

Чего он **не** находит: регистрацию по маркерному интерфейсу — когда тип попадает
в контейнер потому, что реализует `ITransientDependency` или подобное. Синтаксически
это не регистрация, а наследование. В ABP так устроено **997 типов из 8966**, а вызовов
`Add*` там всего 182.

Команда №7 из диагностики покажет, есть ли такое в АС CF. Если есть — это правило
классификации, а не задача для `di.py`:

```yaml
- id: cf.injected-service
  kind: service
  template: service
  priority: 60
  when:
    all:
      - type_kind: ["class"]
      - inherits: ["ICfTransientDependency", "ICfSingletonDependency"]
```

### 3.4 Порядок работы

1. `uv run python tools/unclassified.py $CF` — посмотреть пять срезов;
2. взять самое частое, написать одно правило, прогнать `scan`;
3. повторять, пока `unclassified` перестанет заметно падать;
4. проверить `matched_rules` у спорных типов — там видно, какие правила совпали
   и почему выиграло не то, что ожидалось.

Не пытаться описать всё сразу. Правило, покрывающее 500 типов, полезнее пяти правил
по 10 типов.

## 4. Известные границы: что проверить и чем это грозит

### 4.1 Связанные исходники (команда №4)

Общий код, подключённый как `<Compile Include="$(RepoRoot)\src\Shared\Guard.cs" />`,
физически лежит вне каталога любого проекта. Правило «файл принадлежит ближайшему
`.csproj` вверх по дереву» для него не работает, и такие типы **не попадают в индекс
вовсе**: ни документа, ни участия в графе наследования.

Замер на открытых проектах: 5,0 % типов в OpenTelemetry, 4,8 % в semantic-kernel,
0 % в ABP и eShopOnWeb.

Если команда №4 вернула больше нуля — оценить масштаб:

```bash
grep -rho 'Compile Include="[^"]*"' --include=*.csproj $CF | sort -u | wc -l
```

Полноценное решение вынесено в задачу **T05b** плана: оно меняет предположение
«файл принадлежит одному модулю» и требует решить, в каком модуле показывать документ
для файла, скомпилированного в десять сборок. Если приём в АС CF не используется,
задачу можно закрыть как неактуальную.

### 4.2 Подстановки MSBuild (команда №5)

`<TargetFrameworks>$(TargetFrameworksForLibraries)</TargetFrameworks>` — значение
приходит из цепочки props-файлов и вычисляется функциями MSBuild. Воспроизводить это
означало бы переписать MSBuild, поэтому такие значения отбрасываются, и
`target_frameworks` у модуля остаётся пустым.

**На что это влияет: ни на что важное.** `target_frameworks` — метаданные, ни одно
правило классификации на них не завязано. В OpenTelemetry пусты все 70 модулей, и дерево
документации от этого не пострадало.

Ссылки между проектами (`ProjectReference`) при этом резолвятся: имя файла в них
записано буквально, и оно сопоставляется с известными проектами. В OpenTelemetry так
разрешаются 108 ссылок из 109.

### 4.3 Условная компиляция (команда №6)

Директива препроцессора **внутри выражения** ломает разбор, и объявление типа может
исчезнуть целиком. Мест несколько: аргументы атрибута, fluent-цепочка, модификатор
объявления, базовый список, шаблон в pattern matching.

```csharp
[DependsOn(
    typeof(CoreModule),
#if EF                              // ← из-за этого класс ниже не будет найден
    typeof(EfModule),
#endif
)]
public class AppModule : AbpModule
```

Обойти это в рамках tree-sitter нельзя. Доля пострадавших файлов растёт с числом
целевых платформ: 0 % при одном TFM (eShopOnWeb), 0,5 % в ABP, 2,2 % в semantic-kernel,
**8,7 %** в OpenTelemetry (от `netstandard2.0` до `net10.0`).

Такие файлы видны в сидкаре:

```bash
jq '.parse_error_files' artifacts/doc-tree.run.json
```

Их нужно просмотреть глазами: если среди них важные типы, единственное лекарство —
переписать конструкцию в исходнике (вынести `#if` за пределы выражения).

## 5. Раскладка документации и коллизии

`doc_path` строится как `docs/modules/{имя модуля}/{вид}/{slug}.md`. Два места,
где возможны коллизии:

**Одинаковые имена типов в одном модуле.** Разрешается автоматически: обоим путям
добавляется суффикс-хэш. На ABP так разведены 315 узлов из 828 — это норма, а не
исключение.

**Одинаковые имена проектов** (команда №3). Идентификаторы строятся от путей и не
конфликтуют, но `doc_path` использует имя модуля, и документы двух одноимённых проектов
легли бы в один каталог. Если команда №3 вернула непустой список — проверить после
первого прогона:

```bash
jq -r '.nodes[].doc_path' artifacts/doc-tree.json | sort | uniq -d
```

Список должен быть пуст.

## 6. Чего ожидать по времени и объёму

Ориентиры с ABP (671 проект, 7869 файлов, 9075 объявлений типов):

| | |
|---|---|
| полный прогон | 9,7 с |
| то же с `--jobs 4` | 4,9 с |
| повторный прогон с тёплым кэшем | 2,8 с |
| размер манифеста | 5,1 МБ |
| память | 212 МБ |

Кэш складывается в `<root>/.docpipe/cache` — каталог нужно добавить в `.gitignore`
репозитория АС CF. Если писать в рабочее дерево нежелательно, есть `--no-cache`
или свой `cache_dir` в конфигурации.

Разбор перестал быть узким местом: при тёплом кэше основное время уходит на резолв,
классификацию и сборку дерева, которые идут последовательно.

## 7. Что измерить для шага 3 (наполнение документов)

Эти цифры не влияют на настройку `docpipe`, но определяют, как строить шаг 3.

**Покрытие XML-doc.** На открытых проектах — 3,8 % типов в ABP и 6,5 % в eShopOnWeb.
Если в АС CF так же, агент не сможет опираться на комментарии и будет выводить описания
из структуры кода.

```bash
uv run python -c "
from pathlib import Path
from docpipe.discovery import discover
from docpipe.dotnet.parser import parse_file
from docpipe.emit import DEFAULT_EXCLUDE
R = Path('$CF'); total = documented = 0
for rel in discover(R, DEFAULT_EXCLUDE).cs_files:
    for d in parse_file(R / rel, R).declarations:
        total += 1
        documented += bool(d.xml_doc)
print(f'{documented} из {total} ({100*documented/total:.1f}%)')
"
```

**Кириллица в комментариях.** Подтверждено ранее: в АС CF она есть в комментариях,
но не в сигнатурах. Для `docpipe` это безразлично — идентификаторы латинские, а slug
строится по ним. Для шага 3 это значит, что XML-doc, где он есть, будет на русском,
и агенту не нужно переводить.

**Размер типичного типа.** Сколько членов у среднего сервиса — от этого зависит, сколько
контекста агент должен прочитать на один документ:

```bash
jq '[.nodes[].symbol.members | length] | add / length' artifacts/doc-tree.json
```

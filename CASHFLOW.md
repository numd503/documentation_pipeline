# Настройка docpipe на репозитории АС CF

Рабочий документ: что проверить и что решить, прежде чем запускать `docpipe` на боевом
репозитории. Всё здесь — следствие прогонов на четырёх открытых .NET-проектах
(eShopOnWeb, ABP, OpenTelemetry, semantic-kernel), см. [`docs/findings-stress.md`](docs/findings-stress.md).

Общая инструкция по настройке — в [`README.md`](README.md), раздел «Настройка под
конкретный проект». Здесь только то, что специфично для АС CF или требует решения
человеком.

## 0. Установка внутрь репозитория АС CF

Раскладка на рабочей машине. `$WORK` — `/home/work/<логин>`, переменная уже задана
в целевой системе; дальше по документу используется только она.

```
$WORK/docspipe/documentation_pipeline    клон этого репозитория (разработка)
$WORK/cfml/sbt.cms.cashflow              репозиторий АС CF
└── docs/ml/docspipe/                    поставка: инструмент живёт здесь
    ├── docpipe/                         пакет
    ├── pyproject.toml, uv.lock          только runtime-зависимости
    ├── uv.toml                          зеркало пакетов и сертификаты
    ├── rules/dotnet.yaml                эталонный набор — для сравнения
    └── cashflow-docspipe/               всё, что настроено под АС CF
        ├── docpipe.yaml, rules.yaml
        ├── artifacts/                   манифест и сидкар
        └── .cache/                      кэш разбора
```

Если клон лежит не в `$WORK/docspipe/documentation_pipeline`, а прямо в
`$WORK/docspipe`, поправьте путь в командах ниже — больше от этого ничего
не зависит: `install.sh` берёт исходники относительно самого себя.

Установка — одной командой из клона:

```bash
cd $WORK/docspipe/documentation_pipeline
./deploy/install.sh $WORK/cfml/sbt.cms.cashflow \
    --index https://зеркало/repository/pypi/simple \
    --python 3.12.13
```

Скрипт копирует пакет, манифест зависимостей **без dev-группы** и настройку, после чего
поднимает окружение. В нём 17 пакетов вместо 40: ни `ruff`, ни `mypy`, ни `pytest` на
целевую машину не попадают — их нет и в лок-файле поставки. Тесты, фикстуры, план
и журнал тоже не копируются.

Повторный запуск обновляет код, но **не затирает** настроенные `docpipe.yaml`,
`rules.yaml` и `uv.toml`: новые версии кладутся рядом как `*.new`.

### Закрытый контур: зеркало пакетов, сертификаты, интерпретатор

**`--index` обязателен, и дело не только в адресе.** Лок в поставке собран против
pypi.org и ссылается на файлы поимённо (`files.pythonhosted.org/...` с хэшами) —
с ним uv никуда больше не пойдёт, сколько зеркал ни настраивай. Поэтому `--index`
**пересобирает лок** против указанного зеркала. Сам лок при этом не удаляется:
uv предпочтёт уже записанные версии, если зеркало их отдаёт, и окружение совпадёт
с тем, на котором гонялись тесты.

Адрес пишется в `uv.toml` рядом с пакетом и дальше действует сам — на `uv lock`,
`uv sync` и `uv run`, из какого бы каталога их ни звали. Переменные окружения
помнить не нужно.

| Симптом | Причина | Что делать |
|---|---|---|
| тянет с `files.pythonhosted.org` | лок из поставки используется как есть | `--index <адрес зеркала>` |
| `invalid peer certificate` | сертификат TLS-прокси подписан внутренним УЦ, которого нет в наборе, вшитом в uv | в `uv.toml` уже стоит `native-tls = true`; если и в системном хранилище нет — `SSL_CERT_FILE=/путь/до/corp-root-ca.pem` перед командой |
| пытается скачать Python | не нашёл подходящий интерпретатор | `--python 3.12.13` или полный путь к нему |
| не находит `hatchling` | зеркало не отдаёт сборочный бэкенд | `--no-install-project`: ставятся только 5 зависимостей, пакет не собирается |

`python-downloads = "never"` в `uv.toml` стоит намеренно: без него uv, не найдя
интерпретатор, пойдёт за сборкой на github.com и упрётся в тот же прокси — но
сообщение будет уже про загрузку Python, а не про то, что интерпретатор не найден.

Свежий uv ругается на `native-tls`: «deprecated, use `system-certs`». Настройка при
этом работает. Переименовывать её можно, только зная версию uv на машине: неизвестный
ключ uv.toml не игнорирует, а падает с ошибкой разбора, — то есть новое имя сломает
установку на старом uv.

При неудаче установщик печатает эти же три причины с готовыми командами, а
скопированные файлы остаются на месте: повторный запуск ничего не портит.

**Если зеркало отдаёт не все пакеты** — а это вероятно, — окружение подбирается
один раз руками внутри контура, а результат (`pyproject.toml`, `uv.lock`, `uv.toml`)
возвращается в клон, после чего установка на любую машину периметра идёт без
подбора. Пошаговая инструкция: [`deploy/OFFLINE.md`](deploy/OFFLINE.md). Там же —
что делать, если пакета нет вовсе (принести колёса и собрать с `offline = true`)
и какие ограничения версий в `pyproject.toml` можно ослаблять, а какие нет:
`tree-sitter` ниже 0.25 не заработает, там сменился API запросов.

### Запуск

Переменные окружения — один раз в сессии:

```bash
export CF_ROOT=$WORK/cfml/sbt.cms.cashflow      # корень репозитория АС CF
export DOCPIPE=$CF_ROOT/docs/ml/docspipe        # каталог инструмента
export BUNDLE=$DOCPIPE/cashflow-docspipe        # настройка под АС CF
export PYTHONPATH=$DOCPIPE                      # нужен при установке с --no-install-project
export OUT=$BUNDLE/artifacts/doc-tree.json      # манифест

alias docpipe="uv run --no-sync --project $DOCPIPE python -m docpipe"
```

Дальше по документу команды пишутся так:

```bash
cd $CF_ROOT     # `out` в конфигурации задан от текущего каталога, а не от --root

docpipe scan --root . --config $BUNDLE/docpipe.yaml --stats     # состояние решений
docpipe symbols --root . --config $BUNDLE/docpipe.yaml          # что осталось без решения
docpipe scan --root . --config $BUNDLE/docpipe.yaml --jobs 4    # построить манифест
docpipe validate $OUT                                           # проверить построенное
docpipe diff старый.json $OUT                                   # сравнить манифесты
docpipe --help                                                  # все команды и флаги
```

Три вещи в этих строках существенны, а не просто длинны:

- **`--no-sync`** — запуск не ходит в сеть. Без него `uv run` при каждом вызове
  сверяется с индексом и на машине без доступа к нему падает на команде, которая
  с зависимостями ничего не делает. Окружение поднимает `install.sh`;
- **`python -m docpipe`, а не консольная команда `docpipe`** — работает и когда пакет
  собран, и когда окружение поднято с `--no-install-project`. `PYTHONPATH` нужен
  для второго случая: пакет лежит в дереве, но не в `site-packages`;
- **`--rules` не нужен** — путь к `rules.yaml` прописан в `docpipe.yaml`.

### Каталог `docs/` исключён из обхода

В `docpipe.yaml` поставки стоит `exclude: ["docs/**"]`, и это обязательно:

- инструмент лежит **внутри** сканируемого репозитория вместе с окружением `.venv` —
  обход заходил бы в тысячи чужих файлов;
- если рядом окажутся `.cs`-файлы (фикстуры, примеры, выгрузка), они попадут
  в манифест как настоящие модули продукта;
- когда добавится разбор `.py`, каталог с инструментом станет для него входными
  данными, и docpipe примется документировать сам себя.

Шаблон обязан заканчиваться на `/**`: `"docs"` совпадёт с самим каталогом, но не
с файлами под ним, — и будет выглядеть работающим.

Заданные шаблоны **складываются** со встроенными `**/obj/**`, `**/bin/**`, `**/*.g.cs`,
а не замещают их.

Отличать это от двух других механизмов:

| | что делает | символ в индексе |
|---|---|---|
| `enrolled` в `docpipe.yaml` | что документируем | остаётся |
| `exclude` в `rules.yaml` | что не документируем, но читаем | остаётся |
| `exclude` в `docpipe.yaml` | куда не заходим вовсе | **исчезает** |

Тесты отсекаются вторым способом, а не третьим: их символы нужны графу наследования.

### Вывод сборки лежит в `artifacts/`, а не в `bin/` и `obj/` проектов

В корне репозитория АС CF есть каталог `artifacts/` с подкаталогами `bin` и `obj`. Это
централизованная раскладка вывода сборки .NET 8+ (`UseArtifactsOutput` / `ArtifactsPath`
в `Directory.Build.props`): вместо `bin/` и `obj/` в каждом проекте всё складывается
в один каталог.

Встроенные шаблоны `**/obj/**` и `**/bin/**` формально совпадут и здесь, но полагаться
на совпадение имён не следует — добавить в `rules.yaml` явно:

```yaml
exclude:
  path_glob:
    - "**/artifacts/**"
```

и сверить `scan --stats` до и после: разница в числе файлов покажет, сколько туда
затекало. В `artifacts/obj/**` лежат сгенерированные `.cs`, и правило `**/*.g.cs`
покрывает не все из них.

Побочный эффект той же раскладки, важный при любой разведке репозитория: `grep -rn`
даёт сотни ложных вхождений из `artifacts/bin`. **Все поиски по АС CF вести через
`git grep`** — он ищет только по отслеживаемым файлам:

```bash
git grep -n "StartWorkflow" -- '*.cs' ':!artifacts/**'
```

## 1. Диагностика: восемь команд перед первым запуском

Выполнить в корне репозитория АС CF. Каждая отвечает на вопрос, от которого зависит
настройка. Ответы стоит выписать — они понадобятся на шаге 3.

```bash
CF=/путь/к/репозиторию/АС-CF

# 1. Масштаб: сколько кода и проектов
find $CF -name '*.cs' -not -path '*/obj/*' -not -path '*/bin/*' | wc -l
find $CF -name '*.csproj' | wc -l

# 2. Формат решений: .sln, .slnx или оба
find $CF -name '*.sln' | wc -l
find $CF -name '*.slnx' | wc -l

# 3. Дубли имён проектов
find $CF -name '*.csproj' -printf '%f\n' | sort | uniq -d

# 4. Связанные исходники: общий код, подключённый ссылкой на файл
grep -rl "Compile Include" --include=*.csproj $CF | wc -l

# 5. Подстановки MSBuild в целевых платформах
grep -rho 'TargetFrameworks\?>[^<]*' --include=*.csproj $CF | grep -c '\$('

# 6. Плотность условной компиляции
grep -rl "^#if" --include=*.cs $CF | wc -l

# 7. Маркерные интерфейсы: регистрация в DI наследованием, а не вызовом
grep -rho ': *I[A-Za-z]*Dependency' --include=*.cs $CF | sort | uniq -c | sort -rn | head

# 8. Типы, чьё имя оканчивается на Test, но которые могут быть предметными
#    (без `head`: усечение до 30 строк скрывает масштаб)
grep -rho 'class [A-Za-z]*Tests\?\b' --include=*.cs $CF | sort -u
```

### Что означают ответы

| № | Ответ | Что делать |
|---|---|---|
| 1 | больше ~5000 файлов | ставить `--jobs 4`; ориентир по времени — ниже, в §6 |
| 2 | есть `.slnx` | ничего, поддерживаются оба формата |
| 3 | список непуст | ничего, идентификаторы строятся от путей. Но `doc_path` использует **имя** модуля — проверить §5 |
| 4 | больше нуля | **часть типов не попадёт в документацию**, см. §4.1 |
| 5 | больше нуля | `target_frameworks` будут пусты у части модулей, см. §4.2 |
| 6 | заметная доля от общего числа | будут потери типов при разборе, см. §4.3 |
| 7 | список непуст | **обязательно** добавить правило по базовому типу, см. §3.3 |
| 8 | есть `StressTest`, `BackTest` и подобное | **сузить правило исключения тестов**, см. §2 |

вопрос, который кажется.

### №1. Масштаб: крупнее всего, на чём инструмент проверялся

17 988 файлов против 7869 в ABP — самый большой из виденных репозиториев. При этом
проектов **меньше** (491 против 671), то есть проекты крупнее: в среднем 37 файлов на
проект против 12 у ABP. На состав документации это не влияет, но повышает цену ошибки
в `enrolled`: один лишний глоб втягивает не десяток типов, а сотню.

### №4. Один проект с `Compile Include` — посмотреть, что именно

Файл, подключённый ссылкой, физически лежит вне каталога проекта, не привязывается
ни к одному модулю и **не попадает в индекс вовсе** — ни документа, ни участия в графе
наследования (§4.1). Один проект — это мало, но узнать, что теряется, стоит:

```bash
grep -rl "Compile Include" --include=*.csproj $CF
grep -rho 'Compile Include="[^"]*"' --include=*.csproj $CF | sort -u
```

Если по ссылке подключён общий `Guard.cs` — потеря незаметна. Если целый каталог
предметного кода — задачу **T05b** плана нужно поднимать, а не закрывать.

### №6. Команда отвечает не на тот вопрос

`grep -rl "^#if"` находит директивы **без отступа**, а C# разрешает их с отступом.
И главное: сама по себе условная компиляция безвредна — разбор ломает только `#if`
**внутри выражения** (§4.3). Уточнённый вариант:

```bash
grep -rlE '^[[:space:]]*#if' --include=*.cs $CF | wc -l
```

Но окончательный ответ даёт только прогон: файл, разобранный с ошибками и не давший
ни одного типа, виден в сидкаре и больше нигде.

```bash
jq '.parse_error_files' artifacts/doc-tree.run.json
```

При 13 файлах ожидаемые потери — единицы типов или ноль. Просмотреть список глазами
всё равно нужно: важный тип, исчезнувший молча, стоит дороже, чем десяток неважных.

### №7. Регистрация в DI: вопрос закрыт не полностью

Найдено одно вхождение `IDependency`, и это значит, что маркерных регистраций в АС CF
нет — правило по базовому типу не нужно (заготовка `cf.injected-service` лежит в
`rules.yaml` закомментированной).

Оговорка: шаблон в команде ищет имена, **оканчивающиеся на `Dependency`**. Если в АС CF
принят маркер с другим именем — `IAutoRegister`, `ISingletonService`, — команда его не
покажет. Проверяется шире:

```bash
grep -rhoE ':[^{]*\bI[A-Za-z]+(Dependency|Injectable|AutoRegister|Singleton|Scoped|Transient)\b' \
  --include=*.cs $CF | grep -oE 'I[A-Za-z]+' | sort | uniq -c | sort -rn | head
```

Косвенная проверка после первого прогона: если число найденных регистраций
(`services.Add*`) несопоставимо мало по сравнению с числом сервисов — значит,
регистрация идёт как-то ещё.

### №8. Тесты: решение принято, но не то, которое подсказывал план

План (§2) предлагал при наличии предметных «тестов» **убрать** `name_regex: ^.*Tests?$`.
Здесь это не нужно, и вот почему.

Выражение заякорено с обеих сторон. `StressTestRun` оканчивается на `Run`, а не на
`Test`, поэтому под правило **не подпадает** — «Test» в середине имени безопасен.
Опасно было бы ровно обратное: предметная сущность, названная `StressTest` без суффикса.
Диагностика такой не нашла, поэтому правило по имени остаётся как есть.

**Действовать нужно на другом уровне — в `path_glob`.** В наборе по умолчанию стоят
`**/*Test/**` и `**/*Tests/**`, и они отсекают **любой** каталог, чьё имя оканчивается
на Test(s), — в том числе предметный `StressTest/` или `BackTest/`. Вот это для
финансового моделирования прямой риск. В `rules.yaml` для АС CF шаблоны сужены до точки
перед Test, то есть до каталогов тестовых проектов по конвенции .NET:

```yaml
    - "**/*.Tests/**"     # Cf.Pricing.Tests — тестовый проект
    - "**/*.Test/**"
    - "**/test/**"
    - "**/tests/**"
    - "**/TestUtils/**"
```

Что проверить: сужение не должно оставить настоящие тестовые каталоги невыключенными.

```bash
find $CF -type d \( -name '*Test' -o -name '*Tests' \) -not -path '*/obj/*' | grep -v '\.Tests\?$'
```

Всё, что выведет команда, под новые шаблоны не подпадает. Тестовые каталоги из этого
списка нужно дописать явно, предметные — оставить.

**Отдельно: число ~30 может быть занижено.** В команде из §1 стоял `head -30`, то есть
вывод усечён ровно на тридцати строках, и настоящее количество могло быть больше.
Пересчитать без усечения:

```bash
grep -rho 'class [A-Za-z]*Tests\?\b' --include=*.cs $CF | sort -u | wc -l
```

На состав правил это не влияет — влияет на ожидания от `stats`.

## 2. Первое решение: тесты и предметные «тесты»

> **Решение по АС CF принято, см. §1а №8.** Правило по имени оставлено, шаблоны путей
> сужены; оба изменения уже внесены в `deploy/cashflow-docspipe/rules.yaml`. Раздел ниже
> объясняет, почему выбор вообще стоит, — он понадобится, если появится предметный тип,
> названный `StressTest` без суффикса.

В наборе по умолчанию тесты отсекаются двумя правилами:

```yaml
name_regex: ["^.*Tests?$"]
path_glob:  ["**/test/**", "**/tests/**", "**/*Test/**", "**/*Tests/**"]
```

**Для финансового моделирования правило по имени опасно.** `StressTest`, `BackTest`,
`ScenarioTest` — это могут быть настоящие сущности предметной области, а не юнит-тесты.
Команда №8 из диагностики покажет, есть ли такие.

Если есть — убрать `^.*Tests?$` и положиться на путь:

```yaml
name_regex:
  # - "^.*Tests?$"        # убрано: StressTest и BackTest — предметные сущности
path_glob:
  - "**/*.Tests/**"       # только каталоги тестовых проектов
  - "**/test/**"
```

Проверить результат: в манифесте не должно остаться типов из тестовых проектов,
но `StressTest` остаться должен.

```bash
jq -r '.nodes[] | select(.title | test("Test")) | "\(.title)\t\(.symbol.sources[0].path)"' \
  artifacts/doc-tree.json
```

**Важно понимать разницу.** Исключённый тип всё равно **разбирается**: его символ нужен
графу наследования. Если продуктовый класс наследуется от базового класса, лежащего
в тестовом проекте (так бывает), цепочка не порвётся.

## 3. Правила классификации: что описать для АС CF

### 3.1 Четыре шаблона из постановки

В [`purpose.md`](purpose.md) названы Service, Provider, Workflow, Controller. Первые
правила для них уже есть в `cashflow-docspipe/rules.yaml` и работают по конвенции имён
(`*Service`, `*Provider`, `*Workflow`) и по наследованию (`ControllerBase`).

Проверить на реальном коде, что конвенция соблюдается:

```bash
docpipe scan --root . --config $BUNDLE/docpipe.yaml --stats
```

Раздел «окончания имён» покажет, какие суффиксы в АС CF реально используются. Если
вместо `*Service` там `*Handler` или `*Processor` — правила нужно переписать под них,
а не наоборот.

**Проверка уже сделана, и ответ отрицательный: см. §3.5.** Конвенция имён в АС CF почти
не несёт информации — 3446 типов из 4100 не оканчиваются ни на один из 26 суффиксов,
по которым в .NET обычно опознают вид сущности. Срез «окончания имён» знает только
этот зашитый список, поэтому свои конвенции проекта (`*Rq`, `*Dm`) в нём не видны —
их придётся замерить отдельно:

```bash
grep -rhoP '(?<=\bclass )\w+' --include=*.cs src/ | grep -oP '[A-Z][a-z0-9]*$' \
  | sort | uniq -c | sort -rn | head -20
```

### 3.2 Ignite / GridGain: главная особенность АС CF

В наборе по умолчанию есть два правила, написанных «вслепую» по Apache Ignite .NET:

```yaml
- id: ignite.service
  when: { all: [ { type_kind: ["class", "record"] },
                 { inherits: ["IService", "Apache.Ignite.Core.Services.IService"] } ] }

- id: ignite.compute
  when: { all: [ { type_kind: ["class", "record"] },
                 { inherits: ["IComputeFunc", "IComputeJob", "IComputeTask"] } ] }
```

**Их нужно проверить на настоящем коде.** GridGain — коммерческая сборка на базе
Apache Ignite, и namespace-ы могут отличаться. Что выяснить:

```bash
# какие Ignite-интерфейсы реально реализуются
grep -rhoE ': *I(Service|ComputeFunc|ComputeJob|ComputeTask|CacheEntryProcessor)[<,) ]' \
  --include=*.cs $CF | sort | uniq -c | sort -rn

# как называются пакеты
grep -rho 'PackageReference Include="[^"]*Ignite[^"]*"' --include=*.csproj $CF | sort -u
grep -rho 'PackageReference Include="[^"]*GridGain[^"]*"' --include=*.csproj $CF | sort -u

# полные namespace-ы, чтобы правило совпадало и по короткому, и по полному имени
grep -rho 'using [A-Za-z.]*Ignite[A-Za-z.]*;' --include=*.cs $CF | sort | uniq -c | sort -rn
```

Дальше добавить найденные имена в `inherits`. Предикат `inherits` смотрит на **всё
замыкание наследования**, поэтому сработает и на классе, который наследуется от вашего
собственного `CfComputeBase`, а тот уже реализует `IComputeFunc`.

> **`IService` — слишком общее имя.** В ABP, где Ignite нет вовсе, правило
> `ignite.service` сработало на одном типе: там оказался свой интерфейс с тем же
> коротким именем. Правило сравнивает и короткое имя, и полное, поэтому короткое
> лучше убрать, оставив полное:
>
> ```yaml
> inherits: ["Apache.Ignite.Core.Services.IService"]   # без голого "IService"
> ```
>
> То же касается `IComputeJob` и подобных, если в АС CF есть свои интерфейсы
> с такими именами. Проверяется просто: после прогона посмотреть, что попало
> в `ignite_service`, и убедиться, что это действительно сервисы кластера.
>
> ```bash
> jq -r '.nodes[] | select(.kind | startswith("ignite")) | "\(.kind)\t\(.title)"' \
>   artifacts/doc-tree.json
> ```

Отдельно стоит подумать о видах сущностей, которых нет в наборе по умолчанию:
задачи на кластере, кэши, слушатели событий, continuous queries. Каждая — своё правило
и свой шаблон.

### 3.3 Регистрация в DI: вызовом или маркером

`docpipe` находит регистрации вида `services.AddScoped<IFoo, Foo>()`, включая
`typeof(...)`-форму и top-level statements в `Program.cs`.

Чего он **не** находит: регистрацию по маркерному интерфейсу — когда тип попадает
в контейнер потому, что реализует `ITransientDependency` или подобное. Синтаксически
это не регистрация, а наследование. В ABP так устроено **997 типов из 8966**, а вызовов
`Add*` там всего 182.

> **По АС CF ответ отрицательный, см. §1а №7:** одно вхождение `IDependency` на весь
> репозиторий. Правило ниже лежит в `rules.yaml` закомментированным — включать его
> не нужно, но и удалять не стоит: маркер может появиться позже.

Команда №7 из диагностики покажет, есть ли такое в АС CF. Если есть — это правило
классификации, а не задача для `di.py`:

```yaml
- id: cf.injected-service
  kind: service
  template: service
  priority: 60
  when:
    all:
      - type_kind: ["class"]
      - inherits: ["ICfTransientDependency", "ICfSingletonDependency"]
```

### 3.4 Порядок работы

Работа состоит не в том, чтобы всё классифицировать, а в том, чтобы про каждый тип
принять одно из трёх решений: не наша область (`enrolled`), документировать нечего
(`exclude` с причиной), документируем (правило). Последняя строка отчёта — «решение
не принято» — показывает, сколько осталось.

1. `docpipe scan --root . --config $BUNDLE/docpipe.yaml --stats` — посмотреть блок
   решений и пять срезов под ним. Проектов больше пятнадцати — добавить `--top 40`;
2. взять самый крупный проект из среза «модули» и посмотреть, что в нём осталось:
   `docpipe symbols --root . --config $BUNDLE/docpipe.yaml --module <проект>`.
   Команда печатает замыкание наследования,
   атрибуты, публичные члены и путь — то есть всё, по чему пишется предикат.
   Для АС CF это существенно: имена типов здесь почти ничего не говорят (§3.5),
   и решение принимается по базовым типам, атрибутам и именам методов;
3. записать **одно** решение — правило классификации или отсев с причиной, — прогнать
   заново и проверить, что поймано именно задуманное:
   `docpipe symbols --root . --config $BUNDLE/docpipe.yaml --state documented --rule <id>`;
4. повторять, пока «решение не принято» не дойдёт до нуля или до остатка, который
   вы согласны держать;
5. у спорных типов смотреть, какие правила совпали и почему выиграло не то:
   `--rule` показывает и совпавшие, но не победившие;
6. когда ноль достигнут, закрепить `scan --fail-on-undecided` в CI.
   Тогда новый тип, про который решения нет, роняет сборку, а не растворяется в цифре.

Не пытаться описать всё сразу. Правило, покрывающее 500 типов, полезнее пяти правил
по 10 типов.

### 3.5 Что уже видно из первого прогона на АС CF

Прогон дал около 4100 типов без решения. Три группы из отчёта разобраны заранее —
заготовки лежат закомментированными в `rules.yaml`:

| Из отчёта | Что это | Решение |
|---|---|---|
| атрибут `GenerateCode` — 1478 | генерат по схемам сервисных контрактов | отсев `generated.schemas` |
| namespace `…Services.Schemas.Srv*2020Ver005` — 469 | тот же генерат, вид со стороны namespace | там же |

## 4. Известные границы: что проверить и чем это грозит

### 4.1 Связанные исходники (команда №4)

Общий код, подключённый как `<Compile Include="$(RepoRoot)\src\Shared\Guard.cs" />`,
физически лежит вне каталога любого проекта. Правило «файл принадлежит ближайшему
`.csproj` вверх по дереву» для него не работает, и такие типы **не попадают в индекс
вовсе**: ни документа, ни участия в графе наследования.

Замер на открытых проектах: 5,0 % типов в OpenTelemetry, 4,8 % в semantic-kernel,
0 % в ABP и eShopOnWeb.

Если команда №4 вернула больше нуля — оценить масштаб:

```bash
grep -rho 'Compile Include="[^"]*"' --include=*.csproj $CF | sort -u | wc -l
```

Полноценное решение вынесено в задачу **T05b** плана: оно меняет предположение
«файл принадлежит одному модулю» и требует решить, в каком модуле показывать документ
для файла, скомпилированного в десять сборок. Если приём в АС CF не используется,
задачу можно закрыть как неактуальную.

### 4.2 Подстановки MSBuild (команда №5)

`<TargetFrameworks>$(TargetFrameworksForLibraries)</TargetFrameworks>` — значение
приходит из цепочки props-файлов и вычисляется функциями MSBuild. Воспроизводить это
означало бы переписать MSBuild, поэтому такие значения отбрасываются, и
`target_frameworks` у модуля остаётся пустым.

**На что это влияет: ни на что важное.** `target_frameworks` — метаданные, ни одно
правило классификации на них не завязано. В OpenTelemetry пусты все 70 модулей, и дерево
документации от этого не пострадало.

Ссылки между проектами (`ProjectReference`) при этом резолвятся: имя файла в них
записано буквально, и оно сопоставляется с известными проектами. В OpenTelemetry так
разрешаются 108 ссылок из 109.

### 4.3 Условная компиляция (команда №6)

Директива препроцессора **внутри выражения** ломает разбор, и объявление типа может
исчезнуть целиком. Мест несколько: аргументы атрибута, fluent-цепочка, модификатор
объявления, базовый список, шаблон в pattern matching.

```csharp
[DependsOn(
    typeof(CoreModule),
#if EF                              // ← из-за этого класс ниже не будет найден
    typeof(EfModule),
#endif
)]
public class AppModule : AbpModule
```

Обойти это в рамках tree-sitter нельзя. Доля пострадавших файлов растёт с числом
целевых платформ: 0 % при одном TFM (eShopOnWeb), 0,5 % в ABP, 2,2 % в semantic-kernel,
**8,7 %** в OpenTelemetry (от `netstandard2.0` до `net10.0`).

Такие файлы видны в сидкаре:

```bash
jq '.parse_error_files' artifacts/doc-tree.run.json
```

Их нужно просмотреть глазами: если среди них важные типы, единственное лекарство —
переписать конструкцию в исходнике (вынести `#if` за пределы выражения).

## 5. Раскладка документации и коллизии

`doc_path` строится как `docs/modules/{имя модуля}/{вид}/{slug}.md`. Два места,
где возможны коллизии:

**Одинаковые имена типов в одном модуле.** Разрешается автоматически: обоим путям
добавляется суффикс-хэш. На ABP так разведены 315 узлов из 828 — это норма, а не
исключение.

**Одинаковые имена проектов** (команда №3). Идентификаторы строятся от путей и не
конфликтуют, но `doc_path` использует имя модуля, и документы двух одноимённых проектов
легли бы в один каталог. Если команда №3 вернула непустой список — проверить после
первого прогона:

```bash
jq -r '.nodes[].doc_path' artifacts/doc-tree.json | sort | uniq -d
```

Список должен быть пуст.

## 6. Чего ожидать по времени и объёму

Измерено на ABP (671 проект, 7869 файлов, 9075 объявлений типов); для АС CF —
пересчёт по числу файлов (17 988, то есть ×2,3), а не замер:

| | ABP, замер | АС CF, ожидание |
|---|---|---|
| полный прогон | 9,7 с | ~22 с |
| то же с `--jobs 4` | 4,9 с | ~11 с |
| повторный прогон с тёплым кэшем | 2,8 с | ~7 с |
| память | 212 МБ | ~450 МБ |
| размер манифеста | 5,1 МБ | зависит от `enrolled`, не от числа файлов |

Порядок величин важнее самих чисел: прогон занимает **десятки секунд, а не часы**,
и его нормально гонять в цикле настройки правил. Если получилось радикально больше —
это не «большой репозиторий», а повод разбираться.

Размер манифеста пересчитать нельзя: в него идут узлы, а не файлы, и их число задаётся
`enrolled` и правилами. У ABP 828 узлов дали 5,1 МБ — считайте по 6 КБ на узел.

Кэш складывается в `cache_dir` относительно `--root`. В поставке для АС CF он уведён
внутрь каталога инструмента (`docs/ml/docspipe/cashflow-docspipe/.cache`), чтобы не
засорять рабочее дерево продукта, и уже закрыт в `docs/ml/docspipe/.gitignore`.
Альтернативы прежние: `--no-cache` или свой путь.

Разбор перестал быть узким местом: при тёплом кэше основное время уходит на резолв,
классификацию и сборку дерева, которые идут последовательно.

## 7. Что измерить для шага 3 (наполнение документов)

Эти цифры не влияют на настройку `docpipe`, но определяют, как строить шаг 3.

**Покрытие XML-doc. Разброс между проектами огромный — предполагать нельзя, только мерить:**

| | покрытие |
|---|---|
| ABP, все типы | 3,8 % |
| eShopOnWeb, все типы | 6,5 % |
| **semantic-kernel, все типы** | **52,5 %** |
| **semantic-kernel, только попавшие в дерево** | **93,4 %** |

Вторая строка про semantic-kernel важнее первой: классификация отбирает публичную
поверхность API, а её документируют лучше среднего. Если в АС CF так же, у агента
шага 3 будет с чего начинать. Если как в ABP — придётся выводить описания
из структуры кода.

Меряйте **оба** числа: по всем типам и по узлам готового манифеста.

```bash
# Из каталога инструмента: docs/ml/docspipe
uv run --frozen python -c "
from pathlib import Path
from docpipe.config import load_config
from docpipe.discovery import discover
from docpipe.dotnet.parser import parse_file
from docpipe.emit import exclude_globs
R = Path('$CF'); total = documented = 0
config = load_config(Path('cashflow-docspipe/docpipe.yaml'))
for rel in discover(R, exclude_globs(config)).cs_files:
    for d in parse_file(R / rel, R).declarations:
        total += 1
        documented += bool(d.xml_doc)
print(f'{documented} из {total} ({100*documented/total:.1f}%)')
"
```

`exclude_globs(config)` вместо голого списка — чтобы замер шёл по тому же множеству
файлов, что и прогон: иначе в знаменатель попадёт `docs/` со всем, что там лежит.

**Кириллица в комментариях.** Подтверждено ранее: в АС CF она есть в комментариях,
но не в сигнатурах. Для `docpipe` это безразлично — идентификаторы латинские, а slug
строится по ним. Для шага 3 это значит, что XML-doc, где он есть, будет на русском,
и агенту не нужно переводить.

**Размер типичного типа.** Сколько членов у среднего сервиса — от этого зависит, сколько
контекста агент должен прочитать на один документ:

```bash
jq '[.nodes[].symbol.members | length] | add / length' artifacts/doc-tree.json
```

## 8. Точки входа объявлены не в коде

Разведка репозитория 29.07.2026 (подробно — в
[`docs/findings-cashflow-registries.md`](docs/findings-cashflow-registries.md)) дала вывод,
который меняет ожидания от инструмента:

> **АС CF управляется метаданными.** Джобы, workflow и обработчики событий объявлены
> строками в XML, которые при развёртывании кладутся в БД, а исполняют их универсальные
> раннеры, получающие имя типа из данных. Граф триггеров **не восстанавливается
> статическим анализом C#** — ни tree-sitter, ни Roslyn: этой информации в коде нет.

Проверено на трёх механизмах: `JOBCLASS` резолвится Quartz'ем рефлексией по строке;
`WorkflowRequestRunner.StartWorkflow(request.WorkflowId, request.WorkflowVersion, …)`
получает идентификатор из данных, поэтому литерала конкретного workflow в коде **не
существует**; обработчик события объявлен атрибутом `Class=` в структуре списка.

Четыре реестра, найденные в репозитории:

| Что объявляет | Файл |
|---|---|
| grid-сервисы кластера, их классы и **команды** | `sbt.cashflow.gridservice.subrepo/Sbt.CMS.GridService.Initializer/services.config` |
| джобы Quartz и их расписания | `sbt.cashflow.deployment/Sbt.Deployment.Db/Cashflow/Data/Items/Items_Basic.xml` |
| workflow и их шаги (ссылкой на JSON) | там же, `Items-Workflows.xml` |
| списки, поля, связи и **обработчики событий** | `sbt.cms.cashflow.subrepo/Sbt.CMS.Cashflow.Structure/Cashflow.Structure.xml` |

Что из этого следует для настройки:

- на состав `doc-tree.json` это не влияет: реестры — вход бизнес-слоя, а не шага 1;
- **`Cashflow.Structure.xml` содержит готовый глоссарий**: у каждого списка и каждого поля
  есть `DisplayName` по-русски. Каталог бизнес-сущностей можно генерировать, а не сочинять;
- перечень реестров может быть неполон. Проверяется одной командой:

```bash
git grep -h -o 'InnerName="[^"]*"' -- 'sbt.cashflow.deployment/*.xml' | sort | uniq -c | sort -rn
```

## 9. Шаг 2: документы

Шаг 2 (`docpipe materialize`) закончен — справочник в
[`docs/materialize.md`](docs/materialize.md). Здесь только то, что специфично
для боевого репозитория.

**Каталог документации и обход.** Инструмент лежит **внутри** дерева документации,
поэтому в конфигурацию поставки обязательно:

```yaml
docs_root: "docs"
docs_scan_exclude:
  - "docs/ml/**"        # каталог самого инструмента вместе с окружением
```

Встроенный список (`**/.venv/**`, `**/site-packages/**`, `**/node_modules/**`,
`**/.git/**`) складывается с этим, а не замещается. Третья защита главная и
работает всегда: документом шага 2 считается только файл с `docpipe.node_id`
**и** `docpipe.schema` вида `materialize/*`, поэтому чужой `README.md` сиротой
не станет, даже если его прочитают.

**Первый прогон — обязательно `--dry-run`.** Он ничего не пишет и показывает,
сколько документов создалось бы и где:

```bash
uv run --frozen python -m docpipe materialize artifacts/doc-tree.json \
    --root $CF --config cashflow-docspipe/docpipe.yaml --dry-run
```

Это первая цифра, по которой видно объём документации на АС CF.

**Владение.** Без `ownership.yaml` у всех документов `team: null`. Это не мешает
работать, но `--team` тогда ничего не отбирает. Правила раздают владельца **по узлу**,
а не по модулю — иначе шэренный `.csproj` не разделить. Начинать стоит с одного
слоя приоритета 10 по `module_glob` и смотреть `docs owners --lint`: он покажет,
сколько узлов осталось ничьими и в каких каталогах они лежат.

**Что смотреть в первом отчёте `docs status`:**

| Наблюдение | Что значит |
|---|---|
| много `broken` | документы правились руками и структура нарушена; чинить по одному, `--force` сохраняет исходник рядом |
| много `orphan` | правила классификации менялись после прошлого прогона, часть узлов уехала |
| `probable` в замечаниях о переносах | кандидатов несколько, переносить командой `docs adopt` |
| блокирующая ошибка про регистр | два `doc_path` различаются только регистром — на Windows и macOS они совпадут |

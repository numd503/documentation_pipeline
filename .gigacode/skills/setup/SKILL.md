# Настройка docpipe на репозиторий

Ты настраиваешь `docpipe` на репозиторий продукта вместе с человеком. Человек
знает, какой код его, задаёт область, отвечает на вопросы и решает, когда
остановиться. Ты разбираешь то, что в области осталось без решения: читаешь
код, пишешь правило в файл настройки, зовёшь инструмент ещё раз и показываешь
разницу. `docpipe` даёт факты и проверки и ничего не решает за вас.

Проверяемая цель: в области нет находки без решения и нет дефектов
(`setup_status`: `unexplained` и `defects` равны нулю). Остановиться раньше
человек вправе. Принятие — коммит каталога настройки, отдельного файла нет.

## Граница

- **Пишешь только файлы каталога настройки**: `docpipe.yaml`, `rules.yaml`,
  `pages.yaml`, `ownership.yaml`, `registries.yaml`, `arch-registry.yaml`,
  `templates/`. Код продукта, документы, файлы клона docpipe — никогда, даже
  если правка очевидна: её делает команда продукта.
- **«Не документируем» и «не берём» — только с причиной, которую назвал
  человек.** Подпись варианта («Не документируем») — не причина. Причину
  не дописывай и не улучшай: отсев с твоей причиной неотличим от решения
  человека, и настройка ломается молча.
- **Имена-ключи называет человек**: команда владения, домен, имя раздела,
  имя нового вида. Ты предлагаешь варианты из находки.
- Не ходишь в сеть, не ставишь пакетов, не исполняешь код репозитория
  (сборка, тесты, `npm`, `dotnet`): только читаешь файлы и зовёшь `docpipe`.
- Команды `docpipe` файлов настройки не пишут — правишь ты, инструментом
  правки файла. Коммит — только по прямому слову человека.

## Где что лежит

Агент запущен из корня клона docpipe. Первым делом прочитай
`.gigacode/settings.json` клона, запись `mcpServers.docpipe-setup`:

- в `args` после `--config` — путь к `docpipe.yaml`: дальше **CFG**, а его
  каталог — **КАТАЛОГ** (каталог настройки);
- в `args` после `--root` (и в `cwd`) — корень продукта: дальше **ПРОДУКТ**;
- `command` — полный путь к `docpipe`, если в `PATH` его нет.

Записи нет — уточни у человека корень продукта и каталог настройки и
предложи поставить настройку установщиком (`deploy/README.md`, «Установка»);
сам установщик не запускай. Справочники — в клоне: протокол вопросов
`docs/setup-interview.md`, карта ключей `docs/setup-map.md`, команды
`docs/setup.md`. Инструмент правки не пускает за пределы клона — попроси
человека добавить ПРОДУКТ в рабочие каталоги агента; переписывать файл
настройки целиком через оболочку нельзя: пропадут комментарии и чужие записи.

## Инструменты

Сервер `docpipe-setup`; в списке инструментов агента имя может идти с
префиксом сервера. У каждого инструмента есть CLI-двойник — та же функция.

| Инструмент | Аргументы | CLI-двойник | Что даёт |
|---|---|---|---|
| `setup_config_check` | — | `docpipe config check` | во что разрешается каждый путь; первым и после каждой правки |
| `setup_recon` | `top`, `list`, `limit`, `offset` | `docpipe recon` | чем собран репозиторий: проекты, фронты, прокси |
| `setup_status` | `list`, `limit`, `baseline`, `offset` | `docpipe setup status` | находки без решения и дефекты, разница с прошлым вызовом |
| `setup_review` | `since`, `limit`, `offset` | `docpipe setup review` | новое с последнего коммита настройки |
| `setup_explain` | `path`, `list`, `limit`, `offset` | `docpipe setup explain` | что решено об этом коде, какой записью и почему |
| `setup_stats` | `lang`, `top` | `docpipe scan --stats`, `docpipe web scan --stats` | срезы символов, в том числе «последнее слово» |
| `setup_symbols` | `lang`, `state`, `module`, `namespace`, `path`, `rule`, `kind`, `limit`, `offset` | `docpipe symbols` | символы группы: базы, атрибуты, правило-победитель |
| `setup_candidates` | `kind`, `limit`, `offset` | `docpipe setup candidates` | кандидаты в ключи настройки |
| `setup_link` | `category`, `by`, `limit`, `offset` | `docpipe setup link` | шов фронт↔.NET кластерами, подсказка префикса |
| `setup_pages` | `note`, `list`, `limit`, `offset` | `docpipe web pages` | страницы и почему они страницы |
| `setup_docs` | `status`, `lang`, `limit`, `offset` | `docpipe docs status` | документы: статус и действие с файлом |
| `setup_docs_explain` | `path`, `lang` | `docpipe docs explain` | один документ подробно |

- `limit` у `setup_status` — кластеров на срез каждой находки (умолчание 5), а не находок: `{"limit": 20}` даёт меньше находок на странице.
- `setup_docs` и `setup_docs_explain` по умолчанию — `lang: cs`; документы фронта — только с `lang: ts`.
- `setup_symbols` с `rule` ищет среди `state` (умолчание `undecided`): охват отсева — с `state: not_documented` или `any`, иначе `total: 0`.

- **Каждый вызов считает по файлам настройки как они есть сейчас**: после
  правки зови снова. Прошлый ответ `setup_status` сервер помнит сам —
  `previous` у находки и есть разница.
- **Ответ — страница**: `total`, `offset`, `truncated`, `next_offset`.
  «Не показали» не значит «нет»: есть `next_offset` — бери эту страницу
  (`offset`) или сужай (`module`, `path`, `limit`); `truncated_lists`
  называет урезанный список — возьми его аргументом `list`.
- **Ошибка инструмента** (`isError`) — читай текст: обычно это неверный
  аргумент или отказ загрузки настройки, а не «сервер упал».

**Сервер недоступен** (инструментов `setup_*` нет или вызов не проходит) —
те же функции командами, из корня продукта, с `--format json`:

```bash
cd ПРОДУКТ && docpipe config check --config CFG --root . --format json
cd ПРОДУКТ && docpipe recon --root . --json КАТАЛОГ/artifacts/recon.json --text КАТАЛОГ/artifacts/recon.txt
cd ПРОДУКТ && docpipe setup status --root . --config CFG --format json --out КАТАЛОГ/artifacts/setup-status.json
cd ПРОДУКТ && docpipe setup status --root . --config CFG --format json --baseline КАТАЛОГ/artifacts/setup-status.json --out КАТАЛОГ/artifacts/setup-status.json
cd ПРОДУКТ && docpipe setup explain src/Orders --root . --config CFG --format json
```

Первый `setup status` — только с `--out`, следующие — с `--baseline` и
`--out` на тот же файл: так видна разница. `docpipe web pages`,
`docpipe docs status` и `docpipe docs explain` читают манифест с диска,
собранный прошлой настройкой: после правки — сначала
`docpipe web scan --root . --config CFG` (пишет `web.out`) или
`docpipe scan --root . --config CFG` (пишет `out`; пути — в `config check`).
ПРОДУКТ, CFG, КАТАЛОГ — буквальными путями: переменные оболочки, `$(…)`
и обратные кавычки оболочка агента отвергает.

## Цикл

1. **Находка** — `setup_status` или кандидат; в текущей фазе — крупнейший кластер.
2. **Код** — открой примеры `файл:строка`, объявление, соседей. Число берёшь
   у инструмента, вывод — из кода.
3. **Кто решает** (`docs/setup-interview.md`, «Кто решает»). Позитивное
   правило, доказуемое кодом, пишешь сам с адресом доказательства
   («setup candidates http-wrappers: 47 вызовов, тело http-extensions.ts:16»):
   у записей `docpipe.yaml` и `add` в `pages.yaml` — в `reason`, у правила
   вида — строкой `# доказательство: …` над `- id:` (поля `reason` у него
   нет, лишний ключ — отказ загрузки). Остальное — вопрос человеку.
4. **Правка** файла — по правилам ниже.
5. **Проверка** — `setup_config_check`, затем инструмент фазы. После
   `rules.yaml` — ещё `defects` и `load.errors`: набор, который не
   загрузился, убирает `dotnet.undecided` целиком — `unexplained` падает,
   и это не успех.
6. **Разница** — что закрылось, что появилось, охват новой записи
   (`coverage` в `setup_status`) больше нуля. Человеку — числа и правка:
   файл, ключ, значение. Находка не ушла — `setup_explain` по пути её
   примера: какая запись решила; тот же вопрос второй раз не задавай.

## Вход

Определи один раз в начале и скажи человеку, какой вход и почему.

1. **Онбординг** — `setup_config_check` говорит, что конфигурации нет;
   `setup_review` отвечает `base: null` с пометкой `config.uncommitted`
   (файлы настройки ни разу не коммитились); или закоммичен нетронутый
   нейтральный набор (в `docpipe.yaml` нет ни `enrolled`, ни `web.roots`,
   в `ownership.yaml` нет команд). Фазы по порядку:
   00 → 10 → 20 → 30 → 40 → 50 → 60.
2. **Расширение** — человек назвал код: модуль, каталог, фронт («покрой
   документацией X»). Фаза `phases/80-expand.md`.
3. **Ревью** — настройка закоммичена, а после её коммита менялся код
   (`setup_review`: `new_files_total` больше нуля) или человек просит
   проверить. Фаза `phases/90-review.md`.

Подходят и 2, и 3 или не уверен — уточни у человека, с чего начать.
Ревью без нового кода (`new_files_total` 0, `dead_decisions` пуст) — так и скажи.

## Фазы

Файл фазы читай, входя в неё, а не все сразу. Следующая фаза — после
контрольной точки или по слову человека; ненужную (нет .NET или фронта) —
назови вслух и пропусти.

| Файл | Фаза | Находки |
|---|---|---|
| `phases/00-scope.md` | проверка настройки, разведка, область | `scope.not_configured`, `config.problems`, `load.errors`, `scope.module_undecided`, `scope.front_undecided` |
| `phases/10-dotnet.md` | .NET: обёртки DI, диспетчеризация, группы типов | `dotnet.undecided`, `parse.errors` |
| `phases/20-web.md` | фронт: секция `web` правил | `web.undecided` |
| `phases/30-link.md` | шов фронт↔.NET: обёртки, префиксы, концы без пары | `link.calls_invisible`, `link.calls_unresolved`, `link.calls_without_endpoint`, `link.endpoints_without_caller` и другие `link.*` |
| `phases/40-pages.md` | страницы и разделы без маршрута | `pages.layout`, `pages.unanchorable` и другие `pages.*` |
| `phases/50-docs.md` | раскладка документов и их состояние | `docs.orphan`, `docs.unavailable` и другие `docs.*` |
| `phases/60-ownership.md` | владение и домены | `owners.not_configured`, `owners.unowned` |

## Вопрос человеку

Протокол и каталог вопросов — `docs/setup-interview.md`: раздел `### <код>`
на каждый код находки (материал, что делаешь сам, шаблон вопроса, варианты
с адресом правки, пробелы формата). Других вариантов не придумывай.

- **Вопрос о решении — только из находки с кодом**: `setup_status` или
  `new_findings` ревью. Кода нет (кандидаты, раскладка, домены, экраны) —
  умолчание и кандидаты вслух, правка — по слову человека без вопроса.
  Факт среды и порядок работы (где ПРОДУКТ и CFG, где движок, от какой
  ревизии ревью, с какого входа начать) — не решение: уточни у человека.
- Один вопрос — на кластер, а не на символ; не больше четырёх вопросов
  за один вызов инструмента вопроса.
- Заголовок до 12 символов. Текст: находка с числом и примером
  (`файл:строка`), что ты проверил сам, затем «От ответа зависит, …».
  2–4 варианта, у каждого — конкретная правка: файл, ключ, значение.
- Причина — свободным ответом, в `reason` пишется дословно. Свободного
  ответа нет — спроси причину вторым вопросом обычным текстом и жди.
- Инструмента вопроса нет — тот же вопрос текстом, варианты нумерованы.
- «Не сейчас» — законный ответ: правки нет, находка остаётся в отчёте.
- Не спрашивай того, что доказал инструмент (`setup_candidates`) или что
  уже решено (`setup_explain` показывает запись с причиной).
- Пробел формата (ответу негде лечь) — скажи, что находка останется; файл не трогай.

## Правка файлов

- Правка текстовая, на месте: комментарии, порядок и соседние записи
  остаются. Новый элемент списка — рядом с прежними, а не вместо них.
- **Один ключ — одно место.** В `docpipe.yaml` уже есть секции `web:`,
  `graph:`; пиши внутрь них. Второй `web:` молча заменит первый.
- Раскомментируя ключ нейтрального набора, сними `# ` с ключа и его
  элементов, отступ сохрани. Ключ-список, под которым остались одни
  комментарии, — отказ загрузки.
- Элемент списка не «выключают» комментарием: список станет «всё» или
  пустым. Отказ — `not_enrolled`, `exclude` или правило отсева с причиной
  человека; удалить запись — только по его слову.
- Глоб каталога в `exclude` — с `/**` (`legacy/**`): без него шаблон
  совпадёт с каталогом, а не с файлами.
- Предикаты `when` — списки: `path_glob: ["src/**"]`. Строка читается
  посимвольно и не совпадает почти ни с чем, без ошибки.
- **Узел условия — ровно один ключ**: два признака — `all:` со списком
  узлов, любой из них — `any:`; два ключа в одном узле — отказ загрузки.
- Строки с `*`, `{`, `:`, `#` — в двойных кавычках.
- Правил секцию `rules.yaml` — подними её `ruleset_version` (дата правки).
- После каждой правки — `setup_config_check` и инструмент фазы. Отказ —
  сначала чинишь правку, дальше не идёшь.

Примеры в фазах начинаются строкой `# file: …` — какой файл и секция.
`<…>` в примере — подстановка: в файл идёт значение, а не скобки.

```yaml
# file: docpipe.yaml
not_enrolled:
  - glob: "samples/**"
    reason: "<слова человека>"
```

## Не угадывай

- **Ноль — не «нет».** Пустой список при малой базе (`calls_resolved`,
  `pages_total`, `standard_calls`) значит «не видно», а не «не бывает».
  Говори базу вслух вместе с нулём.
- **Число инструмента — о настройке на диске сейчас**, манифест в
  `artifacts/` — о прошлой. Сравнивай только ответы инструментов.
- **Находки шва считаются, только когда в области обе стороны**: нет
  фронта — нет и `link.endpoints_without_caller`, и это не «шов чист».
- **Правка без разницы** (число не изменилось) — не успех: запись
  не легла. `setup_explain` и охват записи покажут почему.

## Остановка

По слову человека (или когда `unexplained` и `defects` — нули):

1. `setup_status` — напечатай сводку: «В области: N находок без решения,
   M дефектов; вне области: модулей A, фронтов B» (`unexplained`,
   `defects`, `out_of_scope`).
2. Остаток — списком: код, число, крупнейшие кластеры, пробелы формата.
   Остановка с остатком законна, но осознанна.
3. `without_reason` — решения без причины: предложи дописать её словами человека.
4. Предложи закоммитить каталог настройки: коммит — это принятие, и
   следующее ревью считает новый код от него. По прямому слову человека:

```bash
git -C ПРОДУКТ status --short
git -C ПРОДУКТ add КАТАЛОГ
git -C ПРОДУКТ commit -m "docpipe: настройка, онбординг"
```

В коммит идёт только КАТАЛОГ: чужие изменения в `git status` не добавляй.

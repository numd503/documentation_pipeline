# Фаза 90: ревью

## Цель

После изменений в коде — показать, что появилось с последнего коммита
настройки и **как прежние решения обошлись с новым кодом**, и спросить
только о новом. Решённое раньше повторно не задаётся.

## Инструменты

- `setup_review` (`docpipe setup review`), аргумент `since` — ревизия базы;
  без него база — последний коммит файлов настройки;
- `setup_status` — общая сводка после правок;
- `setup_explain` (`docpipe setup explain`) — новый файл подробно.

## Шаги

1. **`setup_review`.** Прочитай по порядку:
   - `base`, `since` — от какого коммита считается новое;
   - `config_dirty`, `config_changes` — файлы настройки изменены и не
     закоммичены: несохранённые решения — ещё не решения. Скажи вслух
     и спроси, закоммитить их сначала или отложить;
   - `new_files_total`, `outside_area_total` — сколько нового кода и
     сколько его вне `roots`/`web.roots`;
   - `applied`, `new_findings`, `dead_decisions`, `notes`.
2. **Пометки** (`notes`):
   - `config.uncommitted` — настройка ни разу не коммитилась: это
     онбординг, а не ревью (`SKILL.md`, «Вход»);
   - `config.outside_repository` — файлы настройки не в этом репозитории:
     база только явной ревизией — спроси человека, от какой (`since`);
   - `git.submodules` — подмодуль в области: новый код внутри него ревью
     не видит, скажи вслух;
   - `status.defects` — дефекты: чинишь, как в фазах, до вопросов.

   Ревью не построилось (не git, нет ревизии, база на границе неглубокого
   клона) — передай текст ошибки человеку: нужна `since` или
   `git fetch --unshallow`, это его действие.
3. **`applied` — первым.** Решения, которые применились к новому коду:
   правило отсева, молча забравшее новые типы, стоит первым. По каждому —
   решение, причина, сколько нового кода и файлы. Покажи человеку и
   спроси, в силе ли (заголовок «Ревью»): «в силе» — правки нет; «не для
   этого кода» — вырез `unless`, новое правило или сужение шаблона по его
   ответу. Символы файла — `setup_explain` по нему.
4. **`new_findings`** — находки с местами в новом коде (`places`,
   `examples`). Каждую — по фазе её кода и разделу каталога
   `docs/setup-interview.md`, как в онбординге, но только по этим местам.
5. **`dead_decisions`** — решения, которые не решают ничего во всём
   репозитории (код удалён или переименован). Вопрос: удалить запись или
   поправить шаблон под новое место. Удаление записи «не берём» — по слову
   человека; правила классификации без побед сюда не попадают.
6. **После правок** — `setup_review` ещё раз и `setup_status`: решённое
   ушло из `new_findings` и `dead_decisions`, новых находок нет. Затем —
   остановка (`SKILL.md`, «Остановка») и коммит: следующее ревью считает
   новый код от него.

## Контрольная точка

- `setup_review` — `new_findings` пуст, `dead_decisions` пуст или по каждой
  записи человек ответил «оставить», `defects` 0;
- по каждой строке `applied` человек ответил;
- после коммита каталога настройки `setup_review` — `new_files_total` 0.

## Ловушки

- **Каталог настройки бывает всем репозиторием** (`docpipe.yaml` в корне):
  база считается по **файлам** настройки, а не по каталогу, иначе каждый
  коммит кода сдвигал бы её.
- **Неглубокий клон врёт молча**: коммит на границе клона «добавляет» все
  файлы. `setup_review` отказывает с подсказкой — не обходи её своей `since`.
- **Подмодули**: `git diff` родителя видит только смену ссылки.
- **Корень — подкаталог репозитория**: новые файлы — от `--root`; код выше
  него ревью не видит, и это не «нового нет».
- **Переименование — новый файл**: путь входит в предикаты (`path_glob`),
  решение могло смениться вместе с ним — оно будет в `applied`.
- **Охват растёт и тогда, когда правило работает как задумано** (новые
  `*Dto` под «dto не документируем»): поэтому ревью — список решений,
  а не коэффициент, и подтверждает его человек.
- **Правило отсева без охвата на нейтральном наборе** (`tests`,
  `generated.code` в репозитории без тестов) — `dead_decisions` всегда;
  его удаляют из копии набора по слову человека, иначе ревью красное
  навсегда.

## Правка файлов

Те же файлы и правила, что в фазах 00–60. Две особенности ревью:

- причину существующей записи не переписываешь — она слова человека,
  сказанные раньше; новая формулировка — только его новыми словами;
- запись из `dead_decisions` удаляешь целиком (с её комментарием), а не
  комментируешь: закомментированный элемент списка — либо отказ загрузки,
  либо пустой список.

Ответ «не для этого кода» на строку `applied` про правило отсева —
вырез `unless` у того же правила: правило вида его не перебьёт, отсев
отменяет классификацию при любом приоритете. `id`, `reason` и `when`
остаются как были, дописан только `unless`:

```yaml
# file: rules.yaml#dotnet
dotnet:
  exclude:
    rules:
      - id: data.contracts
        reason: "Контракт передачи данных: смысл в вызывающем коде, а не в самом типе"
        priority: 50
        when:
          name_regex:
            - "^.*Dto$"
            - "^.*Request$"
            - "^.*Response$"
            - "^.*Options$"
            - "^.*Settings$"
        unless:
          path_glob: ["src/Billing/Commands/**"]   # ответ человека на ревью
```

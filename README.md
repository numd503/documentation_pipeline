# documentation_pipeline

Пайплайн построения, обновления и верификации технической документации проекта **АС CF**
силами AI-агентов.

Сам проект АС CF — собственность компании и в этот репозиторий не переносится. Здесь живут
инструменты пайплайна, его проектная документация и тестовые данные.

## Задача

АС CF — большой проект финансового моделирования на .NET, Python и Angular, с распределённым
кластером вычислений на Ignite (GridGain). Требуется документация, которая:

- генерируется из кода, а не пишется вручную;
- имеет понятную структуру;
- **описывает**, а не пересказывает код;
- содержит ссылки на конкретные места реализации.

Полная постановка — в [`purpose.md`](purpose.md).

## Пайплайн

```
                     ┌─────────────────────────────────────┐
   исходники .NET ──▶│  Шаг 1: docpipe scan (детермин.)    │──▶ doc-tree.json
                     └─────────────────────────────────────┘         │
                                                                     ▼
                     ┌─────────────────────────────────────┐
                     │  Шаг 2: materialize (идемпотентно)  │──▶ docs/**/*.md (скелеты)
                     └─────────────────────────────────────┘         │
                                                                     ▼
                     ┌─────────────────────────────────────┐
                     │  Шаг 3: агент + tools (недетермин.) │──▶ наполненные документы
                     └─────────────────────────────────────┘
```

Граница между детерминированным и недетерминированным проходит по одной линии:
**классификация — правила, описание — агент.** Решение «этот класс — контроллер» принимает
правило из YAML. Решение «что этот контроллер делает» принимает агент.

Отдельно от этих трёх шагов стоит **бизнес-слой**: процессы и сущности, которые из кода
не выводятся и пишутся аналитиками.

```
   реестры платформы ──▶ якоря (точки входа) ──┐
                                               ├──▶ бизнес-документы ◀──▶ технические
   каталог аналитика ──▶ бизнес-процессы ──────┘        (связь по якорю, не по коду)
```

Связь между слоями держится на одном инварианте: **техника ссылается на бизнес, бизнес
о технике не знает.** Якорем служит не имя класса, а строка, которую обязан знать
вызывающий, — имя сервиса кластера, заголовок джоба, идентификатор workflow, маршрут.
Поэтому рефакторинг, не меняющий бизнес-смысла, связь не рвёт. Подробно —
в [`docs/business-implementation-plan.md`](docs/business-implementation-plan.md).

Что уже работает сквозным прогоном:

```bash
# техническая документация
docpipe scan --root . --out artifacts/doc-tree.json     # что документировать
docpipe materialize artifacts/doc-tree.json --root .    # создать документы
docpipe docs status artifacts/doc-tree.json --root .    # что делать агенту
docpipe docs accept artifacts/doc-tree.json PATH        # зафиксировать соответствие коду

# бизнес-документация
docpipe anchors list artifacts/doc-tree.json --registries registries.yaml   # какие есть точки входа
docpipe business new bp.valuation.eod --title "Переоценка"                  # завести процесс
docpipe business build  artifacts/doc-tree.json --config docpipe.yaml       # собрать связь с кодом
docpipe business lint   artifacts/doc-tree.json --config docpipe.yaml       # что сломано и сколько ещё писать
docpipe business status artifacts/doc-tree.json --config docpipe.yaml       # что разошлось с реализацией
```

Как вести бизнес-документацию — [`docs/business-layer.md`](docs/business-layer.md)
и [`docs/entry-guide.md`](docs/entry-guide.md),
образец каталога — [`business.example/`](business.example/).

## Как этим пользоваться

### Установка

```bash
uv sync
uv run docpipe --help
```

.NET SDK не требуется: C# разбирается через `tree-sitter`, без сборки проекта.
Достаточно, чтобы исходники лежали на диске.

### Первый прогон

```bash
uv run docpipe scan --root /путь/к/репозиторию --out artifacts/doc-tree.json
```

Выводит что-то вроде:

```
Модулей: 671, узлов: 828. Записано: artifacts/doc-tree.json и artifacts/doc-tree.run.json
Внимание: 1 файлов разобраны с ошибками и не дали ни одного типа — см. parse_error_files в сидкаре.
```

Попробовать можно прямо на тестовом решении из этого репозитория:

```bash
uv run docpipe scan --root tests/fixtures/SampleSolution --out /tmp/dt.json
cat /tmp/dt.run.json          # статистика прогона
jq '.nodes[].doc_path' /tmp/dt.json
```

### Что получается на выходе

Два файла, и разделение между ними принципиально.

**`doc-tree.json` — манифест.** Не содержит ни одного недетерминированного поля:
ни времени, ни имени машины, ни абсолютных путей. Два прогона дают побайтово
одинаковый файл, поэтому его можно коммитить и смотреть в диффе.

```jsonc
{
  "schema_version": "1.1",
  "ruleset_version": "2026-07-30.1",
  "parser": { "tree_sitter": "0.26.0", "grammar_c_sharp": "0.23.5" },
  "modules": [
    { "id": "module:src/Sample.Pricing.Api/Sample.Pricing.Api.csproj",
      "name": "Sample.Pricing.Api", "domain": "Sample.Pricing.Api", "enrolled": true,
      "target_frameworks": ["net8.0", "net9.0"],
      "project_references": ["src/Sample.Common/Sample.Common.csproj"] }
  ],
  "nodes": [
    { "id": "type:src/…/Sample.Pricing.Api.csproj#…PricingController`0",
      "kind": "controller",
      "doc_path": "docs/modules/controllers/Sample.Pricing.Api/pricing-controller.md",
      "matched_rules": ["controller.aspnet"],       // все совпавшие правила, для аудита
      "endpoints": [{ "http_method": "GET", "route": "api/v1/Pricing/{id:guid}" }],
      "dependencies": [{ "target": "…IPricingService", "via": "constructor",
                         "confidence": "high" }],
      "signature_hash": "sha256:…",                 // контракт: без номеров строк и путей
      "impl_hash": "sha256:…",                      // тело: «переписано при том же контракте»
      "symbol": { "…": "полное описание типа: члены, базы, атрибуты, XML-doc" } }
  ]
}
```

**`doc-tree.run.json` — сидкар.** Всё недетерминированное плюс статистика:

```json
{ "generated_at": "…", "host": "…", "duration_seconds": 9.7,
  "stats": { "symbols": 8966, "documented": 828, "not_documented": 996, "undecided": 7142 },
  "parse_error_files": ["modules/…/CmsKitWebUnifiedModule.cs"] }
```

`parse_error_files` — файлы, где разбор дал ошибки и **ни одного** типа. Обычно это
директива препроцессора внутри выражения; больше этот случай ничем не виден.

### Флаги `scan`

| Флаг | Зачем |
|---|---|
| `--root PATH` | корень репозитория с исходниками (обязательный) |
| `--out FILE` | куда писать манифест; без флага берётся `out` из конфигурации |
| `--config FILE` | `docpipe.yaml`: что документировать и как группировать |
| `--rules FILE` | свой набор правил вместо `rules/dotnet.yaml` |
| `--jobs N` | разбор в N процессов. На ABP: 9,6 с → 4,9 с при `--jobs 4` |
| `--no-cache` | не использовать кэш разобранных файлов |
| `--scope DIR` | перестроить только эти каталоги (можно повторять) |
| `--from-manifest FILE` | откуда взять узлы вне скоупа; обязателен вместе с `--scope` |
| `--stats` | состояние решений и подсказки по правилам; **ничего не пишет** |
| `--fail-on-undecided` | код 1, если про какой-то тип решение не принято. Для CI |
| `--top N` | сколько строк показывать в каждом срезе `--stats` (по умолчанию 15) |
| `--dry-run` | дифф против существующего `--out`; **ничего не пишет** |

Остальные команды:

| Команда | Зачем |
|---|---|
| `symbols --root PATH` | какие именно символы остались без решения; инструмент отладки правил |
| `materialize MANIFEST` | создать или обновить документы по манифесту |
| `docs status MANIFEST` | что делать с каждым документом; вход агента шага 3 |
| `docs accept MANIFEST` | зафиксировать соответствие документа коду |
| `docs adopt MANIFEST` | перенести документ вручную |
| `docs owners MANIFEST` | владельцы документов и диагностика правил владения |
| `anchors list MANIFEST` | инвентаризация точек входа по реестрам платформы |
| `anchors explain MANIFEST REF` | всё, что известно про один якорь: реестр, реализация, узел |
| `business new ID --title …` | скелет бизнес-документа по выведенному из идентификатора пути |
| `business build MANIFEST` | пересобрать генерируемые блоки бизнес-документов |
| `business status MANIFEST` | что разошлось с реализацией; вход агента |
| `business lint MANIFEST` | восемь проверок каталога и отчёт «сколько ещё писать» |
| `business accept MANIFEST` | зафиксировать соответствие документа реализации |
| `diff OLD NEW [--format text\|json]` | что изменилось между манифестами |
| `validate MANIFEST` | схема плюс четыре инварианта; код 1 при нарушении |
| `stats MANIFEST` | состав готового дерева |
| `schema --out FILE` | JSON Schema из моделей |

Кэш включён по умолчанию и создаётся **внутри сканируемого репозитория**:
`<root>/.docpipe/cache/parse.sqlite`. Каталог стоит добавить в его `.gitignore`
(в этом репозитории он уже там). Если трогать чужое дерево нежелательно —
`--no-cache` или свой `cache_dir` в конфигурации.

Кэш не меняет результат, только время: на ABP тёплый прогон 2,8 с против 10,2 с
холодного. Попадание определяется хэшем содержимого, а не временем модификации,
поэтому checkout другой ветки его не сбивает.

### Что изменилось между прогонами

```bash
uv run docpipe diff artifacts/before.json artifacts/after.json
uv run docpipe diff before.json after.json --format json | jq '.[] | select(.change=="reclassified")'
```

Пять видов изменений: `added`, `removed`, `reclassified`, `moved`, `signature_changed`.
На узел приходится **одно**, самое существенное: смена вида влечёт и смену пути,
но сообщается именно смена вида — шагу 3 нужно переписать документ, а не перенести файл.

Основной сценарий — не правка кода, а правка правил. На ABP переход от набора
по умолчанию к настроенному дал `added: 1324, reclassified: 142, removed: 324`,
и по этому списку сразу видно, что сделало новое правило.

Код возврата всегда 0: наличие изменений не ошибка, команда для конвейера.

### Скоуп-режим: перестроить один модуль

```bash
uv run docpipe scan --root . --out artifacts/doc-tree.json          # полный прогон
uv run docpipe scan --root . --out artifacts/doc-tree.json \
    --scope src/Cf.Pricing.Api --from-manifest artifacts/doc-tree.json
```

Разбираются только файлы в скоупе, символы вне скоупа берутся из кэша, узлы вне скоупа
переносятся из прежнего манифеста. На ABP это **2,1 с вместо 10,2 с**, и `nodes`
совпадают с полным прогоном ровно.

Классификация при этом не страдает: тип из скоупа, наследующийся от базового класса
в непарсившемся модуле, сохраняет свой вид — ради этого и строится индекс символов.

**Честная граница режима.** Изменение **вне** скоупа он не увидит: если тип снаружи
поменял базовый класс, сущности внутри могли переклассифицироваться. Поэтому:

- скоуп — инструмент дев-цикла (крутить правила, смотреть на один модуль);
- источником истины в CI остаётся полный прогон;
- результат помечен `partial` в манифесте, чтобы это было видно и downstream, и ревьюеру.

**Режим работает только поверх тёплого кэша.** С пустым кэшем тип не «теряет часть
данных», а исчезает из документации целиком: цепочка наследования обрывается, ни одно
правило не совпадает. Команда предупреждает об этом в stderr.

### Проверка

```bash
uv run pytest -q                                    # 460 тестов
uv run docpipe schema --out schema/doc-tree.schema.json   # JSON Schema из моделей
```

## Настройка под конкретный проект

Настраивается **два** файла, и они отвечают на разные вопросы:

| Файл | Вопрос |
|---|---|
| `docpipe.yaml` | что документировать и как группировать — своё для каждого проекта |
| `rules/dotnet.yaml` | что считать контроллером, сервисом, воркфлоу — переносится между проектами |

Набор правил по умолчанию намеренно консервативен. На чужом коде он покрывает **1–9 %**
типов: 7 % на eShopOnWeb, 9 % на ABP, 2 % на semantic-kernel, 1 % на OpenTelemetry.
Это исходное состояние, а не дефект — словарь «контроллер / сервис / провайдер /
репозиторий» описывает прикладной код, а не SDK. Настройка и состоит в том, чтобы
заменить этот словарь на словарь вашего проекта.

**Цель настройки — не «классифицировать всё».** Про каждый тип нужно принять одно
из трёх решений, и два из них означают «документа не будет»:

| Решение | Где записывается |
|---|---|
| не наша область | `enrolled` в `docpipe.yaml` |
| наше, но документировать нечего | `exclude` в `rules/dotnet.yaml` — с причиной |
| наше и документируем | правило в `rules/dotnet.yaml` |

Настройка закончена, когда типов без решения не осталось. Ровно это и показывает
последняя строка отчёта.

### Шаг 0. Прогнать как есть и посмотреть на состояние решений

```bash
uv run docpipe scan --root . --stats
```

Команда ничего не пишет — она для цикла настройки. Первый блок:

```
Решения по 8966 символам:

  документируем                874  7 видов
  не документируем             996  4 решения
  ------------------------------------
  РЕШЕНИЕ НЕ ПРИНЯТО          7096  <- это и есть работа
```

Значима последняя строка: пока она не ноль, словарь проекта не описан. Когда там ноль,
`scan --fail-on-undecided` начинает держать это состояние в CI — и новый тип
в репозитории, про который решения нет, роняет сборку вместо того, чтобы растворяться
в большой цифре.

### Шаг 1. Посмотреть, за что зацепиться

Отчёт печатает пять срезов по тем типам, про которые решения нет: модули, окончания
имён, базовые типы с учётом наследования, атрибуты, namespace. На ABP это выглядит так:

```
  окончания имён:              базовые типы:
     658  Module                  997  Volo.Abp.DependencyInjection.ITransientDependency
     365  Extensions               658  Volo.Abp.Modularity.IAbpModule
     147  Manager                  775  IDisposable
```

Отсюда сразу видно и что документировать (658 модулей ABP — это архитектурная сущность),
и что документировать не надо (`Extensions`, `IDisposable`).

**Срезы считаются по-разному, и это легко прочитать неверно.** «Модули», «окончания
имён» и «namespace» дают ровно одну строку на тип — их суммы равны числу нерешённых.
«Базовые типы» и «атрибуты» дают по несколько строк на тип, потому что у типа
и базовых типов, и атрибутов бывает много: их суммы больше, и проценты по ним считать
нельзя. В каждом срезе показан топ-15, а не весь список.

### Шаг 1а. Посмотреть, что это за типы

Срез говорит «6 в этом проекте, 4 не опознаются по имени», но не говорит, **что это
за типы**. Когда настройка доходит до одного проекта, нужно именно это:

```bash
uv run docpipe symbols --root . --module Sbt.Cashflow.Grid.Services.AutoConclusionService
```

```
6 символов  ·  решение не принято  ·  модуль ~ Sbt.Cashflow.Grid.Services.AutoConclusionService

Sbt.Cashflow.Grid.…AutoConclusionService.StandardProcessingFactory
  class, public sealed
  где             src/…/StandardProcessingFactory.cs:12
  прямые базы     IProcessingFactory
  замыкание       IProcessingFactory, IDisposable
  атрибуты        Serializable
  public члены    Create, CreateAsync, Reset
  решение         решение не принято
```

Печатается ровно то, по чему пишется предикат: замыкание наследования, атрибуты,
публичные члены, путь. Дальше — либо правило классификации, либо отсев с причиной.

Фильтры: `--state` (по умолчанию `undecided`, ещё `not_documented`, `documented`,
`not_enrolled`, `interface_covered`, `any`), `--module`, `--namespace`, `--rule`,
`--kind`, `--limit`, `--format json`.

И обратная проверка — что новое правило поймало то, что задумано:

```bash
uv run docpipe symbols --root . --state documented    --rule cf.distributed-handler
uv run docpipe symbols --root . --state not_documented --rule generated.schemas
```

`--rule` работает для обеих секций, и на классифицированных показывает правила,
которые совпали, но **не** победили: так видно, почему выиграло не то, что ожидалось.

### Шаг 1б. Записать решения «не документируем»

Отсев без причины — это снова безымянное число. Поэтому каждое решение несёт `reason`,
и отчёт показывает, сколько типов отсеяно каким решением:

```
Не документируем — по какому решению:
    1478  generated.schemas   Сгенерировано по XSD сервисных контрактов
     826  data.contracts      Контракт передачи данных: смысл в вызывающем коде
```

Условия — те же десять предикатов, что в правилах классификации, поэтому генерат,
опознаваемый только атрибутом, отсекается здесь, а не подгонкой шаблона пути:

```yaml
exclude:
  require_public: true
  rules:
    - id: generated.schemas
      reason: "Сгенерировано по XSD сервисных контрактов: документ был бы пересказом схемы"
      priority: 100
      when:
        any:
          - attribute: ["GenerateCode"]
          - namespace_regex: [".*\\.Services\\.Schemas\\..*"]
```

Краткая форма из четырёх полей (`path_glob`, `name_regex`, `type_kind_deny`,
`require_public`) продолжает работать и складывается с `rules:` — дописать решения можно,
ничего в ней не меняя. В отчёте её решения подписаны общими формулировками.

Смотрите на эту таблицу ещё по одной причине: широкое решение с причиной «разберусь
потом» обнулит нерешённое, ничего не решив, и заметно это только здесь — по решению
с неправдоподобно большим счётчиком. Что именно оно поймало, покажет
`symbols --state not_documented --rule <id>` из шага 1а.

### Шаг 2. Enrollment: что вообще входит в документацию

Первый и самый крупный рычаг. На semantic-kernel половина неклассифицированного —
тесты, примеры и conformance-наборы:

```
По каким модулям:
   233  Concepts                 (примеры)
   164  IntegrationTests
   135  SemanticKernel.UnitTests
    70  VectorData.ConformanceTests
```

Ничего из этого документировать не нужно. В `docpipe.yaml`:

```yaml
enrolled:               # список только положительный: отрицаний нет,
  - "src/**"            # нужные каталоги перечисляются явно
  - "modules/*/src/**"
```

Глоб сравнивается с путём `.csproj`, поэтому `"src/**"` включает всё под `src/`,
а тесты в `tests/` не попадают. Если тесты лежат вперемешку с кодом, перечислите
продуктовые проекты явно — по одному глобу на группу.

**Важно: неenrolled ≠ неразобранный.** Тестовые проекты всё равно парсятся — их символы
нужны графу наследования, — но документов не порождают. Если исключить их через
`exclude.path_glob`, наследование через них порвётся.

#### Чужой код внутри репозитория: `exclude` в `docpipe.yaml`

`enrolled` управляет составом документации, но обход всё равно заходит всюду. Когда
внутри репозитория лежит код, который не имеет отношения к продукту, — сам инструмент,
положенный в дерево, вендоренные зависимости, выгрузки — его исключают на уровне обхода:

```yaml
exclude:
  - "docs/**"           # внутри лежит docpipe со своим .venv
  - "third_party/**"
```

Три похожих понятия, которые легко перепутать:

| | что делает | символ в индексе |
|---|---|---|
| `enrolled` в `docpipe.yaml` | что документируем | остаётся |
| `exclude` в `rules/dotnet.yaml` | что не документируем, но читаем | остаётся |
| `exclude` в `docpipe.yaml` | куда не заходим вовсе | **исчезает** |

Последнее означает, что наследование через исключённый код рвётся — это цена за то,
чтобы не читать чужое дерево. Для тестов и вспомогательного кода правильный
инструмент — первые два, для постороннего — третий.

Заданные шаблоны **складываются** со встроенными `**/obj/**`, `**/bin/**`, `**/*.g.cs`,
а не замещают их: иначе одна строка в конфигурации молча вернула бы `obj/` в документацию.

**Шаблон обязан заканчиваться на `/**`.** `"docs"` совпадёт с самим каталогом, но не
с файлами под ним, — и будет выглядеть работающим.

### Шаг 3. Исключения: что отсеять внутри enrolled

Секция `exclude` в `rules/dotnet.yaml` работает **до** правил. Форма записи — в шаге 1а;
здесь про то, что в неё писать.

**Главный рычаг здесь — `require_public`.** Теперь эти цифры показывает сам отчёт,
в таблице «не документируем — по какому решению». Замер, какая причина срабатывает чаще:

| | главная причина исключения |
|---|---|
| eShopOnWeb | `name_regex` — 28 из 36 |
| ABP | `name_regex` — 508 из 996 |
| OpenTelemetry | **`require_public`** — 463 из 535 |
| semantic-kernel | **`require_public`** — 1203 из 1492 |

В библиотечном коде `internal`-реализаций много, и `require_public: true` убирает
половину типов. В прикладном на первое место выходит отсев Dto/Request/Response.
Решите, документируете ли вы внутренние типы, — это переключатель на одну строку:

```yaml
exclude:
  require_public: true        # false, если внутренняя кухня тоже нужна
  name_regex:
    - "^.*Dto$"
    - "^.*Options$"
    - "^.*Tests?$"            # тесты — см. ниже
    - "^.*Cf.*Message$"       # добавьте свои конвенции
  type_kind_deny: ["enum"]
  path_glob:
    - "**/Migrations/**"
    - "**/test/**"
    - "**/tests/**"
    - "**/*Tests/**"
```

**Про тесты отдельно.** Правила по имени типа (`^.*Tests?$`) **недостаточно**, и это
неочевидно. Само по себе оно отсеивает ноль узлов на всех четырёх проверочных
репозиториях: класс `PricingServiceTests` не оканчивается ни на `Service`, ни на
`Controller`, то есть и так не проходит ни одно правило классификации.

Реальный шум идёт из вспомогательных типов **внутри** тестовых проектов — они названы
как продуктовые и классифицируются на общих основаниях:

```
AuditTestController                            → controller
AuthorizationTestPermissionDefinitionProvider  → provider
```

На ABP таких **104 узла из 828**. Отсекает их только `path_glob` по каталогам тестов.
С обоими правилами: ABP 828 → 694, OpenTelemetry 10 → 7, semantic-kernel 69 → 67.

Оба правила уже в наборе по умолчанию. Два замечания:

- `^.*Tests?$` покрывает и `*Test`, и `*Tests`; вторая форма встречается на порядок чаще
  (в ABP 777 против 54);
- если в вашей предметной области «тест» — бизнес-понятие, правило нужно сузить.
  Для финансового моделирования это реально: `StressTest`, `BackTest` — настоящие
  сущности, а не юнит-тесты.

#### Каталог, где нужен один вид типов: `unless`

Частый случай: в каталоге лежат сервисы, которые надо документировать, и вокруг
них опции, расширения и хелперы, которые не надо. Приоритет здесь не поможет —
и это стоит понять до того, как настраивать:

**`exclude` — стадия до правил, а не участник соревнования с ними.**
`classify()` сначала спрашивает `is_excluded()` и при истине выходит,
не дойдя до `rules`. Поэтому `priority: 1000` у правила классификации не отменит
исключающее правило с `priority: 0`: их приоритеты не сравниваются никогда.
`priority` ранжирует **внутри** стадии — в `exclude` выбирает, чья причина
попадёт в отчёт, в `rules` выбирает вид.

Отсюда два следствия. Первое: **чтобы тип не документировался, исключать его
не обязательно** — узел создаётся только при совпадении с правилом из `rules`,
остальное просто не порождает документов. `exclude` нужен, чтобы такой тип
попал в `not_documented` с причиной, а не в `undecided`.

Второе: исключив каталог целиком, вы теряете и нужные типы. На это есть
`unless` — вырез внутри решения об отсеве:

```yaml
exclude:
  rules:
    - id: grid.support
      reason: "Вспомогательные типы каталога сервисов: контракта не несут"
      priority: 50
      when:
        path_glob: ["src/Grid/**"]
      unless:
        inherits: ["GridService"]
```

Правило совпадает, когда `when` истинно **и** `unless` ложно. Читается
построчно: «исключаем каталог, кроме наследников `GridService`». Причина
остаётся одна на всю группу — отчёт `--stats` не дробится.

Это единственная форма отрицания в движке, и она узкая намеренно. Общего `not`
внутри дерева условий нет: он превращает набор в систему уравнений, которую
нельзя прочитать построчно. `unless` же привязан к одному правилу и описывает
исключение из **его** группы.

Пустой `unless` — ошибка загрузки: это недописанное правило, а не «исключений
нет», и молча оно вело бы себя как обычный отсев.

### Шаг 4. Правила: словарь сущностей проекта

Правило — это `when`-условие плюс `kind`, `template` и `priority`:

```yaml
- id: ignite.service
  kind: ignite_service
  template: ignite-service
  priority: 95
  when:
    all:
      - type_kind: ["class", "record"]
      - inherits: ["IService", "Apache.Ignite.Core.Services.IService"]
```

Десять предикатов, комбинируются через `any` / `all` любой вложенности:

| Предикат | Против чего матчится |
|---|---|
| `attribute` | имена атрибутов типа |
| `base_type` | прямые базовые типы |
| `inherits` | **всё замыкание** наследования — работает через свой базовый класс из другого модуля |
| `name_suffix`, `name_regex` | имя типа |
| `namespace_regex` | namespace |
| `path_glob` | пути исходников |
| `type_kind` | `class`, `interface`, `struct`, `record`, `record_struct`, `enum` |
| `modifier` | `public`, `sealed`, `abstract`, `partial`, … |
| `has_member_with_attribute` | атрибуты членов — так ловятся контроллеры без `[ApiController]` |

Практические соображения:

**Начинайте с самого частого.** Одно правило на `inherits: ["ITransientDependency"]`
покрыло бы 997 типов ABP — больше, чем весь набор по умолчанию.

**`inherits` сильнее `base_type`.** Первый смотрит на всё замыкание наследования, поэтому
правило `inherits: ["ControllerBase"]` срабатывает и на контроллере, который наследуется
от вашего собственного `BaseApiController` в другом модуле. Это работает и через границу
проекта — ради этого и строится индекс символов.

**Приоритеты решают, `matched_rules` объясняет.** Когда совпало несколько правил,
побеждает больший `priority`, но в узел записываются **все** совпавшие. Если тип
классифицирован не так, как ожидалось, — смотрите туда:

```bash
jq '.nodes[] | select(.title=="RiskComputeService") | {kind, matched_rules}' artifacts/doc-tree.json
# { "kind": "ignite_service", "matched_rules": ["ignite.service", "service"] }
```

**Порядок правил в файле ничего не значит.** При равном приоритете побеждает
лексикографически меньший `id` — иначе перестановка строк в YAML меняла бы манифест.

**Опечатка в предикате роняет загрузку сразу.** `attribut` вместо `attribute` — это
ошибка при старте, а не молча не срабатывающее правило.

### Шаг 5. Домены: как сгруппировать модули

Домен — это смысловая группировка поверх проектов, по ней потом строится навигация:

```yaml
domains:
  "src/Cf.Pricing.*/**": "pricing"
  "src/Cf.Risk.*/**": "risk"
  "src/Cf.Common.*/**": "platform"
```

Проверяется первый совпавший glob **в лексикографическом порядке ключей**, а не в порядке
записи. Без совпадения доменом становится имя модуля.

### Шаг 6. Проверить, что получилось

```bash
uv run docpipe scan --root . --out artifacts/doc-tree.json
uv run docpipe validate artifacts/doc-tree.json    # схема плюс четыре инварианта
uv run docpipe stats artifacts/doc-tree.json       # состав получившегося дерева
```

`validate` падает с кодом 1, если два узла претендуют на один документ, если
повторяются идентификаторы или если разбор какого-то файла сломался так, что тип
исчез целиком. Предупреждения (например, тип в нескольких файлах без `partial`)
идут в stderr, но код возврата не меняют.

На что смотреть:

- **«решение не принято» дошло до нуля** — словарь описан, и состояние можно
  закрепить в CI: `scan --fail-on-undecided`;
- **`parse_error_files` не пуст** — там файлы, где разбор сломался и тип пропал целиком
  (обычно `#if` внутри выражения). Их надо посмотреть глазами: доля растёт
  с мультиплатформенностью, от 0 % при одном TFM до 8,7 % в OpenTelemetry;
- **дубли `doc_path`** — их быть не должно, но если появились, значит два типа
  претендуют на один документ.

### Что стоит проверить в своём репозитории заранее

Три известные границы подхода. Проверяются одной командой каждая:

```bash
# 1. Общий код, подключённый ссылкой на файл, а не отдельным проектом.
#    Такие файлы не принадлежат ни одному модулю и в документацию не попадают.
#    На OpenTelemetry и semantic-kernel это 5 % типов.
grep -rl "Compile Include" --include=*.csproj . | head

# 2. Подстановки MSBuild в путях. Ссылки между проектами дорезолвливаются
#    по имени файла, а вот TargetFramework через цепочку props достать нечем.
grep -rho 'TargetFrameworks*>[^<]*' --include=*.csproj . | grep '\$(' | head

# 3. Плотность условной компиляции. Чем больше целевых платформ,
#    тем чаще #if стоит внутри выражения и ломает разбор.
grep -rc "^#if" --include=*.cs . | awk -F: '$2>0' | wc -l
```

Подробности и цифры — в [`docs/findings-stress.md`](docs/findings-stress.md).
Чек-лист под АС CF со всеми решениями, которые предстоит принять, — в [`CASHFLOW.md`](CASHFLOW.md).

## Как это работает

Парсинг выполняется грамматикой `tree-sitter-c-sharp` вместо Roslyn. Проверено на четырёх
реальных репозиториях — eShopOnWeb, ABP, OpenTelemetry и semantic-kernel: **11 850 файлов,
941 проект, ноль падений**. ABP целиком (671 проект, 3,9 ГБ) разбирается за 8 секунд;
Roslyn потребовал бы .NET SDK и `restore` всех проектов, то есть минуты вместо секунд.

Семантики tree-sitter не даёт, но для построения **структуры** она почти не нужна:
классификация идёт по атрибутам, именам базовых типов и конвенциям имён — это синтаксис.
Недостающее (цепочки наследования внутри решения) достраивается по индексу символов.

Артефакт шага — манифест `doc-tree.json`, не содержащий **ни одного** недетерминированного
поля. Метаданные прогона вынесены в сидкар `doc-tree.run.json`, поэтому проверка
воспроизводимости сводится к побайтовому сравнению файлов.

## Разработка

Полная проверка перед коммитом:

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy docpipe && uv run pytest -q
```

Конвенции и подводные камни для тех, кто продолжает работу, — в [`CLAUDE.md`](CLAUDE.md).

## Проверочные репозитории

`examples/` содержит склонированные .NET-проекты для проверки на реальном коде
(`eshoponweb`, `abp`, `opentelemetry-dotnet`, `semantic-kernel`). Каталог в репозиторий **не входит** — тесты обязаны быть
самодостаточными и опираться только на фикстуры.

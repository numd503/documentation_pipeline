Указания для работы над этим репозиторием. Общее описание проекта — в [`README.md`](README.md).

## Что здесь происходит

Реализуется `docpipe` — пайплайн документации. Шаг 1 (**детерминированное** построение
дерева по исходникам .NET), шаг 2 (материализация документов, статусы, приёмка),
бизнес-слой (B01–B11: реестры, каталог процессов, `business_hash`, линт, приёмка),
шаг `web` (F01–F19: разбор Angular, связь фронт↔бэк, якорь страницы) и страница
как единица документации (P01–P12: граф вызовов, ручной состав, документ-агрегат)
закончены. Шаг 3 (наполнение агентом) не начат. Работа ведётся по плану,
а не свободно.

**Порядок работы над задачей:** прочитать её раздел в плане → реализовать → прогнать её
команду проверки → обновить журнал (включая трудности и отклонения) → при расхождении
плана с реальностью **править план**, а не молча обходить.

Реализовывать план будет более слабый агент в другой среде. Поэтому каждая найденная
ловушка должна попадать в план с объяснением, иначе он наступит на неё снова.

## Жёсткие правила

**Детерминизм — не пожелание, а проверяемое свойство.** Один и тот же вход обязан давать
байт-в-байт одинаковый выход.

- Любой список в выводе — через явный `sorted()` с явным `key`.
- Порядок обхода ФС **никогда** не используется как источник порядка.
- В `doc-tree.json` не должно быть ни одного недетерминированного поля: ни времени,
  ни хоста, ни абсолютных путей. Всё это идёт в сидкар `doc-tree.run.json`.
- Пути — репо-относительные, POSIX-разделители, даже на Windows.
- Разрешение коллизий — по хэшу ключа, никогда по порядку вставки.

**FQN — не уникальный ключ.** Проверено на ABP: 255 коллизий на 9075 объявлений.
Ключ символа — `модуль + FQN + арность дженерика`, и даже он оставляет остаток
(файлы, не компилируемые вместе, — `Platforms/iOS/` против `Platforms/MacCatalyst/`).
Хэш-суффикс от FQN не разводит ничего там, где FQN совпадает.

**`signature_hash` не включает номера строк и пути.** Иначе переформатирование файла
заставит агента на шаге 3 перегенерировать документ впустую, и вся экономия от
инкрементальности пропадёт.

**Тесты самодостаточны.** `examples/` в репозиторий не входит — опираться на него в тестах
нельзя. Реальные конструкции воспроизводятся в `tests/fixtures/` или в `tmp_path`.

## Ловушки, проверенные на реальном коде

Каждая из них однажды прошла бы все критерии приёмки и сломалась бы в проде.

**`fnmatch` не понимает `**` как «ноль или больше сегментов».** `**/obj/**` не ловит
`obj/x.cs` в корне, `**/*.g.cs` не ловит `Foo.g.cs` там же. Использовать
`discovery.matches_glob`, а не `fnmatch` напрямую.

**Базовые типы бывают многострочными:**
`class X : EndpointBaseAsync\n  .WithRequest<A>\n  .WithActionResult<B>`. Нормализуются
двумя шагами (`\s+` → ` `, затем `\s*\.\s*` → `.`) в `parser.normalize_type_text`.
Без второго шага остаётся `X .WithRequest<A>` — не канонический C#.

**Модификаторы и атрибуты — потомки узла объявления, а XML-doc — предшествующие соседи.**
Асимметрия неочевидная и ловит на ней всех.

**Директивы препроцессора — самая злая находка ABP:**
- `#if` — **контейнер**: члены под ним не являются прямыми детьми `declaration_list`.
  Реализация, перебирающая прямых детей тела, потеряет их молча;
- `#region` — плоский маркер, не контейнер. Асимметрия неочевидная;
- `#if` **внутри выражения** рвёт разбор. Мест много: аргументы атрибута, fluent-цепочка,
  модификатор объявления, базовый список, шаблон в pattern matching. Атрибут —
  потомок объявления, поэтому вместе с ним ломается и объявление: остаток файла
  переразбирается как top-level statements, и тип исчезает из вывода целиком.
  Обойти нельзя. Единственный признак — `parse_errors > 0` при пустом списке объявлений;
  ловить это обязан `validate` (T20). Фикстура: `WildSolution/…/Modules/ConditionalModule.cs`.

**`.csproj` и решения в реальных проектах:**
- сохранены с BOM — читать байтами, `read_text(encoding="utf-8")` уронит `ET.fromstring`
  (в ABP с BOM и 72 % файлов `.cs`);
- обычно **не объявляют** `TargetFramework` (в eShopOnWeb — 0 из 10), он приходит из
  `Directory.Build.props` / `Directory.Packages.props` выше по дереву;
- проекты legacy-формата объявляют `xmlns` — сравнивать только по локальному имени тега;
- `<TargetFrameworks>` может содержать неразвёрнутое `$(TargetFrameworks)` — отбрасывать;
- имена проектов **не уникальны** (в ABP 39 повторов), поэтому `id` модуля и
  `project_references` строятся от путей, а не от имён;
- решение может быть в формате `.slnx` (XML, VS 17.10+): в ABP их 30, в OpenTelemetry 1,
  и в обоих `.sln` — ноль; semantic-kernel держит оба формата сразу;
- `Include` в `ProjectReference` часто собран из подстановок MSBuild (`$(RepoRoot)\…`).
  Склеивать такое с каталогом проекта **нельзя** — получится выдуманный путь, который
  выглядит настоящим. Дорезолвливает `csproj.resolve_references` по имени файла.

**`Program.cs` в современном .NET — top-level statements**, без класса и метода.
Поиск DI-регистраций обязан идти по всему дереву файла, а не внутри `method_declaration`.

**Версия API tree-sitter — 0.25+.** `Query(LANG, src)` + `QueryCursor(q).captures(node)`,
возвращающий `dict[str, list[Node]]`. Старые формы `LANG.query(...)` и
`query.captures() -> list[tuple]` не работают.

## Ловушки фронта, проверенные на реальном коде

Грамматика TypeScript ломает почти все привычки, вынесенные из C#. Каждая
из этих форм однажды прошла бы приёмку и дала бы неверный результат молча.

**Декоратор — сосед объявления, а не потомок, и это инверсия правила C#.**
У неэкспортируемого класса `decorator` лежит **внутри** `class_declaration`,
у экспортируемого — **рядом** с ним в `export_statement`, у члена класса —
предшествующим соседом в `class_body`. Три формы, и собирать надо все три:
в Angular экспортируется всё, что имеет декоратор, поэтому реализация,
перенесённая с .NET буквально, не классифицирует **ни одного** компонента
при нулевом числе ошибок разбора.

**JSDoc — сосед `export_statement`, а не объявления.** Комментарий стои́т перед
словом `export`, снаружи узла. Обход предыдущих соседей `class_declaration`
находит его только у неэкспортируемых классов, и выглядит это как случайность
в данных: у половины символов описание есть, у половины нет.

**Списки захватов `QueryCursor.captures()` между собой не выровнены.**
На одном запросе `@method` пришёл в порядке `[innerDebtsSnapshot, get, post, …]`,
а `@call` — в другом; `zip` даёт пары, которых в коде нет. Брать один ключ
и спускаться от узла.

**Три клаузы наследования устроены по-разному.** У `extends` класса дженерик
лежит отдельным полем узла (`value` + `type_arguments`), у `implements`
и у `extends` интерфейса — внутри типа. Единый обход отдаёт `Base` вместо
`Base<T>` ровно у одной клаузы из трёх.

**`tsconfig.json` — это не JSON.** И `ng new`, и `nx` генерируют его
с комментариями, а руками дописывают `//` и висящие запятые; `json.loads`
на таком файле бросает исключение. Без разбора JSONC не читается ни один боевой
`tsconfig`, а с ним не разрешается ни один импорт вида `@shared/…`. Комментарии
вырезать сканером: `//` внутри `"http://host"` регулярное выражение примет
за начало комментария.

**`paths` дочернего `tsconfig` замещает родительский целиком**, а не дополняет.
Слияние даёт набор алиасов, которого у компилятора нет, — то есть резолв,
расходящийся со сборкой.

**Счётчик `.get(`/`.post(` без получателя меряет не то.** `Map.get`,
`form.get('search')`, `headers.get(…)`, `queryParams.get(…)` — на боевом модуле
таких 327 против 79 настоящих, и отношение «литералов ко всем вызовам»,
посчитанное по ним, бессмысленно, а выглядит убедительно.

**Дерево роутов собирается спредом импортированного массива**, а не `loadChildren`.
В боевом модуле `loadChildren` — ноль, `RouterModule.forRoot/forChild` — ноль,
а 26 записей `path:` разложены по `routesPath/*.ts`. Разбор одного `app.routes.ts`
даёт два пути из двадцати шести, и молча.

**`() => import('./x').then(m => m.ROUTES)` — это две стрелки.** Тело внешней —
`import(…).then(…)`, у которого свойство называется `then`. Реализация, берущая
первое попавшееся свойство, подставит `then` и в имя таблицы, и в имя компонента.

**Вид `page` не выдаётся правилом, и без источника маршрута его нечем объяснить.**
Правило говорит «компонент», страницей класс делает повышение по таблице роутов
(`web/tree.py`), а таблица собирается межфайлово. Поэтому `scan --stats` и `symbols`
на вопрос «почему этот класс — страница» не отвечают в принципе, а в записи маршрута
обязаны быть `source` и `table`: `/models/loader/quiz` объявлен не в `app.routes.ts`,
через который до него доходит обход. Показывает это `docpipe web pages`, и он же
называет два случая, которые иначе молчат: страницу, у которой все записи
`route_unresolved` (вид есть, якорь поставить нельзя), и вызовы, которых не видно,
потому что поход за данными идёт через `dispatch`, а не через конструктор.

**«Страница внедрила сервис» и «страница зовёт метод» — разные утверждения.**
На боевом модуле первое давало `ForecastComponent` 51 эндпоинт, а 43 эндпоинта
из 61 приезжали ровно на четыре страницы разом: сервис на тридцать методов зовут
ради двух. Поэтому состав страницы считается по графу вызовов (`Usage`), где ребро
— это «член зовёт член», а вызовы берутся только из позванного члена. Список
по внедрению остаётся рядом второй величиной: разница между ними и есть мера.

**Цепочка `dispatch(new X())` → `@Action(X)` → сервис — единственный путь к данным
у половины экранов.** Звено лежит в манифесте: у члена стейта записан атрибут
`Action` с именем класса экшена. Три формы, каждая из которых даёт ноль при
наивном разборе: массив в `dispatch`, один экшен на два стейта (законно в NGXS),
две формы выборки (`@Select` и `store.select`). Тип экшена живёт на **ребре**,
а не на вызове: тот же метод сервиса зовут и обработчик, и компонент напрямую.

**Один маршрут на много смыслов.** `api/items/query` с `listInnerName` в теле
и `api/items?listInnerName=…` в query — четырнадцать вызовов в один эндпоинт
платформы, различающихся значением параметра. Ключ «метод + маршрут» склеит
обращения к пользователям, к моделям и к справочникам в одну точку. Различитель
идёт в ключ вызова, но **не** участвует в сопоставлении с эндпоинтом.

**Файл правил секционный: `dotnet` и `web` в одном файле.** Секцию называет
вызывающий (`load_ruleset(path, section)`), и умолчания у неё нет: плоский файл
старого формата, прочитанный шагом `web`, дал бы правила .NET на TypeScript —
следующая ловушка ровно про это. Поэтому плоский файл — отказ с командой переноса
(`tools/migrate_rules.py`, перенос текстовый и сохраняет комментарии), а не
молчаливый разбор. `version` живёт снаружи секций, `ruleset_version` — внутри
каждой.

**`require_public: true` отсеивает весь фронт.** У TypeScript модификатора
`public` на уровне объявления нет вовсе: видимость задаётся словом `export`.
Значение, перенесённое из секции `dotnet`, даёт пустое дерево без единого
сообщения об ошибке.

**`sourceRoot` в `project.json` задан относительно корня nx-workspace**, а не
относительно проекта. Склейка с каталогом проекта даёт правдоподобный
и несуществующий путь, а файлы модуля остаются ничьими.

## Классификация: решение, а не «покрытие»

**Про каждый символ должно быть принято решение, и «не документируем» — тоже решение.**
Три исхода: `<kind>` (правило классификации), `not_documented` (отсев с обязательной
причиной), `undecided` (решения нет). Последнее — единственное число, которое обязано
идти к нулю, и единственное, по которому видно, что настройка набора закончена;
`--fail-on-undecided` держит это в CI. Пока «не решено» смешивалось с «решено не
документировать», отчёт не мог отличить «ещё не смотрели» от «посмотрели и решили»,
и появление нового типа в репозитории в большой цифре не выделялось.

**Отсев без `reason` запрещён.** Иначе «не документируем 4820» — снова безымянное
число, ради которого и переделывался отчёт. Причина обязательна на уровне загрузки.

**Гранулярность решения — группа, а не символ.** Перечислять FQN нельзя: список
сломается на первом переименовании и создаст работу там, где смысл не менялся. Довод
тот же, что у якорей бизнес-слоя.

**Атрибуция решения — по `priority`, затем по `id`, никогда по порядку в файле.**
Иначе перестановка двух правил в YAML меняет цифры отчёта, а они идут в журнал и в CI.

**Краткая форма `exclude` из четырёх полей обязана продолжать работать.** Её копия
лежит на боевом репозитории АС CF; форма разворачивается в правила с зарезервированным
префиксом `exclude.` и складывается с `rules:`. `require_public` остаётся полем:
отрицания в движке правил нет, и «не public» предикатами не выражается.

## Шаг 2: правила, которые ломаются молча

**Раскладка `doc_path` на коллизии не влияет.** `kind-first` и `module-first` —
перестановка одной тройки (модуль, вид, slug), каждая однозначно определяется
тройкой, поэтому за файл узлы спорят в них одновременно (на ABP — одни и те же
19 путей на 47 узлов). Дубли разводит то, что имя модуля **входит** в путь, а не
порядок сегментов. Спор о «более безопасной раскладке» уже был один раз и стоил
захода: `docs/findings-eshoponweb.md` утверждал обратное и был неправ.

**Зоны документа. Затирается только то, что принадлежит инструменту.** Ключ `docpipe:`
и генерируемый блок пересобираются всегда; секции, чужие ключи front matter и всё
остальное в теле — **никогда**. Инвариант, на котором это стоит:
`assemble(parse_document(t)) == t` байт в байт.

**Слои различаются по `docpipe.schema`, а не по наличию ключа `docpipe`.** Формат зон
у шага 2 и бизнес-каталога общий. Отбор по ключу перепутает их в обе стороны: каталог
станет сиротами шага 2, документы шага 2 — битыми бизнес-документами.

**`is_section_empty` — самая дорогая функция шага 2.** Ошибка в сторону «не пусто»
заставит агента счесть всё дерево написанным. Отсюда правило: подсказки в шаблонах —
только HTML-комментарии.

**Сравнение «писать или нет» — по нормализованному тексту, а не по байтам.** Иначе
на репозитории с `core.autocrlf=true` каждый документ окажется изменённым при каждом
прогоне. Действие «без изменений» не открывает файл на запись вовсе.

**Всё, что мешает надёжно прочитать состояние, — отказ, а не самолечение.** Единственный
экземпляр принятых хэшей живёт в самом документе. Испорченный документ не переписывается
даже тогда, когда узел на его пути выглядит «без файла».

**Статус документа и действие с файлом — независимые вещи.** `status` про содержимое,
`file_action` про запись, и документ со статусом `current` и решением `skip` переписывается,
когда сменился владелец или домен: это поля проекции. Пока наружу выходил только статус,
на вопрос «что именно перепишет прогон» ответа не было ни в одном отчёте, а `current`
вместе с ним молча исчезал из подробного списка. Теперь действие — колонка в `docs status`,
поле `file_action` в его JSON и в очереди (формат 1.1), флаг `--file-action` и отдельная
команда `docs explain ПУТЬ` для одного документа.

**`missing` означает «файла нет», а не «обход его не вернул».** Разница стоит документа:
`missing` → `create` → запись поверх существующего файла без копии, с «создано: 1»
в отчёте. Выпасть из обхода можно пятью способами (BOM или иная форма `---` не первой
строкой, front matter без `docpipe.schema`, `docs_scan_exclude`, каталог за симлинком —
`rglob` в такие не заходит, права на файл), и шестой появится сам. Поэтому проверка
не перечисляет причины, а спрашивает диск: `shadowed_docs` сверяет узлы без файла
с `is_file()`, совпало — `refuse`/`broken` и `content=None`, чтобы и `--force`
не перезаписал. `docpipe docs explain МАНИФЕСТ ПУТЬ` называет, какой фильтр сработал.

**У отсева и у разбора один ответ на вопрос «это наш файл».** Дешёвая проверка первых
байт при обходе нужна (в `.venv` лежат `.md` на мегабайты), но она была строже разбора:
`read_document` читает `utf-8-sig`, а отсев сравнивал байты с `---` и выбрасывал
документ с BOM до него. Ловушка была обезврежена на уровень ниже и заново создана
уровнем выше — тест на BOM звал `read_document` напрямую и этого не видел.

**`docs_scan_exclude` умеет накрыть само дерево документов.** Пара `docs_root` +
`modules_dir` держит инвариант «пишем туда, где ищем» структурно, но исключения обходят
его с другой стороны: `docs_scan_exclude: ["docs/ml/**"]` из конфигурации поставки
отсекает все документы, как только `docs_root` уедет под `docs/ml`. Симптом — вечный
`missing` на всём дереве и перезапись каждым прогоном. Шаблоны сверяются с реальными
`doc_path` манифеста, находка блокирующая.

**Очередь шага 3 (`docpipe worklist`) — артефакт для чужого процесса, а `docs status` —
отчёт для человека.** Отсюда три свойства, которые ломаются молча: времени в файле нет
(иначе он меняется каждый прогон и его нельзя сравнить), сводка считается по **всему**
дереву при какой угодно суженной очереди (иначе `--team` объявит, что документов
двадцать), а пустая очередь — записанный файл с нулём записей, потому что отсутствие
файла означает «прогон не состоялся».

**Префикс `doc_path` — пара ключей `docs_root` + `modules_dir`, а не один путь.** При
паре инвариант «`materialize` пишет туда, где ищет `docs status`» держится структурно.
Одним значением его можно развести, и тогда каждый документ навсегда `missing`,
переписывается на каждом прогоне, и всё это без единого сообщения.

**Раскладка замерзает в манифесте, а конфигурация читается заново.** `doc_path`
собирается на шаге 1 из `docs_root` + `modules_dir` + `doc_layout`; шаг 2 берёт те же
ключи ещё раз, уже чтобы знать, где искать. Смена любого из трёх без повторного `scan`
не ломает ничего **видимо**: документы остаются на местах, а `worklist` кладёт в очередь
префикс из конфигурации — тот, которого в очереди нет. Сверка префикса роняет прогон;
полная карта ключей — в `docs/configuration.md`.

**Вход шага 2 собирает одна `_prepare`.** Копий было три (`materialize`, `docs status`
и она), и ключ, добавленный в одну, до остальных не доезжал. Писателем документов при
этом был `materialize` — та копия, где отставание заметили бы последней.

**`accept` берёт хэши из манифеста, а не из front matter.** Тот — зеркало и мог отстать;
приняв его значение, документ навсегда останется `current`, будучи `stale`.

**Приёмка идёт через тот же план и ту же запись.** Отдельный путь записи — это вторая
реализация слияния зон, и она разойдётся с первой на первом же документе с чужими
ключами front matter.

**Вход и цель записи разрешаются по-разному, и путать их нельзя.** Файлы, которые
инструмент **читает** (`rules`, `web.rules`, `templates`, `ownership`, `registries`),
идут через `config.resolve_input`: сначала от текущего каталога, потом от каталога
`docpipe.yaml`, выигрывает первый существующий. Конфигурация лежит не в корне
(на АС CF — `docs/ml/docspipe/`), и путь внутри неё пишут относительно неё же;
без второй ступени `scan` падал на «No such file or directory: 'rules.yaml'»,
а `business new` — на «Скелет не найден». Порядок ступеней обратным быть не может:
конфигурации в корне писались от текущего каталога, и смена приоритета не уронила
бы прогон, а молча взяла другой набор правил. Цели записи (`out`, `worklist`,
`web.out`, `web.link_out`) ступени не получают — угадывать, куда писать, нельзя.
Отсюда несимметричный случай: `web.out` **читает** `business build`, и ступени там
тоже нет, иначе один ключ разошёлся бы на две раскладки; вместо неё — предупреждение,
потому что «страниц ноль» иначе неотличимо от репозитория без фронта.

## Бизнес-слой: правила, из которых следует всё остальное

Полный план — в `docs/business-implementation-plan.md`, факты о боевом репозитории —
в `docs/findings-cashflow-registries.md`. Здесь четыре правила, нарушение которых
разваливает конструкцию целиком.

**Стрелка одна: техника ссылается на бизнес.** Бизнес-документ не знает ни `node_id`,
ни `doc_path`, ни FQN. Тогда рефакторинг физически не может его сломать: худшее, что
случается, — висящий якорь на технической стороне, и чинит его тот же PR, что сломал.
Обратная стрелка возвращает нас к схеме, которая уже была признана неподдерживаемой.

**Якорь — то, что обязан знать вызывающий.** Имя grid-сервиса, `JOBTITLE`, `Id@Version`
workflow, пара «список + `EventType`», HTTP-маршрут. Не имя класса и не путь: они
меняются от вещей без бизнес-смысла — вплоть до того, что `doc_path` меняется при правке
`rules/rules.yaml`, когда код вообще не трогали.

**Точки входа АС CF объявлены не в коде.** Джобы, workflow и обработчики событий
диспетчеризуются по данным из XML-реестров. Литерала конкретного workflow в C# **не
существует структурно** — реализация, считающая пустой литеральный поиск ошибкой, даст
вечно красный линт по всем 45 workflow.

**Находка роняет прогон линта, только если её может починить автор документа.**
Непокрытые точки входа и записи реестров без узла — состояние работы, а не дефект:
они печатаются всегда, но кода возврата не меняют, пока не названы в `--fail-on`.
Линт, красный с первого дня, выключат на второй, и вместе с ним пропадут шесть
работающих проверок.

**Зеркала текущего `business_hash` во front matter нет.** Единственный хранимый
хэш — принятый, он в `docpipe_state`. Второй источник обязан отстать, и `accept`,
взявший значение оттуда, зафиксирует устаревшее.

**Словари видов расходятся намеренно.** Аналитик пишет `table` и `kafka`, реестр
объявляет `list` и `kafka_topic`. Мост — `resolve.REGISTRY_KIND`; новая пара обязана
попасть туда, иначе якорь просто никогда не разрешится и это будет выглядеть
как «инструмент не нашёл».

**У бизнес-слоя нет статусов `missing` и `orphan`.** Документ здесь **и есть файл**:
«файла нет» означает «документа нет». О ненаписанном сообщает отчёт линта
о непокрытых точках входа — он считается по реестрам.

**`business_hash` считается по разрешённым фактам и не содержит имён C#-типов.** Это
проверяемая формулировка требования «рефакторинг без смены смысла не создаёт работы»:
переименование класса шага хэш не меняет, добавление шага — меняет. Единственное
исключение — имена методов grid-сервиса: их вызывают по имени через прокси, поэтому
они и есть контракт.

## Инварианты фикстур

`tests/fixtures/SampleSolution/` — канонические случаи. **На точные количества в нём
завязаны критерии приёмки T04–T20** (11 файлов после исключений, 10 символов, 6 узлов).
Расширять эту фикстуру нельзя: новые случаи идут в `WildSolution`.

`tests/fixtures/WildSolution/` — конструкции, пойманные в реальных репозиториях.

Два инварианта, которые легко нарушить:

1. **Не добавлять `obj/` и `bin/` в `.gitignore`.** В `SampleSolution` есть файл под `obj/`,
   на котором проверяются правила исключения. Стандартный .NET-шаблон `.gitignore` его
   выкинет, и тесты T04/T14 продолжат проходить, ничего не проверяя.
2. **Тесты фикстур проверяют наличие конструкций, а не только файлов.** Иначе «упрощение»
   фикстуры оставит тесты зелёными и бессмысленными.

## Конвенции кода

- Комментарии, docstring и сообщения об ошибках — по-русски; идентификаторы — по-английски.
- Комментарий объясняет **почему**, а не что. «Читаем байтами, потому что BOM уронит
  `ET.fromstring`» — полезно; «читаем файл» — нет.
- Модели — `pydantic`, `frozen=True`, `extra="forbid"`.
- `ruff` настроен с `line-length = 100` и исключает `docs/` и `examples/`: в плане лежат
  намеренно компактные псевдо-сигнатуры в python-блоках, `ruff format` их ломает.
- `mypy` в режиме `strict`.

## Git

**В `main` напрямую не пушить.** Любая работа идёт в отдельной ветке и попадает
в `main` только через pull request. Это касается и правок документации: исключений
нет, иначе правило держится ровно до первой мелочи.

Порядок:

```bash
git checkout main && git pull                 # от свежего main, а не от прошлой ветки
git checkout -b <тип>/<о-чём>                 # docs/manifest-guide, fix/csproj-bom
# ... работа, коммиты ...
uv run ruff check . && uv run ruff format --check . && uv run mypy docpipe && uv run pytest -q
git push -u origin <ветка>                    # затем pull request в main
```

Префиксы веток: `feat/`, `fix/`, `docs/`, `chore/`.

Коммит на осмысленную группу задач, не на каждую мелкую. В сообщении — что найдено
и почему решено так, а не перечисление файлов.

Полная проверка (ruff, mypy, pytest) обязана проходить **до** отправки ветки:
ловить это в PR дороже, чем у себя.
